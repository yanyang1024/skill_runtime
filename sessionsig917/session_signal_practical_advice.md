# 结合多轮实践：下一步怎样让信号产生真正的改进

我的判断是：你已经具备“发现大量现象”的能力，下一步最值得投入的是把少量现象变成可复现问题、可验证改动，以及用户愿意认可的结果。继续扩充指标有收益，但每增加一个信号，都应能回答“它会改变哪个决定”。

本文以当前可读的实际反馈、已有会话/Agent/Skill 材料和前轮设计为依据。报告中的历史数字是你提供的观测，不是本次全平台重算；不同批次、用户范围与评测设置分开理解。

## 1. 从你的实践里，哪些事情已经值得坚定推进

| 反馈中的证据 | 我认为可以保留的判断 | 下一步最小行动 |
|---|---|---|
| 已能按用户获取会话，组织信息和请求级数据有实际用途 | 平台级只读扫描有现实基础；不必停留在几个演示会话 | 复用现有采集器，每批记录时间窗、用户/会话覆盖和去重规则 |
| 部门×Skill 暴露不同热点 | 部门是很有价值的分诊维度 | 输出“本部门最值得处理的具体问题”，附事件证据与支持用户数 |
| 多次实验中 TF-IDF+LR 优于关键词/多数类 | 轻量路由值得作为当前基线 | 固定标签与保留题，再测试路由后的提示补充 |
| 共享存储分桶找到路径候选，直接比较 I/O hash 得不到匹配 | 资产关联需要存储语义和指纹来源 | 保留 namespace、hash_origin、时间关系；暂不强算统一复用率 |
| 缺 run/branch/issue、phase 和运行时版本 | 历史会话对精细归因存在边界 | 保留候选；新数据只补最影响当前实验的少量字段 |
| 一度没有人工确认，部分 bench 全由合成题构成 | 当前最稀缺的是可信验收和真实任务覆盖 | 先做一小批可复现回归题，再补真实任务与人工语义标签 |

你的报告中“暂时没有复用数据”后来发展到“找到共享路径候选”，路由也出现过多组不同 F1。这些应作为能力与数据批次的演进记录，不合并成一个固定结论或一条未经对齐的提升曲线。

## 2. 给每条信号补一个“下一步决定”

不需要再建立一个复杂评分体系。给复核队列多写三项就够了：可能改哪里、还缺什么证据、用什么小实验判断。

| 信号 | 应引出的决定 | 最小验证 |
|---|---|---|
| 校验器说成功但检查目标为空 | 修校验器目标发现/错误契约 | 正常、缺目标、未索引目标的固定夹具 |
| Agent 交接后遗漏输入约束 | 改委派输入模板/引用方式 | 相同初始输入与模型，旧/新模板逐项检查 |
| 材料转换遗漏单位或例外 | 改保真步骤或对应脚本 | 带单位、否定、范围、例外的真实片段 |
| question 经常重复询问已知信息 | 改上下文选择或状态传递 | 核对问题前是否确实可见所需信息 |
| 反复读取相同大文件 | 评估按需读取/摘要是否有收益 | 同任务总消耗、遗漏与过期信息错误 |
| 某 Skill 常加载但收益未知 | 判断适用性与上下文负担 | 有/无或旧/新对照，记录质量、总消耗和波动 |

优先做“证据清楚、改动集中、能便宜复现”的条目。重复多可以提高优先级，但一个确定的严重 bug 不需要等频次达标。只有聚合异常、无法指向具体操作的信号先留观察，不自动生成一段新 SOP。

你早期反馈过工具修改权限不足。如果仍然如此，最小交付就是**失败复现 + 明确预期 + 建议修改位置 + 回归题**。能够修改的 Prompt/Skill 可以先做对照，不需要等待整个工具平台都归你管理。

## 3. 任务分布图谱应围绕用户目标建立

建议保持两个轴，不急着建设知识图谱数据库：

- **需求轴**：用户要完成什么，以及所属业务域。优先从初始请求提取，支持多意图和 unknown。
- **执行轴**：实际使用了哪些 Skill/Agent/工具，产生什么可见结果，卡在哪一步。

第一版是一张表即可：任务类型、业务域、部门、会话/用户/任务家族数、能力接触、问题现象、验收覆盖、确认采用。多标签时同时注明按会话还是按标签计数，避免合计超过 100% 被误读。

这能分出四类不同动作：

| 需求与供给状态 | 更合理的动作 |
|---|---|
| 有明确需求，没有合适能力 | 补能力或做一个最小业务 Skill |
| 有能力、有适用需求，但很少接触 | 查发现入口、描述、路由与可见范围 |
| 能力已接触，但重复出现具体缺陷 | 修 Harness 或工具实现 |
| 能力已接触、质量可用、消耗偏大 | 做精简上下文/流程的效率实验 |

这些分类避免把“没有调用”“调用失败”“没有收益”混成一个问题。特别是 `load>0、invoke=0`：说明型 Skill 的正常使用可能就是加载指令并指导后续操作，它没有专属 invoke。只有先定义了该能力预期出现的可见事件，才能解释所谓“沉默供给”。

对 Agent，建议先看交接损失：目标是否传全、输入版本是否明确、回执中的 warning 是否被处理、用户修改是否传到下游。委派次数和角色数更适合描述架构，不适合当作价值指标。

## 4. 部门分析继续做，但把解释收敛到证据支持的范围

你发现的组织×技能×可靠性差异，足以支撑部门问题清单。它还不能直接证明哪个部门“用得差”、哪个 Skill 本身“质量差”或某个模型应被替换。

开发部门可能在做负例测试，业务部门可能只使用打磨后的版本；重试次数、工具组合和用户构成也可能不同。缺少 phase/test_definition 时，先称“记录的工具错误”，不要称“非预期故障”。同事件 ID 能证明错误发生在对应调用上，但不能单独证明根因就是 Skill 文本。

建议每次比较只保留四个问题：

1. 两边是否同窗口、同口径、同一观察单位？
2. 是否有相近任务、模型、工具版本与使用阶段的共同范围？
3. 差异由几个用户、几个任务家族支持，是否主要来自一个高频用户的反复尝试？
4. 去掉最大用户/一个异常任务家族后，方向是否仍然相同？

这是敏感性检查，不等于因果识别。unknown 与 unknown 同桶也不代表条件相同。“部门无关”更适合暂写为“多个部门都值得检查的共性问题候选”；区间重叠或没有显著差异不能证明独立于部门。

你不同报告中出现过“8 用户”“36 部门切片”等描述，应先写清它们是实际观测对象、组织目录覆盖，还是不同批次的统计。不要让多个正确数字因范围不同被拼成错误的总体叙事。

题集也应先按材料/任务家族防泄漏，再决定是否按部门保留：面向新部门上线时，跨部门 holdout 很有价值；服务已有部门的新任务时，时间/任务家族保留更贴近目标。部门切分不是所有评测的统一默认，也不能单独防住跨部门共享材料泄漏。

## 5. 资产信号：优先把“比较的对象”说清楚

你的存储分桶很有用，但有几处推导需要继续降级：

| 当前推导 | 更稳妥的解释 |
|---|---|
| write/read hash 无交集，因此字节匹配方法失效 | write 参数与 read 包装输出不是同一表示；这次实现无法证明完整文件内容是否相同 |
| 共享绝对路径相同，就是同一文件/版本 | 还需同租户、同存储命名空间与时序；路径可能被覆盖，目录可能挂在不同卷 |
| 私有 workspace 的 identical=0，证明都不是复用 | 能拒绝“仅凭同名确认复用”；内容经过修改、截断或另存后的来源仍可能未知 |
| 去空白、casefold 后 hash 相同，是语义相同 | 这只是特定归一化表示相同；代码缩进、大小写、单位符号等可能有业务含义 |
| edit 和疑似 bash 写入可直接补足文件操作覆盖 | edit 可以记录修改意图/结果；shell 正则匹配只生成候选，命令可能未执行或只是字符串 |

特别不要默认归一化适用于代码、配置、工艺参数或带单位数据。即便来源链可靠，读到资产也不等于业务采用。

近期可以只展示三项：**可观察文件操作覆盖、跨会话共享路径候选、人工/运行证据确认的实际采用**。这比一个分母和证据层级混杂的“复用率”更有说服力。

如果以后能在上传/复制/发布环节增加 `source_artifact_id + source_version`，其边际价值可能高于继续给历史日志加复杂相似度模型。历史候选仍保留，不必全部强行确证。

## 6. 路由后的提示补充，是适合你的下一项模型侧实验

你已经有 TF-IDF+LR 的实际基线，可以先固定模型，比较三种策略：

| 组别 | 行为 | 所检验的问题 |
|---|---|---|
| A | 原请求 + 当前默认流程 | 现有基线 |
| B | 路由到对应 Skill/场景提示，原请求保留 | 场景指引是否有增量 |
| C | B + 简短任务卡/缺失条件提示 | 明确条件是否帮助完成任务 |

任务卡只补组织结构，不编造业务事实，例如：目标、已有输入、必须保留的单位/约束、期望输出、当前缺少的关键条件。原请求原样保留；补充内容与原文分区。低置信度保留默认路径或按需澄清。

先用固定任务做离线对照，检查正确性、遗漏、总 token、重试和延迟。若 C 需要用户补答，真实试用时把用户回答耗时与打扰一起记录；不能用获得额外信息的 B/C 组，声称证明“单纯换一句 Prompt 就更好”。

“少提问”不是目标。question 至少区分补背景、补数据、业务决策、授权、偏好、重复询问。允许模型整理资料和提出选项，关键业务选择仍由用户决定。无 issue/branch/user-turn 关联时，也不能用 `1 - 自愈率` 推导人工介入比例。

你报告过不同数据划分下的 F1、阈值覆盖与选中准确率。后续汇报固定一组条件，并同时报告覆盖率、错误路由、各类支持量和低置信度去向。若标签本身由关键词生成，高一致性首先说明模型学会了这些标签，仍需少量独立复核验证其业务含义。

## 7. 把三种评测用途放进同一题库的不同视图

现在可优先维护三种用途：

- **回归题**：明确错误 + 明确预期，用来证明某个问题修好且不再回来。
- **代表任务**：来源于真实使用，用来比较 Harness/模型在你的业务中的表现。
- **裁判校准题**：明确正例、反例、边界和缺资料，用来发现 Judge 的错误放行。

这三种用途不等于 diagnostic / selection / holdout。前者说明题用来测什么，后者说明谁可以看、处于哪一步。用标签和视图管理即可，不必建立三套数据服务。

首批可以只选若干独立任务家族，补一两个典型反例；数量以能否给出可信验收为准。你反馈持续人工运营不现实，因此建议采用事件触发：新 rubric、模型/模板变化、哨兵异常、准备把结论推广为规则时，才集中复核一小批。没有复核时，缩小自动结论范围，仍可运行明确规则检查。

抽样保留两路：普通随机样本用于了解分布，异常定向样本用于修问题。二者不能直接混算总体失败比例。用户修正也先分清“补了新要求”还是“同条件下纠错”，后者才可能构成合适的偏好/纠错训练对。

小模型训练建议后移到标签稳定之后。更容易起步的是已有路由、工具错误类型、输入字段提取等窄任务；同一冻结题集先与规则/轻量模型比较，再判断是否值得训练。合成题适合扩展边界条件，不能替代真实分布，也不能把自己的生成结果直接当正确答案。

## 8. 向上汇报与用户认可，可以共享同一条证据链

建议每次只讲清一条链：**出现了什么问题 → 改了什么 → 固定任务上怎样变化 → 用户是否实际采用**。

领导版本可以是：

> 在【范围/窗口】发现【具体问题】，涉及【用户/任务家族/调用数】。修复【具体位置】后，在【冻结题集】改善【结果】，出现【退步/未知】；总资源变化为【同口径数值】。已有【确认采用数】，尚未确认【范围】。下一步只补【最关键证据】。

向用户确认时，用中性选择即可：

> 这次结果对你的工作处于哪一步：尚未使用 / 作为参考 / 已修改后使用 / 直接用于后续工作？若已使用，可否指一下用在哪份报告、脚本或下一步任务中？也可以跳过。

未回复不算失败，更不补成认可。先获得“实际采用及去向”的证据，再询问相对于原有做法减少了什么工作。工时估计注明来自用户回忆或小范围对照；没有人工基线时不换算节省金额。内部服务器成本、token 消耗、业务收益分别展示，避免把输入 token 直接当货币成本。

你的实践还提示一个好题目：用户在同一类任务上跨会话反复尝试。如果人工确认是同一未解决目标，这比单次会话长短更接近真实摩擦。把它作为产品优化候选，避免按标题相似自动认定用户失败。

## 9. 建议的下一轮，只交付四样东西

1. 一张口径清楚的任务×能力×问题表，标出 unknown 和采样范围。
2. 一个证据最清楚的问题包：复现、修改位置、正常与错误反例。
3. 一次冻结题上的旧/新对照，包含失败、缺失和总消耗。
4. 一条有来源、适用条件和复查触发的经验候选，外加可选的用户采用确认。

新埋点也只跟着问题补：版本对照缺证据就先记录实际加载版本；恢复链路不清楚就补调用与用户轮次/子会话关系；验收不可信就补 checked_targets。无需先补齐所有 run/branch/issue 层次才开始改进。
