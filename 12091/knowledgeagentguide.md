# 一、执行摘要

## 1.1 核心结论

截至 2026 年 11 月，较可靠的工程主线不是“用某种新技术取代 RAG”，而是把知识系统拆成以下部分：

> **权威事实源＋可重建派生视图＋分层检索接口＋会话工作区＋最小上下文装配＋受控知识写回。**

几个关键判断：

1. **RAG、Agentic RAG、grep、working tree、WeKnora、OKF 不在同一层。**
   - RAG 是检索与上下文供给管线。
   - Agentic RAG 是模型参与检索决策的控制流。
   - grep／glob／read 是确定性寻址和文件消费工具。
   - working tree 是任务工作区或修改隔离边界。
   - WeKnora 是集成知识平台。
   - OKF 是知识表示与交换格式。

2. **知识库不等于记忆，记忆不等于上下文，上下文不等于检索结果。**

3. **默认架构不应是“所有数据进入向量库”。**
   - 当前业务状态优先 SQL／API 直查。
   - 已知路径、错误码、产品编号优先 read／grep／关键词检索。
   - 自然语言文档问答使用混合 RAG。
   - 多跳、歧义和跨源问题再升级为 Agentic RAG。
   - 关系与全局问题经评测后再增加 GraphRAG。

4. **SOP、案例、参数、规则应采用不同载体。**
   - SOP：版本化文档＋Skill 编排。
   - 案例：原始记录＋标准化 Case＋WeKnora 或本地索引。
   - 参数：业务数据库／API 是唯一权威源。
   - 硬规则：决策表、规则配置、脚本或规则引擎确定性计算。

5. **长期记忆默认少写，候选写回默认需要验证。**

## 1.2 如果只能押三件事

### 第一，事实源与派生物分离

向量索引、摘要、Wiki、图、案例标签、检索缓存都应是可重建的派生视图。任何生成物都不能悄悄取代原始业务事实。

### 第二，分层检索与会话工作区

建立少量统一工具：SQL／API、read／grep、混合检索、规则检查；大型工具输出落盘，主上下文只保留路径、摘要和证据指针。

### 第三，任务级评测与受控写回

不能只看检索召回率，应看任务成功率、证据支持率、陈旧事实使用率、权限泄漏率、成本与延迟。会话产物必须经过去重、权限、时效、冲突和正确性检查后才能晋升。

# 二、统一概念模型：知识库、记忆、上下文与检索不是一回事

## 2.1 四个概念

| 概念 | 回答的问题 | 典型内容 |
|---|---|---|
| **知识库** | 组织外部化了哪些可复用事实与经验？ | 文档、案例、术语、规则说明、来源 |
| **记忆** | 系统从历史交互中保留了什么状态？ | episode、用户事实、项目状态、经验 |
| **上下文** | 本次模型推理实际看到了哪些 token？ | 指令、工具、消息、证据、摘要 |
| **检索** | 如何从更大的信息空间找到候选内容？ | SQL、API、grep、BM25、向量、图、网页搜索 |

因此：

- 被检索到，不等于应当进入上下文。
- 进入上下文，不等于内容真实。
- 被模型记住，不等于已经写入长期记忆。
- 写入长期记忆，不等于应当在未来会话中无条件召回。

## 2.2 一个更完整的系统公式

```text
Knowledge System
  = Source of Truth
  + Derived Views
  + Runtime Working Set
  + Retrieval & Context Assembly
  + Governance Loop
```

其中：

- **Source of Truth**：业务 DB、原始文档、规则版本、原始 episode。
- **Derived Views**：向量索引、关键词索引、图、Wiki、摘要、标准化案例。
- **Runtime Working Set**：当前 prompt、会话文件、计划和工具结果。
- **Retrieval & Context Assembly**：路由、召回、过滤、重排、读取、压缩。
- **Governance Loop**：来源、权限、版本、时效、冲突、写回、退役和审计。

学术上，传统“短期／长期记忆”已经显得过粗。较新的 Agent Memory 综述采用 **Forms–Functions–Dynamics**：记忆以什么形式存在、承担什么功能，以及如何形成、演化和检索。[^agent-memory]

## 2.3 上下文是工作集，不是数据库

上下文窗口再大，也仍然是当前推理的有限工作集。Anthropic 对上下文工程的定义强调：在推理期间持续策划和维护最有用的 token，而不是尽可能多地注入材料。[^context-engineering]

工程上应区分：

```text
知识总量：可以很大，保存在外部系统
候选证据：经检索和过滤后缩小
本轮上下文：只保留当前步骤需要的高信号内容
长期状态：通过文件、数据库和受控记忆持久化
```

# 三、知识的功能分层与横切标签

## 3.1 主分层：按任务功能划分

| 功能层 | 典型内容 | 权威存储 | 运行时消费方式 |
|---|---|---|---|
| **行为契约** | 系统策略、安全约束、输出规范 | 版本化配置、策略仓库 | 少量预加载，不依赖语义检索 |
| **程序性知识** | 操作流程、排障手册、工具用法、验证清单 | Skills、Runbook、脚本、工具 Schema | 元数据预加载，命中后读正文和附属文件 |
| **语义知识** | 概念、指标定义、架构决策、领域文档 | 文档库、Git、OKF、知识平台 | 目录导航、grep、混合 RAG、必要时多跳检索 |
| **业务事实** | 订单、库存、价格、负责人、服务状态、产品参数 | 业务数据库、SaaS、事件流 | SQL／API 直查，返回 `as_of` 和版本 |
| **情景记忆** | 历史会话、任务案例、用户经历 | 原始 episode 日志＋提炼后的事实 | 按用户／项目命名空间检索，带时间和权限 |
| **工作记忆** | 当前计划、上传文件、工具输出、中间结果 | 会话 working tree、临时对象存储 | manifest＋路径＋预览，按需 read／grep |
| **派生知识视图** | 向量索引、摘要、Wiki、图、交叉引用 | 可重建的索引和生成物 | 加速发现与综合，但不能成为最高权威 |

模型参数中的知识可以支持语言、通用推理和稳定常识，但不适合承担私有、时效性或可审计事实的权威来源。

## 3.2 四组横切标签

每条知识除了“属于哪一层”，还应带：

### 时效

- 近似不变；
- 慢变；
- 快变；
- 仅当前任务有效。

### 权威

- 原始事实；
- 人工策展；
- 机器提炼；
- 模型猜测。

### 作用域与权限

- 平台；
- 组织；
- 项目；
- 用户；
- 会话。

### 访问形状

- 点查；
- 精确匹配；
- 语义查找；
- 关系遍历；
- 全局综合。

因此，“这是一条长期记忆”不是足够的数据契约。更完整的描述应是：

> 用户级、机器提炼、慢变、仅本人可见、30 天后复核、可追溯到原始 episode 的偏好事实。

## 3.3 权威源、派生物和会话证据必须分开

建议所有知识对象至少能回答：

```text
它从哪里来？
谁负责？
何时生效？
何时需要复核？
是否经过验证？
谁可以读取？
它是原件还是派生物？
本次任务实际使用了哪个版本？
```

# 四、方法成熟度、共识度与证据边界

## 4.1 综合矩阵

| 方法 | 成熟度与共识 | 工程判断 |
|---|---|---|
| **结构化业务事实走 SQL／API** | 成熟，高共识 | 快变事实的默认路径，向量库只能辅助发现 |
| **BM25／关键词＋向量＋过滤＋rerank** | 成熟，高共识 | 文档型知识库的稳健基线，但不保证端到端答案正确 |
| **少量稳定指令预加载，其余按需读取** | 正在体系化，高共识 | 比巨型系统提示和全量知识预装更可持续 |
| **Skills 渐进披露** | 正在体系化，中高共识 | 程序性知识的重要载体，不应全部塞进 RAG |
| **文件外置、结构化笔记、子代理隔离** | 正在体系化，中高共识 | 长任务中实用，但证据以工程实践为主 |
| **Agentic RAG** | 正在体系化，中等共识 | 对歧义、多跳、跨源任务有价值；简单点查不应使用 |
| **GraphRAG** | 场景化成形，中等共识 | 多跳、关系、全局问题可选；不是普通 RAG 的普遍升级 |
| **双时态、冲突失效、版本治理** | 数据库思想成熟，Agent 领域正在吸收 | 快变事实和历史审计的重要机制 |
| **自动长期记忆写回与自我巩固** | 尚未成熟，低共识 | 写回精度、污染、遗忘、跨用户隔离仍是难点 |
| **OKF、知识编译、自维护 Wiki** | 早期，低共识 | 值得试验，但不能宣称已经取代 RAG |
| **端到端学习记忆管理策略** | 研究阶段 | 暂不建议作为生产主链路 |

## 4.2 渐进披露与 Skills

Skills 的关键不是 Markdown 文件本身，而是分级加载：启动时只加载名称和描述，任务命中后再读正文，继续按需读取附属文件或执行脚本。[^agent-skills]

OpenCode 当前官方文档同样支持 `.opencode/skills/<skill-id>/SKILL.md` 的技能加载方式。[^opencode-skills]

设计推论：

- 全局指令只放跨任务高压线。
- 角色或任务专属流程放 Skill。
- 细节放 `references/`。
- 确定性计算放脚本或工具。
- 不要为了“让 Agent 知道”而把所有内容预加载到系统提示。

## 4.3 Agentic RAG 的收益与代价

Agentic RAG 将何时检索、使用哪个工具、是否重写查询、是否继续阅读和何时停止纳入模型控制循环。2026 年 SoK 将其作为规划、记忆、工具编排和检索策略共同作用的系统，而非固定“retrieve → generate”管线。[^agentic-rag-sok]

A-RAG 则提供 `keyword_search`、`semantic_search`、`chunk_read` 三个层次化接口，让模型先获得 ID／snippet，再决定是否读取完整 chunk 或相邻内容。作者报告了多组开放域 QA 上的效果和检索 token 收益。[^a-rag]

证据边界：

- 这是机制有价值、值得试验的信号。
- 单篇论文的作者实验不能证明所有企业语料都优于固定混合检索。
- 多轮 Agentic RAG 同时增加了 test-time compute，评测必须对齐调用次数、阅读 token 和延迟。

## 4.4 长上下文与 GraphRAG 都不是统一答案

长上下文研究显示，资源充足时长上下文平均表现可能更好，但 RAG 成本显著更低，按查询路由更合理。[^long-context]

GraphRAG 系统评测则提示：普通 RAG 在单跳和细节型问题上仍有竞争力，图方法更可能在多跳、关系和部分全局综合问题中获益。[^graph-rag-eval]

因此：

- 小而稳定、需要全局理解的语料，可以有界全量阅读。
- 巨大、常变、需要权限过滤的语料，仍需要检索。
- 图结构应是按问题类型增加的派生视图，而不是默认底座。

# 五、主要方案的机制、适用场景与组合关系

## 5.1 总表

| 方案 | 最适用场景 | 主要短板 | 在整体架构中的位置 |
|---|---|---|---|
| **传统／混合 RAG** | 大型文档库、自然语言表达差异、需要引用证据的 QA | 索引更新、chunk 噪声、精确标识符和时效冲突 | 默认语义检索工具 |
| **Agentic RAG** | 查询歧义、多跳、跨库、需要查询重写和证据充分性判断 | 延迟、成本、轨迹不稳定、停止条件困难 | 复杂查询的升级控制流 |
| **grep／glob／read** | 代码、日志、错误码、ID、已知目录、要求穷尽匹配 | 不擅长同义改写和未知语义位置 | 确定性寻址与文件消费基元 |
| **working tree：工作区文件树** | 当前任务证据、计划、中间结果、上传文件、可恢复状态 | 不自动提供语义检索和长期治理 | 会话工作记忆与事实面 |
| **git worktree** | 多代理并行修改、版本隔离、回滚 | 不是知识检索算法 | 修改隔离与版本边界 |
| **GraphRAG** | 多跳关系、实体网络、跨文档综合、部分全局问题 | 构建和更新成本、图覆盖不足、简单问题收益有限 | 按需增加的派生视图 |
| **WeKnora** | 私有化、团队共享、文档接入、权限审计、一体化产品 | 功能多不等于每个环节都适合当前负载 | 承载知识库、RAG、Agent、Wiki 的平台 |
| **OKF** | 稳定、可策展、需 Git 评审和跨系统交换的核心知识 | 不提供检索引擎、运行时、权限系统或固定领域 taxonomy | 知识表示与交换契约 |

## 5.2 RAG 与 Agentic RAG

### 传统／混合 RAG 适合

- 文档量大，无法稳定全量放入上下文；
- 用户表达与原文措辞存在差异；
- 需要返回来源和引用；
- 语料可以通过解析、切块、索引和更新管线维护。

推荐基线不是单纯向量 top-k，而是：

```text
查询理解
→ 元数据与权限过滤
→ 关键词＋向量召回
→ rerank
→ 读取完整证据
→ 答案与引用
```

### Agentic RAG 适合

- 初始查询不完整或存在歧义；
- 需要跨多个数据源；
- 第一次检索不足以判断答案；
- 需要比较、验证、重写查询或追溯相邻证据。

不适合：

- 已知产品编号的参数点查；
- 已知文件路径的读取；
- 简单错误码匹配；
- 低延迟、固定流程、高确定性的业务动作。

## 5.3 grep 不是“新 RAG”

Anthropic 的工程经验是：文件系统保存可以被拉入上下文的信息，目录、文件名和时间戳也是导航信号；语义搜索通常更快，但维护、透明度和准确性存在权衡，因此建议先尝试 agentic search，再按速度和表达变化需求增加语义检索。[^claude-agent-sdk]

这个结论应限定为：

- 对代码、日志、当前工作区、精确标识符，grep 经常比盲目 top-k 更可靠。
- 对大规模非同构文档、自然语言改写、概念发现，向量或混合检索仍然必要。
- grep 替代的是部分语料上的预索引和固定检索流程，不是所有语义召回。

## 5.4 working tree 的两种含义

### 工作区文件树

用于保存：

- 当前任务计划；
- 用户上传文件；
- 工具查询结果；
- 检索证据；
- 中间分析；
- 最终产物；
- 待验证的知识候选。

它是会话事实面和可恢复上下文，不是独立检索算法。

### git worktree

用于：

- 多 Agent 并行修改；
- 分支隔离；
- 版本快照；
- 回滚。

它解决修改隔离，不解决知识召回。

## 5.5 WeKnora：平台而非单一算法

WeKnora 官方功能覆盖 Quick Q&A、ReAct Agent、自维护 Wiki，以及混合检索、rerank、parent-child chunking、GraphRAG、RBAC 和审计等。[^weknora]

适合：

- 私有化部署；
- 团队共享知识库；
- 业务人员需要网页上传、查询和管理；
- 需要文档解析、权限和审计；
- 希望快速获得一体化产品，而不是完全自行拼装。

验收时仍应分别测试：

- 文档解析质量；
- 精确与语义召回；
- 权限过滤；
- 索引更新延迟；
- Agent 轨迹；
- Wiki 的内容正确性；
- 与 OpenCode、业务 API 的集成成本。

## 5.6 OKF：知识格式而非检索系统

OKF v0.2 官方规范采用目录树中的 Markdown＋YAML frontmatter，只有 `type` 始终必需；它不规定存储、服务和查询基础设施，也不规定固定领域 taxonomy。[^okf]

其治理价值包括：

- `sources`：来源；
- `generated`／`verified`：生成与验证；
- `status`／`stale_after`：生命周期与复核时间；
- Attested Computation：受认可的计算及确定性验证接口。

合理组合：

```text
OKF 保存核心策展知识
→ grep／搜索索引／WeKnora 建立不同消费视图
→ Agent 按需读取
→ 会话产物经评审后写回 OKF
→ 重建派生索引
```

不要把 OKF bundle 直接等同于权限系统、检索系统或事实正确性证明。

## 5.7 一张组合关系图

```text
权威来源
  ├── 业务 DB／API
  ├── 原始 SOP 与规则
  ├── 原始案例与工单
  └── 外部官方文档
        │
        ▼
派生视图
  ├── 关键词／向量索引
  ├── 标准化案例
  ├── OKF／Wiki
  └── 图视图
        │
        ▼
运行时访问
  ├── SQL／API
  ├── read／glob／grep
  ├── 混合 RAG
  ├── Agentic RAG
  └── 规则检查工具
        │
        ▼
上下文装配＋会话 working tree
        │
        ▼
答案、处置建议、业务产物
        │
        ▼
候选写回 → 验证 → 权威源更新 → 派生物重建
```

# 六、从数据本体出发的知识治理

## 6.1 不同数据的处理矩阵

| 数据类型 | 首选事实源 | 索引与读取 | 更新和淘汰 |
|---|---|---|---|
| **近似不变知识** | 原始文档、规范、论文、决策记录 | Git／OKF＋全文／向量索引；小规模可全量读 | 版本化，保留来源，不按时间简单删除 |
| **慢变领域知识** | 官方文档、政策、指标定义、Runbook | 混合 RAG＋目录导航＋引用 | `valid_from`、复核日期、superseded 版本 |
| **应用侧知识与能力** | 配置、工具 Schema、Skills、权限策略 | 元数据预加载，正文和脚本按需加载 | 随应用版本发布，做技能评测和回滚 |
| **业务快变事实** | DB、SaaS、交易系统、事件流 | SQL／API 点查；短 TTL 缓存；返回 `as_of` | 以源系统为准，不让向量副本决定当前状态 |
| **会话即时数据** | 用户上传、工具结果、运行时生成文件 | 会话 manifest＋路径＋预览；read／grep／分页 | 默认会话级 TTL，不自动进入长期记忆 |
| **历史交互与案例** | 原始 episode 日志 | 按用户／项目／时间／任务类型检索 | 原始记录追加，提炼记忆单独验证 |
| **外部公开知识** | 原始网页、官方文档、论文 | 搜索发现→打开原文→保存快照和日期 | 记录抓取时间、作者、来源等级和引用位置 |
| **审计与历史状态** | append-only 日志、版本仓库、双时态存储 | 按有效时间和摄入时间查询 | 失效而非物理覆盖，支持 point-in-time 重建 |

## 6.2 时效不是简单的 recency 排序

对价格、负责人、政策、配置、产品参数等会变化的事实，“最新”不能只作为向量排序中的加权项，而应成为：

- 查询约束；
- 数据契约；
- 冲突处理依据；
- 失效语义；
- 回答时必须展示的时间信息。

Zep／Graphiti 的双时态模型提供了可参考机制：区分事实在现实世界中的有效时间与系统创建、失效该事实的时间，并通过 invalidation 保留历史。[^graphiti]

建议至少区分：

```text
valid_from / valid_to：业务事实上何时有效
observed_at / ingested_at：系统何时观察到或摄入
as_of：本次查询对应的数据时间点
superseded_by：被哪个版本替代
```

## 6.3 数据源注册表

每个数据源应注册：

```yaml
source_id: product-master-api
owner: 产品数据团队
authority: authoritative
data_class: business_fast_changing
access:
  type: api
  read_only: true
freshness:
  expected_lag: 60s
  response_requires: [as_of, data_version]
permissions:
  scope: organization
  filter_before_generation: true
retrieval:
  preferred_route: point_lookup
  allow_vector_copy: false
writeback:
  allowed: false
```

这份“关于数据源的知识”往往比继续优化 embedding 更能降低 Agent 的搜索空间。

## 6.4 权限和安全

权限过滤应尽量发生在检索和上下文装配之前，而不是让模型先看完全部内容再要求它保密。

以下来源默认都是不可信输入，而不是指令：

- 用户上传文档；
- 网页内容；
- 工具输出；
- 历史案例；
- 其他 Agent 的笔记；
- 从会话中提炼的记忆候选。

长期记忆是持久攻击面。相关 Agentic 安全研究已经把跨会话记忆投毒、泄漏和级联传播列为独立风险。[^agentic-security]

## 6.5 知识写回与晋升

推荐默认策略：

> **长期自动写回关闭，候选写回开启。**

流程：

```text
候选生成
→ 去重与实体对齐
→ 来源、权限、隐私检查
→ 时效与冲突检查
→ 测试／人工／独立证据验证
→ 写入对应知识层
→ 版本提交与审计
→ 重建派生索引
```

不同产物进入不同层：

| 会话产物 | 晋升方向 |
|---|---|
| 单次事件 | episode |
| 稳定用户事实 | 用户语义记忆 |
| 可复用成功流程 | SOP 或 Skill |
| 当前项目进展 | 项目状态 |
| 可泛化领域事实 | 策展知识库 |
| 可防复发的错误 | 测试、lint、规则或 guardrail |

“模型觉得值得记住”不能成为写回依据。

# 七、Agent runtime 的知识消费路径

## 7.1 启动：只加载导航，不加载整个知识世界

预加载：

- 核心行为契约；
- Skills 的名称与描述；
- 数据源目录；
- 当前任务目标；
- 文件 manifest。

知识引导建设应优先写“检索技能／Source Map”，而不是继续扩充巨型知识提示词。

每个领域检索技能至少包含：

```text
什么时候使用／不要使用
有哪些权威数据源
各类问题分别走 API、grep、RAG 还是图
查询如何构造
证据必须读到什么粒度
怎样检查时效、冲突和权限
输出与引用格式
何时停止、何时升级人工
```

## 7.2 按查询形状路由

推荐优先级：

1. 当前业务状态 → SQL／API。
2. 已知路径、文件、ID、错误码 → read／glob／grep／BM25。
3. 概念或自然语言表达差异 → 向量或混合检索。
4. 多跳、跨源、证据不足 → Agentic RAG；确有结构收益时加图。
5. 语料小且需要全局理解 → 有界全量阅读或长上下文。
6. 仍不足 → 明确承认未知、扩大来源或转人工，而不是无限检索。

## 7.3 渐进披露证据

统一返回：

```text
source_id / document_id / chunk_id
标题与路径
snippet
来源 URI
版本与 as_of
权限标签
是否允许写入长期记忆
```

先返回目录和片段，模型再决定读正文、相邻段、父文档或原始记录。

**snippet 用于导航，不应自动被视为充分证据。**

## 7.4 大结果落工作区，主上下文只保留指针

建议会话目录：

```text
/session
  /inputs       用户上传与原始输入
  /evidence     检索证据、网页快照、查询结果
  /notes        计划、决策、开放问题、压缩笔记
  /artifacts    代码、表格、报告等任务产物
  /candidates   待验证的长期知识候选
```

LangChain 的 Deep Agents 示例采用“Retrieve, offload, and delegate”：检索 chunk 写入文件系统，子代理分别读取、搜索和摘要，主代理只接收压缩结果。[^langchain-offload]

核心原则是：

> **证据地址与证据内容分离，使压缩可恢复。**

## 7.5 回答前的证据检查

至少检查：

- 关键结论是否有原文支持；
- 是否读到完整上下文，而非只看 snippet；
- 来源时间是否满足问题的时间要求；
- 是否存在相互冲突的有效版本；
- 权限过滤是否发生在生成之前；
- 检索文本中的指令是否被当作数据而非命令；
- 产品、版本、单位、区域等适用条件是否一致。

## 7.6 压缩与恢复

压缩笔记保留：

- 当前目标；
- 已确认事实；
- 已作决策；
- 未决问题；
- 证据路径；
- 工具版本；
- 失败与排除项；
- 下一步。

原始全文留在工作区，需要时重新读取。压缩不是把全部历史变成一段越来越长的摘要。

# 八、值得试验但尚未成为普遍共识的 insight

## 8.1 先建设“如何找到知识的知识”

包括：

- Source Map；
- 目录语义；
- 数据 owner；
- 查询配方；
- 工具选择规则；
- 停止条件。

**机制价值：高。** 先缩小搜索空间，再让检索器工作。  
**证据强度：中。** Skills、A-RAG 和文件系统实践支持这一方向，但缺少跨企业统一量化。

## 8.2 把知识编译前移到摄入期，但生成物必须可重建

原始资料可以离线编译成互链 Wiki、摘要、索引、FAQ、图和 Skills，减少每次查询时重复综合。

**机制价值：中高。** 适合稳定、反复查询的领域。  
**证据强度：偏弱。** 产品采用在增加，但“全面优于查询时 RAG”的证据不足。

边界：

> 原始来源是事实底座；Wiki、图、摘要和向量索引都是可再生的派生物。

## 8.3 “少写记忆”往往比“更聪明地写记忆”更可靠

多数会话内容只应在当前任务存活。只有能证明未来复用价值、权限允许且经过验证的内容才晋升。

**机制价值：高。** 同时降低陈旧、污染、隐私和检索噪声。  
**证据强度：中偏弱。** 主要是安全机制与工程经验的一致性，而非统一基准结论。

## 8.4 Agentic RAG 的收益可能来自接口和额外计算，而非“Agent”标签

候选收益至少有三部分：

1. 更好的检索工具接口；
2. 更多查询、阅读和重排；
3. 更强模型的规划能力。

如果 Agentic 方法进行了八轮检索，而基线只有一轮，不能把全部收益归因于“Agentic”。必须报告质量—成本 Pareto，而不是只报告成功率。

# 九、特定业务场景：SOP、案例、参数与规则应放在哪里

## 9.1 场景定义

已有条件：

- 业务 SOP：出现什么情况、如何处理问题的流程；
- 历史业务经验：具体问题—处理方案文档；
- 具体业务数据：产品编号—参数；
- 复杂逻辑：跨产品、交叉业务、兼容性和依赖约束；
- 软件环境：OpenCode；
- 模型环境：自部署大模型推理节点。

这个场景最重要的不是先选知识库，而是识别四类内容的不同本质：

| 内容 | 本质 | 主要风险 |
|---|---|---|
| SOP | 控制流与行动约束 | 检索到片段后跳步、忽略停止条件 |
| 案例 | 可复用经验 | 表面相似但根因、版本或适用条件不同 |
| 产品参数 | 当前权威事实 | 副本陈旧、产品串号、单位与版本错误 |
| 业务规则 | 确定性约束与依赖计算 | 模型凭推理放行本应禁止的操作 |

## 9.2 反例：所有内容进知识库，通用 Agent 自由检索并执行

不推荐：

```text
全部 SOP、案例、参数和规则导入 WeKnora
→ 建一个通用 Agent
→ 模型自由检索
→ 直接执行
```

问题不在于 WeKnora 能否保存这些内容，而在于这种架构混淆了四件事：

1. **知识发现与权威事实。**
2. **文档检索与流程执行。**
3. **案例相似与方案适用。**
4. **规则说明与规则判定。**

即使为了统一检索把四类内容都同步进 WeKnora，也必须保持：

- SOP 检索副本 ≠ 执行版本；
- 案例检索结果 ≠ 可直接采用方案；
- 参数检索副本 ≠ 当前业务事实；
- 规则说明文档 ≠ 规则判定器。

## 9.3 推荐的最小架构

```text
用户描述业务问题
        │
        ▼
OpenCode：识别任务、收集必要输入
        │
        ▼
business-triage Skill：读取对应 SOP
        │
        ├── 产品参数问题
        │       └── get_product_params(product_id)
        │
        ├── 历史相似问题
        │       └── search_cases()
        │             ├── 小规模：grep／本地索引
        │             └── 大规模：WeKnora
        │
        ├── 跨产品、交叉业务
        │       └── check_business_rules()
        │             └── 决策表／兼容性矩阵／规则脚本
        │
        └── 高风险操作
                └── 人工确认或现有业务审批系统
        │
        ▼
runs/<task-id>/：保存本次证据和处置记录
        │
        ▼
输出：结论＋依据＋步骤＋验证方法＋风险＋升级条件
        │
        ▼
有复用价值的新案例 → 候选区 → 人工验证后入库
```

大模型负责：

- 理解用户描述；
- 判断需要补充什么信息；
- 选择合适的 SOP；
- 组合工具结果；
- 对历史案例进行比较；
- 生成可读的处置说明。

大模型不负责：

- 凭记忆填写产品参数；
- 自己发明跨产品兼容规则；
- 仅凭相似案例宣布处理成功；
- 未经确认执行高风险业务动作。

## 9.4 四类内容的最终放置表

| 内容 | 权威源放哪里 | OpenCode 里放什么 | WeKnora 里放什么 | 谁负责执行／计算 |
|---|---|---|---|---|
| **SOP** | Git 版本化 SOP 文档，或 OKF bundle | Skill 只放触发条件、流程编排、工具调用顺序、停止条件 | 可选：SOP 检索副本，用于发现，不作为执行版本 | Skill 编排；确定性动作由工具或人工执行 |
| **历史案例** | 原始工单／经验文档＋标准化 Case 记录 | 案例选择、适用性检查、排除规则 | 主要使用场景：混合检索、语义召回、权限过滤 | Agent 比较案例，不直接照搬 |
| **产品参数** | 业务数据库、主数据系统、产品 API | 只读查询工具及参数 Schema | 原则上不放实时参数；可放产品说明书等解释材料 | SQL／API 确定性查询 |
| **业务规则** | 版本化决策表、规则配置、规则引擎或代码仓库 | Skill 只负责何时调用规则检查 | 可选：规则解释文档，不把检索结果当判定结果 | 规则脚本／规则引擎返回判定、命中规则和版本 |

一句话：

> **SOP 进 Skill 编排，案例进 WeKnora 检索，参数留在业务系统直查，规则交给确定性工具计算。**

## 9.5 SOP：权威文档与 Skill 分工

### SOP 权威文档包括

- 适用范围；
- 触发条件；
- 所需输入；
- 详细业务步骤；
- 分支条件；
- 异常处理；
- 验证和回滚；
- 升级人工条件；
- 版本、负责人、生效时间。

### Skill 只包括 Agent 如何消费 SOP

```text
1. 检查必要输入是否完整。
2. 调用产品参数工具。
3. 根据问题类型读取某份 SOP。
4. 查询相似案例。
5. 涉及跨产品时调用规则检查工具。
6. 验证通过后才允许给出“可执行”结论。
7. 高风险动作必须人工确认。
```

二者关系：

> **SOP 是业务规定，Skill 是执行导航。**

如果某段 SOP 完全确定，例如“满足 A、B、C 就禁止操作”，不应让模型自由判断，而应下沉为规则工具。

不建议“一篇 SOP 对应一个 Skill”，否则技能数量容易失控。第一版按任务类型建立少量 Skill：

1. `business-triage`：问题分诊；
2. `known-issue-resolution`：已知问题处置；
3. `cross-product-check`：跨产品影响检查。

### AGENTS.md 只放全局高压线

```text
1. 产品参数必须来自业务查询工具，不得根据上下文猜测。
2. 案例只能作为候选方案，必须检查产品、版本和适用条件。
3. 跨产品影响必须调用规则检查工具。
4. 不得把“已生成处理建议”写成“问题已经解决”。
5. 证据不足、规则冲突或超出权限时必须升级人工。
6. 所有关键结论必须保存来源、版本和查询时间。
```

## 9.6 案例：原始记录是权威，WeKnora 是检索视图

历史案例适合进入 WeKnora，但应保留两层：

```text
knowledge/cases/
├── raw/          # 原始工单、原始经验文档，保留原貌
└── normalized/   # 标准化案例
```

标准化案例至少包含：

```text
case_id
产品编号／产品类型
适用版本
业务场景
问题现象
错误码
根因
处理步骤
验证方法
回滚方法
适用条件
不适用条件
风险等级
验证状态
来源
```

其中适用条件、验证方法、不适用条件尤其重要。没有这三项，Agent 很容易把“表面相似”误当成“可以采用同一方案”。

推荐检索顺序：

```text
产品编号／错误码精确匹配
→ 版本和业务场景过滤
→ 症状语义检索
→ 读取完整候选案例
→ 比较适用条件
→ 给出采用或排除理由
```

案例默认不进入 Skill。只有某类案例被反复验证、抽象成稳定流程后，才晋升为 SOP；Skill 随后引用新的 SOP。

## 9.7 产品参数：只认业务系统，不认知识库副本

产品编号—参数的权威来源应是：

```text
业务数据库／主数据平台／产品服务 API
```

OpenCode 只暴露受控工具：

```text
get_product_basic_info(product_id)
get_product_params(product_id, version)
get_parameter_history(product_id, parameter, time_range)
```

返回结果至少带：

```json
{
  "product_id": "P1001",
  "parameters": {},
  "data_version": "2026.11.16-03",
  "as_of": "2026-11-16T10:30:00+08:00",
  "source": "product-master-api"
}
```

不建议把实时参数导入 WeKnora 后让 Agent 检索回答，因为会引入：

- 同步延迟；
- 多版本冲突；
- 参数被错误 chunk 截断；
- 相似产品串号；
- 无法确认回答对应哪个时间点。

WeKnora 可以保存产品手册、参数含义解释、单位说明，但回答“产品 P1001 当前参数是多少”时，仍必须调用业务工具。

## 9.8 业务规则：先区分硬规则与软经验

### 硬规则：必须确定性执行

例如：

- 产品 A 的参数不能同步到产品 B；
- 某区域不支持该操作；
- 版本低于某值必须禁止；
- 跨产品操作必须满足依赖顺序；
- 某条件下必须人工审批。

放在：

```text
knowledge/rules/
├── compatibility.yaml
├── region-constraints.yaml
├── operation-dependencies.yaml
└── ruleset-version.yaml
```

由工具加载：

```text
check_business_rules(
  product_ids,
  action,
  product_snapshots,
  business_context
)
```

工具应返回：

- 允许／禁止／需人工确认；
- 命中的规则 ID；
- 失败原因；
- 受影响产品；
- 规则集版本；
- 后续检查要求。

OKF 可以保存规则的可读定义、owner、来源和生效时间，但真正参与判定的仍是规则文件或规则引擎。

### 软规则：可以留在 SOP 或经验文档

例如：

- 通常先检查缓存，再检查下游服务；
- 某类现象优先考虑网络配置；
- 某产品出现问题时建议同时检查关联模块。

这些属于排障启发，不一定适合硬编码。

判断标准：

> **违反后是否一定造成业务错误？是，就硬规则化；只是推荐做法，就保留为 SOP 或经验。**

## 9.9 跨产品逻辑的复杂度升级顺序

### 第一阶段：决策表＋兼容性矩阵＋脚本

适合规则数量有限、边界相对明确的阶段。工具输出不应只有 `true／false`，还要给出命中规则、原因、影响范围和规则版本。

### 第二阶段：真正的规则引擎

当出现以下情况再升级：

- 规则数量多、组合复杂；
- 业务人员需要独立维护规则；
- 需要规则优先级、冲突检测和解释；
- 需要独立发布规则版本，而不修改 Agent 代码。

### 第三阶段：才考虑图

只有经常需要回答以下问题，且现有决策表已经难以表达时，图才有明确价值：

- 某参数变化会影响哪些下游产品；
- 两个产品之间存在哪些间接依赖；
- 某故障如何通过跨业务链路传播；
- 为什么两个看似无关的业务规则发生冲突。

图应该是规则与依赖关系的派生视图，不是把文档扔进去自动生成的“业务真相”。

## 9.10 什么时候需要 WeKnora

### 可以先不用

- 案例数量不大；
- 文件命名和目录规范；
- 错误码、产品编号等精确检索已经能解决大部分问题；
- 主要由技术人员通过 OpenCode 使用；
- 暂时没有复杂权限和网页端需求。

此时直接使用：

> Markdown 案例库＋frontmatter＋grep／glob＋一个简单关键词索引。

### 建议加入

- 文档格式杂、数量持续增长；
- 用户经常使用自然语言描述症状，而不是准确错误码；
- 业务人员需要网页上传、查询和管理；
- 需要团队共享、权限、审计和文档解析；
- 本地 grep 已出现明显的同义表达漏召回。

加入后定位为：

> **案例与非结构化文档的检索平台。**

不要把它变成产品参数事实源、SOP 执行引擎、跨产品规则引擎或处置成功判定器。

OpenCode 可以通过 API 或 MCP 调用案例检索。MCP 工具会消耗模型上下文，应只暴露少量业务所需接口，而不是把整个平台的工具无差别接入。[^opencode-mcp]

建议只暴露：

```text
search_cases(query, product_id, error_code, version)
get_case(case_id)
get_product_params(product_id, version)
check_business_rules(product_ids, action, context)
```

## 9.11 OKF 在该场景中的位置

OKF 适合承载：

- 核心 SOP；
- 业务术语；
- 指标定义；
- 跨产品规则说明；
- 数据源的 owner 和权威级别；
- 案例的验证状态、来源与复核时间。

Skill 只引用这些概念，不复制正文。

如果目前只有一个 Git 仓库、一个团队、一套 OpenCode 环境，且没有跨系统交换需求，普通 Markdown＋YAML frontmatter 已足够，没有必要为了使用 OKF 而使用 OKF。

## 10.2 自部署模型节点的分工

建议区分：

- **聊天／推理模型**：任务理解、流程选择、案例比较、结果解释；
- **Embedding 模型**：仅在采用语义检索时需要；
- **Reranker**：可选，用真实回放集判断是否值得；
- **确定性工具**：参数查询、规则计算、校验、权限、写操作。

不要默认一个聊天模型可以同时高质量承担 embedding、rerank、规则执行和最终结果验证。

如果自部署模型的工具调用或自主规划能力不稳定，应把路由收敛为：

- 显式斜杠命令；
- 固定工作流；
- 脚本化分诊；
- 少量受控工具。

此时让模型负责意图抽取、案例比较和解释，而不是把整个业务控制流交给模型自由规划。

## 10.3 每次任务的工作区

```text
runs/<task-id>/
├── job.json              # 输入、任务类型、权限和预期产物
├── inputs/               # 用户提供的材料
├── evidence/
│   ├── product.json      # 产品参数及 as_of
│   ├── cases.json        # 候选案例及来源
│   └── rules.json        # 规则检查结果及版本
├── notes.md              # 决策、排除项和未决问题
├── resolution.md         # 最终处置单
└── candidates/           # 待验证的新案例或新知识
```

关键原则：

- 每次重试使用新的任务目录，不覆盖旧证据。
- 工具不可用必须显式返回 `tool_unavailable`。
- 生成处置建议不等于执行成功。
- 业务写操作需要独立权限和确认，不与只读诊断共用能力。
- 返回码为零不代表业务成功，仍需检查业务哨兵和验证结果。

# 十一、三种可执行方案与选型

| 方案 | 组成 | 适合情况 | 评价 |
|---|---|---|---|
| **A．纯本地轻量版** | OpenCode＋Skills＋Markdown 案例＋grep＋只读业务工具 | 文档不太多、技术人员使用、快速验证 | 最推荐先跑通 |
| **B．业务团队实用版** | A＋WeKnora 案例检索＋网页管理＋权限 | 文档多、自然语言查询多、业务人员使用 | 最推荐的正式形态 |
| **C．规则治理版** | B＋OKF＋版本化决策表／规则引擎＋系统评测 | 跨产品规则复杂、审计和跨系统交换要求高 | 有明确需求后再做 |

## 11.1 方案 A：最小可用

```text
OpenCode
├── 2～3 个 Skills
├── Markdown SOP
├── Markdown 标准化案例
├── grep／glob
├── 产品参数只读工具
└── 规则检查脚本
```

优点：

- 依赖少；
- 透明；
- 容易调试；
- 容易建立基线；
- 不需要先解决知识平台与模型平台集成。

## 11.2 方案 B：推荐正式形态

在 A 的基础上，仅把案例和非结构化文档检索迁移或同步到 WeKnora。SOP、参数和规则的权威位置不变。

```text
Skill：流程
SOP 文档：业务规定
WeKnora：案例发现
业务 API：参数事实
规则工具：跨产品判定
runs：本次证据
```

## 11.3 方案 C：治理升级

只有出现明确需求才增加：

- OKF：跨系统交换、owner、审计、生命周期；
- 规则引擎：复杂组合、冲突检测、业务人员独立维护；
- 图：间接依赖和影响路径；
- 多 Agent：确实需要并行调查或上下文隔离；
- 长期记忆：有稳定复用价值且通过安全与写回评测。

# 十二、实施路线、评测与反模式

## 12.1 推荐的第一期范围

先选一个高频、边界清晰的业务闭环：

1. 选择 2～3 条高频 SOP。
2. 整理 50～100 个已验证历史案例。
3. 接通一个产品参数只读接口。
4. 建立 `business-triage` 和 `known-issue-resolution` 两个 Skill。
5. 如需跨产品判断，增加一个规则检查脚本。
6. 统一处置单输出格式。
7. 用 30～50 个历史问题回放验收。

以上数量是试点建议，不是架构硬阈值。重点是先形成完整闭环，而不是追求文档覆盖率。

统一处置单至少包括：

- 问题判断；
- 产品参数及查询时间；
- 命中的 SOP 和版本；
- 相似案例及采用／排除理由；
- 跨产品规则结果；
- 处理步骤；
- 验证和回滚方法；
- 风险及升级条件。

## 12.2 按失败原因决定下一步，而不是按技术热度

| 观察到的问题 | 优先改进 |
|---|---|
| 产品参数错误、陈旧 | 业务 API、权限、版本与 `as_of`，不是优化向量模型 |
| 找不到同义表达的案例 | 混合检索、Embedding、rerank 或 WeKnora |
| 找到案例但套错方案 | 案例元数据、适用条件、排除逻辑、完整证据读取 |
| SOP 跳步或忘记停止条件 | Skill 编排、输出校验、确定性 workflow |
| 跨产品误判 | 决策表、规则工具、规则版本和冲突处理 |
| 长任务丢失调查状态 | runs 工作区、证据指针、结构化笔记 |
| 多轮检索成本过高 | 查询路由、提前停止、固定混合检索基线 |
| 历史错误在未来会话反复出现 | 减少自动记忆、加强写回验证和失效治理 |
| 需要网页管理和团队协作 | 引入 WeKnora |
| 需要跨系统知识交换与审计 | 引入 OKF 或等价知识契约 |

## 12.3 评测集必须按查询类型分桶

至少覆盖：

1. 精确产品参数查询；
2. 单产品已知问题；
3. 自然语言症状检索；
4. 跨产品规则检查；
5. 表面相似但案例不适用；
6. 数据缺失或工具不可用；
7. 规则冲突；
8. 陈旧数据与多版本冲突；
9. 无答案和必须升级人工；
10. 权限不足；
11. 长会话恢复；
12. 高风险写操作拦截。

## 12.4 指标体系

### 任务与证据

- 端到端任务成功率；
- claim 级证据支持率；
- 引用正确率；
- 案例适用性判断准确率；
- 规则判定一致率；
- 无答案识别率；
- 高风险动作拦截率。

### 时效与安全

- 陈旧事实使用率；
- 冲突披露率；
- 权限泄漏率；
- 跨会话污染率；
- 长期写回准确率；
- 错误知识回滚率。

### 成本与稳定性

- P50／P95 延迟；
- 总输入／输出 token；
- 工具调用成本；
- 检索轮数；
- 工具失败率；
- 压缩后任务恢复率；
- 同一输入多次运行的结果方差。

## 12.5 消融必须对齐预算

固定 backbone，并同时报告：

- 总 LLM 调用次数；
- 最大检索轮数；
- 检索与阅读 token；
- 工具费用和 wall-clock；
- pass@1，而非不计选择器成本的 best-of-n。

建议依次做：

```text
SQL／read／grep 基线
→ ＋向量
→ ＋混合与 rerank
→ ＋分层检索接口
→ ＋Agentic 多轮
→ ＋GraphRAG
→ ＋自动记忆写回
```

这样才能定位收益来自检索器、上下文装配、文件工作区、额外轨迹预算，还是记忆层。

## 12.6 反模式清单

### 知识存储

- 所有文档、数据库、消息、网页都进同一个向量库。
- 把派生 Wiki、摘要或图当作不可再生的唯一事实源。
- SOP、Skill、OKF 和 WeKnora 同时各维护一份权威正文。

### 检索与上下文

- 用向量相似度回答库存、价格、当前负责人、产品实时参数。
- 检索到 snippet 就直接回答，不读完整证据。
- 为所有查询默认启用多轮 Agentic RAG。
- 把全部 SOP 和案例塞进系统提示。
- 认为长上下文可以统一取代权限、时效和检索治理。

### 业务执行

- 仅凭相似案例直接执行处理方案。
- 让模型自由推理硬业务规则。
- 只读诊断与业务写操作共用同一套权限。
- 工具返回码为零就宣布业务成功。
- 将“已生成处理建议”写成“问题已经解决”。

### 记忆与写回

- 用一条越来越长的 MEMORY.md 同时承担策略、事实、项目状态和经验。
- 把会话摘要、工具输出、网页指令直接写成长期记忆。
- 把所有失败轨迹都当作可复用经验，而不是转成测试或规则。

### 平台与规则

- 把 WeKnora 的功能列表当作知识质量已经合格。
- 把 OKF 的字段存在当作事实已验证。
- 为多跳问题建图，却没有图覆盖率和更新延迟指标。
- 一开始上多 Agent、GraphRAG、长期记忆和自维护 Wiki，却没有简单基线。

## 12.7 最终验收清单

### 权威与治理

- [ ] 每类知识都有唯一权威来源。
- [ ] 派生索引可以删除并重建。
- [ ] 产品参数返回 `as_of` 和数据版本。
- [ ] SOP、案例和规则都有 owner、状态和来源。
- [ ] 权限过滤发生在上下文装配之前。

### Runtime

- [ ] 点查不会被路由到语义 RAG。
- [ ] 案例检索后会读取完整案例。
- [ ] 跨产品问题必须调用规则工具。
- [ ] 大型结果落工作区，主上下文只保留指针。
- [ ] 工具缺失、无答案和冲突会显式停止或升级。

### 评测

- [ ] 有真实历史问题回放集。
- [ ] 有表面相似但不适用的负例。
- [ ] 有陈旧数据、权限和无答案用例。
- [ ] Agentic 方法与基线对齐了推理期预算。
- [ ] 报告成功率的同时也报告延迟和成本。

### 写回

- [ ] 会话产物默认只进入候选区。
- [ ] 新案例经过验证才进入权威案例库。
- [ ] 可复用流程经过抽象才晋升为 SOP。
- [ ] 可防复发错误优先转为测试、规则或 guardrail。
- [ ] 所有写回均可审计和回滚。

## 13.1 `business-triage/SKILL.md`

```markdown
---
name: business-triage
description: 业务问题分诊；当用户报告产品异常、处理失败或跨产品影响时使用
---

## 目标

把用户描述转成可验证的业务处置任务，不在证据不足时给出确定结论。

## 工作流程

1. 按 references/input-checklist.md 收集必要输入。
2. 涉及产品参数时，必须调用产品查询工具。
3. 根据问题类型读取 knowledge/sop 下对应 SOP。
4. 疑似已知问题时，调用案例检索工具。
5. 涉及多个产品或跨业务操作时，调用规则检查工具。
6. 将工具原始结果保存到 runs/<task-id>/evidence/。
7. 按 references/output-contract.md 输出处置单。

## 停止条件

- 缺少必要产品或环境信息；
- 数据来源冲突且无法确认有效版本；
- 案例适用条件与当前问题不一致；
- 规则检查失败；
- 需要执行高风险写操作；
- 必要工具不可用。

## 禁止事项

- 不得猜测产品参数；
- 不得仅凭 snippet 采用案例；
- 不得绕过规则工具；
- 不得把建议写成已执行；
- 不得自动把本次会话写入长期知识库。
```

# 结语

不要把知识治理做成“更大的向量库”，而要做成一个能够区分：

- 权威事实源与派生视图；
- SOP 与案例；
- 当前业务状态与历史经验；
- 软经验与硬规则；
- 当前工作状态与长期知识；

并能控制它们在何时、以何种权限、花多少预算进入上下文的系统。

对于本文的业务场景，最简明的落地原则是：

> **Skill 管流程，SOP 管业务规定，API 管参数事实，规则工具管硬逻辑，WeKnora 管案例召回，OKF 管可选知识契约，runs 工作区管本次证据，人工验证管最终写回。**
