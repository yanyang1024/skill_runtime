> 目标读者：内网研发同学（Windows / Linux），不想折腾、不想自建工具。

## 第 0 章：内网工具地图

先搞清楚两类工具的区别：

- **补全/问答助手**（灵码）：帮你补代码、答问题，**不会自己改文件、跑命令**。安全，适合所有人。
- **Agent 工具**（Cline / opencode / dsh / pi）：能自己读项目、改文件、跑测试。**能力强，但会动手，需要权限意识。**

### 选择速查表

| 你是谁 | 推荐 | 理由 |
|---|---|---|
| 普通开发，只想提效 | **灵码**（补全）+ 想试 Agent 就上 **Cline** | 都在 VS Code 里，不用碰终端 |
| 习惯终端、要多模型切换 | **opencode** | npm 源直接装，模型随便接内网网关 |
| 想要网页界面、重视安全 | **dsh** | 默认只读 + 审批，Web UI 只在本机，天然适合内网 |
| 高级玩家，愿意折腾 | pi | 见第 5 章，**不推荐作为团队标配** |

### 内网生存四法则（所有 Agent 工具通用）

1. **git 先行**：让 Agent 动手前 `git commit`。内网没有 Docker 兜底，git 就是你唯一的时光机。
2. **小任务起步**：第一次用先给只读任务（"读一下目录结构，别改东西"），确认模型接通了、目录对了，再给真任务。
3. **审批弹窗要看内容**：无脑点"允许"= 关掉安全系统。
4. **在专用目录里跑**：不要把 Agent 的工作目录指到 home 目录、下载目录或生产配置目录。

## 第 1 章：通义灵码

### 定位
代码补全 + 问答 + 简单生成。**它不会自动改你的文件、不会跑命令**，所以是内网最安全的 AI 工具，也是大多数同事的主力。

### 使用要点

- 在 VS Code 插件市场（或公司插件仓库）安装"通义灵码"，按引导登录
- 适合：补全、解释代码、写单函数、写注释/单测草稿
- 不适合：跨文件重构、跑测试修 bug 这类"多步任务"——那是 Agent 工具的活

### ⚠️ 内网注意事项

- 灵码依赖云端服务，**纯内网（不出网）环境可能无法使用**。如果你们用的是企业版/专有云部署，以服务地址为准；如果发现登录不上、补全无响应，先确认网络策略，别怀疑插件坏了
- 代码片段会发到服务端处理，**涉密代码遵守公司数据分级规定**

## 第 2 章：Cline

### 定位
VS Code 插件形态的 Agent：在编辑器侧边栏里读项目、改文件、跑命令，每步给你看 diff 并等你确认。**不想碰终端的用户的 Agent 首选。**

### 安装与配置

1. VS Code 插件市场搜 "Cline" 安装（内网走公司插件仓库或 VSIX 离线包）
2. 打开 Cline 设置，API Provider 选 **OpenAI Compatible**
3. 填入公司内网模型网关地址和 Key（找平台组要，格式通常是 `http://gateway.internal.company/v1` + 一个 API Key）
4. 选择模型名（以网关提供的为准）

### 日常使用

- 任务描述公式：**目标文件 + 验收标准 + 边界**
  ```
  ✅ "给 src/api/user.ts 的列表接口加分页，保持现有参数兼容，
      改完跑 npm test，有失败先报告不要继续改"
  ❌ "优化一下代码"
  ```
- 每次它要改文件/跑命令都会问你，**看清 diff 再点 Approve**
- 设置里的 **Auto-approve**（自动批准）建议全部关闭，等用熟了再逐项放开读文件类操作

### 内网坑点

| 症状 | 原因 | 解法 |
|---|---|---|
| 一直转圈/报网络错 | 网关地址填错或该网段不通 | 找平台组确认 endpoint；浏览器先访问网关地址验证 |
| 改了一堆文件想回退 | 没先提交 git | `git checkout .` 回退；下次先 commit |
| 上下文超长变"傻" | 会话太长 | 开新任务重来，把结论先存成 md 文件 |

## 第 3 章：opencode（内网版）

### 适合谁
习惯终端、想在多个模型间切换（比如内网网关上的千问/DeepSeek 等多个模型）的用户。

### 安装（走内网 npm 源）

```bash
npm install -g opencode-ai
opencode --version
```

Windows 和 Linux 通用。如果公司 npm 源里没有这个包，找源管理员同步。

### 首次配置

```bash
cd your-project
opencode
# TUI 里输入 /connect，选 OpenAI Compatible，填内网网关地址 + Key
# /model 选模型
# /init 生成 AGENTS.md
```

### 必做：权限配置（装完第一件事）

opencode **默认全自动放行**，内网又没有沙箱兜底，必须自己配。在项目根目录或全局配置 `opencode.json`：

```json
{
  "permission": {
    "bash": {
      "*": "ask",
      "npm run *": "allow",
      "git status": "allow",
      "git diff *": "allow",
      "rm -rf *": "deny",
      "git push *": "ask",
      "curl *": "ask"
    },
    "edit": {
      "*": "allow",
      ".env*": "deny",
      "../*": "deny",
      "/etc/*": "deny",
      "C:\\*": "deny"
    }
  }
}
```

规则是 **last-match-wins**（后面的覆盖前面的）。`edit` 一个键同时管住写文件/改文件。内置两道防呆不用配：同一操作重复 3 次自动拦截；改项目外目录默认会问你。

### 两个模式

- **build**（默认）：能改文件
- **plan**：只读分析，按 **Tab** 切换——让它先出方案再动手，复杂任务养成先 Tab 的习惯

### 内网坑点

| 症状 | 原因 | 解法 |
|---|---|---|
| 某个模型工具调用老失败 | 内网网关对小模型的适配不一 | 换网关上的主力模型 |
| 死循环重复同一操作 | 内置拦截会停它，但如果你禁用了工具，截断提示可能指向不存在的工具 | 别乱禁 Grep/Read |
| allow 的命令干了坏事 | 无沙箱，只查命令字符串 | 高危项目在专用测试机/专用账号下跑（内网没有 Docker，见第 6 章替代方案） |

## 第 4 章：dsh（内网版）

### 适合谁
想要**网页界面**、重视安全默认值的用户。**它是内网条件下的优选**：Web UI 只监听本机（天然不暴露）、默认只读模式、Linux 上自带 bwrap 沙箱（不需要 Docker！）。

### 安装

```bash
# 先确认 Node 版本：必须 22.19+ 或 24+（不对就找运维装内网 Node 镜像里的对应版本）
node -v

# 走内网 npm 源
npm install -g @deepseek-ai/dsh
dsh web
```

浏览器自动打开 `http://127.0.0.1:3080`（纯内网无碍，就是本机）。

### 首次三步

1. **Settings → Models**：模型服务商选 OpenAI 兼容，填内网网关地址 + Key（存在本机 `~/.dsh/.credentials.yaml`，Windows 在 `C:\Users\你\.dsh\`）
2. **添加工作区**：选项目目录。**第一次建议建个空的练习目录**，别选 home/下载目录
3. 发个只读小任务验证："读一下当前目录，告诉我有哪些文件，别修改"

### 权限三档（重要）

| 档位 | 含义 | 建议 |
|---|---|---|
| `read-only`（默认） | 只能看 | 第一次用就保持这个 |
| `workspace-write` | 只能写工作区内 | **日常开发用这个**，改工作区外的文件会要求审批 |
| `danger-full-access` | 无限制 | **永远不要开**——它会把沙箱和审批一起关掉 |

### Windows vs Linux 差异（内网重点）

- **Linux**：dsh 自带 bwrap 沙箱，越权写入是内核级拒绝——这是内网没有 Docker 的情况下**最好的隔离方案**，不用额外装任何东西
- **Windows**：沙箱能力弱，靠审批弹窗。务必：保持 `workspace-write` 档位 + 看清每个审批 + 在专用项目目录跑

### 特色：Trajectory 回放

它把 Agent 做的每一步都记录在只追加日志里，Web UI 里可以回看、甚至从中间某步 fork 重跑。Agent 干出问题（改错文件、跑错命令）时，用 Trajectory 复盘到底哪步出了错——这是五款工具里最强的"事后查账"能力，内网排障很值钱。

### 内网坑点

| 症状 | 原因 | 解法 |
|---|---|---|
| 装不上/起不来 | Node 版本不对（要 22.19+ 或 24+） | 从内网 Node 源换版本 |
| 功能怪怪的、升级后配置失效 | 它是 v0.1 预览版，官方明说会有 breaking change | 固定一个版本用，别追新：`npm install -g @deepseek-ai/dsh@版本号` |
| 想从别的机器访问 Web UI | 只绑 127.0.0.1 | **不要**自己开端口暴露；需要远程就在那台机器上装一个 |

## 第 5 章：pi（内网版）

### 先说结论

pi 的设计哲学是"极简内核 + 自己装扩展"，它的 bash **完全没有权限防护**。对于"不想自建工具、没有 Docker"的内网环境，**不建议作为团队标配**，只推荐给愿意折腾的少数高级用户。普通用户请用 Cline / opencode / dsh。

### 如果你确实要用

```bash
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
cd your-project && pi
# /login 或配置 API Key（OpenAI 兼容网关也可以走 models.json 自定义 provider）
```

### 内网特有的两个坑（重要）

1. **grep/find 依赖外网下载**：pi 首次用 grep/find 会自动从公网下载 ripgrep 和 fd 二进制到 `~/.pi/agent/bin/`，**纯内网会卡死**。
   解法（任选）：
   - 找一台能出网的机器装好，把 `~/.pi/agent/bin/` 整个目录拷到内网机器同路径
   - 或请 IT 把 ripgrep/fd 放进内网源/共享盘
2. **bash 裸奔**：没有任何权限层。没有 Docker 的替代隔离方案：
   - 在**专用测试机或虚拟机**里跑（找运维申请）
   - 用**低权限专用账号**登录后再跑 pi
   - 只让它在已提交 git 的项目目录工作

## 第 6 章：内网常见问题 FAQ

**Q1：这些工具会不会把代码传到外网？**
工具本身（opencode/pi/dsh/Cline）都是本地运行、开源的，代码只发给你配置的模型端点。**只要模型端点指向内网网关，代码就不出内网。** 灵码用云端服务，按公司数据分级规定执行。

**Q2：没有 Docker，Agent 跑坏了怎么办？**
三道替代防线（按成本排序）：
1. git 先提交，随时 `git checkout` 回滚（零成本，人人该做）
2. Agent 工具自身的权限配置（opencode 的 permission / dsh 的 workspace-write / Cline 的手动审批）
3. 高风险任务（动数据库脚本、部署脚本）去专用测试机 + 低权限账号跑

**Q3：API Key 怎么管？**
- 找平台组申请内网网关 Key，不要个人乱申请外网 Key
- 别截图、别提交进 git、别发群里
- 配置文件（opencode.json、dsh 的 credentials.yaml）注意别被 git 跟踪

**Q4：模型响应慢/超时？**
内网网关负载或模型排队。换网关上的备选模型（opencode/dsh 都支持会话中切换），或把大任务拆小。

**Q5：Agent 改完代码能直接合入吗？**
**不能。** 所有 Agent 都会写出"看着对、能跑、语义错"的代码。必须：`git diff` 逐行看 → 跑测试 → 代码评审。Agent 是实习生，不是外包。

**Q6：我该花时间学哪个？**
- 只想提效：灵码用熟 → Cline 上手 → 够用了
- 想再进一步：opencode（终端）或 dsh（网页）二选一
- pi：除非你就是想研究 Agent 本身，否则跳过

## 第 7 章：每种工具的局限性——什么时候好用、什么时候别用

> 本章基于 2026 年下半年的公开评测和大量真实用户反馈整理，回答三个问题：**它什么时候好用？什么时候不好用？这个场景我该用哪个？**

### 7.0 局限性总表

| 工具 | 什么时候好用 | 什么时候不好用 |
|---|---|---|
| 灵码 | 日常补全、写注释/单测、中文问答、Java/Go 国产栈 | 跨文件重构、多步任务、纯内网无云端（非企业版）、海外小众框架 |
| Cline | 编辑器内完成"改代码+跑命令"闭环、每步 diff 确认、GUI 党 | 长任务 token 消耗大、大仓库上下文管理弱、审批弹窗疲劳 |
| opencode | 多模型切换、成本敏感任务分级、终端流、可定制 | 开箱体验糙、任务速度偏慢、有"顺手重排代码"的 harness 级毛病、无沙箱 |
| dsh | 长程复杂任务、批量无人值守、审计复盘、Linux 沙箱隔离 | 日常轻量交互（杀鸡用牛刀）、预览版稳定性、插件生态无治理、Windows 沙箱弱 |
| pi | 高级用户定制工作流、嵌入自己系统、低上下文成本跑任务 | 想要全家桶的人、无隔离环境（bash 裸奔）、内网首装（rg/fd 拉不下来） |

### 7.1 灵码的局限性

**好用**：行级/函数级补全体验流畅，中文指令理解是国产工具里最好的一档；写注释、写单测、解释代码、异常排查这类"单点辅助"几乎零学习成本；企业版支持 VPC 私有化部署，合规方案成熟。

**不好用**：
1. **跨文件能力弱**。全网用户反馈最集中的一条：对话基本局限在当前文件，不支持跨文件重构——复杂重构要换 Agent 类工具（Cline/opencode/dsh）。这不是bug，是"插件助手"和"Agent"的品类差异。
2. **Agent 自动化弱**。它不会自己分步骤改多个文件、跑测试迭代——别拿它当 Agent 用。
3. **对海外小众框架支持偏弱**（如 NestJS、Svelte 等新框架的生成准确率偏低），微服务架构类复杂工程生成质量一般。
4. **依赖云端**。个人版走阿里云云端，纯内网不出网就用不了——需要企业专属版（VPC 部署）。内网推灵码前先确认公司买的是哪个版本。
5. 交互细节有毛刺：IDE 内复制为纯文本、不能直接新建/插入项目文件等。

**场景建议**：全员日常的"副驾驶"，配合一个 Agent 工具（Cline 或 opencode）处理跨文件任务，是最舒服的组合。

### 7.2 Cline 的局限性

**好用**：在 VS Code 里完成"读项目 → 改文件 → 跑命令 → 看结果再改"的完整闭环，每步给你看 diff 等确认，是不想碰终端的用户唯一能用的 Agent 形态；支持 OpenAI 兼容端点，内网网关一接就能用。

**不好用**：
1. **token 消耗偏大**。实测数据：每个任务约消耗 50 万–500 万 token（对比 Claude Code 约 20 万–300 万）。它每一步都重新发送大量上下文，长任务账单会肉眼可见地涨。对策：长任务拆成多个会话；内网网关侧设配额提醒。
2. **大仓库上下文管理弱**。项目大了以后它会反复读文件、上下文越堆越长，表现为"越聊越笨"。对策：`.clinerules` 里限定操作范围，任务描述里点名具体文件。
3. **审批疲劳是它的安全模型死穴**。每一步都要点 Approve，点多了人手比脑子快，等于关掉安全。对策：只给读文件类操作开 auto-approve，写文件/跑命令永远手动。
4. 强依赖模型质量：接弱模型时"改错→跑→再改错"的循环会明显变多，token 消耗雪上加霜。内网网关上的主力模型决定 Cline 体验上限。

**场景建议**：编辑器党的主力 Agent，适合中小仓库、边界清晰的任务；超大仓库的重构和长链路任务交给 opencode/dsh。

### 7.3 opencode 的局限性

**好用**：模型自由（内网网关上挂了几个模型就能随时切，简单任务用便宜模型、硬骨头切旗舰）；开源可读；build/plan 双模式；社区最大、迭代快；token 单价敏感团队的省钱主力。

**不好用**（有实测数据支撑）：
1. **同模型下任务速度偏慢**。Builder.io 同模型同任务对比：完成同一批任务 opencode 耗时约为 Claude Code 的 1.8 倍（client-server 架构 + LSP 反馈环的开销）。赶时间的高频小任务会觉得"肉"。
2. **有 harness 级的"重排代码"毛病**：实测中三个不同模型在 opencode 下都试图顺手 reformat 未相关代码——这是 harness 问题不是模型问题，diff 评审时要特别留意无关改动。
3. **开箱体验糙**：装完必须自己选模型、配权限（默认全自动放行！），新手第一道门槛比灵码/Cline 高。
4. **无 OS 沙箱**：权限只查命令字符串，内网无 Docker 时高危任务要靠专用测试机兜。
5. 非主流模型路径打磨不一，小模型的 tool-calling 翻车率明显高。

**场景建议**：终端用户的主力；成本敏感任务（批量改名、写测试、文档生成）用便宜模型跑最划算；别让它在没配权限的情况下碰任何重要目录。

### 7.4 dsh 的局限性

**好用**：长程复杂任务能力强（社区反馈一句 prompt 能连续跑几十分钟到几小时不摆烂）；PTC 模式缓存命中率约 99%，批量任务 token 成本极低；Trajectory 回放是排障和复盘神器；Linux 上 bwrap 内核沙箱是内网无 Docker 条件下的最强隔离；headless 模式适合批量无人值守。

**不好用**：
1. **v0.1 预览版，稳定性一般**：实测有会话卡死需刷新、权限判定异常、插件导致启动崩溃等报告；官方明说会有 breaking change。**务必锁版本**。
2. **日常轻量交互是杀鸡用牛刀**：没有传统 CLI 交互模式（日常要开浏览器），UI 细节（如三栏布局）还没打磨完；改个错别字这类小活用灵码/Cline 顺手得多。
3. **学习成本**：Cordis 插件、Profile、预设一整套概念，不是"装上就用"。
4. **插件生态无治理**：没有官方插件市场，社区市场各自为政，无统一安全审核——**团队规范里应禁止业务同事自行安装来源不明的插件**。
5. **提示注入风险有实测数据**：腾讯朱雀实验室 14,560 次运行测试中，基线配置下约 5.6% 的运行被提示注入完全达成攻击目标（如 fake_completion 类攻击成功率约 17%）。含义：**不要让 dsh 在开了写权限的情况下处理不可信外部内容**（来路不明的网页/文档/Skill），批处理外部数据时保持 read-only。
6. Windows 沙箱弱、WSL 有已知失效问题。

**场景建议**：Linux 上的长任务/批量任务/需要审计的任务首选；CI 类无人值守场景（配 read-only 或 workspace-write）；不适合作为日常交互主力工具，不适合 Windows 上跑高危任务。

### 7.5 pi 的局限性

**好用**：极简内核行为可预测；Databricks 内部基准测试中，pi 在同模型下 pass rate 最高且成本显著更低（每轮上下文少约 3 倍）——证明"少即是多"对纯执行任务成立；树状会话、四种运行模式（TUI/print/RPC/SDK）适合嵌入自动化。

**不好用**：
1. **没有全家桶**：无 plan mode、无子代理、无权限弹窗、无 MCP——全是"自己装扩展"。对不愿自建的同事，这就是"缺功能"而不是"哲学"。
2. **bash 裸奔**：无任何权限层，无 Docker 的内网里隔离成本最高（要专用测试机或低权限账号配套）。
3. **内网首装坑**：rg/fd 二进制要从公网拉，离线环境直接卡住（解法见第 5 章）。
4. 生态和文档体量远小于 opencode/Cline，踩坑主要靠 Discord 和源码。
5. Windows 支持相对次要。

**场景建议**：只推荐给愿意"拥有自己 harness"的高级用户和嵌入自动化流水线的场景；不要作为团队标配推广。

### 7.6 场景 → 工具决策表（内网版）

| 场景 | 首选 | 次选 | 别用 |
|---|---|---|---|
| 日常写代码（补全/注释/单测/问答） | 灵码 | — | Agent 工具（浪费 token） |
| 跨文件改需求，我在 VS Code 里盯着 | Cline | opencode | 灵码（做不到） |
| 终端流，多模型按任务成本分级 | opencode | dsh | — |

| 批量/无人值守任务（CI、夜间批处理） | **dsh headless**（read-only 起） | opencode 脚本模式 | Cline（GUI 依赖） |
