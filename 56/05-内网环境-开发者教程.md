# 公司内网 AI 编程工具开发者教程（进阶/管理篇）

> 目标读者：内网技术骨干、Team Leader、平台/工具链负责人——负责给团队搭好 AI 编程环境、定规范、做安全治理的人。
> 内网前提：npm/pip 源可用；可装 pi / dsh / opencode；已有 Cline、通义灵码；Windows+Linux 混合；**Docker 受限**；**大多数同事没有自建工具的意愿**。
> 核心设计原则：**配置驱动，不是扩展驱动**。所有方案都是"下发配置文件 + 定规范"，不要求业务同事写任何扩展代码。

## 一、内网约束对工具策略的影响

| 约束 | 推论 |
|---|---|
| 无公网 | 一切"首次运行自动下载"的机制都是雷（pi 的 ripgrep/fd 自动下载、模型选择页拉公网列表等），要么预置要么绕开 |
| npm/pip 源可用 | npm 分发的四款工具（opencode/dsh/pi）可装；Node 本体和版本要靠内网源/离线包解决 |
| Docker 受限 | 放弃"容器隔离"这条路，改用：**工具内建权限 + dsh 的 bwrap（Linux 原生，非 Docker）+ 专用测试机/低权限账号 + git 纪律** |
| Win+Linux 混合 | 配置模板要给双平台路径；沙箱类能力按 Linux 设计、Windows 降级为"审批+目录隔离" |
| 用户不愿自建 | 不推 pi 的"自己写扩展"路线；团队产出一个"黄金配置仓库"，同事复制即用 |

**工具分层策略（推荐）**：

```
第一层（全员）：灵码 —— 补全/问答，零风险
第二层（自愿）：Cline / opencode / dsh —— Agent，配好权限模板下发
第三层（个别高级用户）：pi —— 不强推，配隔离环境
```

## 二、基建层：内网环境准备清单

### 2.1 Node 运行时

- dsh 要求 **Node 22.19+ 或 24+**；opencode/pi 对版本宽容些，但建议团队统一 22 LTS
- 内网准备：Node 官方离线安装包（Win `.msi` / Linux `.tar.xz`）放共享盘，或在内网源里建 Node 分类
- 版本管理：Linux 可用内网镜像里的 nvm 离线包；Windows 直接装固定版本即可，别折腾

### 2.2 npm 源确认清单

```bash
npm config get registry          # 确认指向内网源
npm view opencode-ai versions    # 确认内网源已同步目标包
npm view @deepseek-ai/dsh versions
npm view @earendil-works/pi-coding-agent versions
```

缺包找源管理员同步。**建议团队锁定版本**（见 4.x 各章），预览版工具（尤其 dsh）追新会被 breaking change 咬。

### 2.3 预置"自动下载型"依赖

内网用户的典型卡点是工具首次运行时去公网拉东西。提前把这些放进共享盘/内网源：

| 依赖 | 谁需要 | 预置方式 |
|---|---|---|
| ripgrep + fd 二进制 | pi（grep/find 必需） | 出网机器装好后打包 `~/.pi/agent/bin/`，内网同路径覆盖；或内网源上架 |
| VS Code 插件 VSIX | Cline、灵码 | 插件仓库或共享盘 VSIX 离线安装：`code --install-extension xxx.vsix` |
| Node 各版本安装包 | 全部 | 共享盘/内网源 |

### 2.4 pip 源的角色

Agent 干活常要跑 Python 脚本（数据分析、文档处理），pip 源可用意味着 Agent 装依赖不会卡。团队规范里明确：**允许 Agent 从内网 pip 源装包，禁止它从公网源装**（在 AGENTS.md 里写明，见第六章）。

## 三、统一入口：内网模型网关

### 3.1 为什么必须收敛到一个网关

四款工具（Cline/opencode/dsh/pi）**全部支持 OpenAI 兼容端点**。让平台组维护一个内网模型网关（开源方案如 one-api / LiteLLM 均可，部署在服务器上，不需要业务机有 Docker），背后接千问/DeepSeek 等模型，对业务同事只暴露：

```
Base URL: http://gateway.internal.company/v1
API Key:  找平台组申请
```

收益：
- **Key 集中管理**：吊销、轮换、配额都在网关侧，不依赖个人自觉
- **审计**：网关日志 = 全团队 AI 调用台账（谁在什么时候用了多少 token、发了什么请求级别）
- **工具无关**：换工具不换 Key，新工具来了接同一个网关
- **数据合规兜底**：代码只流向内网网关，天然不出网

### 3.2 各工具接网关的方式速查

| 工具 | 配置入口 | 备注 |
|---|---|---|
| Cline | 插件设置 → OpenAI Compatible → Base URL + Key | 最简单，适合推广 |
| opencode | TUI `/connect` 或 opencode.json 的 provider 块 | 支持多模型随时 `/model` 切换 |
| dsh | Web UI Settings → Models → OpenAI 兼容端点 | Key 存本机 credentials.yaml |
| pi | `models.json` 自定义 provider，或环境变量 | 仅高级用户 |

## 四、分工具进阶配置模板

> 用法：把本节内容放进团队的"黄金配置仓库"（git 内网仓库），新同事 clone 后复制到对应位置。

### 4.1 opencode：团队权限模板

`opencode.json`（项目级，可提交到各业务仓库）：

```json
{
  "$schema": "https://opencode.ai/config.schema.json",
  "permission": {
    "bash": {
      "*": "ask",
      "npm run *": "allow",
      "npm test*": "allow",
      "git status": "allow",
      "git diff *": "allow",
      "git log *": "allow",
      "mvn *": "allow",
      "pytest *": "allow",
      "rm -rf *": "deny",
      "git push *": "ask",
      "curl *": "ask",
      "wget *": "ask",
      "ssh *": "deny",
      "sudo *": "deny"
    },
    "edit": {
      "*": "allow",
      ".env*": "deny",
      "*.pem": "deny",
      "*.key": "deny",
      "../*": "deny"
    }
  }
}
```

设计依据（来自 opencode 源码机制）：
- **last-match-wins**：deny 规则放最后兜底
- `edit` capability 同时覆盖 write/edit/patch 三个工具，一个键管全
- 内置防呆（重复 3 次自动拦截、项目外路径默认 ask）不用配，但**别禁用 Grep/Read**——截断提示会引导模型用它们，禁了会死循环
- 按团队技术栈增删 allow（上面给了 npm/maven/pytest 示例）

### 4.2 dsh：团队使用规范

- **锁版本**：`npm install -g @deepseek-ai/dsh@<验证过的版本>`，写进团队 wiki；它是 v0.1 预览版，官方明说会 breaking change
- **预设选择**：业务同事只用 `Standard`；重复性多步任务（如批量数据处理）可试 `PTC`（缓存命中率高、省 token）；`Minimal` 是评测用的；`Creation` 禁止业务使用（运行时改框架，等同 shell 权限）
- **权限档位**：全员默认 `workspace-write`；`danger-full-access` 列入红线（它把沙箱和审批一起关，且没有第二道防线）
- **Linux 服务器场景**：dsh 本地执行器走 bwrap（内核级隔离，**不需要 Docker**），这是内网条件下能拿到的最强隔离——有集中式 Agent 任务（如 CI 里跑）优先放 Linux + dsh
- **审计**：利用 append-only 会话日志 + Trajectory 视图做事故复盘；它能从第 N 步 fork 重跑，适合给团队做"Agent 失败案例库"

### 4.3 Cline：团队约定

- Auto-approve 设置建议发文明确：新同事全关；熟手可开"读文件"类
- 项目根目录放 `.clinerules` 文件写项目规矩（等价于 AGENTS.md，见第六章）
- 评审要求：Cline 的 diff 确认必须真看， Team Lead 抽查 commit 记录

### 4.4 灵码：定位管理

- 明确告诉团队：灵码是"助手"不是"Agent"，涉密代码按数据分级规定走
- 纯内网不通云端时，排查方向是网络策略而非插件本身；有企业版/专有云部署则以企业版为准

### 4.5 pi：仅限白名单用户

- 不建议写入团队标配；确需使用的同事，先解决两件事：**预置 ripgrep/fd 二进制**（见 2.3）和**运行环境隔离**（见第五章）

## 五、没有 Docker 的安全治理体系

Docker 受限时，用四层替代方案叠出等效纵深：

### 第 1 层：工具内建权限（人人有）
- opencode 权限模板（4.1）、dsh 的 workspace-write、Cline 手动审批
- 这是"进程内策略"：快、可读，但只查命令字符串，防不住名不副实的命令

### 第 2 层：OS 级隔离（Linux 白捡的）
- **dsh 的 bwrap/Landlock 是原生 Linux 能力，不是 Docker**——在 Linux 开发机/服务器上装 dsh 就有内核级沙箱，越权写入直接内核拒绝
- Windows 没有对应物，降级方案：专用项目目录 + 审批 + 不让 Agent 碰系统路径（opencode 模板里已 deny `C:\*`）

### 第 3 层：环境隔离（替代容器的重方案）
- **专用测试机/虚拟机**：找运维申请几台，跑高危任务（数据库迁移脚本、部署脚本、批量删除类）
- **低权限专用账号**：在测试机上建无 sudo、无生产凭据的账号，Agent 只能在这个账号下跑
- 成本比 Docker 高，但只需少量几台，覆盖高危场景即可

### 第 4 层：流程兜底（最便宜也最容易被忽视）
- git 纪律：Agent 动手前必须 clean commit；分支保护 + 强制评审
- **红线清单**（发文明确）：
  - 禁止任何 Agent 工具使用 `danger-full-access` / 全自动模式跑生产相关目录
  - 禁止把 API Key 提交进仓库（配 pre-commit 钩子扫描）
  - Agent 产出代码必须 `git diff` 人工过目 + 测试通过 + 评审，三件套缺一不可
- **审计**：模型网关日志（3.1）+ dsh Trajectory + git 提交记录，三方对得上

## 六、团队规范：AGENTS.md

AGENTS.md 是行业公约，opencode/Cline(`.clinerules`)/dsh/pi 都认。团队统一模板，放每个仓库根目录：

```markdown
# AGENTS.md

## 项目概况
- 技术栈：Java 17 + Spring Boot 3 / Node 22 + React
- 构建：mvn package / npm run build
- 测试：mvn test / npm test（改动代码后必须运行）

## 环境约束（内网）
- 只允许使用内网 npm/pip 源安装依赖，禁止访问公网源
- 模型端点走内网网关，禁止配置任何公网 API 地址
- 本机没有 Docker，不要生成或执行 docker 命令

## 禁区
- 禁止修改 deploy/ 目录下的生产配置
- 禁止执行 git push、rm -rf、任何写数据库的脚本
- 密钥文件（.env、*.pem）只读

## 约定
- 重要结论和中间状态写入 docs/agent-notes.md，不要只放在对话里
- 拿不准的操作先停下来问
```

两份价值：一是约束 Agent 行为（内网约束写进去，Agent 就不会去够公网源和 Docker）；二是新人 onboarding 文档，人也能看。

## 七、推广落地路线

考虑"用户不愿自建"的现实，按这个顺序推：

**第 1 步（第 1-2 周）：铺助手层**
- 全员灵码，零风险提效，建立信任

**第 2 步（第 3-4 周）：试点 Agent 层**
- 选 3-5 个愿意尝鲜的同事，发"黄金配置包"（网关 Key + opencode.json 模板 + AGENTS.md 模板 + 一页纸使用说明）
- 首选 **Cline**（GUI 友好）或 **dsh**（安全默认值好），opencode 给终端党
- 收集失败案例，用 dsh Trajectory 复盘，充实 FAQ

**第 3 步（第 2 月起）：规模化**
- 黄金配置进内网 git 仓库，新人入职随环境一起发
- 红线清单发文；网关配额和审计上线
- pi 仅在有人主动要求时个别开放

**持续运营**：
- 版本季度评估（尤其 dsh，锁版本 + 升级前先在试点组验证）
- 每月汇总网关用量和典型失败案例，迭代 AGENTS.md 模板

## 八、（可选）轻量扩展路径

个别有研究兴趣的同事想做扩展时，给这条最低成本路线：

1. **先别写代码**：opencode 的配置、Cline 的 rules、dsh 的预设组合，80% 的"定制需求"配置层就能解决
2. **要拦截/审计**：dsh 插件监听 agent loop 的 waterfall 事件（模型请求前/工具执行前/轮次结束），不用改框架源码；或者给团队仓库加 pre-commit/CI 钩子（不依赖 Agent 工具本身，最稳）
3. **要新工具/新流程**：pi 的 TypeScript 扩展是五家里上手最快的（50+ 官方示例，`/reload` 热加载），但仅限个人玩，不要进团队关键链路
4. **有价值的验证机制**：两个零 LLM 成本的设计值得抄到任何内部平台——opencode 的 doom_loop（同输入重复 3 次即拦截）和 dsh 的"编辑后附 LSP 诊断摘要"（edit 返回值直接带 `N error(s), M warning(s)`）

## 九、局限性速查与选型决策（治理视角）

> 详细的用户向局限性分析见《04-内网环境-用户教程》第 7 章；本章是给负责人做工具治理时的浓缩版。结论均来自 2026 年下半年公开评测与真实用户反馈。

### 9.1 各工具的"能力边界"与治理含义

| 工具 | 已验证的局限 | 对治理的含义 |
|---|---|---|
| 灵码 | 对话局限于当前文件、不能跨文件重构；Agent 自动化弱；依赖云端（个人版） | 定位为"助手层"即可，别承诺它能干 Agent 的活；纯内网必须用企业专属版（VPC 部署），采购前先确认版本 |
| Cline | 每任务 token 消耗约 50 万–500 万（约为 Claude Code 的 2 倍量级）；大仓库上下文管理弱；审批疲劳 | 网关侧**必须设配额监控**；推 `.clinerules` 限定范围；auto-approve 策略发文规范 |
| opencode | 同模型任务耗时约为 Claude Code 的 1.8 倍（client-server + LSP 开销）；实测存在 harness 级"顺手 reformat 无关代码"问题；无沙箱 | 评审规范里加一条："diff 中留意无关重排改动"；高危任务强制走专用测试机 |
| dsh | v0.1 预览版（会话卡死、权限判定异常均有实测报告）；无官方插件市场、生态无治理；腾讯朱雀 14,560 次注入测试基线下约 5.6% 完全攻击成功 | **锁版本 + 插件白名单**双红线；处理不可信外部内容的任务强制 read-only；面向生产的自动化不要用预览版默认值上线 |
| pi | 无权限层（bash 裸奔）；rg/fd 依赖公网拉取；生态小 | 白名单制开放，配套专用测试机；不进团队标配 |

### 9.2 场景选型决策（与第四章工具策略对应）

- **日常提效（全员）**：灵码。它的边界（不动手、不跨文件）恰好就是它的安全边界。
- **交互式 Agent（GUI 党）**：Cline，中小仓库、边界清晰任务；成本用网关配额兜。
- **交互式 Agent（终端党）**：opencode，多模型分级省钱是内网网关架构下的最大红利。
- **长程/批量/无人值守**：dsh（Linux + bwrap + workspace-write），这是内网无 Docker 条件下唯一能拿到内核级隔离的组合。
- **需要审计复盘**：dsh（Trajectory + append-only 日志），其他工具只有 git 可查。
- **嵌入自研系统**：pi（SDK/RPC）或 dsh（Python SDK），仅限平台组。
- **不可信内容处理**（网页/文档/外部 Skill）：任何工具都强制 read-only 档位——提示注入是有实测成功率数据的真实风险，不是理论问题。

### 9.3 写进红线的三条（源自局限性证据）

1. **dsh 锁版本 + 插件白名单**：预览版 breaking change + 生态无治理，这两条不锁住，故障会在业务侧随机爆发。
2. **处理外部内容的任务一律 read-only**：dsh 注入测试里 `fake_completion` 类攻击成功率约 17%、隐藏 Unicode 在文件载体上达 25.5%——开写权限处理不可信内容等于把注入风险变成实际操作风险。
3. **diff 评审必须留意"无关改动"**：opencode 的 reformat 倾向是 harness 级现象，与模型无关，换模型不能解决，只能靠评审流程兜。
