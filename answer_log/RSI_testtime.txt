我认为你的四个原语抓住了一个关键：**系统改进是否发生，不取决于它有没有“反思”，而取决于经验是否改变了持久状态、这种改变是否有可信收益，以及未来运行是否真的使用了它。**

但需要进一步分清三件事：

- **形成闭环**：写入的东西以后能被用到。
- **产生改进**：未来任务的表现确实更好。
- **构成递归改进**：这些变化也提升了系统发现问题、提出修改、验证修改的能力。

这三者不能互相替代。一个不断把会话总结写进 Skill 的系统，可能闭环完整，却在持续积累错误和复杂性。

以下涉及“四原语重构、验证边界和落地路径”的部分，主要是针对你场景的推演；引用研究时会单独指出。

**一、你的四原语可以成立，但它更像“最小闭环结构”，不是四个同层级操作**

你提出的第一项“持久介质”，是状态载体；第二项“写入”，是操作；第三项“判定”，是决策；第四项“回读”，是状态生效机制。它们混合了不同抽象层次，但并不妨碍工程使用。

我建议保留你的框架，把它重新表述为：

| 原语 | 核心问题 | 在 Skill / Agent 中对应什么 |
|---|---|---|
| 可继承状态 | 什么可以跨运行保留下来？ | Agent 文档、Skill 全目录、脚本、路由、依赖、经验索引 |
| 候选变异 | 如何产生一个不同的未来行为？ | 增删改规则、替换脚本、调整加载条件、删除过时经验 |
| 选择 | 为什么让这个变异进入后续运行？ | 对照评估、约束检查、成本比较、适用范围判定 |
| 继承与表达 | 保留的变化如何成为实际行为？ | 版本激活、路径解析、按需加载、执行和效果观测 |

其中，有两个值得调整的地方。

**第一，“写入”不要等同于 memory。**

写入一个失败案例，写入一个可执行脚本，修改 Agent 的调度规则，虽然都是持久化，但改变行为的机制不同：

- 案例通过检索和类比影响决策；
- Skill 通过指导过程影响决策；
- 脚本直接改变执行能力；
- 路由决定什么知识有机会被读取；
- 删除规则则减少干扰和过时约束。

因此，RSI 的变异空间应该包含**新增、替换、删除、合并、缩小适用范围**，不能只有积累。

**第二，“回读”必须包含实际生效，而不只是文件被加载。**

可以把证据分成四级：

> 版本存在 → 运行加载了该版本 → 行为发生了相关变化 → 变化改善了结果。

“读取过 SKILL.md”只证明第二级。模型可能忽略它，也可能本来就会这样做。要证明它有作用，还需要对照或消融。

所以，你的四原语能描述“可进化系统”，但**不能单独保证它向好的方向进化**。真正决定方向的是第三项，而决定改进能否兑现的是第四项。

---

**二、第一性原理下，真正要优化的是“有边界的未来收益”**

设持久状态为 \(S_t\)，实际运行还依赖模型 \(M\)、环境 \(E\)、任务 \(x\) 和预算 \(B\)：

\[
y = \operatorname{Run}(S_t,M,E,x,B)
\]

修改得到候选状态 \(S'\)。我们希望它在未来任务分布 \(D\) 上更好：

\[
\Delta U =
\mathbb{E}_{x\sim D}
[U(\operatorname{Run}(S',x))-U(\operatorname{Run}(S_t,x))]
\]

这里的 \(U\) 应包含结果质量、运行成本和副作用；重要的权限、隔离、数据完整性约束，最好单独作为硬门槛，而不是允许被平均分抵消。

现实中的困难是：**你看不到完整的未来分布，只能用有限样本、有限验证能力估计它。**

所以一次评估能够支持的结论应该是：

> 在指定任务范围、模型、环境和预算下，已有证据支持这一修改改善某项能力，且未发现超出容忍范围的回归。

不能直接升级为“这个 Skill 变强了”。

这意味着，每次晋升的不只是一个版本，还应该是一个**带适用范围的改进主张**。

例如：

> 在工具返回结果过大的检索任务中，先读取摘要再按需读取正文，降低上下文成本，同时保持答案完整性。

它明显比“以后优先读摘要”更容易验证，也更容易防止错误泛化。

---

**三、可修性不是问题本身的标签，而是问题与当前系统条件的关系**

你说“判断什么不可修，比修更重要”，我赞同。但“不可修”最好拆开，否则系统容易把缺少证据误认为缺少能力。

| 边界 | 典型情形 | 正确的下一步 |
|---|---|---|
| 目标未定义 | “回答更专业”没有可共同认可的标准 | 澄清目标或提供条件化选择 |
| 结果不可观测 | Agent 说写入成功，但没有数据库结果可查 | 补结果观测接口 |
| 验证能力不足 | 有产物，但现有裁判无法判断专业正确性 | 补专家、实验、参考证据或更窄的断言 |
| 执行能力不足 | 需要访问的数据或工具不存在 | 补能力、转交或明确阻塞 |
| 授权不足 | 技术上可做，但不能访问或执行 | 走授权流程；不能靠修改提示词绕过 |
| 策略缺陷 | 工具和证据都在，但参数、顺序、加载方式错误 | 适合修改 Skill / Agent |
| 预算不足 | 可以完成，但成本超过可接受范围 | 调整范围、算法或资源预算 |
| 环境失效 | 依赖、进程、磁盘状态使任务无法正常运行 | 修复运行环境，并单独验证 |

**“没有验证手段”意味着尚不能可信晋升，不意味着没有正确解。**

同样，“当前模型连续失败”也不足以证明不可解。它只说明在已经尝试的方法和预算下，没有获得成功证据。

可以用一个简单矩阵控制动作：

|  | 能可靠验证 | 暂时不能可靠验证 |
|---|---|---|
| 当前具备执行能力 | 可以进入自动改进实验 | 可以探索，但限制晋升和影响范围 |
| 当前缺少执行能力 | 建立能力补充需求及验收标准 | 先做信息获取和问题澄清 |

这里最有价值的边界评估，往往不是给出一个结论，而是指出：

> **缺少哪一项证据或能力，补上之后这个问题就能进入可验证改进区？**

这让“blocked”成为可行动状态，而不是失败垃圾桶。

---

**四、验证边界要先于修改建立，但允许在独立流程中被修正**

每个候选修改，建议先冻结六项内容：

| 项目 | 要回答的问题 |
|---|---|
| 改进主张 | 预期改善什么可观察行为或结果？ |
| 适用范围 | 对哪些任务成立？明确不覆盖什么？ |
| 可修改范围 | 允许改哪些文件、工具和状态？ |
| 成功证据 | 什么观测足以支持“更好”？ |
| 反证条件 | 出现什么结果就否定这次改进？ |
| 预算与停止条件 | 最多试多少次，何时停止或转交？ |

**尤其需要提前写反证条件。** 否则系统很容易在看到结果后重新解释目标。

例如修改一个“工具失败后重试”的 Skill：

- 改进主张：减少瞬时故障导致的失败。
- 适用范围：幂等读取、明确的暂时性错误。
- 反证条件：对权限错误重复请求；重复执行有副作用的操作；成功率不变但成本显著增加。
- 边界案例：超时后实际已经写入成功，不能盲目再次写入。

这比一个“重试后成功了”的正例更能说明修改是否可靠。

验证者本身也可能有错。Anthropic 的评测文章明确区分轨迹与环境最终结果，并指出 Agent 可能产生符合用户目标、却不符合原有评分逻辑的解法。因此，判定失败不能自动等同于行为错误。[anthropic.com](https://www.anthropic.com/research/demystifying-evals-for-ai-agents?utm_source=chatgpt.com)

但这里要坚持一个顺序：

> 发现评分器缺陷 → 单独修订并校准评分器 → 用同一新评分器重评 baseline 和候选。

**不能让候选通过修改自己面临的标准而获得晋升。**

可以把验证边界看成“实验期间冻结、实验之间可修订”的契约。它既不应该随候选漂移，也不应该永久僵化。

**五、把四原语展开成可执行的原子化流程**

下面是我建议的工程拆分。它没有否定四原语，而是在各原语之间补齐证据交接。

| 步骤 | 最小产物 | 需要避免的错误 |
|---|---|---|
| 1. 固定当前 baseline | 文件及依赖版本、模型、环境、加载配置 | 只保存 Markdown，漏掉真正执行的脚本 |
| 2. 收集运行事件 | 输入、工具结果、产物、环境结果、成本 | 把 Agent 自述当结果真值 |
| 3. 提取问题主张 | 观察事实、原因假设、缺失证据 | 把假设直接写成长期经验 |
| 4. 判断可修性 | 策略可修／能力阻塞／证据不足等 | 任何失败都用加提示词解决 |
| 5. 构造验证任务 | 起始状态、成功条件、反例、回归样本 | 把事后答案放进任务输入 |
| 6. 产生候选变异 | diff、适用条件、预期效果 | 一次改太多，无法归因 |
| 7. 隔离执行对照 | baseline 与候选的独立运行结果 | 缓存、文件、进程和答案互相污染 |
| 8. 判定与限域 | 晋升、拒绝、证据不足、限范围试用 | 强制二选一，把未知当成功 |
| 9. 激活并验证回读 | 新运行的版本和加载证据 | 仓库更新了，运行仍用旧版本 |
| 10. 观测与退役 | 后续收益、回归、过时和删除记录 | 只新增经验，永不撤销 |

这里特别值得强调：**最小修改单位不一定是一个文件，而应该是一个可检验的行为假设。**

比如“先判断错误类别，再决定是否重试”，可能需要同时改 Skill 和脚本；只改一个文件反而不完整。原子化追求的是因果清晰，不是文件数量少。

**六、用会话构造 benchmark，最重要的是避免把“经历过”当作“学会了”**

会话天然是有价值的诊断材料，但不是天然的合格考题。

它通常混合了：

- 任务开始时的信息；
- 后来补充的背景；
- 人类纠错；
- 执行后才知道的事实；
- 最终答案；
- 特定环境中的偶然状态。

因此，应从会话里分别提取两种资产：

**诊断材料**可以包含完整过程，帮助系统找原因、提出修改。

**评测任务**则必须冻结输入截止点，只提供当时可获得的信息，并明确后续交互方式。不能把用户后来告知的答案提前提供给 Agent。

样本可以按用途分成四类：

| 用途 | 主要作用 | 是否可以给修改者看 |
|---|---|---|
| 诊断样本 | 理解失败并生成候选 | 可以 |
| 筛选样本 | 比较候选 | 控制反馈粒度；承认其会逐渐被适应 |
| 保留样本 | 最终检验迁移 | 不向修改者暴露 |
| 后续真实任务 | 检验实际使用收益 | 任务发生前未参与优化 |

划分应尽量按**任务家族、来源项目、时间、关联文件或模板**隔离。一个业务任务拆成十段会话，不能被当成十个独立样本随机散入不同集合。

另外，要给每个失败模式配一个“相邻反例”：

- 应该重试，也要测不该重试；
- 应该加载专业 Skill，也要测无需专业化的通用问题；
- 应该调用子 Agent，也要测单 Agent 更合适的简单任务；
- 应该清理环境，也要测仍有价值的缓存和长期服务。

**正例验证规则有用，反例验证规则知道什么时候停止适用。**

对你关注的 Skill 组合，这一点尤其重要：单个 Skill 都通过，不代表组合后通过。至少还要测触发重叠、指令冲突、交接丢失、重复执行和不必要加载。

**七、评估体系应该同时评任务、评边界、评裁判**

只评最终成功率，会漏掉很多真正决定闭环质量的东西。

| 层面 | 应评估什么 |
|---|---|
| 任务结果 | 正确性、完整性、真实环境效果 |
| 能力边界 | 是否知道缺哪些信息、工具、权限；是否正确求助或停止 |
| 改进收益 | 对新任务是否有效；是否只是增加尝试次数 |
| 副作用 | 回归、资源残留、数据隔离、成本增长 |
| 验证者 | 是否误放行错误、误拒绝正确、对未知强行判断 |
| 继承链路 | 发布版本与真实加载版本是否一致 |

其中，“边界评估”可以故意设计**无法完成的任务**。

例如数据接口明确不存在，此时成功标准不应该是“给出答案”，而应该是：

> 准确识别缺失接口，不虚构结果，提供具体的补充需求，并避免无效循环。

也要防止系统靠“遇事就拒绝”提高表面安全性。因此同时观察：

- 可完成任务被错误放弃的比例；
- 不可完成任务被错误宣称完成的比例；
- 求助或停止之后是否提供了有效的下一步。

对于裁判，应准备“看起来很好但实际错误”和“表达普通但实际正确”的校准样本。不同提示词、不同模型和 A/B 换位有助于发现偏差，但**裁判一致并不等于正确，独立会话也不等于独立认知能力**。

当人也无法判断时，要进一步缩小主张。例如不能证明某项工艺建议会提升良率，但可能可以验证它有没有引用正确数据、违反已知约束、遗漏关键假设。可以晋升这些局部能力，不能顺带宣称业务结果已得到验证。

**八、你说它是 test-time scaling，有道理，但需要区分计算花在哪里、收益留在哪里**

经典 test-time compute 研究主要讨论：针对当前输入，多投入推理、搜索或验证计算，能否改善当前答案。它也指出，不同难度任务适合不同计算分配方式。[arxiv.org](https://arxiv.org/abs/2408.03314?utm_source=chatgpt.com)

你的路径多了一步：把当前计算的成果写入持久状态，让之后的任务受益。

| 方式 | 额外计算用于 | 收益主要留在哪里 |
|---|---|---|
| 单次推理扩展 | 多想、多试、搜索、验证 | 当前答案 |
| 跨会话 harness 优化 | 诊断、生成修改、比较候选 | 后续任务使用的 Skill / Agent |
| 递归改进 | 改善提出修改和验证修改的机制 | 后续改进过程本身 |

因此我会把你的方案称为：

> **以推理计算驱动的跨任务持久适应，尝试把探索成本摊销到未来运行。**

它可以包含 test-time scaling，但不宜把二者完全等同。是否修改模型权重，也不是唯一分界线。

GEPA 提供了相近的已有做法：从运行轨迹反思问题、提出和测试提示词更新，并组合不同候选的互补经验。DGM 则修改 Agent 自身代码，并通过基准测试验证变化。两者都说明，额外推理可以用于改进未来运行所使用的系统。[arxiv.org](https://arxiv.org/abs/2507.19457?utm_source=chatgpt.com)

你要验证的核心不是“会话越多，系统越强”，而是：

> **随着经验增加，在相同未来运行预算下，对未参与优化的任务，系统是否持续改善？**

建议至少比较三组：

- 原始 harness，常规预算；
- 原始 harness，增加推理或重试预算；
- 优化后的 harness，常规预算。

同时单独计算优化消耗。否则，难以分清收益来自持久改进，还是来自花了更多计算。

长期收益可以用一个简单思路估算：

\[
\text{净收益}
\approx
N\times\text{每次未来运行的收益}
-\text{探索与验证成本}
-\text{维护与回归损失}
\]

这解释了为什么一个高频任务的小改进，可能比一个罕见难题的大幅提升更值得优先做。

**九、泄漏、环境堆积、成本积压和换代，需要不同的修复层**

这些问题不能全靠 Skill 内写一句“注意清理”“避免泄漏”。

| 问题 | 需要关注的机制 | 验证重点 |
|---|---|---|
| 评测答案泄漏 | 输入截止、样本隔离、访问边界 | 修改者是否接触保留答案 |
| 跨用户数据泄漏 | 租户隔离、权限、经验来源范围 | 经验是否携带其他用户私有事实 |
| 进程或内存泄漏 | 运行生命周期、资源归属、回收 | 完成、异常、取消后是否仍有残留 |
| 环境堆积 | 临时文件、缓存、依赖和服务管理 | 连续运行后的增长趋势及清理正确性 |
| 成本积压 | 无效循环、过度检索、规则膨胀 | 单次及长期成本是否超出收益 |
| 模型或工具换代 | 重新建立基线、兼容检查、消融 | 旧规则是否仍必要，是否反而妨碍新模型 |

一个关键推论是：

**修复对象的时间尺度，必须匹配验证的时间尺度。**

单次任务成功，不能证明不存在环境堆积。需要连续运行、取消、失败重启等测试。模型升级后旧 Skill 仍然“能跑”，也不能证明它仍有价值，需要比较去掉旧补丁之后是否更好。

对于你基于 OpenCode 的平台，我建议把职责分清：

- Skill / Agent 负责策略、判断、工具使用和适用范围；
- runtime 负责能够强制执行的隔离、配额和生命周期；
- 评估系统负责证明这些机制是否达成预期。

提示词可以帮助 Agent 更节制地使用资源，但不能替代资源硬限制。

---

**十、我会从一个“窄而可证”的闭环开始，再逐步扩大自治范围**

第一阶段不要追求自动修所有问题。选择一个高频、可复现、结果可观测的失败家族，例如：

> 工具返回过大，导致上下文膨胀和回答遗漏。

围绕它完成一次真正闭环：

1. 从会话中找到问题，区分返回太大、检索偏离、加载错误等原因。
2. 固定 baseline，并构造正例、相邻反例和回归任务。
3. 提出一个明确修改，如“先摘要定位，再读取必要正文”。
4. 在隔离环境中比较质量、成本和失败行为。
5. 晋升到限定场景。
6. 在新会话中确认实际加载和收益。
7. 尝试删除不必要的旧规则，验证是否进一步改善。

等这条链路稳定，再逐步允许系统：

- 自动提出候选；
- 自动执行评估；
- 对窄范围、低风险且证据充分的修改自动晋升；
- 对证据不足或边界变化的修改转交处理。

我认为最值得长期积累的，也不是越来越长的 Skill，而是三类资产：

- **有效策略**：什么条件下怎样做更好；
- **反例与边界**：什么条件下不能这样做；
- **可复用的判别方法**：以后如何更便宜、更可信地知道做得好不好。

最后给你一个可能更有启发性的判断：**RSI 的关键扩展方向，不只是扩大“系统可以修改什么”，还包括扩大“系统可以可信判断什么”。**

当候选生成已经很便宜时，真正稀缺的往往是有区分力的反馈。下一单位计算，未必应该拿去再生成一个 Skill 版本；它可能更应该拿去复现一次失败、补一个结果接口、构造一个反例，或者验证一条旧经验是否已经该删除。
