课程总主线

这门课不是单纯介绍 OpenCode 的命令和功能，而是希望回答两个问题。

第一个问题是：

当模型逐渐具备知识检索、工具调用、文件处理、代码执行和结果验证能力后，AI 应用的形态正在发生什么变化？

第二个问题是：

当 AI 从回答问题走向完成任务后，人类应该怎样定义任务、组织环境、控制风险、判断质量并推动迭代？

我们可以观察到一条大致的应用演化路径：

Chatbot
→ Chatbot + RAG
→ Tool Use
→ Workflow
→ Skill
→ Workspace Agent

这条路径表面上像是在聊天机器人上不断增加功能，但更深层的变化是：

过去依赖人类临时提供的知识、工具、流程、经验和工作状态，正在逐渐被外置到一个模型可以理解、操作和持续工作的系统环境中。

应用的交付物也随之发生变化：

过去主要交付一段回答。

现在可能交付：

* 修改后的代码；
* 处理完成的文件；
* 一份结构化报告；
* 一张表格；
* 一个可运行项目；
* 一次实际完成的业务操作。

因此，课程最终希望大家建立这样一个认识：

成熟的 Coding Agent 不是一个更会写代码的大模型，而是由模型、Workspace、Context、Tool、Workflow、Skill、Permission、State、Verification、Recovery 和 Human Feedback 共同构成的工作系统。

第1页｜封面

标题

从 Agent 技术演进到 OpenCode 工程实践

副标题

从 Chatbot、RAG、Workflow 到 Workspace Agent

讲师稿

大家好，今天这节课我们先不急着讲 OpenCode 的具体命令，而是先从 AI 应用整体演化的角度，看 Coding Agent 为什么会出现。

过去几年，我们大致经历了这样一条路径：

最开始是 Chatbot，用户提出问题，模型生成回答。

之后加入 RAG，让模型能够读取企业知识、垂直资料和最新信息。

再往后出现 Tool Use，让模型不仅可以“知道”，还可以调用接口、查询数据和执行程序。

Workflow 又把模型、知识和工具组织成稳定流程。

Skill 则开始封装某一类任务的做事方法。

最近越来越多产品走向 Workspace Agent，也就是让模型真正进入一个持续存在的工作空间，读取文件、运行程序、修改项目并交付成果。

OpenCode 就可以放在这条演化路径中理解。

它不只是代码生成工具，而是一种面向本地项目的 Workspace Agent 和 Coding Agent Runtime。

第2页｜课程目标

标题

今天要带走什么

要点

1. 理解 AI 应用从 Chatbot 到 Workspace Agent 的演化逻辑。
2. 理解 RAG、Tool、Workflow、Skill 和 Workspace 的角色。
3. 理解为什么系统瓶颈正在从模型转移到任务环境。
4. 理解人类在 Agent 工作流中的新角色。
5. 掌握 OpenCode 的基本模块和安全使用方法。
6. 学会把一句模糊需求转化为 Agent 可执行任务。
7. 学会组织 Context、Tool、Permission、Verification 和 Feedback。
8. 学会把临时对话沉淀成可复用的 Agent 工作流。

讲师稿

今天不只是学习怎样使用一个工具。

更重要的是建立一个新的应用设计视角。

过去做 AI 应用，我们经常首先讨论模型选哪个、Prompt 怎么写、上下文窗口有多长。

但随着模型能力不断提高，很多失败已经不再是因为模型不会推理，而是因为模型之外的环境没有准备好。

例如：

* 找不到正确文件；
* 环境缺少依赖；
* 工具参数不清楚；
* 权限范围不合理；
* 上下文被污染；
* 执行后没有验证；
* 用户反馈无法沉淀。

未来 AI 应用之间的差距，可能越来越不只是模型差距，而是任务环境和工程系统的差距。

第3页｜应用演化总览

标题

从回答问题到完成任务

演化路线

阶段	主要解决的问题	核心交付
Chatbot	自然语言表达和通用推理	文本回答
RAG	私有、垂直和最新知识	有依据的回答
Tool Use	模型无法直接执行动作	工具调用结果
Workflow	灵活过程不稳定	可重复流程
Skill	同类任务缺少可复用方法	任务 SOP
Workspace Agent	缺少持续状态和执行环境	真实工作成果

讲师稿

这条路线并不是产品功能的简单叠加。

每个阶段都在解决上一个阶段无法解决的问题。

Chatbot 能回答问题，但不知道企业内部知识。

RAG 能读取资料，但通常仍然交付文本。

Tool Use 能执行动作，但单个工具无法表达完整做事方法。

Workflow 能稳定执行，但面对开放问题时不够灵活。

Skill 试图把方法和灵活性结合起来。

Workspace Agent 则提供持续存在的环境，让模型围绕同一个任务不断读取、执行、观察、纠偏和交付。

所以这条路线的本质是：

AI 应用正在从信息系统走向工作系统。

⸻

第4页｜Chatbot：回答是主要交付物

标题

第一阶段：模型负责表达和推理

主要能力

* 自然语言交互；
* 知识问答；
* 文本生成；
* 摘要和改写；
* 开放式推理。

主要限制

* 不知道私有知识；
* 不知道最新信息；
* 无法直接执行动作；
* 不保留真实工作状态；
* 最终交付物通常还是文本。

讲师稿

Chatbot 最先解决的是人与模型之间的自然语言交互问题。

过去需要学习复杂菜单和命令，现在可以直接描述意图。

但这个阶段的模型主要提供建议和回答。

即使它告诉你应该怎样修改代码，实际修改仍然需要人类完成。

即使它告诉你如何整理文件，文件仍然要由人类操作。

因此，Chatbot 更像会表达、会解释和会建议的助手，还不是一个真正进入工作空间的执行系统。

⸻

第5页｜RAG：让模型读取外部知识

标题

第二阶段：从参数知识走向知识感知

RAG 解决的问题

* 企业私有知识；
* 行业知识；
* 最新文档；
* 大规模资料；
* 信息来源追踪。

基本流程

用户问题
→ 检索相关资料
→ 将资料加入上下文
→ 模型基于资料回答

讲师稿

RAG 解决的是模型不知道的问题。

企业内部有大量知识不在模型参数中，例如产品文档、业务规则和历史报告。

RAG 让模型能够按需读取这些资料。

但 RAG 主要增强的是知识能力，而不一定直接增强任务执行能力。

它可以告诉模型数据库接口应该怎样使用，但并不代表查询已经完成。

因此，在 Agent 系统中，RAG 仍然重要，但它可能逐渐从应用主角变成一个知识感知组件。

⸻

第6页｜Tool Use：从“知道”到“能做”

标题

第三阶段：模型开始调用真实能力

常见 Tool

* 文件读取；
* 文件修改；
* 数据库查询；
* API 调用；
* 搜索；
* 计算；
* 代码执行；
* 消息发送。

一句话定义

Tool 表达模型可以做什么。

讲师稿

Tool Use 是 AI 应用从建议走向执行的重要分水岭。

没有 Tool 时，模型只能告诉你应该怎样做。

有了 Tool 后，模型可以调用一个明确接口，把参数交给系统执行，再读取真实结果。

但 Tool 只是最小动作。

它能够表达“查询数据库”，却不能完整说明面对某类任务时应该先查什么、怎样判断、什么时候停止以及失败后怎样处理。

所以我们还需要 Workflow 和 Skill。

⸻

第7页｜Workflow：确定性业务骨架

标题

企业不仅需要灵活，还需要稳定

Workflow 解决的问题

* 固定执行顺序；
* 明确条件分支；
* 状态追踪；
* 失败重试；
* 审计记录；
* 系统集成；
* 可重复执行。

适合 Workflow 的任务

* 财务审批；
* 数据同步；
* 固定报表；
* 批处理；
* 标准化业务流程。

一句话定义

Workflow 表达动作按照什么确定顺序执行。

讲师稿

企业系统不能只有模型的灵活性，还需要确定性。

例如财务审批和数据同步，不能每次由模型临时规划执行顺序。

Workflow 在模型外部提供稳定的业务骨架。

Agent 出现以后，Workflow 并不会消失。

更可能的方向是：

确定部分继续由 Workflow 控制，不确定部分交给 Agent 动态决策。

⸻

第8页｜Skill：可复用的做事方法

标题

从动作和流程，走向任务方法

Skill 可以包含

* 适用条件；
* 输入要求；
* 参考资料；
* 处理步骤；
* 工具；
* 脚本；
* 输出格式；
* 异常处理；
* 验证方法；
* 人工 Review 点。

三者区别

Tool 是动作。

Workflow 是动作的固定排列。

Skill 是面对某一类任务时的可复用做事方法。

讲师稿

Skill 位于固定 Workflow 和自由 Agent 之间。

它不会规定所有任务必须执行完全相同的步骤，但会告诉模型面对某类问题时应该采用什么方法。

一个 Skill 可以引用工具，也可以包含参考资料、执行原则、异常处理和验收方式。

因此，Skill 更接近组织的 SOP。

它不是单纯告诉模型什么是正确的，而是告诉模型应该怎样做、使用哪些能力、输出什么以及怎样检查。

⸻

第9页｜Workspace Agent：环境成为系统核心

标题

模型获得持续存在的工作空间

Workspace Agent 可以

* 读取文件；
* 修改文件；
* 运行脚本；
* 查看输出；
* 保留中间状态；
* 根据失败继续调整；
* 生成正式成果；
* 在多轮任务中持续推进。

交付变化

过去：

* 回答；
* 建议；
* 代码片段。

现在：

* 文件；
* 代码；
* 项目；
* 报告；
* 表格；
* 数据结果；
* 实际业务状态。

讲师稿

到了 Workspace Agent 阶段，模型获得的不再只是知识和单个工具，而是一个持续存在的工作环境。

它可以在项目目录中读取、修改和运行。

任务失败后，它还能根据结果继续调整。

这个阶段的核心交付物已经不再是对话，而是真实成果。

这也可能带来一个反直觉趋势：

AI 应用能力越强，用户需要进行的对话轮数可能反而越少。

用户真正想要的通常不是多聊几轮，而是把事情做完。

⸻

第10页｜推动力一：从回答问题到完成任务

标题

评价标准正在发生变化

Chat 产品关注

* 回答是否流畅；
* 内容是否正确；
* 对话是否自然。

Agent 产品关注

* 任务是否完成；
* 结果是否可用；
* 动作是否安全；
* 过程是否可观察；
* 失败是否可恢复；
* 结果是否经过验证。

讲师稿

Agent 应用最重要的变化，是从回答问题走向完成任务。

评价一个 Agent，不能只看回答得像不像专家。

更应该看：

它有没有真正完成工作？
产物能不能使用？
是否越权？
是否经过测试？
失败后能不能恢复？

从这里开始，AI 应用的指标也要从语言质量转向任务完成质量。

⸻

第11页｜推动力二：瓶颈从模型转向环境

标题

很多失败并不是因为模型不会推理

常见原因

* 文件路径错误；
* 工作目录不清楚；
* 环境缺少依赖；
* 工具接口模糊；
* 权限不合理；
* 上下文污染；
* 状态丢失；
* 无法验证；
* 无法回滚。

核心判断

未来应用的差距，越来越可能来自 Workspace 质量，而不只是模型质量。

讲师稿

早期大家更关注模型本身。

但随着模型能力变强，很多失败开始发生在模型之外。

一个模型可能已经知道应该怎样解决问题，但它找不到文件。

它知道应该运行测试，但环境没有安装依赖。

它完成了修改，但系统没有明确验收标准。

因此，未来真正重要的问题会变成：

模型能看到什么？
模型能操作什么？
模型怎样知道自己做对了？
失败后怎样恢复？
经验怎样沉淀？

⸻

第12页｜推动力三：灵活性与确定性结合

标题

Agent 和 Workflow 更可能形成混合系统

模型擅长

* 模糊需求；
* 开放问题；
* 非结构化资料；
* 动态判断；
* 未知问题探索。

Workflow 擅长

* 固定步骤；
* 状态管理；
* 审计；
* 重复执行；
* 失败重试；
* 严格顺序。

混合结构

Workflow 确定性骨架

* Agent 动态处理
* Permission
* Evaluator
* Human Gate

讲师稿

Agent 不会简单替代 Workflow。

完全确定的任务没有必要让模型自由规划。

完全开放的任务也无法提前编码所有分支。

因此，合理的系统通常是混合结构：

确定的部分交给 Workflow 和代码。

不确定的部分交给模型。

权限和验证器负责控制风险。

人类在关键质量门进行确认。

⸻

第13页｜推动力四：人类控制关系变化

标题

从控制每一步，到治理目标和边界

传统软件

人类操作每个步骤。

Workflow

开发者预先定义步骤。

Workspace Agent

人类主要负责：

* 定义目标；
* 交代背景；
* 提供输入；
* 设置边界；
* 说明验收；
* 观察过程；
* 暂停和接管；
* 体验和反馈。

核心观点

更少确认，不等于更少控制。

讲师稿

在 Agent 系统里，人类可能不再控制每一个按钮和操作步骤。

但这不代表失去控制。

控制方式正在从操作控制，转变为治理控制。

成熟系统不一定每一步都要求人工确认，而是通过权限、可观察性、中断、回滚和验收标准提供更强控制。

人类更像导演。

AI 更像执行团队。

⸻

第14页｜推动力五：应用开始持续演化

标题

从版本发布驱动，到使用反馈驱动

新的能力来源

* 用户反馈；
* 成功轨迹；
* 失败轨迹；
* 新增资料；
* 新工具；
* 新脚本；
* 新测试；
* 更新后的规则。

关键风险

未经控制地自动写入长期 Skill，可能造成：

* 临时要求永久化；
* 错误经验扩散；
* 恶意输入污染；
* 规则冲突；
* 能力退化。

受控演化

运行轨迹
→ 候选经验
→ 验证
→ 人类确认或质量门
→ 版本化发布
→ 支持回滚

讲师稿

Workspace Agent 的另一个变化，是应用能力可能从真实使用中持续增长。

但记录经验不等于应该自动吸收经验。

真正需要的是受控演化。

候选经验需要被提取、验证、审查、版本化，并且可以回滚。

因此，未来重要的不是简单的自动学习，而是可治理的能力迭代。

⸻

第15页｜需要重新理解的旧观点

标题

部分共识正在发生变化

RAG 是核心壁垒？

RAG 仍然重要，但向量数据库本身越来越接近基础能力。

真正的价值在于：

* 知识是否可信；
* 权限是否准确；
* 是否及时更新；
* 何时检索；
* 怎样验证；
* 怎样参与后续行动。

Prompt 是核心资产？

Prompt 仍然重要，但单独 Prompt 已不足以构成完整系统。

Workspace、Tool Contract、Skill、权限、测试和恢复能力越来越重要。

长上下文可以替代记忆和 Skill？

长上下文解决能不能装进去，没有解决应该装什么、哪些可信、哪些过期。

Agent 越自主越先进？

成熟 Agent 可能不是做得更多，而是更克制、更安全、更可验证。

Multi-Agent 就是数字组织？

Multi-Agent 首先可以被理解为上下文、权限和执行隔离机制，其次才是角色模拟。

讲师稿

我们需要避免把新技术包装成过于简单的结论。

RAG、Prompt、长上下文、Agent 自主性和 Multi-Agent 都有价值。

但它们都不能脱离任务环境和工程系统单独发挥作用。

真正成熟的产品，不一定展示最多的智能行为。

它可能只是更稳定、更克制地完成任务。

第16页｜第一部分总结

标题

AI 应用正在从信息系统走向工作系统

核心结论

1. Chatbot 解决表达问题。
2. RAG 解决知识问题。
3. Tool 解决动作问题。
4. Workflow 解决确定性问题。
5. Skill 解决方法复用问题。
6. Workspace 解决状态和成果承载问题。
7. Agent 负责处理难以提前编码的不确定性。
8. 系统竞争力正在从模型扩展到任务环境。
9. 人类正在从操作执行者转向目标和质量治理者。
10. 应用能力增长需要受控演化。

讲师稿

第一部分我们建立了理解 OpenCode 的行业背景。

OpenCode 不是突然出现的代码工具。

它是 AI 应用从回答问题走向完成任务、从聊天界面走向 Workspace 的一种工程化表现。

接下来第二部分，我们会具体看：

如何使用 OpenCode；
怎样设计可靠的 Coding Agent 工作流；
怎样组织 Context、Tool、Permission、Verification 和 Feedback；
以及怎样把临时对话沉淀为长期工程能力。

第17页｜什么是 OpenCode

标题

本地项目中的 Coding Agent Runtime

核心定义

OpenCode 是一个运行在终端、本地项目和 Git 仓库中的 AI Coding Agent。

它可以：

* 阅读代码；
* 搜索文件；
* 编辑文件；
* 执行命令；
* 运行测试；
* 查看结果；
* 在会话中持续推进任务。

正确协作方式

人类提供：

* 目标；
* 背景；
* 输入；
* 工具；
* 边界；
* 验收标准。

AI 负责：

* 探索；
* 搜索；
* 执行；
* 修改；
* 验证；
* 整理。

人类再进行：

* 审查；
* 体验；
* 反馈；
* 接受或迭代。

讲师稿

OpenCode 可以理解成在本地项目中工作的智能执行系统。

它和普通聊天工具的最大差异，是能够实际进入项目并执行动作。

正因为它能够执行，我们就不能只关心回答是否正确。

还要关心：

它改了什么？
调用了什么工具？
是否越权？
是否通过测试？
失败后能否恢复？

所以 OpenCode 的正确使用方式，是把它放入一个受控、可观察和可验证的工作流。

第18页｜ReAct 与 Agent 循环

标题

Agent 不是一次回答，而是持续决策

核心循环

观察任务
→ 提出假设
→ 调用工具
→ 获得结果
→ 修正计划
→ 再次行动

工程示例

发现程序异常
→ 搜索相关入口
→ 阅读调用链
→ 运行失败测试
→ 定位根因
→ 最小修改
→ 再次验证

讲师稿

ReAct 提供了 Agent 最基本的工作循环。

但不要过度关注模型是否展示了复杂推理。

真正重要的是：

动作是否合理；
观察是否可靠；
是否根据结果纠偏；
最终成果是否通过验证。

Agent 的价值在执行闭环，而不只是思考过程。

第19页｜Tool Calling 与 Tool Contract

标题

工具定义决定 Agent 怎样行动

示例

{
  "tool": "grep",
  "input": {
    "pattern": "refreshToken",
    "path": "src"
  }
}

工具设计应回答

* 输入参数是否明确？
* 输出是否结构化？
* 错误是否可理解？
* 权限边界是否清楚？
* 是否有超时？
* 是否可以单独测试？
* 是否能够审计？

讲师稿

Tool Calling 将自然语言意图转成结构化动作。

工具接口越明确，Agent 行为通常越稳定。

因此，构建 Agent 应用时，不能只优化 Prompt。

还要优化 Tool Contract。

很多所谓的模型问题，实际上是工具输入模糊、返回混乱或错误信息不可理解。

第21页｜Agent 六个抽象槽位

标题

系统化理解 Agent

槽位	工程含义	OpenCode 对应
Goal	目标和验收	Prompt、Command、AGENTS.md
State	当前会话和中间状态	Session、Message、Todo、Snapshot
Actions	可执行动作	Tool Registry
Observations	文件、命令、测试结果	Tool Output

Runtime	调度、安全、恢复	Processor、Permission、Server

讲师稿

模型不是 Agent 的全部。

目标不明确，强模型也可能做错方向。

动作空间过大，模型可能越权。

观察结果不可靠，模型会在错误信息上继续执行。

运行时没有恢复机制，一次错误就可能破坏整个项目。

因此，需要从完整系统角度理解 Agent。

第23页｜Plan 与 Build

标题

先想清楚，再允许执行

Plan 负责

* 澄清需求；
* 只读探索；
* 查找证据；
* 设计方案；
* 识别风险；
* 制定验证计划。

Build 负责

* 修改文件；
* 生成代码；
* 调用脚本；
* 运行命令；
* 补充测试；
* 执行验证。

推荐主流程

Brief
→ Plan
→ 人类确认
→ Build
→ Verify
→ Review

讲师稿

Plan 和 Build 的分离，是 OpenCode 使用中最重要的操作习惯。

Plan 的目标不是写一份形式化计划，而是降低错误方向的成本。

它应该找到相关文件、确认调用链、说明风险和提出最小方案。

人类确认方向后，再进入 Build。

这种设计符合人机优势：

人类更熟悉业务目标和风险。

AI 更擅长大量阅读、搜索、修改和验证。

第24页｜核心动机：相信 AI，优化人类信息

标题

问题梳理由人主导，问题解决由 AI 主导

一个完整任务需要交代

1. 为什么做；
2. 最终要达到什么效果；
3. 有哪些输入文件；
4. 文件和字段是什么含义；
5. 可以使用哪些工具；
6. 有哪些数据源；
7. 哪些动作不能做；
8. 怎样判断完成；
9. 人类怎样体验和反馈；
10. 经验怎样进入下一轮。

人机分工

问题梳理阶段：人类主导。

任务执行阶段：AI 主导。

体验评价阶段：人类主导。

迭代改进阶段：人机共同完成。

讲师稿

我们不是因为不相信 AI，才强调人类参与。

恰恰相反，是因为相信 AI 已经具备较强执行能力，所以人类更应该把任务环境布置好。

AI 可以读很多文件、执行很多步骤、快速生成和验证。

但它不知道人类心里的业务背景。

因此，人类的价值从亲自执行，转向定义问题、提供背景、设计边界和判断质量。

可以把人类理解成导演，把 AI 理解成执行团队。

导演不需要亲自完成每个镜头，但必须知道什么作品才算合格。

第25页｜好的 Prompt 是结构完整

标题

不要让 AI 猜任务

模糊请求

“帮我重构这个模块。”

缺失信息

* 为什么重构？
* 当前问题是什么？
* 涉及哪些文件？
* 哪些行为不能变化？
* 有哪些可用工具？
* 哪些动作禁止？
* 最终怎样验收？

推荐任务结构

* 动机；
* 目标；
* 背景；
* 输入；
* 工具；
* 边界；
* 验收；
* 反馈。

讲师稿

高质量 Prompt 的本质，不是更长，也不是更花哨。

它是在布置一个可执行任务环境。

人类不需要规定 AI 每一步具体怎么写。

但需要明确告诉 AI：

为什么做；
做什么；
基于什么；
可以做什么；
不能做什么；
怎样判断完成。

第26页｜把需求转成任务卡

标题

从一句话需求到可执行任务

字段	核心问题
动机	为什么做？当前问题是什么？
目标	最终交付什么成果？
输入	文件、目录、数据、接口在哪里？
背景	文件含义和业务规则是什么？
工具	可以调用哪些脚本、API 和服务？
边界	哪些不能读、不能改、不能执行？
流程	先分析还是直接执行？
验收	什么条件算完成？
反馈	用户怎样评价结果？

讲师稿

用户的一句话通常只是任务入口，不是完整任务。

例如“分析这些数据”，里面缺少字段含义、业务口径、异常值规则和输出目标。

任务卡的作用，是把人类掌握的隐性信息显性化。

这一步应主要由人类主导，AI 可以帮助补全和发现缺失项。

第27页｜Context 分层

标题

不要把所有内容都塞进聊天框

层	内容	推荐位置
需求层	当前任务	Chat
背景层	业务、文件和数据说明	docs、references
规则层	项目规范和禁止操作	AGENTS.md
流程层	某类任务方法	Skill
入口层	高频任务入口	Command
动作层	工具和脚本	tools、scripts
证据层	Schema、样例和历史实现	references、tests
观察层	Diff、测试和报告	output
反馈层	Review 和体验	logs、review
安全层	权限、白名单和沙箱	policy、opencode.json

讲师稿

Context 的重点不是越多越好，而是分层、按需加载和生命周期管理。

当前需求可能只使用一次。

项目规则可能长期有效。

Skill 描述某一类任务。

测试和 Manifest 记录执行结果。

反馈则可能成为未来改进输入。

如果所有内容都堆在 Prompt 中，系统会越来越难维护。

第28页｜AGENTS.md：项目作业指导书

标题

把长期项目知识外置

建议包含

* 项目结构；
* 安装和运行命令；
* 测试命令；
* 编码规范；
* 路径规则；
* 安全边界；
* 禁止操作；
* 验收标准；
* 团队约定。

讲师稿

AGENTS.md 不只是提示词文件，而是 Agent 的项目作业指导书。

如果每次会话都要重复解释同一条规则，说明这条信息应该沉淀。

它应该描述长期有效的项目知识，而不是把一次性任务全部放进去。

第29页｜Tool、Script 与 API 设计

标题

让 Agent 做事，但不要让它临时发明所有执行方式

高频动作应封装为

* Tool；
* Script；
* API；
* Data Service；
* Validator；
* Report Generator。

好的执行能力应具备

* 输入 Schema；
* 结构化输出；
* 清晰错误；
* 权限边界；
* 超时；
* 审计；
* 可测试性；
* 幂等或回滚机制。

核心分工

模型负责理解和动态决策。
代码负责确定性执行。
API 负责系统边界。
验证器负责判断结果。

讲师稿

不要让 Agent 每次临时拼一段复杂 Shell 命令。

稳定、高频或危险的动作，应该封装成工具、脚本或 API。

例如数据库查询，应该通过字段白名单和明确参数的数据服务，而不是允许模型自由执行任意 SQL。

模型适合处理不确定性。

确定性部分应该尽可能交给可靠代码。

⸻

第30页｜Permission：把安全写进运行时

标题

限制动作，不是限制智能

权限等级

allow：低风险，自动执行。
ask：中风险，需要确认。
deny：高风险，禁止执行。

推荐原则

* 常规读取可以适度开放；
* 修改根据风险设置 ask；
* 敏感文件拒绝读取；
* 删除、杀进程默认拒绝；
* destructive Git 操作拒绝；
* 生产操作需要额外审批。

讲师稿

只在 Prompt 中写“不要读取敏感文件”是不够的。

Prompt 是软约束。

权限系统、目录隔离、工具白名单和数据服务才是运行时边界。

Agent 越有执行能力，越需要明确权限。

成熟 Agent 不是任何事情都能做，而是在允许范围内稳定完成任务。

⸻

第31页｜Git、快照与恢复

标题

可恢复性是 Agent 成熟度的重要指标

修改前

git status
git add -A
git commit -m "checkpoint: before agent task"

或者：

git stash push -u -m "checkpoint before agent task"

修改后

* 查看 Diff；
* 确认范围；
* 运行测试；
* 人工 Review；
* 正式提交。

核心原则

Git 是主保险。
OpenCode Undo 是辅助工具。

讲师稿

成熟系统不是永远不犯错，而是错误发生后可以快速发现和恢复。

Agent 修改代码前，要让 Git 记住当前状态。

复杂任务尤其需要明确 checkpoint。

不要把会话级 Undo 当作唯一回滚方案。

⸻

第32页｜常见工程风险

标题

多数故障来自环境设计

常见问题

1. pkill -f 误杀进程。
2. 后台服务导致 Tool 挂起。
3. 工具和资料过多导致上下文膨胀。
4. write 覆盖整个文件。
5. 修改范围不断扩大。
6. 测试失败后修改无关代码。
7. 路径不明确导致脚本失效。
8. 敏感变量被读取。
9. 未经验证就声明完成。

讲师稿

这些问题通常不是模型推理不足，而是工作环境没有被正确治理。

Agent 工程化的重要任务，就是提前消除这些可预测风险。

例如：

长跑服务放到独立终端；
Agent 只执行短命令；
优先使用 patch；
路径写清楚；
高风险动作直接 deny；
完成声明必须附带验证证据。

第33页｜五阶段通用工作流

标题

Brief → Plan → Build → Verify → Review

Brief

人类提供目标、背景、输入、工具、边界和验收。

Plan

AI 只读分析、提取证据、形成方案和风险。

Build

根据已确认方案执行最小实现。

Verify

运行自动检查，输出 Diff、测试和 Manifest。

Review

人类体验结果，决定接受、反馈、回滚或继续迭代。

讲师稿

这五个阶段不仅适用于代码修改。

也适用于：

* 数据分析；
* 文件处理；
* 报告生成；
* 系统迁移；
* 问题排查；
* 工具构建。

它们共同遵循一个原则：

先把问题说明清楚，再执行。

执行后必须有观察和证据。

最终由人类判断真实价值。

⸻

第34页｜文件和数据处理

标题

结构化和非结构化输入需要不同策略

结构化数据

例如：

CSV、Excel、JSON、数据库。

人类重点说明：

* 字段含义；
* 主键；
* 时间字段；
* 缺失值；
* 异常值；
* 业务口径；
* 输出要求。

非结构化数据

例如：

PDF、Word、图片、长日志、报告。

推荐流程：

原始文件
→ Evidence 抽取
→ 结构化结果
→ 分析或生成
→ 自动验证
→ 人工 Review

讲师稿

对于非结构化资料，不建议让 AI 读完后直接生成最终结论。

应该先抽取证据，再基于证据执行。

例如从 PDF 提取关键字段、方法、参数和来源位置，然后再生成报告或代码。

结构化数据的关键则是业务口径。

计算正确不等于业务语义正确。

⸻

第35页｜验证体系

标题

没有验证，就没有可靠的 Agent 工作流

五层验证

1. 结构验证；
2. 语法验证；
3. 样例验证；
4. 行为验证；
5. 人工验证。

Agent 交接应包含

* 做了什么；
* 改了哪些文件；
* 使用了哪些输入；
* 运行了哪些检查；
* 哪些检查通过；
* 哪些没有覆盖；
* 哪些需要人工确认。

讲师稿

Agent 说“已经完成”不能作为完成标准。

任何任务都应该设计验证。

生成文件可以检查结构。

代码可以运行测试和类型检查。

数据分析可以检查字段、行数和样例。

但自动验证只能说明满足已写出的规则。

是否真正满足业务目标，仍然需要人类判断。

⸻

第36页｜Chat、Artifact、Trace 与 State

标题

不要让对话承担所有正式状态

Chat

用于：

* 协商；
* 澄清；
* 解释；
* 控制；
* 临时反馈。

Artifact

正式成果：

* 文件；
* 代码；
* 表格；
* 报告；
* 配置；
* 数据结果。

Trace

记录 Agent 实际做了什么。

Workspace State

记录项目和任务当前真实状态。

Skill 与 Memory

保存经过验证、可复用的经验。

讲师稿

聊天记录不是一个好的正式状态载体。

对话里有很多试探、重复、错误和临时要求。

因此需要明确区分：

Chat 是控制面。

Artifact 是事实面。

Trace 是过程记录。

Workspace State 是真实状态。

Skill 和 Memory 是经过验证的长期经验。

⸻

第37页｜反馈沉淀

标题

让系统越用越好，而不是每次从零开始

反馈可能涉及

* 背景理解错误；
* 输出格式不好用；
* 工具使用不合理；
* 流程步骤有问题；
* 验收覆盖不足；
* 权限过宽或过窄；
* 出现新的成功方法；
* 重复发生相同失败。

应沉淀到

类型	位置
长期规则	AGENTS.md
任务流程	Skill
高频入口	Command
动作逻辑	Tool / Script
验收规则	Tests / Validator
背景知识	References
失败案例	Logs
安全边界	Permission / Policy

讲师稿

如果用户每次都需要纠正同一个问题，说明反馈还没有变成系统能力。

但不能把所有反馈直接写进长期 Skill。

需要判断：

哪些只适用于本次任务？
哪些是长期规则？
哪些应该更新工具？
哪些应该增加测试？
哪些需要先验证？

反馈必须被分类并受控沉淀。

⸻

第38页｜从对话到 Skill

标题

什么时候应该沉淀为可复用能力

保留为普通对话

* 只做一次；
* 背景高度临时；
* 没有稳定流程；
* 主要需要解释；
* 不需要固定工具。

适合沉淀为 Skill

* 同类任务频繁发生；
* 每次需要类似资料；
* 有稳定工具集合；
* 有明确验收方式；
* 经常重复相同错误；
* 需要多人共享；
* 需要异常处理方法。

Skill 应包含

* 适用条件；
* 输入要求；
* References；
* 执行步骤；
* 工具使用；
* 停止条件；
* 输出规范；
* 验证方法；
* 人工 Review 清单。

讲师稿

Skill 的价值，是把组织做事方法变成模型可执行资产。

它不是把所有聊天记录存下来，也不是把 Prompt 写得更长。

它应该保留稳定、经过验证和可以复用的部分。

⸻

第39页｜受控演化

标题

自动成长必须经过质量门

推荐流程

运行 Trace
→ 提取候选经验
→ 分类
→ 验证
→ 人类确认或自动质量门
→ 更新 Preview
→ 测试
→ 版本化发布
→ 支持回滚

不应直接自动吸收

* 一次性用户偏好；
* 未验证结论；
* 临时环境信息；
* 恶意输入；
* 与已有规则冲突的要求；
* 无法追溯来源的经验。

讲师稿

“越用越好”不等于“所有会话都自动写入长期记忆”。

真正成熟的 Skill 演化需要候选、审查、测试、发布和回滚。

这和软件开发本身非常类似。

长期能力也需要版本治理。

⸻

第40页｜通用 Agent 项目结构

标题

把临时聊天变成工程资产

AGENTS.md
opencode.json
.opencode/
  commands/
  skills/
  tools/
scripts/
references/
input/
output/
tests/
logs/

目录职责

AGENTS.md：长期项目规则。
opencode.json：权限策略。
commands：任务入口。
skills：可复用方法。
tools：Agent 可调用动作。
scripts：确定性执行。
references：背景、规范和样例。
input：任务输入。
output：正式成果。
tests：验收机制。
logs：Trace 和反馈。

讲师稿

一次对话只有进入这些正式结构，才可能成为长期工程资产。

规则、方法、动作、输入、输出、测试和反馈需要分开保存。

这样不同会话和不同人员才能共享同一套能力。

⸻

第41页｜Human UI 与 Agent Interface

标题

未来软件需要同时服务人和 Agent

Human UI

用于：

* 输入意图；
* 查看状态；
* 比较结果；
* 纠错；
* 审批；
* 接管；
* 查看成果。

Agent Interface

用于：

* 发现能力；
* 读取状态；
* 调用工具；
* 理解错误；
* 查询权限；
* 执行撤销；
* 验证结果。

讲师稿

未来不一定没有 UI。

软件可能同时提供 Human UI 和 Agent Interface。

人类界面负责观察、比较、纠错和审批。

Agent Interface 负责机器能够安全理解和执行。

传统软件会反过来因为 Agent 的出现而改变设计方式。

⸻

第42页｜薄界面 + Agent Runtime

标题

未来应用可能保留三类前端能力

前端负责

1. 输入意图；
2. 展示状态和成果；
3. 确认、纠错和接管。

Runtime 负责

* 理解任务；
* 加载 Workspace；
* 选择 Skill；
* 调用工具；
* 管理权限；
* 执行沙箱；
* 保存状态；
* 调用验证器；
* 生成成果。

讲师稿

未来很多应用可能走向薄界面加 Agent Runtime。

但这不代表所有软件都会变成聊天框。

更合理的形式可能是：

聊天用于表达开放意图。

表单用于精确输入。

Viewer 用于查看成果。

结构化控件用于审批和纠错。

复杂执行则发生在后台 Runtime 中。

⸻

第43页｜几个非共识判断

标题

值得继续讨论的方向

1. 未来壁垒可能是任务环境，而不只是模型。
2. 最好的 Agent 产品可能表面上不那么自主。
3. Coworker 更像传播比喻，而不是准确责任模型。
4. 未来重要能力可能是任务环境设计，而不是 Prompt 技巧。
5. Multi-Agent 首先是隔离机制，其次才是组织模拟。
6. Agent 可能制造更多临时软件，而不是减少软件数量。
7. Workspace 可能成为连接人、模型和系统的新型中间件。
8. Chat 可能逐渐成为控制面，Artifact 成为事实面。

讲师稿

这些判断未必都是最终答案，但有助于我们避免为了展示智能而过度设计。

成熟 Agent 可能不会展示复杂的数字组织。

它可能只是用一个主 Agent、少量隔离子任务和可靠工具完成工作。

真正高级的产品，也可能不是做得最多，而是在该停的时候停，在该验证的时候验证。

⸻

第44页｜第二部分总结

标题

Agent 工程实践的核心原则

六个原则

1. 人类负责定义问题，AI 负责执行任务。
2. 先设计动作空间，再谈自治。
3. 先取证和计划，再修改和生成。
4. Context 应分层，而不是无限堆进 Prompt。
5. 结果必须可验证、失败必须可恢复。
6. 反馈应受控沉淀，而不是直接自动学习。

讲师稿

第二部分的重点可以浓缩成一句话：

Agent 工程实践的关键，不是让 AI 自由发挥，而是为 AI 布置一个目标明确、背景充分、工具清晰、权限合理、结果可验证和失败可恢复的任务环境。

⸻

第45页｜最终 Takeaway

标题

人类定方向，AI 做执行，系统保稳定

最终口诀

人类讲清楚，AI 做扎实。

人类定方向，AI 做执行。

人类给反馈，系统再迭代。

工程口诀

先背景，后任务。
先 Plan，后 Build。
先最小修改，后扩大范围。
先验证，后声明完成。
先 checkpoint，后放手。
先体验，后沉淀。
先质量门，后自动成长。

讲师稿

未来重要的个人能力，可能不只是写 Prompt。

而是能够把一个任务布置成可执行环境。

为什么做？

成功标准是什么？

有哪些输入和背景？

可以使用什么工具？

哪些动作禁止？

结果怎样验收？

失败后怎样恢复？

反馈怎样沉淀？

这会成为研发、数据分析和 AI 应用构建中的重要能力。

第46页｜行动建议

标题

从一个小任务开始

第一步

选择一个：

* 低风险；
* 高频；
* 边界明确；
* 容易验证；
* 会重复发生的任务。

第二步

补齐：

* 动机；
* 输入；
* 背景；
* 工具；
* 边界；
* 验收；
* 反馈。

第三步

按照五阶段运行：

Brief
→ Plan
→ Build
→ Verify
→ Review

第四步

将重复经验逐渐沉淀为：

AGENTS.md
→ Skill
→ Tool
→ Test
→ Review Checklist

讲师稿

不建议一开始就构建万能 Agent。

先选择一个小而明确的任务。

让它能够稳定完成、验证和回滚。

再观察真正的瓶颈在哪里。

如果同类任务可以稳定复用，再逐渐扩大范围。

第47页｜结尾页

标题

谢谢 / Q&A

一个成熟 Agent 工作系统

**模型

* Workspace
* Context
* Tool
* Workflow
* Skill
* Permission
* State
* Verification
* Recovery
* Human Feedback**

建议讨论的问题

1. 当前应用交付的是回答，还是工作成果？
2. 当前瓶颈是在模型，还是文件、工具、权限和验证？
3. 哪些部分应该保持确定性，哪些适合交给 Agent？
4. Skill 应保持静态，还是应该受控迭代？
5. Chat、Workflow、Skill 和 Workspace 应分别承担什么角色？
6. 人类在哪些环节必须保留判断和接管能力？

最后一句话

Agent 的价值不是让人类消失，而是把人类从重复执行中解放出来，让人类更专注于定义问题、判断质量、治理风险和推动迭代。

讲师稿

今天我们从 Chatbot 的演化讲到了 Workspace Agent，又从行业趋势落到了 OpenCode 的具体工程方法。

未来的软件不一定都会变成聊天框。

更可能的变化是：软件从由人逐步操作的功能集合，转变成由人、模型、Workflow、工具和验证器共同组成的混合工作系统。

人在其中负责提出目标、提供背景、定义边界和验收结果。

模型负责理解任务、组织执行和处理不确定性。

代码、Workflow、权限和测试系统提供确定性约束。

最终通过文件、代码、报告和真实业务状态，判断任务是否真正完成。
