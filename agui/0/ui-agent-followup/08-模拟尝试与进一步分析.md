# 模拟尝试：交互行为、反例与收益敏感性

日期：2026-10-03。模拟基于上一轮的头脑风暴，覆盖口径澄清、产物版本冲突、停止任务和投入回收。所有业务内容和收益参数均为构造示例。

## 1. 实际做了什么，以及没有证明什么

本轮制作了两个可操作模拟：任务工作区和工时回收计算。任务工作区有三种独立场景，用户可以改变字段、制造版本冲突、在不同提交阶段停止。

实际交互脚本通过简化 DOM 适配器执行，20 项检查通过；另有标准库 Python 模拟器，19 项状态检查通过。前者验证展示状态和动作逻辑，后者提供可复跑的概念模型。两组有重叠，不能相加成为 39 个独立能力样本。

未调用真实 LLM、业务服务、数据库或沙盒进程；重算内容与外部回执使用固定事件。因此不证明模型正确理解或合并，也不证明真实服务能被取消。本地缺少浏览器执行文件，未完成浏览器布局、屏幕阅读器、跨端和视觉 QA；交互可操作性需在实际客户端再检查。

数值部分为确定性公式计算与人为编排路径，不是真实任务性能或人机实验结果。

## 2. 尝试 A：开放输入之后，只补关键字段

### 构造任务

用户：“比较研发与工艺部门本月的使用情况。”

已知：部门、时间和希望有比较结果。缺失：使用情况指会话数、活跃用户数还是任务完成率？

界面保留已知信息，只让用户选择统计口径，允许调整部门。未选口径不启动；零个部门不启动；补齐后建立任务。真实业务还应检查数据是否有对应口径，例如完成率是否存在可靠分母和标签。

### 发现

字段稳定时，一次结构化选择可以减少序列澄清。但这并不必然优于一条集中问句：Agent 完全可以一次问完三个缺失项，用户一次回答。结构化 UI 的额外价值在于选项可见、字段校验与局部修改，不应把低效的串行问答当成唯一聊天基线。

如果字段本身未知，强行表单会固化错误假设。开放任务应允许继续描述或暂时按探索模式执行，不能被迫填入伪精确字段。

### 路径模拟

脚本统计的是构造路径中的用户动作和模型步骤，包含最终查看结果，不推断实耗时间。

| 同类任务 | 模式 | 用户动作 | 模型步骤 | 应如何解释 |
|---|---|---:|---:|---|
| 清晰的重复任务 | 聊天短指令 | 2 | 1 | 打字 + 查看结果 |
| 清晰的重复任务 | 情境 shortcut | 2 | 1 | 点击 + 查看结果，动作数相同但输入方式不同 |
| 清晰的重复任务 | 强制完整表单 | 8 | 1 | 不必要字段增加负担 |
| 稳定字段，缺三项 | 串行聊天 | 5 | 4 | 构造的低效聊天路径 |
| 稳定字段，缺三项 | 可选结构化澄清 | 5 | 2 | 用户动作不减，但减少模型往返 |
| 稳定字段，缺三项 | 一次集中回答 | 3 | 2 | 聊天也可达到相同模型步骤数 |
| 未知任务结构 | 集中聊天探索 | 3 | 2 | 保留开放表达 |
| 未知任务结构 | 猜测表单后纠错 | 9 | 2 | 模型步骤不增，人的负担仍变高 |

它们不是模型采样结果。脚本只是把设计中的路径假设显式化，方便替换为你实际观察的路径。动作数也不等于努力：一次写长描述可能比三次选择更费力，一次审查可能比所有输入更贵。

### 更合理的产品假设

给结构化字段一个可用入口，而非用表单替代所有聊天。优先针对参数稳定、错误常见、后续计算昂贵的任务；对明确简单任务直接执行。

## 3. 尝试 B：Agent 提案与人工修改同时发生

### 构造过程

1. Agent 根据文档第 1 版提出标题修改，提案尚未写入。
2. 用户模拟人工编辑，文档成为第 2 版。
3. 用户接受旧提案，版本检查阻止写入，人工内容保留。
4. 重新基于第 2 版生成提案，预览保留人工补充。
5. 接受新提案成为第 3 版。
6. 额外测试：重算之后用户再次编辑，仍然阻止旧版本写入。

### 发现

展示 diff 只有信息价值；绑定对象版本并在提交时校验，才有覆盖防护价值。检查必须发生在真正写入边界，而非仅在打开预览时。真实多用户环境需要原子性的比较版本并写入，例如条件更新；前端检查不能替代并发控制。

重算与合并是另一个问题。本次示例固定保留了一句人工注释，不证明模型能正确合并任意文档。生产场景可以从不自动覆盖、另存候选产物起步，再增加专业差异工具。

### 投资判断

只读产物预览通常更便宜；共同编辑与部分接受更复杂。若你平台里输出主要是独立新文件，先做产物定位和版本标识；只有同一对象经常被人和 Agent 共同修改时，版本冲突治理才有明显的额外价值。

## 4. 尝试 C：停止任务究竟停止了什么

### 构造过程

同一个任务包括“汇总报告”和“提交内部系统”。用户可以在三个时点请求停止。

| 停止时点 | 本地执行状态 | 外部效果 | 合理 UI 描述 |
|---|---|---|---|
| 提交之前 | 请求停止，随后确认停止 | 尚未提交 | 已停止；没有外部提交 |
| 提交请求在途 | 确认本地停止 | 回执未知 | 执行已停止；提交结果待核查 |
| 外部成功回执之后 | 本地停止 | 已生效 | 已停止；既有提交仍保留 |

在第二条路径中，再查询模拟服务，发现提交已生效。Python 模拟另有“最终未提交”的分支，说明未知状态应允许被核查收敛，而非预先断言成功或撤回。

### 发现

“停止生成”“停止新动作”“终止受管进程”“取消外部请求”“撤回已生效业务动作”具有不同语义。UI 可以用渐进展开解释，但必须先有对应能力。

对于短脚本，可用受管作业和退出回执支撑状态。对于长 server，应明确属于任务还是独立服务、何时回收、停止作用范围。对于外部业务效果，通常需要单独查询或补偿。这里是设计要求，不是对任何具体沙盒实现的已验证结论。

### 投资判断

如果 runtime 已有可靠取消与资源回收，UI 改造性价比较高。如果没有，完整停止按钮是后端能力建设，不能当作纯前端低成本项目。最低版本应诚实显示停止请求与确认，避免夸大效果。

## 5. 尝试 D：工时回收的敏感性

### 模型与参数

每月用户净节省工时：

`适用任务数 × 实际采用比例 ×（每次省下的操作与返工分钟 − 新增审查分钟）/ 60`

计入维护后的净节省：上述用户工时减去每月维护工时。等权回收时间：一次开发工时除以每月净节省；净节省小于等于零时没有有限回收期。

这是容量/工时示例，不是财务 ROI。假定工程师与用户工时等权，且收益稳定、用户采用不随时间变动；没有计工资差异、token、服务器费、机会成本和收益重叠。

基线假设：每月 2,000 个适用任务、60% 采用、每次节省 3 分钟、新增审查 1 分钟、开发 10 人日、每月维护 12 小时、每人日 8 小时。它与平台历史用户数没有换算关系。

| 改变一个条件 | 用户净节省/月 | 维护后净节省/月 | 工时等权回收期 |
|---|---:|---:|---:|
| 示例基线 | 40.0 小时 | 28.0 小时 | 2.86 个月 |
| 采用率降为 20% | 13.33 小时 | 1.33 小时 | 60.0 个月 |
| 适用任务仅 500 个 | 10.0 小时 | -2.0 小时 | 无有限回收期 |
| 新增审查升为 4 分钟 | -20.0 小时 | -32.0 小时 | 无有限回收期 |
| 开发仅需 3 人日 | 40.0 小时 | 28.0 小时 | 0.86 个月 |
| 每月维护升为 40 小时 | 40.0 小时 | 0 小时 | 无有限回收期 |

这些数字已由脚本计算，不是收益预测。基线中的正净收益门槛是适用任务数每月超过 600；若单次新增审查已大于节省，增加任务量反而放大负收益。

### 进一步分析

1. 大用户池不自动代表采用率。入口是否在用户工作的地方，可能比模型本身更影响回收。
2. 新增审查是容易被漏算的成本。省操作但多读一份长报告，可能没有净收益。
3. 最小改动的优势常在开发与维护，而不是每次节省特别多。
4. 动态界面、协议适配和大量 Agent 角色会增加长期维护；不能只算演示成本。
5. 若改动主要减少严重错误，单纯时间模型会低估价值。应另外记录错误率和影响，再选合适权重，避免人为塞进节省分钟。

## 6. 四个更值得验证的命题

- 稳定字段任务中，结构化输入相较优化后的批量聊天，是否减少错填、返工和理解负担？
- 产物独立呈现后，用户找结果与复查耗时是否下降，还是只是多一个区域？
- 显示真实阶段与阻塞是否减少重复询问和重复启动？
- 把成功流程固化为动作是否真的被复用，维护成本是否保持低水平？

这些比“AI UI 是否更先进”更容易得到有用答案。

## 7. 最小真实实验

选两类任务、三种界面：现有 UI、优化后的聊天、聊天 + 对象/固定组件。使用同一模型、工具、输入与验收口径。先做小样本形成性观察，不用十几条任务宣布统计显著。

把数据充分度、任务复杂度与用户熟练度记录下来；同一人体验多种界面时平衡顺序，避免后一次因为已熟悉任务而看起来更快。质量由独立规则或独立评审验证，不能让生成 Agent 自评成功。

记录：实际完成与错误、用户操作时间、等待时间、新增审查、返工、接管、模型成本和维护问题。若用户没有完成，时间再短也不能算效率提升。

暂停或改版依据可以是：误确认增加；净节省接近零；结构化界面固化错误口径；状态与执行不一致。下一轮规模扩展需要在这些问题收敛后再考虑。

## 8. 本次模拟之后调整的判断

结构化澄清有价值，但其主要优势未必是减少点击；好的集中聊天是强基线。版本预览有价值，但不配合写入时校验不能保护人工工作。停止有价值，但状态表达与取消能力必须匹配。高采用、低审查、低维护比功能数量更影响投入回收。

下一步的重点可以从“增加 AI 功能”转向“选择一处真实的理解/状态/返工瓶颈”。这个选择应由平台会话与用户观察决定，本次模拟提供的是筛选工具。
