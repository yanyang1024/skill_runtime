# 继续头脑风暴：确定性、价值与投入顺序

日期：2026-10-03（中国时间）。承接前一轮《UI 与 AI 应用的开放式头脑风暴》。这是基于当前公开技术和你已描述的平台条件的设计判断；没有检查你的内网代码、业务接口和真实用户数据。

## 1. 这一轮更明确的判断

值得优先探索的方向是：把工作对象、真实执行状态和用户可修改的位置做清楚。它们通常不需要模型获得更强的通用自治能力，既能帮助人，也能让 Agent 得到更明确的上下文与反馈。

但“技术可做”“用户需要”“收益能覆盖投入”必须分开判断。自由生成整套界面可以很快做出演示，却未必易维护；完整任务治理也许十分重要，却不是一个前端卡片就能完成。

可把基本方向描述为：**让概率性的理解与生成，接到可检查的对象、可约束的操作与可恢复的状态上。** 这是一条架构与交互假设，不是所有产品都必须采用的答案。

## 2. 什么叫相对确定性

| 维度 | 可以较有把握地判断什么 | 本次不能据此保证什么 |
|---|---|---|
| 工程可实现性 | 固定组件、对象 ID、版本检查、事件展示等可实现 | 当前模型会正确选择对象或业务动作 |
| 交互需求稳定性 | 用户需要看见结果、修正误解、知道执行状态 | 每个任务都需要常驻聊天或任务看板 |
| 场景收益确定性 | 高频返工点存在时，相关改动有较明确的收益机制 | 未观察用户前就能给出节省百分比 |
| 商业/组织回收 | 可按采用率、时间节省与维护计算门槛 | 可用人数等于活跃采用人数、工时节省等于现金收益 |

本文“高、中、低”为判断等级，不是测量分数。“高”是指不依赖尚未实现的模型突破，且有明确工程路径，不指零风险。

## 3. 当前能力的合理设计边界

模型能够解释语言、生成结构化内容、提议工具调用；运行系统可以提供环境反馈和持久状态。但复杂开放任务仍需要错误处理、状态恢复和验证。能力不是一句“Agent 已经成熟”可以概括的。

Anthropic 的工程材料区分预定 workflow 与模型动态选择过程的 agent，并讨论增加自治带来的延迟和成本。将其作为设计原则参考，而不是今天所有模型的性能证据。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

关于跨上下文的长任务，其工程材料展示了增量工作、进度资料和测试的作用，同时讨论了提前宣布完成等失败。这说明工作记录与验证很重要，不证明后台运行越久结果越好。[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

| 能力 | 当前值得采用的边界 | 对应 UI 选择 |
|---|---|---|
| 语言理解 | 提议目标和字段；重要歧义可修正 | 可编辑意图摘要、少量澄清选项 |
| 结构化输出 | Schema/程序校验结构；另查业务语义 | 固定组件渲染结果，失败有回退 |
| 工具调用 | 动作、参数和效果由执行层校验 | 绑定对象、范围和实际回执 |
| 检索 | 来源可以定位；支持关系仍需核查 | 来源状态与验证状态分开 |
| 文件编辑 | 读写容易；正确合并与覆盖防护需设计 | 先做预览，再做带版本的写入 |
| 长任务 | 日志与检查点可实现；跨进程恢复有成本 | 阶段和阻塞可见，取消语义诚实 |
| 多模态 | 支持指向；识别准确率依输入与模型 | 可修正识别对象和选区 |
| 多 Agent | 分工可实现；净增益需要对照 | 先呈现复核结果，再按需展开角色 |
| 动态 UI | 受控组件选用可实现；任意界面治理困难 | 稳定骨架、少量动态区块 |
| 计算机使用 | 适合补齐无接口能力；长链可靠性需测 | 人能接管并查看外部状态 |

如果私有模型不支持可靠函数调用或约束输出，部分交互仍可用普通 JSON + 解析校验 + 固定模板做；不能默认前沿公有模型能力已存在于你的内网端点。

## 4. 为什么更多自治未必需要更多聊天

模型越能执行，用户越需要区分：系统理解了什么、提议了什么、实际做了什么、验证了什么。自然语言适合表达意图和解释，结构化对象适合承载状态。

一个思维实验：无恢复、步骤独立、每步正确概率假设为 0.98 时，20 步全部正确约为 0.668。该数值不是任何模型或平台的实测；实际错误有关联，也可能被校验与重试恢复。它只提醒我们：长链任务不能仅靠流畅叙述建立可靠感。

UI 的机会包括缩短无必要的交接、使用户及时纠正范围、让失败可局部修复。它不能代替工具实现、沙盒隔离和业务验收。

## 5. 候选投资表

| 方向 | 工程确定性 | 条件满足时的价值 | MVP 投入/运行成本 | 值得优先做的前提 |
|---|---|---|---|---|
| 已采用资料与范围可见 | 高 | 高：减少误用背景和反复解释 | 低至中；不必新增 LLM | 有输入对象与读取/发送记录 |
| 产物独立展示、可定位 | 高 | 高：减少找结果与复制 | 低；只读起步 | 任务经常输出文件/表格 |
| 任务阶段、阻塞与真实结束 | 高；依赖事件 | 高：减少重复催问和误判完成 | 有事件则低，否则中 | 可以映射可信执行状态 |
| 缺失字段的选择/表单 | 已知 Schema 时高 | 中至高：减少串行问答 | 低；选择本身不需模型 | 任务字段稳定，确有歧义 |
| 已知错误的局部修复 | 高 | 高：减少整任务重做 | 低至中 | 工具错误可分类、有修复路径 |
| 带版本的差异与局部接受 | 高；集成依赖明显 | 高：保护人工修改、降低返工 | 中；复杂编辑可变高 | 多轮编辑和同时修改常见 |
| 参数化复用动作/shortcut | 高 | 高频场景高 | 低至中；长期收益较好 | 成功路径与参数能固定 |
| 来源定位与证据状态 | 定位高，支持判断中 | 分析任务高 | 低至中；自动判断另计成本 | 来源有对象身份和版本 |
| 待决策收件箱 | 展示高，完整生命周期中 | 多后台任务时高 | 中；需持久任务与通知 | 用户确实同时管理多个任务 |
| 可编辑委托与授权范围 | 设计可实现，执行需核实 | 高影响任务高 | 中至高 | runtime 真正执行边界与撤销 |
| 受控动态组件 | 中至高 | 跨任务表达有潜力 | 中；组件/协议治理持续投入 | 固定模板已无法满足需求 |
| 通用跨应用桌面 Agent | 场景差异大 | 上限高，兑现不确定 | 高 | 身份、API、环境与恢复成熟 |
| 自由生成整套 UI | 演示可做，生产收益低确定性 | 不确定 | 初始低、维护可能高 | 动态性确实比稳定性重要 |
| 可视化多 Agent 组织图 | 高 | 业务用户价值不明；开发者较明确 | 中，可能增加认知负担 | 用于诊断和分工管理 |
| 每个用户一套长期定制 UI | 可做但收益不确定 | 取决于任务重复与用户习惯 | 治理成本高 | 足够行为证据支持定制 |

MVP 成本等级是相对判断，不是代码审查后的报价。几个“高价值”方向只有在底层具备事件、对象和校验能力时才有高性价比。

## 6. 对你的平台，投入顺序可以更具体

### 第一批：复用已有信号，改善看清任务

优先试资料范围、产物入口、任务状态和已知工具错误。这批与已知的文件操作、工具调用和时间戳相邻，可减少额外模型开销。

必须注意可观测字段的边界：文件指纹可以帮助识别版本与复用，不能证明文件全文已进入模型上下文；工具调用成功不证明业务任务完成；时间戳也不自动提供进程是否已退出。

资料可区分“用户提供”“已读取”“已加入模型上下文”“结论引用”，只显示实际观测到的状态。若暂时只知道上传与读取，就按这两个状态展示，不虚构后两层。

产物从只读预览和定位起步，不先建设完整协同编辑器。任务从现有运行事件展示阶段，不让模型凭感觉生成百分比。错误从最常见的三类开始，而非用 LLM 解读所有异常。

### 第二批：让纠错和重复执行更省力

选择两个字段稳定的业务任务做结构化澄清；选择一个频繁产出文档的场景做版本冲突；把一个高频成功路径固化为参数化动作。

不要每个任务都弹确认页。对于低影响、可回退且范围明确的操作，直接执行与明确反馈可能更好。需要确认的动作应有具体影响依据，而不是因为“由 AI 做”就重复要求同意。

### 第三批：确有长期任务负担时再增加组织层

待决策收件箱、后台恢复、跨端接续、可编辑授权很有价值，但需要真实任务生命周期、对象权限和外部效果记录。先核实需求再做完整框架。

这一层与前端相邻，却主要是 runtime 工作。若只有漂亮卡片而无有效取消与恢复，收益不能按完整能力计算。

## 7. 高价值方向为什么可能不划算

- 跨应用 Agent：能省很多导航，接口和身份维护可能更昂贵。
- 自动证据判断：能减少审查，但模型裁判自己也需要校准。
- 全量差异审查：理论上更安全，实际可能使用户机械接受。
- 高度个性化：短期有吸引力，跨用户支持与培训变难。
- 后台主动建议：发现问题有价值，但打断和解释成本可能抵消收益。

高价值应按重要的业务瓶颈判断；高性价比应按真实采用、净节省、维护和风险成本判断。两者不是同义词。

## 8. 当前协议给了哪些实际支点

ACP v1 提供会话更新、取消和权限请求等机制，说明客户端可以承载交互控制；取消方法存在并不保证所有子进程和外部请求同时停止。[ACP v1](https://agentclientprotocol.com/protocol/v1/overview)

MCP Apps 提供交互式 UI 资源及与宿主的通信；客户端支持有差异。它使专业控件嵌入对话有工程路径，不证明你的平台必须迁移到该协议。[MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview)

A2UI 采用声明式描述与客户端组件渲染，适合讨论受控动态 UI。仍需校验组件、动作权限和业务效果；声明式渲染不自动解决这些问题。[A2UI](https://a2ui.org/introduction/what-is-a2ui/)

前一轮已梳理 A2A 和 AG-UI；本轮不把协议扩展数量当作价值指标。可以先用现有事件与固定组件验证需求，后续再决定协议化边界。

Microsoft 的 Human-AI Interaction 指南将初次使用、持续使用、错误与长期变化都纳入设计。这里借用这种生命周期视角，优先让能力边界、纠正和恢复可用，而不是只优化首次演示。[Microsoft Research](https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/)

## 9. 如何做真实的投入产出判断

先选一个错误高频或工作高频的切口，记录：每月适用任务数、采用率、每次省掉的操作与返工、新增审查、开发和维护投入。按同类任务对照；不按整个平台注册人数放大收益。

收益可以来自时间、任务完成率、错误减少和复用增加。先分别记录，避免把“返工减少”同时算进节省时间和额外业务收益而重复累计。

本次提供的是工时等权模型，适合看门槛。如果用于经费汇报，还需要工资/资源权重与成本口径；如果用于容量规划，用户时间与工程时间应分别展示，而非只合成一个数。

## 10. 下一步仍保持开放

更值得先验证的命题是“共享对象与状态是否减少沟通和返工”，而不是“聊天是否取代 UI”。当用户有清晰任务和熟练动作时，稳定按钮可能更高效；当用户还不知道问题是什么时，开放对话仍有优势。好的 AI UI 可能会随任务成熟度切换表达方式。
