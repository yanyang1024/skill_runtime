# 阶段三：Web、Web UI 与 SaaS——链接、共享和服务边界

## 1. 从本地对象走向可寻址资源

CERN 的历史材料记录了 Web 的起源、首个网站和超文本项目。本文借此讨论一种交互变化：资源通过地址连接，跨计算机访问成为界面的基础能力。[CERN：Web 的诞生](https://home.cern/science/computing/the-birth-of-the-web/)

浏览器降低分发和跨平台访问的门槛；网页从文档浏览扩展到表单、动态界面和业务工作流。SaaS 又使账号、角色、协作和服务端状态成为重要约束。这些演进互相交叠，并非 HTML 出现后立即成为完整云应用。

| 交互对象 | 常见动作 | 能力变化 | 新负担 |
|---|---|---|---|
| 页面与链接 | 浏览、搜索、跳转 | 资源可以被引用 | 导航和信息过载 |
| 表单与交易 | 填写、提交、确认 | 远程修改业务状态 | 校验、会话和提交风险 |
| 共享文档 | 评论、协作编辑 | 多人围绕同一对象工作 | 版本、冲突与权限 |
| SaaS 流程 | 审批、派单、批量处理 | 跨角色组织工作 | 系统碎片化与集成成本 |

## 2. Agent 会改变哪些 Web 习惯

人需要看清页面层次；Agent 更需要稳定对象引用、可用操作与效果说明。一个页面可以视觉易用但语义不明确，也可以有完备 API 而业务人员无法理解结果。

因此应用可以同时维护三种表示：视觉页面给人；语义结构给辅助技术及部分自动化；业务操作接口给稳定执行。它们应映射到同一业务状态，但并不需要拥有同样的按钮和字段。

WAI-ARIA 提供角色、状态和属性等可访问性语义。这有助于理解网页如何向非视觉消费者表达结构，但 ARIA 不等于完整 Agent 业务接口，也不提供授权和业务事务保证。[W3C ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/)

## 3. 四条 Agent 适配路线

| 路线 | 优势 | 失败条件 |
|---|---|---|
| 截图与模拟输入 | 兼容已有应用，改造较少 | 页面变化、视觉歧义、调用成本 |
| DOM / 可访问性语义 | 更容易定位控件和状态 | 自绘内容、缺失语义、动态结构 |
| API / 工具接口 | 结构明确，可处理批量任务 | 缺少业务解释，与 UI 状态不一致 |
| 面向任务的聚合操作 | 减少多次调用和中间错误 | 过度聚合，用户难以修正局部 |

这些路线可能共存：操作接口处理核心事务；语义界面用于发现与确认；计算机使用补齐长尾。更大的模型可能改善通用视觉操作，但提供高质量接口也可能始终更经济。需要比较实际总成本，而非只比较演示成功率。

## 4. “每个应用为语言适配”需要拆开

它可能指增加一个聊天入口，也可能指提供语义操作目录，或让应用输出可解释结果。它还可能意味着将常见用户意图封装为业务任务，例如“解释这次库存变化”而非只暴露表字段。

不同适配的成本与商业动机不同。广告、内容推荐和流量平台可能不愿让 Agent 绕过页面；企业工具可能愿意降低操作成本；强专业应用可能更愿意保留用户在界面中的判断。技术可行不代表产品会开放。

## 5. URL 的历史启发：任务和产物能否被引用

一个可分享地址让人无需复述整个导航路径。Agent 协作也可能需要类似能力：直接引用本次任务、特定产物版本、某项未决问题或证据片段。

开放设计：链接携带对象身份，服务端执行访问控制；聊天里显示简短摘要，按需加载完整内容。链接不能隐式成为无限授权令牌，也不能把当前版本与已审查版本混淆。

这与文件连接阶段有相似之处，但业务系统里的对象可能是数据库记录、视图或外部服务资源，不宜全部强制转成文件。

## 6. 从页面导航到跨服务任务

用户目标可能穿过多个 SaaS：拿数据、做分析、写报告、安排评审。界面可以保持应用中心，也可以转向任务中心。后者减少切换，但要承担来源展示、身份切换、状态恢复和外部效果记录。

**假设**：应用的页面可能逐渐成为工作对象的专业编辑器，跨应用任务由另一个入口组织。

**反例**：业务口径高度依赖单一系统，统一入口遗漏必要上下文；或者平台不开放关键能力。此时应用内 Agent 可能更可靠。

## 7. 可尝试的 Web UI 模式

- 在表格筛选旁加入语言解释与批量操作提案。
- 让操作显示“目标对象 + 变化摘要 + 生效范围”，并支持点击回到原系统。
- 把错误转为可修复字段，而不是把原始异常整段塞进聊天。
- 让用户选择当前页面哪些内容进入模型上下文，显示已发送的范围。
- 对跨服务任务保留每个子结果的状态，避免一个总成功标签掩盖部分失败。

## 8. 待讨论问题

未来浏览器是文档阅读器、应用容器，还是任务中枢？应用会把最有价值的能力公开给别人的 Agent 吗？人与 Agent 使用同一操作模型是否比分别维护接口更经济？一个统一入口会带来便利，还是更强的平台锁定？
