# 企业 Agent 平台：最小改动与验证路线

日期：2026-10-03。基于你描述的 OpenCode 二开平台、多租户、文件操作、工具调用、Skill/Agent 与沙盒等条件。下列为候选方案，未访问内网，字段是建议契约，不是你当前已经实现的事实。

## 1. 一个会话内的最小组合

保留现有聊天入口，增加任务附近的三个可展开对象：采用资料、产物、运行状态。某些任务出现缺失字段时再显示澄清组件；不让所有用户先填写任务配置。

这能复用现有工作方式。它的目标是减少寻找、误读和返工，不是建立全新“Agent OS”。业务用户仍按工作理解界面；开发者按需进入调用与日志。

## 2. 最小 UI 与 runtime 契约

| 对象 | 候选最低字段 | 必须确认的事实边界 |
|---|---|---|
| 资料引用 | resource_id、名称、版本/指纹、可观测使用状态 | 指纹不等于模型已读取全文 |
| 任务 | task_id、run_id、状态、阶段、阻塞 | 状态来自执行事件，不从回答语气猜测 |
| 产物 | artifact_id、来源 run、版本、位置、生成/验证状态 | 文件生成不等于验收通过 |
| 提案 | proposal_id、对象、base_version、变化、状态 | 写入时原子校验版本与权限 |
| 待决策事项 | decision_id、原因、对象、选项、时效 | 不能为每个正常步骤制造确认 |
| 取消 | 请求 ID、作用范围、请求/确认状态、未决外部效果 | 取消会话不必然取消受管进程与外部提交 |

这些字段只在需要对应能力时加入。若先做只读产物展示，不需要提前实现所有提案和冲突字段。

## 3. 一条可落地的状态规则

生成结束、执行结束、校验结束和外部提交分别记录。默认用户界面可以简化为阶段和结果，但展开后能看到它们的事实来源。

例如：“报告已生成；数值核查待完成。”比一个笼统绿勾更容易指导后续工作。对于失败，显示可修复位置和当前保留的产物，不只显示整任务 FAIL。

真实事件可能重复、乱序或重连后重放。至少有 run_id 与事件序号/幂等键，UI 不把旧运行的完成事件套在新运行上。多租户读写校验在服务端，界面隐藏按钮不构成隔离。

## 4. 不先为哪些东西付费

- 不先迁移全部协议：用当前前后端连接验证有价值的状态模型。
- 不先实现任意 UI 生成：先用资料列表、表单、结果表、文档预览和差异等固定组件。
- 不先自动沉淀所有会话：先挑一条可复用、参数明确的路径。
- 不先把多 Agent 拓扑展示给业务人员：先显示任务与独立验证证据。
- 不先创建跨系统万能撤销：先准确记录取消与外部效果。

这不是否定后续扩展，而是让扩展由观察到的需求推动。

## 5. 一个候选实验时间盒

下列是分配实验精力的建议，不是未经代码审查的工期报价。可按团队规模缩放。

| 时间盒 | 可 review 的具体产物 | 需要决定的问题 |
|---|---|---|
| 1–2 个工作日 | 十余条真实任务的瓶颈记录、现有字段映射 | 最大损失在背景、找结果还是执行状态？ |
| 2–4 个工作日 | 一个场景的只读产物/资料/状态原型 | 已有事件是否足以支撑真实 UI？ |
| 2–4 个工作日 | 一种局部纠错：缺参数、版本冲突或已知工具错误 | 是否减少返工且不增加过多审查？ |
| 后续小规模试用 | 使用与质量记录、维护问题 | 净价值和采用率是否支持扩展？ |

如果第一轮发现后端缺乏对象身份和真实状态，应先做契约与观测，不把时间盒当作强行完成所有功能的承诺。

## 6. 验证和经验沉淀

结合你已有的评测方向，规则层判断对象、状态、格式与版本；独立评审判断是否满足任务；人工观察理解负担、接管与误确认。界面变化与 Agent/Skill 变化尽量分开比较。

一条 UI 经验适合沉淀时，应记录适用任务、用户类型、采用条件、实际证据与反例。例如“参数稳定的任务中，可选表单减少填错”，比“所有任务都用表单”更可复用。

UI 的行为记录可以进入会话诊断，但别把低点击数直接当作成功。新增的用户编辑、拒绝提案、重算和接管信号，有助于定位 runtime 的不足；也可能反映用户改变了目标，需要保留原因而非直接标成失败。

## 7. 如何运行附带模拟

Python 模拟只依赖标准库：

```bash
python3 simulate_agent_ui.py --output simulation-results.json
```

它输出工时敏感性、构造交互路径和 19 项状态检查。你可以替换适用任务数、采用率、操作节省、审查和维护假设，也可替换交互路径；替换后结果依然是模型计算，直到输入来自实际观测。

`ui-scenario-results.json` 另记录了本轮实际交互脚本的 20 项本地逻辑检查及其验证边界。它不是浏览器兼容认证，也不是用户研究。

## 8. 仍然没有确定的选择

面向业务人员的主界面是否应是任务、产物还是决策？UI 与 Skill 是否应共享一份任务 Schema？自动推荐方法时用户应看到多少内部结构？重复动作何时成为公共资产？

先用小场景得到答案，再决定是否建设更完整的组织层。对于平台负责人，最有价值的下一步可能是把“模型能力不足”和“界面没让用户有效纠正”区分出来，而非一律用更强模型解决。
