## 如何理解本文的证据

- **事实锚点**：来自官方协议、平台设计指南及历史机构材料，段落附链接。
- **分析**：对机制和场景的解释，包含作者判断，不代表来源的原话。
- **假设**：使用“可能、如果、值得尝试”等表述，并配以反例或失败条件。
- **设计草案**：为思考构造的示例，不表示某项协议已经提供全部实现。

这里不使用厂商宣传判断协议是否“胜出”，也不将文档列出的计划能力当作所有产品已具备的能力。协议网页可能滚动更新；实施时需要重新锁定版本和能力协商结果。

## 一组贯穿所有阶段的问题

| 观察轴 | 问题 |
|---|---|
| 表达 | 用户需要记忆语法、识别对象，还是描述目标？ |
| 工作对象 | 操作的是命令、文件、页面、服务、任务，还是产物？ |
| 状态 | 状态在哪里存放？人和机器能否指向同一个版本？ |
| 时间 | 交互是瞬时、持续、后台，还是跨天协作？ |
| 控制 | 用户如何改变方向、接管、撤销、缩小授权？ |
| 反馈 | 看见的是文字、视觉效果、执行状态，还是可检查证据？ |
| 经济 | 界面服务谁的收益？平台会愿意开放什么？ |

一个值得带着疑问阅读的观察：界面可能把越来越多的执行细节交给机器，同时把越来越多的目标、约束和结果判断交给人。这未必降低人的总工作量，也可能只是将工作从操作转移到审查。
