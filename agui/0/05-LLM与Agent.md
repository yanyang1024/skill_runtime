# 阶段五：LLM 与 Agent——能力、协议和交互压力

资料核查日期：2026-10-02。这里的“能力涌现”指实践中出现的组合能力及其交互影响，不据此判断某种能力在统计上属于严格的涌现现象。

## 1. 从文本生成到可委托工作

LLM 提供了自然语言解释、生成和转换能力。结合工具、环境、状态与反馈后，系统能执行多步任务。Agent 的产品价值来自整个运行系统，不能只用模型回答质量概括。

| 能力变化 | 可以尝试的交互 | 必须保留的问题 |
|---|---|---|
| 语言理解与生成 | 模糊目标启动、解释选项 | 假设是否正确、用户能否修改 |
| 结构化输出 | 表单、操作参数、结果卡片 | 结构合法不代表业务正确 |
| 工具调用 | 从建议走向执行 | 操作效果、范围、权限 |
| 图像与音频 | 指向、现场输入、语音反馈 | 识别错误、延迟与隐私 |
| 多步规划与迭代 | 长任务、阶段性产物 | 进度真实性、停止条件 |
| 检索与记忆 | 减少重复说明、领域上下文 | 来源、时效、过度继承 |
| 计算机使用 | 兼容缺少接口的应用 | 稳定性、成本和歧义 |
| 多 Agent 协作 | 专业分工、独立审查 | 协调开销、权限传播、上下文污染 |

这是一张能力类别图，不是所有模型的统一能力清单。界面应该依实际产品能力给承诺。

## 2. 协议的现实分工

本文的 ACP 指 **Agent Client Protocol**；ACP 缩写也曾用于其他协议，讨论时必须写全名和实现版本。不能把几个协议混成一套“Agent UI 标准”。

| 协议/扩展 | 主要边界 | 官方材料中的重点 | 对 UI 的启发，属于本文推断 |
|---|---|---|---|
| ACP | Agent 与客户端，如编辑器 | 会话、更新、取消、权限请求 | 客户端可承载控制与反馈 |
| A2A | Agent 服务之间 | 能力发现、任务、消息、产物和异步更新 | 可围绕任务与结果组织界面 |
| MCP | Agent 应用与工具/数据 | tools、resources、prompts | 将能力发现与视觉布局分离 |
| AG-UI | Agent 后端与用户应用 | 事件式、双向交互 | 执行状态与用户干预可独立于文本流 |
| A2UI | Agent 提供 UI 描述，客户端渲染 | 声明式组件与数据 | 由受控组件表达动态任务界面 |
| MCP Apps | 工具提供交互式 UI | UI 资源、宿主嵌入与双向通信 | 专业交互可以嵌入对话 |

官方资料：[ACP v1 概览](https://agentclientprotocol.com/protocol/v1/overview)；[A2A 规范](https://a2a-protocol.org/latest/specification/)；[MCP server 概览](https://modelcontextprotocol.io/specification/draft/server/index)；[AG-UI](https://docs.ag-ui.com/introduction)；[A2UI](https://a2ui.org/introduction/what-is-a2ui/)；[MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview)。

上表说明接口范围，不能据此推出广泛采用率或互操作质量。尤其 ACP 已出现版本变化资料，A2UI 页面区分 Current 与 Candidate；本次核查的 ACP overview 自动指向 v1。落地时应锁版本并检查具体实现，避免把候选规范混进生产契约。

## 3. 哪些协议事实值得关注

ACP v1 定义会话 prompt、update、cancel 等交互，并让客户端处理权限请求；这体现客户端并非只是文本显示器。[ACP v1](https://agentclientprotocol.com/protocol/v1/overview)

A2A 将任务状态与产物纳入数据模型，并提供更新机制。这给长期工作提供了可观察对象，但不自动实现跨系统事务或产物版本管理。[A2A 规范](https://a2a-protocol.org/latest/specification/)

AG-UI 定位于前后端事件交互，A2UI 定位于声明式 UI 描述，二者可配合，职责不同。官方介绍中包含 today & upcoming 能力，不能将介绍列表整体视为所有集成已支持。[AG-UI 概览](https://docs.ag-ui.com/introduction)

MCP Apps 用 UI 资源让工具返回交互界面，Web 宿主通常采用受控 iframe。A2UI 的另一条思路是交由客户端渲染声明式描述。两者不是简单的先进与落后关系：前者可复用丰富 Web 能力，后者强调受控组件和平台渲染，各自有灵活性、兼容性与治理成本。[MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview)；[A2UI](https://a2ui.org/introduction/what-is-a2ui/)

## 4. 对话式应用的几种既有模式

以下是观察性分类，各产品往往同时采用多种模式。

| 模式 | 强项 | 弱项 |
|---|---|---|
| 纯聊天 | 启动快、容纳模糊输入 | 产物与状态埋在时间流 |
| 聊天侧栏 | 依托原应用上下文 | 范围和选择可能不透明 |
| 聊天 + 画布/文档 | 讨论与产物并存 | 修改同步和版本需要处理 |
| 行内补全/改写 | 局部操作成本低 | 不适合长任务与跨系统工作 |
| 搜索 + 引用答案 | 证据导向 | 来源存在不等于结论成立 |
| 任务型 Agent 工作台 | 长任务和交付可见 | 容易把内部日志变成负担 |
| 对话内表单/图表 | 精确输入和探索 | 动态组件生命周期复杂 |
| 语音实时交互 | 低输入门槛与现场感 | 长信息、纠错与公共场合困难 |

## 5. 新的 UI 压力来自不确定执行

传统 UI 也处理异步、工作流和自动化；Agent 并没有发明这些问题。变化可能在于：系统根据开放目标选择路径，并在执行中改变计划。因此“可预测界面”需要容纳“不可完全预定的过程”。

一个文本回答结束不等于任务结束；一个任务完成不等于业务验收通过；一张卡片显示成功不等于外部状态真的提交。UI 应由可靠的执行状态驱动，语言可用于解释，不应成为状态的唯一来源。

## 6. 透明度应该展示什么

用户可能需要：当前目标、采用的数据、已完成动作、未决问题、失败事实和可接管位置。开发者还需要工具参数、错误和耗时。二者可以按需展开，但不用让所有人阅读全部轨迹。

这里展示可观察事件与证据，而非原始模型内部推理。模型生成的理由也不应被误当成执行审计。进度百分比若无可测分母，阶段描述和阻塞原因更诚实。

## 7. 面向 Agent 的界面与面向人的界面

人需要可辨识对象、视觉比较与有效控制；Agent 需要操作契约、资源引用、版本和结构化结果。共享的部分可能是业务语义与状态，呈现层可以不同。

一个按钮背后可对应稳定操作：目标对象、参数、前置条件、权限、效果和错误。Agent 读取这些语义；人看到自然语言摘要及预览。不要因为工具名叫“safe_update”就相信它安全，权限与校验应在运行系统中执行。

## 8. 各种可能的近期路线

- 固定 UI 保持稳定，语言帮助导航与解释。
- 固定 UI 中出现可配置任务区，Agent 选择受控组件。
- 对话成为启动入口，产物工作区成为主要操作面。
- 任务在后台持续，人从决策收件箱参与。
- 系统级 Agent 组织跨应用流程，应用提供专业编辑器和执行接口。

每条路线都存在现实障碍：商业激励、权限、体验习惯、执行稳定性以及迁移成本。技术进步可能改变它们的相对优势，却不必使所有场景收敛。
