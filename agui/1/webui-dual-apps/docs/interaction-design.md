# 从两套可运行原型观察交互设计

这次没有把“AI 应用”当成一种统一界面，而是在同一个任务、同一组数据上实现两个不同的控制结构。原型验证的是流程能否成立，尚不能验证用户更喜欢哪种方式或业务 ROI。

## 两种结构的区别

| 设计问题 | A：表单增强 | B：目标工作台 |
| --- | --- | --- |
| 启动任务的入口 | 明确字段与提交按钮 | 目标描述 |
| 结构化内容出现的位置 | 一开始就出现，AI 提议局部修改 | 需要澄清时出现条件卡，工具执行后出现统计和草稿 |
| AI 的作用范围 | 提议和解释 | 有预算的工具选择与任务推进 |
| 人的主要负担 | 设置所有条件、组织步骤 | 确认歧义、核对证据、处理草稿与产物 |
| 不确定性的表现 | 未识别字段保持不变；错误建议可忽略 | 歧义暂停；工具错误可反馈给模型；未完成任务明确失败 |
| 异步结果与人工修改冲突 | 建议绑定表单修订序号 | 草稿绑定报告基准版本 |
| 最终对象 | 一次表单查询的结果 | 一个可继续工作的任务，以及独立的当前报告 |

两个版本都有语言入口。真正的差别是：语言只帮助操作既有控件，还是参与决定接下来执行哪些操作。

## 相对确定、值得先投入的部分

以下判断来自应用控制结构和已经验证的行为，不是用户研究结论。

| 投入项 | 为什么相对确定 | 原型中的实现 | 预计开发相对投入 |
| --- | --- | --- | --- |
| 保留可独立使用的表单提交路径 | 有明确字段的重复任务，不依赖语言理解也应能完成 | A 未接入 AI 仍可统计和导出 | 低 |
| 把 AI 的字段建议做成可核对差异 | 用户可以判断被修改的具体对象，避免重读整段描述 | 字段旧值 → 建议值；显式应用 | 低 |
| 将统计数值交给确定性代码 | 比率、去重与范围必须遵守同一口径 | A / B 共用 `analyze()` | 低至中，取决于数据接口 |
| 草稿与当前产物分开 | 模型结果晚到或不合意时，现有成果仍然可用 | 草稿需采纳；拒绝不改报告 | 中 |
| 显示真实执行状态 | 用户需要区分进行中、等待输入、已停止和失败 | 服务器事件、轮询与明确状态 | 中 |
| 异步写入的版本检查 | 人和 Agent 可能同时修改同一个对象 | 报告写入与草稿采纳均进行原子版本检查 | 中 |

“确定”主要指这些机制能控制具体错误，并不意味着每个任务都需要同时展示全部机制。一次简单查询可以沿用 A；多步骤报告任务更可能从 B 的任务与产物结构获益。

## 可能高价值，但需要验证的部分

1. **按任务阶段出现的结构化交互。** B 的条件卡在歧义出现时才展示；一开始只要求目标。这可能降低初次使用门槛，也可能让熟悉字段的用户觉得多绕一步。应比较新用户与熟练用户的完成时间，而非只看启动速度。
2. **围绕产物继续工作。** 当前报告可以人工修改，Agent 接收新版本后重新提案。价值可能来自减少重复解释上下文；但若模型常丢失人工补充，重做成本会抵消收益。
3. **Agent 自行选择工具与顺序。** 真实模式里选择由模型完成，演示模式里是规则。工具数量小且边界清晰时容易检查；工具越多，找到合适工具和恢复失败的成本越需要测量。
4. **面向异常的主动协作。** 模型遇到数据范围或口径问题，可以请求澄清。收益取决于它是否在必要时提问，以及问题是否具体可答。提问次数多本身不代表更可靠。

暂时没有实现任意生成 UI、多 Agent 调度、跨系统发布、长时后台自动执行或自动合并报告。这些方向可以探索，但不应先于这个任务中已有的输入、统计、版本和产物问题。

## 四个可复现模拟

### 模拟一：熟练用户的确定查询

任务：“比较研发和工艺，9 月 5—10 日的工具失败率”。

- A：可以直接填写并提交，也可用语言形成字段建议。提交路径固定，结果容易复核。
- B：目标 → 工具统计 → 草稿 → 采纳。多了组织报告的能力，也多了模型轮次和等待。

启发：如果任务只需一张统计表，B 的自主推进未必带来足够增益。可以测量是否减少了完整报告的总工作量，而非只比较点击次数。

### 模拟二：问题尚未成形

任务：“看看各部门的使用情况”。

- A：用户仍需选择“会话”“活跃用户”或“工具失败率”；演示填写助手不会自行把宽泛目标变成确定指标。
- B：进入等待输入状态；用户确认指标与范围后再统计。

启发：AI Native 的价值可能出现在帮助形成任务，而不是加快已确定任务。但真正有价值的澄清应关联业务含义，不能只是把原表单换个地方展示。

### 模拟三：人和 Agent 同时工作

在草稿等待采纳时，人先写入一条日志排查补充并保存。

- 当前报告版本变为 v1，草稿仍基于 v0。
- 前端提示过期；后端拒绝采纳并返回 `409`。
- Agent 基于新版本重新提案后，用户再次核对。

启发：版本检查能确定地避免覆盖，但“重新生成”可能增加耗时。下一步可研究局部提案与段落级修改，前提是存在明确的段落身份与可检验的修改范围。

### 模拟四：结果迟到或任务取消

用户执行中停止任务。

- 本地后续步骤被取消；迟到响应不得继续创建草稿。
- 当前报告保留；用户可以继续任务。
- 远端模型已经接收的请求不能保证撤回。

启发：界面上“停止”的承诺需要与实际执行边界一致。未来若增加外部写入工具，应区分停止后续步骤、撤销已完成动作和补偿业务状态，而不是复用一个笼统的取消按钮。

## 对投入产出的判断方式

不在这个样例上编造开发天数、成功率或收入。对真实任务可以使用下面的测量结构：

`净收益 ≈ 原流程完成成本 − 新流程完成成本 − 核对与纠错成本 − 模型/运行成本 − 维护摊销`

| 优先试验 | 重点记录 | 什么结果会推翻当前判断 |
| --- | --- | --- |
| A 的字段建议 | 正确应用率、改回率、填写与核对总时间 | 建议核对比手工填写更慢，或常修改未要求的字段 |
| A 的结果解释 | 可用建议比例、错误陈述率、人工整理时间 | 解释空泛或引入需要额外纠正的因果判断 |
| B 的澄清卡 | 澄清后完成率、重复提问率、放弃率 | 关键条件仍被误读，或问题过多打断熟练用户 |
| B 的产物协作 | 人工补充保留率、重新生成次数、整份报告完成时间 | 版本冲突虽安全，但重做成本过高 |
| B 的自主工具循环 | 正确工具选择率、无效参数次数、轮次与失败恢复率 | 频繁触达预算，难以恢复而需要用户重来 |

可以先在重复性高、输入可枚举的任务上加入 A 的字段建议与确定性结果。对“目标模糊、需要多步整理、产物会被多人继续修改”的任务，再比较 B 的完整完成成本。这是一个可检验的投入顺序，不是关于所有 UI 未来形态的定论。

## 与 Agent 协议的关系

本项目只实现 Responses 的应用内函数工具循环，**没有实现 ACP、A2A 或 MCP 服务端**。

未来若接入某种 Agent 会话或跨 Agent 协议，可以把其运行事件映射到这里的任务状态、澄清请求、统计证据和提案对象。协议负责传递任务与能力，不自动决定哪些结果需要用户核对，也不能替代应用自己的版本与权限检查。具体对接需以选定协议和版本的正式规范为准。
