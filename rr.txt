从 Chatbot 到 Coworker：变化的不是界面，而是“工作如何被编码”

截至 2026 年 7 月，可以观察到一条相当清晰但并非线性的产品演化路径：

Chatbot → Knowledge/RAG → Tool Use → Workflow → Skill → Workspace Agent / Coworker → 可能的“智能工作运行时”

Dify 已经把自身定位从聊天应用构建工具扩展为集 RAG、工具、Agentic Workflow 和可观测性于一体的平台；Claude Skills 将指令、脚本和资源打包为按需加载的能力；Claude Cowork、Claude Code、OpenCode、Codex App 则进一步把模型放进文件、终端、应用和持续项目状态中工作。 

但我认为，不能把它理解成后一代产品淘汰前一代产品。更准确的理解是：每一层都在把原来依赖人类临时提供的某种东西，变成模型可以直接访问、执行和积累的系统资源。

⸻

一、这条演化链究竟在外置什么

阶段	被外置给系统的东西	模型的主要角色	主要交付物	新出现的瓶颈
Chatbot	表达与推理	回答者	文本回答	不知道私有信息，无法行动
RAG	外部知识	基于资料回答	有依据的答案	检索质量、知识更新、上下文拼装
Tool Use	操作能力	工具选择者	查询结果或动作	调错工具、参数错误、权限风险
Workflow	固定流程	流程节点中的推理器	稳定的业务输出	流程僵化、分支爆炸
Skill	可复用的做事方法	动态加载专业能力	一致的专业成果	触发、版本、依赖、技能冲突
Workspace/Coworker	工作状态和执行环境	持续工作的执行者	文件、代码、表格、报告、项目变更	长期漂移、监督、隔离、验证
下一阶段	组织经验和反馈循环	可学习的工作系统	持续改进的工作能力	治理、责任和演化控制

这背后是五次重要迁移。

1. 从“回答问题”迁移到“完成任务”

Chatbot 的价值单位是一段回答。

Workspace Agent 的价值单位则是：

* 修改后的文件；
* 可以运行的程序；
* 一份经过资料核对的报告；
* 一个提交记录；
* 一张可继续编辑的表格；
* 一个被实际执行的业务动作。

Claude Cowork 当前强调的是给出目标后，在本地文件和应用中完成工作并交付成果；Codex App 也已经不再只强调聊天，而是项目、并行任务、文件、可检查产物和持续执行。 

因此，真正推动演化的不是“用户更喜欢聊天”，而是：

只有回答，没有执行，经济价值通常存在明显上限。

⸻

2. 从“上下文窗口”迁移到“工作空间”

早期应用试图把所有内容塞进 prompt：

* 系统提示词；
* 用户资料；
* RAG 文档；
* 工具定义；
* 历史对话；
* 业务规则。

但上下文窗口并不是工作空间。

上下文窗口适合模型暂时“看到”信息；工作空间则允许模型：

* 读取和修改文件；
* 运行脚本；
* 查看中间产物；
* 失败后继续；
* 保留任务状态；
* 创建可被下一轮继续使用的结构；
* 利用测试、数据库、版本控制获得外部反馈。

这也是 coding agent 为什么率先成熟。代码仓库天然具有机器可读状态、编译器、测试、Git diff 和相对明确的验证信号。OpenAI 将 Codex 的核心描述为模型、工具、提示和执行循环构成的 agent harness；Anthropic 对长时任务的讨论也越来越集中于持久记忆、测试 oracle 和 harness，而不仅是模型本身。 

代码场景可能不是 Agent 的终点，而是工作空间范式的第一个试验场。

⸻

3. 从“提供能力”迁移到“组织能力”

Tool 给模型一个动作，例如：

* 搜索数据库；
* 发送邮件；
* 执行 SQL；
* 调用图像分析接口。

Skill 则通常表达一整套“应该怎样完成某类任务”：

* 什么情况下使用；
* 先检查什么；
* 调用哪些工具；
* 输出什么格式；
* 遇到异常怎样处理；
* 使用哪些脚本和参考资源。

Anthropic 对 Skills 的定义就是包含指令、脚本和资源的目录，由模型在任务相关时动态加载。 

可以粗略地区分：

Tool 是动词。
Workflow 是动词的固定排列。
Skill 是带条件、知识和质量要求的做事方法。
Workspace 是这些方法实际运行、留下状态和产物的场所。

因此，Skill 并不是“更复杂的 Tool”，也不是“小型 Workflow”。它更接近可被模型解释和执行的组织经验单元。

⸻

4. 从“人类控制每一步”迁移到“人类监督任务”

传统软件里，人控制操作步骤：

点击按钮 → 填参数 → 执行 → 查看结果。

Workflow 里，人或开发者预先控制流程：

A 完成后执行 B，满足条件 C 时进入 D。

Coworker 形态中，人越来越多地控制：

* 目标；
* 边界；
    -评价标准；
* 可访问范围；
* 是否接受结果。

Anthropic 对 Claude Code 使用行为的研究发现，有经验的用户会批准更多自动动作，同时也会更频繁地中断 Agent。这说明监督并没有消失，而是从“逐动作批准”转向“持续观察、必要时干预”。 

这有点像驾驶方式的变化：

* 手动驾驶：每个动作由人完成；
* 辅助驾驶：机器执行局部动作；
* Agent 工作：人决定目的地、规则和是否接管。

所以“更少确认”并不等于“更少人类控制”。成熟系统可能是：

更少打断人的确认，更强的可观察性，更容易随时接管。

⸻

5. 从“开发完成后发布”迁移到“运行中持续演化”

传统应用的能力主要来自代码版本。

Skill 和 Workspace Agent 的能力则还可能来自：

* 新增加的文档；
* 用户修正；
* 成功和失败轨迹；
* 新脚本；
* 新测试；
* 项目级说明；
* 运行时积累的规则；
* 经确认后沉淀的局部经验。

这意味着应用从静态程序变成一种部分可生长的软件系统。

不过这里要避免一个过度结论：

能记录经验，不代表能安全地自我改进。

未经过审查的自动经验沉淀，可能把偶然成功、错误假设、用户临时要求和恶意输入一起写入长期能力。未来真正重要的不是简单的“自动学习”，而是：

可追溯的候选经验 → 验证 → 人类确认或质量门 → 版本化发布 → 可回滚。

这与你正在思考的 Skill Growth、Replay、Preview、Quality Gate 和 Stable/Preview 分层，实际上处于这条演化链的下一步：从使用 Skill，转向管理 Skill 的成长过程。

⸻

二、为什么这种演化现在会发生

1. 模型能力提升后，瓶颈转移到了模型之外

模型不够强时，大家主要研究：

* prompt 怎么写；
* 是否需要微调；
* 如何让回答更准确。

当模型能够完成多步推理、代码执行和工具调用后，实际失败越来越多来自：

* 找不到正确文件；
* 环境缺依赖；
* 权限过大或过小；
* 上下文被污染；
* 工具描述不清；
* 无法验证结果；
* 中间状态丢失；
* 长任务发生漂移。

于是竞争重点逐渐从“谁有更好的聊天模型”转向：

谁能为模型提供更好的工作环境、反馈信号、工具、权限和恢复机制。

OpenAI 将 sandbox 单独视为 Agent 工作流中的执行层；Anthropic 也强调 Agent 的自主性、透明度、权限和安全性需要产品层面的系统设计。 

⸻

2. 企业需要重复性，而模型擅长灵活性

Dify Workflow 一类产品的核心价值，并不是比模型更智能，而是把部分业务确定性重新放回系统：

* 哪些数据必须读取；
* 哪些节点必须经过；
* 什么情况下失败；
* 输出必须符合什么结构；
* 哪些步骤可以使用模型；
* 哪些步骤必须是确定性代码。

Anthropic 早在其 Agent 架构总结中就区分了 workflow 和 agent：workflow 的路径主要由代码预定义，agent 则动态决定执行过程，并建议从最简单的方案开始，仅在确实需要时增加自主性和复杂度。 

因此推动力不是“所有流程都要 Agent 化”，而是：

企业想在确定性流程和模型灵活性之间找到新的边界。

⸻

3. 用户并不真正想“和 AI 多聊天”

很多产品把聊天次数、对话时长当作体验指标，但用户的真实目标通常不是产生更多对话，而是减少完成工作的总摩擦。

例如用户让 Agent 分析数据，真正需要的可能是：

* 自动发现数据；
* 运行清洗脚本；
* 生成图表；
* 形成解释；
* 保存成报告；
* 允许修改其中一项；
* 下次继续使用。

聊天只是表达不完整需求的一种入口。

因此未来可能出现一个看似反直觉的趋势：

越强的对话式应用，用户实际需要输入的对话轮数可能越少。

⸻

三、这些阶段不是替代关系，而是不同的不确定性配置

一个应用应该选择 Chat、Workflow、Skill 还是 Coworker，关键不是哪种技术更新，而是任务里有多少东西可以预先确定。

“Chat 会替代传统界面”

这个观点在以下场景比较正确：

* 低频任务；
* 用户不知道具体操作步骤；
* 输入高度非结构化；
* 需求需要逐步澄清；
* 结果允许多种正确形式。

但在以下场景并不正确：

* 高频重复操作；
* 少量固定参数；
* 高风险交易；
* 用户需要快速扫描大量状态；
* 必须精确比较多个选项。

订一张机票时，自然语言适合描述模糊需求；但比较二十个航班，表格和筛选器往往优于连续对话。

所以未来不是 Chat 替代 GUI，而更可能是：

Chat 负责表达意图，GUI 负责呈现状态和精确控制，Agent 负责在两者背后执行。

⸻

“Agent 会替代 Workflow”

只在任务分支无法穷举时成立。

例如：

* 调研一个开放问题；
* 排查未知程序错误；
* 根据不同文件组织报告；
* 探索数据中的异常原因。

对于以下任务，Workflow 仍然更合理：

* 财务审批；
* 数据同步；
* 合规检查；
* 标准化报告；
* 可明确列出全部步骤的批处理。

甚至在复杂科学任务中，Anthropic 的案例也显示，引入确定性的检索工具后，可靠性显著提高；其结论是确定性检索层目前仍然是可靠 Agent 工作流的重要组成部分。 

因此更合理的未来形态是：

Workflow 作为骨架，Agent 处理其中无法编码的局部不确定性。

⸻

“Skill 会替代独立应用”

Skill 适合：

* 专业知识和规则；
* 一组可复用步骤；
* 组织级输出规范；
* 跨项目的处理习惯；
* 需要与其他能力组合的任务。

独立应用仍然适合：

* 权威数据系统；
* 高频固定操作；
* 强事务一致性；
* 大规模结构化状态浏览；
* 不允许行为歧义的功能。

Skill 更可能替代的是大量“一次性小工具、胶水脚本、内部 SOP 页面和个人操作经验”，而不是银行核心系统、ERP 或数据库。

⸻

“Coworker 会替代 SaaS”

更可能发生的是重新分层：

1. SaaS 继续作为权威数据和事务系统；
2. Agent 成为这些系统的新型使用者；
3. Coworker/Workspace 成为跨 SaaS 的任务协调层；
4. Chat 和可视化界面成为人类监督层。

Google 已开始为 Workspace 提供 MCP、CLI 和 Agent 管控能力，这反映出软件正在同时为人类用户和 Agent 用户提供接口。 

所以 SaaS 不一定消失，但它的前端价值可能被部分削弱，后端数据、权限、规则和事务能力反而更加重要。

⸻

四、一些已经被削弱或推翻的观点

观点一：RAG 会成为长期核心壁垒

被部分推翻。

RAG 很重要，但“接一个向量数据库”正在成为基础设施能力，而不是充分壁垒。

真正难以复制的逐渐变成：

* 文档是否可信；
* 数据是否及时；
* 切分与权限是否正确；
* 何时应该检索；
* 如何验证答案；
* 检索结果如何参与行动；
* 失败案例如何回流。

RAG 没有消失，而是从产品主角退回到 Agent 的一个基础感知组件。

⸻

观点二：Prompt Engineering 是 Agent 应用的核心资产

明显被削弱。

Prompt 仍然重要，但已经很难单独构成系统能力。现在更重要的是：

* Harness；
* Workspace；
* Tool contract；
* Skill；
* 权限；
* 测试；
* 可观测性；
* 状态恢复；
* 版本和发布流程。

一个优秀 prompt 放在混乱工作空间里，往往不如普通 prompt 配合结构清晰、可测试的环境。

⸻

观点三：模型上下文越长，就越不需要 RAG、Skill 和记忆系统

基本被推翻。

更长上下文可以容纳更多信息，但不能自动解决：

* 什么信息应该加载；
* 信息是否过期；
* 文件之间的关系；
* 中间产物如何更新；
* 哪些内容具有权威性；
* 哪些经验应该长期保留；
* 如何避免不相关信息干扰。

“能装进去”不等于“能有效组织”。

⸻

观点四：自主程度越高，产品越先进

被推翻。

无限自主常常意味着：

* 成本不可控；
* 错误传播；
* 权限扩大；
* 难以理解过程；
* 无法确定完成标准；
* 长时漂移。

更成熟的 Agent 未必具有更高的无条件自主性，而可能具有：

* 更明确的边界；
* 更好的暂停和接管；
* 更小的权限范围；
* 更强的验证；
* 更少但更关键的确认点。

⸻

观点五：Multi-Agent 就是模拟一个数字化组织

正在被重新认识。

很多多 Agent 方案表面上模仿“经理、研究员、审查员”，但其真正技术价值往往不是角色扮演，而是：

* 隔离上下文；
* 并行探索；
* 分离不同权限；
* 为不同任务配置不同工具；
* 避免主会话被中间过程污染；
* 独立验证结果。

Claude Code 的 Subagent 也强调任务专门化和上下文管理。 

所以非共识判断是：

Multi-Agent 首先是一种上下文与执行隔离技术，其次才是组织模拟技术。

复杂数字组织未必比“一个主 Agent + 若干确定性工具 + 少数隔离子任务”更有效。

⸻

观点六：Coding Agent 只是程序员的垂直工具

已经被明显削弱。

Coding Agent 之所以领先，不只是因为模型会写代码，而是代码工作空间提供了一整套适合 Agent 的基础设施。

现在这种形态正在外溢到报告、数据、财务、法律、设计和运营等知识工作。OpenAI 自己披露，Codex 的非开发者用户占比正在增加，并被用于报告、表格、演示文稿、合同、研究、数据分析和轻量工具开发；这是厂商自报数据，但至少说明产品方向已经从“代码生成器”扩展为通用工作空间。 

⸻

五、未来可能出现的几种方向

方向一：应用变成“薄界面 + Agent Runtime”

未来很多应用可能只保留三类界面：

* 意图输入；
* 状态和产物展示；
* 权限、确认与纠错。

复杂执行被放到 Agent Runtime 中，包括：

* Workspace；
* Skill；
* Tool；
* Sandbox；
* Memory；
* Evaluator；
* Scheduler；
* Permission policy。

这与传统“前端—后端—数据库”结构不同，它增加了一层能够动态理解任务和操作其他系统的运行时。

⸻

方向二：工作空间成为新的中间件

过去中间件连接服务。

未来 Agent Workspace 可能连接：

* 人的目标；
* 模型；
* 文件；
* 数据库；
* SaaS；
* 执行环境；
* Skills；
* 历史任务；
* 验证器。

这可能比单个模型更具有长期粘性。

模型可以替换，但一个已经组织好的 Workspace 中包含：

* 企业规则；
* 项目结构；
* 工具；
* 权限；
* 历史产物；
* 成功经验；
* 测试标准。

迁移成本会非常高。

⸻

方向三：Chat 变成控制面，Artifact 变成事实面

现在很多系统仍以对话历史为中心。

但对话历史有几个问题：

* 难以结构化；
* 含有大量试探和错误；
* 不能直接作为权威状态；
* 很难被其他任务复用。

未来更合理的划分可能是：

* Chat： 协商、澄清、指导和解释；
* Artifact： 当前正式成果；
* Trace： Agent 实际做了什么；
* Workspace State： 项目当前真实状态；
* Memory/Skill： 经验证后可复用的经验。

换句话说：

对话不是数据库，对话也不应该成为应用唯一的状态载体。

⸻

方向四：Skill 会成为“可执行的组织知识”

传统组织知识通常存在于：

* 文档；
* SOP；
* 培训材料；
* 老员工经验；
* 脚本；
* 模板；
* 零散规则。

Skill 有机会把这些内容组合为：

说明 + 资源 + 代码 + 触发条件 + 输出标准 + 验证方法。

这比单纯知识库更接近真正的组织能力。

但最有价值的 Skill 很可能不会主要来自公共市场，而是来自组织内部的长期使用和修正。公开 Skill 解决通用问题；私有 Skill 承载组织真正特殊的做事方式。

⸻

方向五：Agent 会反向改变软件设计

今天的软件主要为人类设计：

* 菜单；
* 按钮；
* 页面；
* 表单。

当 Agent 成为重要用户，软件还需要提供：

* 稳定 API；
* 结构化语义；
* 明确权限；
* 幂等操作；
* 预览与撤销；
* 可机器理解的错误；
* Agent 专用视图；
* 可验证的操作结果。

因此未来可能同时存在两套界面：

Human UI：便于人观察、比较和纠错。
Agent Interface：便于模型发现能力、读取状态和安全执行。

这不是“没有 UI”，而是 UI 的用户从只有人类扩展为人类和 Agent。

六、几个值得保留的非共识判断

1. 最重要的壁垒可能不是模型，也不是数据，而是“高质量任务环境”

所谓高质量环境，包括：

* Agent 能看到什么；
* 能操作什么；
* 如何知道自己做对了；
* 失败后如何恢复；
* 哪些经验可以沉淀；
* 结果如何被人审查。

模型能力越接近，环境质量差异越容易成为结果差异。

⸻

2. 最优秀的 Agent 产品，表面上可能比普通 Agent 更“不自主”

它会主动限制自己：

* 不访问不需要的目录；
* 不调用无关工具；
* 不把每次经验自动写进 Skill；
* 不在缺乏验证时直接发布；
* 不为展示智能而制造复杂计划。

用户感受到的不是“Agent 想了很多”，而是“事情稳定地完成了”。

⸻

3. “Coworker”可能是一个容易产生误解的比喻

真实同事具备：

* 责任；
* 长期价值判断；
* 社会关系；
* 对组织后果的理解；
* 对模糊规范的持续学习。

当前 Agent 更像：

一个把意图编译成文件、动作和中间成果，并在规则约束下反复执行的智能运行时。

称为 Coworker 有助于产品传播，但在系统设计上，把它当成“同事”容易高估其责任能力；把它当成“可监督的执行系统”通常更准确。

⸻

4. 未来最重要的个人能力可能不是写 Prompt，而是“布置可执行环境”

即能够向 Agent 交代：

* 为什么做；
* 成功是什么；
* 有哪些输入；
* 哪些文件可信；
* 可以使用哪些工具；
* 哪些事情不能做；
* 怎样验证；
* 出错如何反馈。

这比一句漂亮的 prompt 更接近导演、产品经理和系统设计者的结合。

⸻

5. Agent 不一定减少软件数量，反而可能制造更多软件

因为当创建小工具的成本下降后，人和 Agent 会为大量局部需求生成：

* 临时脚本；
* 数据看板；
* 小型网页；
* 自动化流程；
* 领域 Skill；
* 项目专用工具。

减少的可能不是软件数量，而是：

人类必须亲手操作和理解每一个软件的必要性。

⸻

6. 真正的大变化不是“人少做多少工作”，而是“组织经验第一次能够被执行”

过去的知识管理系统只能保存知识。

Agent + Skill + Workspace 可能让知识变成可以运行的行为：

* 读取新案例；
* 按组织规则处理；
* 生成成果；
* 检查质量；
* 保存修正；
* 下次自动使用。

这可能比单次自动化节省多少小时更深远，因为它改变了组织能力积累和复制的方式。

⸻

七、一个更可能的未来结构

我倾向于把未来应用描述为六层，而不是“一个万能聊天框”：

人类意图与监督层
    ↓
项目 / 任务工作台
    ↓
Agent 编排与上下文管理
    ↓
Skills / Workflows / Policies
    ↓
Tools / APIs / Files / Applications
    ↓
Sandbox / Data / Systems of Record

其中：

* Chatbot 不会消失，它是意图入口和解释层；
* RAG 不会消失，它是知识感知层；
* Tool Use 不会消失，它是动作层；
* Workflow 不会消失，它是确定性骨架；
* Skill 是可复用经验层；
* Coworker 是把这些组件放入持续工作状态中的产品形态；
* Workspace、权限、验证和反馈循环，可能才是长期基础设施。

因此，这条趋势最核心的表达或许不是：

AI 从 Chatbot 进化成了 Coworker。

而是：

软件正在从“由人操作的功能集合”，变成“由人设定目标、由模型组织执行、由确定性系统约束、由工作产物验证”的混合工作系统。
