# Web Native Bulilder

从用户要完成的工作与已有能力出发，构建可运行的原生智能体 Web 应用。沿用技能名 `web-native-bulilder`；将运行时、业务能力、界面和交互职责分开设计，并只实现当前场景需要的部分。

## 1. 收拢场景和可复用能力

- 读取工作目录的项目约束、已有文件和未提交改动；保护用户提供的实现，在清楚的应用目录内新增必要文件。
- 提取目标用户、目标/输入、完成标准、交付对象、常见失败及可产生的业务影响。优先读取已有材料，只询问阻塞实现的缺口；对非关键未知采用明确的可替换假设继续工作。
- 盘点用户提供的 Skill、脚本、数据接口、模型端点、身份与 runtime。逐个区分“文档描述”“代码存在”“可在本环境调用”“已实际验证”。
- 阅读 [skill-adapters.md](references/skill-adapters.md)，把已有实现映射成能力契约。Skill 文档本身不等于 API；不要把整份文档放进提示词就宣称已集成，也不要让模型任意执行文档里的命令。
- 使用 [capability-contract.example.json](assets/capability-contract.example.json) 的字段建立最小能力表，按真实能力删改。优先连接现有 Agent runtime；已有平台能承担会话、工具与隔离时，不重造一套通用 runtime。
- 无法连接内网或模型时，实现清楚标记的替身与真实适配接口，用本地样例走通流程；保留待联调项，不编造成功数据或调用证据。

## 2. 设计任务与页面

先阅读 [interaction-patterns.md](references/interaction-patterns.md)，判断任务是条件较明确的 A、需要探索的 B，还是两者的组合。用 [interaction-brief.md](assets/interaction-brief.md) 记录必要的交互决策，再进入代码实现。

A/B 是分析视角，不是必须实现的两套固定页面。根据已有能力和用户判断成本决定当前页面，把长期可复用的路径与本次探索清楚区分。

- 把页面主体放在用户的任务和领域对象上：文档、数据集、分析结果、待执行动作或其他真实产物。让对话负责表达意图、补充和修订，不用聊天记录承担全部状态。
- 对 A，尝试先生成可核对的表单草稿，让人验证、选择候选和改写例外。建议可以是初始值、原因解释、变化监测或多个可比较候选。可用的历史记录、数据库和身份上下文应在当前用户的授权范围内参与推荐，并显示来源与适用时间；不要求人重填已可靠获取的条件。
- 对 B，围绕目标、探索动作、观察结果和下一步组织页面。记录反复出现的条件和步骤，寻找能被验证与复用的稳定路径；当路径足够清楚时可沉淀为 A 的候选流程。若这类 A 太多，B 可以承担统一意图入口与场景路由，让用户看到它选择了哪个任务及依据；A 遇到例外也可回到 B 探索。不要假定一次成功就已经得到稳定流程。
- 根据任务设计目标输入、必要的上下文选择、条件澄清、执行状态、证据、结果和下一步动作。简单单轮任务可以只保留“输入 → 结果”；开放多步骤任务才需要任务生命周期。
- 明确每个页面动作的对象、输入、后端行为、结果和失败恢复。为缺信息、空结果、执行失败、等待输入及完成状态给出实际可操作的界面。
- 对有副作用的业务操作按影响设置提案与执行边界；对本地可逆操作和已授权步骤直接推进。不要把人工审批当成所有任务的默认组成部分。
- 需要产物共编时，分开候选与当前版本，提供采纳、修订或丢弃。用户确认的结构化条件由服务端约束工具调用；改变范围需要明确的新用户输入或重新澄清。
- 需要组织上下文输入、执行反馈或报告阅读时，按 [composable-agent-ui.md](references/composable-agent-ui.md) 选择可组合的交互：可操作上下文、渐进展开的执行摘要、尊重回看的流式反馈及独立产物视图。明确每个组件的状态与业务责任，复用既有视觉系统。
- 选择排版、视觉层次与组件，使用户能看到当前对象、进展和下一步；兼顾窄屏、键盘与焦点。不要暴露与用户判断无关的工具 JSON、提示词或模型内部推理。

## 3. 选技术并完成一个纵向闭环

- 用户指定 Flask 或 FastAPI 时遵从指定。无偏好时：以同步表单/Jinja 与简单操作为主可选 Flask；异步端点和任务协作为主可选 FastAPI。复用现有团队能力优先于换框架。
- 默认使用 HTML/Jinja + 少量 CSS/JS；已有前端资产或复杂交互需要其他框架时再选择。应用运行不默认依赖 Node 构建、Docker 或额外消息系统。
- 阅读 [implementation.md](references/implementation.md) 与 [runtime-and-endpoints.md](references/runtime-and-endpoints.md)，完成“目标/输入 → 能力调用 → 可见结果/产物”的真实闭环，再扩充异常和修订路径。
- 有现成 runtime 时适配其任务、事件与产物；无现成 runtime 且确需多步 Agent 时，实现有预算的工具循环、参数校验和状态存储。固定流程不必伪装成动态 Agent。
- 将模型调用留在服务端，适配用户已提供的协议。缺省新端点可采用 Responses API；协议与模型可配置，不强制替换用户现有 Chat Completions 或专用 Agent 接口。
- 把精确计算、数据过滤、格式转换和写入交给确定性代码。把需判断的解释与提议单独呈现，关联来源与输入范围。
- 配置缺失时允许明确的演示路径；配置错误、模型拒绝、结构错误、超时和工具失败必须产生真实失败状态，不自动改成演示结果。
- 控制主任务、子任务和进程的寿命。页面刷新不得重新提交任务；取消须阻断迟到写入；重启须展示真实恢复状态。只读查询不强加完整版本系统，共编或外部写入则实现所需的一致性检查。

## 4. 验证并交付

使用 [acceptance.md](references/acceptance.md) 选择匹配风险的验证。运行已接入的真实脚本/函数路径，并用替身测试模型协议和异常；有授权且存在可用凭据时再测试真实端点。验证层级分别记录，不互相替代。

真实浏览器中完成一条主任务和一个关键失败/修订路径，检查桌面与窄屏、加载/空态/错误态和导出等实际操作。共享产物必须测试旧草稿、未保存编辑及保存期间继续输入；长期任务必须测试刷新、取消与重启。复杂应用可在独立上下文中验收，允许直接报告失败。

交付可运行工程、环境配置样例、启动方式、交互与能力映射、测试证据和明确的待联调项。演示数据与真实数据分清。若用户要求评估效果，记录完成时间、核对/纠错时间、模型成本及失败恢复，避免凭界面外观宣称效率提升。
