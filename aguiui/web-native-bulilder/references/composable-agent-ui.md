# 可组合的 Agent UI：从 Astryx 样例提炼

## 使用范围与来源

用于选择输入、执行反馈、产物布局及组件行为；按任务采用，不强制引入 Astryx、React 或 StyleX。Flask/Jinja 与 FastAPI 的 HTML/CSS/JS 也可表达这些交互。以下是对用户提供 `astryx.zip` 中源码的观察与设计推导，不代表完整项目或真实服务已经通过验证。

| 所见材料 | 可借鉴的设计 | 需要应用补齐的部分 |
| --- | --- | --- |
| `Chat/ChatComposer*.tsx`、`useChatPasteAsToken.ts` | 输入区可组合；上下文折叠；标签与实际序列化值区分 | 对象解析、资源权限、持久化与提交契约 |
| `Chat/useChatStreamScroll.ts`、`useChatNewMessages.ts` | 跟随与回看分开；新消息提示；减少动画 | 应用滚动容器、跨任务恢复与用户操作验证 |
| `Chat/ChatToolCalls.tsx` | 单项内联、多项摘要、按需展开结果 | 真实运行事件映射、失败恢复与业务可读描述 |
| `page/page.tsx` | 产物卡进入桌面分栏或窄容器全屏视图；可调面板 | 保存、版本、继续执行等实际业务行为 |
| `src/neutralTheme.ts`、组件 `.spec.md` 与 `.test.tsx` | 语义样式变量与行为约束分别管理 | 本应用的主题、测试与可访问性验收 |

样例 `page.tsx` 的提交和部分版本操作是空回调；版本标签与布局不证明持久协作已完成。材料中的部分组件契约标为 draft；将其作为设计线索，逐项核对实际代码与本应用行为。分析文档中的热度、法规、技术趋势等结论不作为选型依据。

## 1. 把上下文作为用户能控制的对象

- 对 A，把当前记录、历史值、组织规则及所选推荐呈现为有来源的条件或对象；区分用户已确认、模型建议、仍需补齐的内容。查看、替换或删除上下文后，让建议显示是否需要重算。
- 对 B，允许以文件、数据集、记录或能力选择补充目标。对象标签帮助用户理解引用了什么；执行依赖真实资源 ID、版本和服务端权限，不能从显示名称或 `@工具` 文本直接取得授权。
- 长粘贴可折叠成摘要或上下文卡，保留查看、编辑、移除和恢复全文的路径；摘要标签不能替代原内容。字符阈值按场景决定，不固定复刻样例值。
- 可先用 textarea 加上下文列表。只有确需行内对象混排时再做富输入，并验证复制粘贴、删除、撤销、光标、序列化和中文输入；折叠文字不等于减少模型输入成本。

## 2. 让输入区保持清楚的提交边界

按任务组合目标输入、上下文、少量模式选择和提交动作。常用内容直接可见，附件与低频配置可进抽屉；折叠后保留摘要，错误与缺少必需上下文不能被藏住。模式名称应说明不同的结果或影响，避免仅换标签却没有对应行为。

生成建议、采纳字段、执行查询、保存产物及停止任务是不同动作。展示当前是否在运行，但不要把 Spinner 当成取消或完成证明；失败后保留用户输入与可复用上下文。

为 Enter、换行和中文 IME 确认输入建立一致规则；组合输入期间 Enter 不提交。选择一个主要滚动区域，按现有页面采用底部停靠或常规表单布局，给输入区留空间，避免覆盖结果。无需对所有 A 页面使用聊天式底部输入。

## 3. 尊重阅读，不让流式内容抢走位置

在用户跟随最新输出时继续跟随；用户向上回看后暂停自动跟随，显示“有新内容/回到最新”。只有用户回到底部或主动操作时恢复。区分首次加载定位、内容增长和任务切换；消息与产物区域各自保留合理位置。

不因每个 token、轮询或图片延迟加载强制滚到底部。减少动画偏好下保留功能并弱化动画。滚动和焦点是交互状态，不应被模型输出或刷新任意重置。

## 4. 用摘要解释执行，用细节支持核对

将后端事件适配成应用可读的动作：对象、实际状态、结果摘要、必要证据及可恢复错误。单次动作可以内联；多步调查可以分组，默认展示阶段摘要，按需查看工具参数、证据或差异。不是所有协议都直接提供同一种消息数组，也不能把组件默认 complete 当真实完成状态。

分组有部分失败时，总摘要要显示失败或限制，不能被成功项数量掩盖。区分等待、执行、工具结果已到、模型仍在整理和业务结果已完成；状态来自实际 runtime。不要为了展示细节公开凭据、完整原始日志或内部思维链。

对 A，可把多个字段建议按业务含义分组，突出变化与理由；对 B，摘要帮助看清有效路径及失败例外。后续沉淀为 A 时保留经验证的输入、输出和边界，而非照抄整段对话。

## 5. 让产物拥有独立、连续的阅读空间

按场景使用“结果卡 → 详细面板”：桌面可并排比较对话/条件与报告，窄容器可转为全屏视图。布局判断看可用容器，而非只看屏幕；视觉与打开行为使用同一判断，避免嵌入业务页面后两者冲突。

切换视图保留当前对象、草稿和阅读位置；关闭对话框后返回原触发处，键盘能进入和退出。可调宽度只有在比较任务受益时才采用，设置边界并提供键盘路径；保存面板宽度不等于保存产物内容。候选、已保存版本与人工编辑仍按业务版本契约处理。

## 6. 将行为、视觉和能力分别约定

先明确组件的对象、输入/输出、拥有的状态、受控或内部状态、失败与焦点行为，再用语义样式变量处理表面、文本、强调、错误、间距、密度和动效。复用已有设计系统；不要把示例字体、色值、动画或某个主题当通用最优解。

视觉摘要可由应用组合，但展开控件的可访问名称、键盘行为和展开状态仍有明确责任方。把依赖业务的判断留在应用层，把可复用行为留在组件层。根据实际复杂度保留少量组件说明与对应验证，不照搬样例的整个文档治理体系。

判断采用收益时比较完整任务成本：上下文卡是否方便核对，折叠是否藏住错误，分栏是否促进比较，动画是否干扰阅读。简单 A 可保留候选表单；复杂 B 再组合输入、执行摘要和产物视图。
