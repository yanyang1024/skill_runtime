## 2. P0：三个字段级机制

### P0-1 噪声地板 δ —— "涨 2/51 题"到底是不是提升

**理念**：RRSI 在进化开始前，先用**未改动的基础 harness 重复评测**估出经验噪声带 δ；此后任何候选若 ΔS 未超过 δ，不判为提升。它还引用 Dwork et al. 2015（自适应数据分析）：反复用同一批题做采用决策，本身就是自适应过拟合——即便题没有泄漏给生成侧。

**为什么对你重要**：你的 bench_v2 是 51 题、trials=1。±1 题就是 ±2pp，模型采样抖动就能制造这个幅度假象。你已有原则"样本数不能单独判显著"，δ 是它的可操作形态。

**最小改动**（落在 `compare_change.py`）：

```python
# 一次性标定：同题同环境对 H_0 跑 N=5 次（或沿用历史重复运行）
# noise_floor = max(|run_i.pass_rate - run_j.pass_rate|) 取各题不一致率的某种包络
def verdict(before, after, noise_floor):
    d = after.pass_rate - before.pass_rate
    if after.regression_cases:        return "REJECT_or_fix_first"   # 沿用 0921
    if abs(d) <= noise_floor:         return "WITHIN_NOISE"          # 新增：不算提升也不算退步
    ...
```

汇报口径随之升级为："本次改动通过率 +Xpp，**噪声地板 ±δpp**（同条件重复运行实测），结论：超出/未超出噪声"。这和 v1.3 里"不设没有基线的警戒线"是同一纪律——δ 就是这条警戒线，只是先测出来再使用。

### P0-2 被证伪假设不再重复提出（tried set）

**理念**：RRSI 给每一次编辑记录 component/hypothesis/diff/分数变化/verdict 的 JSONL 历史，并让提案方**条件于全部历史**——已被否证的机制作为负证据保留，提案方不得重画。动机很朴素：每次评测都是对同一有限题集的一次自适应窥视，重复测试已证伪的假设是纯浪费。

**你的对应物**：`change_record` 已有改动-结果记录；`review_prompt.md` 已要求 AI"给观察、假设、替代解释、依据、适用范围、验证办法"。缺的一环是**被拒改动的假设没有回流到复盘提示里**——同一个失败方向（比如"给 bash 工具加超时提示"被证伪后）下个月可能被换个措辞再提一次。

**最小改动**：

```text
# review_prompt.md 增加一节
## 已被证伪的方向（不要再提议，除非有新证据）
- {change_id}: {hypothesis 一句话} → 验证结果 {verdict}，{日期}
# 由 change_record 中 verdict=REJECT 的记录自动生成这份清单
```

成本：一个把 change_record 过滤拼接进提示词的几十行脚本。收益：复盘质量随轮次累积而非原地打转——这正是 RRSI 说的"credit assignment over the full evolution history"。

### P0-3 泄漏筛查（critic-before-eval）

**理念**：RRSI 在候选**进入评测之前**先过 critic：凡是编码了任务名、实体名、题目特定值、答案的改动直接拒绝。筛泄漏要放在评测前，因为泄漏候选一旦拿到虚高的进化集分数，就会成为后续轮次的吸引子。

**你的对应物**：你已有"反复调提示的题归回归集、评测保留家族不进训练"的隔离原则——那是**题集侧**的隔离。critic 是**改动侧**的对偶：防止改动本身把题"背"下来（例如 prompt 里写死"遇到 fabagent_bench 类请求就……"）。

**最小改动**：change_record 提交时跑一条规则——改动 diff 中若出现 bench 题的题面关键词/case_id/golden 片段，标记 `leak_suspect=true`，人工复核后才许进评测。几行正则，但守住的是"bench 数字还能向领导自证"的底线。

## 3. P1：两条规则升级

### P1-1 成本偿付规则：ΔC ≤ β0 + β1·ΔS

0921 你把 SICA 的效用函数改成了硬规则"涨分但贵 30% 以上挂起"。RRSI 的版本是它的参数化升级：**新增成本必须由实测增益偿付**——ΔS>δ 的候选要求 ΔC ≤ β0 + β1·ΔS（β0 是微量增益容忍的成本上浮，β1 是增益越大允许的成本斜率）。保留你的硬规则形态，只需把"30%"换成两个数，并给每次 ADOPT 记录一个**偿付比**（ΔC/ΔS）。

汇报价值：RRSI 实测未加成本约束的进化最终 harness 贵 58% 且 OOD 更差（3.80M vs 2.42M tokens/trial）。你可以对领导说："我们对每次改动执行分数-成本偿付检查，防止平台越改越贵——这是 Google 该方法实证过的主要失败模式。"这直接呼应你的 ⚠️ 风险项（单任务 token 228万→722万 上升待归因）：**改动级成本门控**是"变贵"假设的微观检验工具之一。

### P1-2 组件剪枝：长期无贡献的 harness 组件要退役

**理念**：RRSI 的 Lasso 式剪枝——追踪每个组件在近期窗口内是否产生过正增益，持续无产出的组件被列为删除目标。最终 harness 是三者中最精简的（26.3 steps/trial vs 其他 27.3–34.6）。

**映射到你的场景时要小心一个你已踩过的坑**：0911 修正指出"92% load>0 但 invoke=0"不能读作沉默供给——很多 Skill 通过加载指令参与任务，本无独立 invoke 事件。所以剪枝的输入**不是** invoke 计数，而是 change_record 层面的归因：某 Skill 小节/工具说明在近 M 轮评测中与任何通过/退步无关联 → 进退役候选队列 → 人工确认。这和你已有的记忆治理记录（candidate→evaluated→active/retired）是同一形态，只是方向是"退"。

## 4. P1 续：改进对象清单补第四层——上下文管理

**理念（Weng）**：harness 优化的对象有一条递进链：**指令 prompt → 结构化 context → 工作流 → harness 代码 → optimizer 代码**。你 0921 定的候选池是"Agent 提示 + Skill 小节 + 工具行为"三处轮换——对照递进链，缺的恰是第二层 **context 管理**。

**为什么这一层对你不是学术细节而是头号实务问题**：
- 911 实测：长上下文 token 占比 66–93%，I/O 比普遍偏高（读多写少）；
- tasktarget ⚠️：单任务 token 中位 139 万、月度趋势 228万→722万，"知识库未命中/重复注入"是待归因假设之一；
- 0921 P3 你已记下 SICA 的"子 Agent 返回后上下文只留摘要"。

Weng 的清单给了你合法性和词汇：把**上下文压缩/摘要注入策略**列为与 prompt/Skill/工具平等的第四类改动对象。具体候选（都可用你现有的同题对照框架验证）：
1. 长会话的**产物摘要缓存**（911 已建议）：同会话内反复重读同一文件时注入摘要而非全文——用"会话内路径重读"信号定位候选场景；
2. **子 Agent 摘要回传**（0921 P3）的实测确认：抽长会话看子 agent 上下文是否累积膨胀；
3. 验证时沿用同题对照：摘要版 vs 全文版，看通过率是否保真、token 降多少——这正是你 v1.3 里"抽长输入的同题对照，看摘要/引用优化是否仍保真"的既有计划。

这一层还有一个汇报红利：token 趋势从"需要解释的风险"变成"正在治理的对象"——"我们已把上下文管理列为与提示词平等的优化对象，首批对照实验显示……"。

## 6. 新增减法项（0921 清单的补充）

| 不做 | 为什么 | 替代 |
|---|---|---|
| ❌ RRSI 全套技术栈（Vertex/Opus 4.8/三个商业 benchmark 接入） | 依赖重、与你的 opencode 平台不兼容 | 只拿机制（δ、tried set、critic、偿付规则、剪枝），不拿栈 |
| ❌ RRSI 的正则超参全套标定（δ bootstrap、β0/β1、bmin/bmax 退火） | 你的改动频率是"每周几处"不是"每天数百候选"，标定成本超过收益 | δ 用最简单的重复运行包络；β0/β1 拍一个保守固定值写进口径说明 |
| ❌ 退火编辑预算（早期 bundle 多处改动） | 你 0921 的"一次一处"在小规模下就是最优退火 | 维持现状 |
| ❌ Weng 列的进化搜索全家桶（AlphaEvolve/GEPA/MCTS 工作流搜索） | 种群规模和评测预算都不支撑 | 维持"候选队列 + 人工切准" |
| ❌ "regularized self-improvement"话术 | 对领导无意义，且容易被追问超参细节 | 话术见下节 |

## 7. 向上汇报话术（0924 版）

> "我们跟踪了自我改进 Agent 方向的四项代表性工作，包括 Google 本月发表的 RRSI。关键事实是：**在评测集上反复进化的 harness 会过拟合评测集**——Google 实测四个同类方法在未见任务上的增益全部缩水或倒退，而最早的可行性演示（SICA）今年被攻破：它改进出来的代码不经审核直接运行、评分档案可被篡改。
>
> 我们的平台改进循环在设计时已避开这些陷阱：改动一次一处、人工确认、回归集与保留家族隔离、成本涨幅必须被通过率增益偿付、涨幅小于实测噪声不算提升。每次平台改进都有'通过/退步/成本/噪声地板'四个数字背书。
>
> 下一阶段我们把**上下文管理**列为与提示词平等的第四类优化对象，针对的是单任务 token 上升趋势；被证伪的改动方向进入负例库，不再重复提议。"
