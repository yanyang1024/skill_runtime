Agent 化改造实战：
把理论变成能开工的三条路径

原理大家都懂了——接口决定模型能发挥多少能力。但回到工位，面对一堆传统 API、CLI 脚本和 WebUI 老系统，第一步到底怎么走？这份讲义把三个典型改造场景拆成可操作的方法论、清单和样例。

基于《agent化改造场景方法论.md》重组 · 2026-08

场景 ① 传统 API 改造不破坏老消费者的前提下，让 API 更适合 Agent 工作流——核心动作是"加一层 Façade"。
场景 ② 融入 Skill 与 Agent工具正确只是第一层；还要教模型"怎么用"（Skill）、管住"边界"（Harness）。
场景 ③ WebUI 转型拒绝模拟点击，把业务能力接口化（MCP），把操作流程 SOP 化（Skill）。
开场

三个场景，一张共同的地图

三个场景看似不同，其实共享同一个底层原则和同一个判断框架。先掌握它们，后面每个场景只是套用。

共同原则：加一层，而不是改一层

老消费者前端、脚本、合作方——一切照旧
Agent（新消费者）走新增的 Agent Façade / MCP 层
↓ 各走各路 ↓
同一套业务核心（不改）逻辑、数据、权限体系复用——改的是"怎么暴露"，不是"业务本身"
🏢
打个比方老楼加装电梯：住户（老消费者）照常走楼梯，新电梯（Façade 层）贴着外墙建，楼的承重结构（业务核心）一根钢筋都不动。凡是需要拆承重墙才能装的电梯，方案本身就是错的。

共同框架：三层包装

无论改造什么，最终都要回答三层问题——很多团队只做第一层，然后奇怪"为什么 Agent 还是用不好"：

第 1 层 · 工具本身单次调用正确、错误可恢复、输出双视图
→
第 2 层 · 组合方式Skill：什么时候用、按什么顺序、失败怎么办
→
第 3 层 · 运行约束Harness/Policy：谁能调、要不要审批、状态怎么存
🧭
阅读路线场景① 主要讲第 1 层怎么改；场景② 讲第 1 层之后的三层怎么配齐；场景③ 讲整套方法如何落到一个存量 WebUI 系统上。可以按顺序读，也可以直接跳到你手头的场景。
场景 ①

传统 API 梳理 / 改造方法论

💣
先排掉最大的雷老接口已经有真实消费者（前端、脚本、合作方）。直接改返回格式让 Agent 更好用 = 生产事故。所以第一原则：老接口一个字不动，新增 Agent-facing Façade 层，两边复用同一业务核心。

方法论总览：四步走

① 盘点分级API 清单 + 风险/语义双轴分级
→
② 差距评估Agent-Ready 清单逐项打分
→
③ Façade 改造按性价比做五个动作
→
④ 度量验收四个指标对比改造前后

第 1 步：盘点与分级

把 API 拉成一张清单，按两个轴分级，决定改造顺序：

维度分级改造优先级
读写风险只读 / 可逆写 / 不可逆写（付款、删除、外发）只读先行；不可逆写最后做，且必须带审批
语义密度一目了然（get_user）/ 需要领域知识（settle_acct_v2）语义越模糊，越需要重命名 + 补描述

产出物：一张 API 清单，每行标注 风险级 / 语义级 / 是否高频 / 返回体大小。

第 2 步：Agent-Ready 差距评估清单

对每个候选接口逐项过一遍，打分排序：

  • 名字能区分吗？query_order 和 query_order_detail 同时存在时，模型选错的概率有多大？
  • 参数自解释吗？type=3 还是 type="refund"？枚举值写全了吗？
  • 错误可恢复吗？失败时返回 500 还是 {error_type, field, expected, retryable}？
  • 返回体能进上下文吗？一次调用吐 200KB JSON？需要 summary + 分页 + handle。
  • 有幂等键吗？模型重试时会不会重复下单？
  • 粒度合适吗？完成"查用户最近订单并判断是否超时"要调 5 次接口？该聚合了。

第 3 步：五个改造动作（按性价比排序）

动作 1 · 错误结构化 —— 性价比最高，一天能做

❌ 改造前

{
  "code": 500,
  "msg": "error"
}

模型只能瞎猜：改参数？重试？放弃？

✅ 改造后：可自我恢复

{
  "error_type": "invalid_argument",
  "field": "start_date",
  "expected": "YYYY-MM-DD...",
  "received": "2026/08/08",
  "retryable": true
}

错误分五类分别对待：参数可修复（告诉怎么改）/ 临时错误（有限重试）/ 权限不足（请求授权）/ 状态失效（重建 handle）/ 永久失败（停止并说明原因）。

动作 2 · 输出双视图

summary:    "共 47 条订单，其中 3 条已超时，最早超时单 #A1023"  # 给模型快速判断
structured: { overdue: [...], total: 47 }            # 给程序组合消费
resources:  { list_cursor: "cur_8x2", full_export: "file_91m" } # 大对象不进上下文
evidence:   { source: "orders_db", as_of: "2026-08-09T13:00Z" } # 供验证
control:    { status: "completed", retryable: false }

动作 3 · 粗粒度聚合接口

把"要调 5 次才能完成"的常见任务合成 1 个 Façade 接口。判断标准（来自 Programmatic Tool Calling 原则）：

步骤之间只需要结构化字段传递，不需要新的语义判断？
是 → 聚合合成一个接口批量、过滤、Join、汇总——确定性逻辑收进服务端，模型一次调用拿结果。
否 → 保持分开留给模型逐步调每一步结果会改变下一步方向，拆开让模型逐步判断。

动作 4 · 幂等与副作用声明

写接口接受 idempotency_key，模型重试不会重复下单；Schema 里声明 side_effect: "creates_record" / "sends_email" / "charges_money"，让 Harness 能自动识别哪些调用需要审批。

动作 5 · 大返回体资源化

列表接口默认返回 summary + cursor；原始数据通过 resource handle 按需拉取。模型上下文里只放"当前工作集"。

样例：订单系统四周改造路线

阶段动作Agent 体验变化
第 1 周只读接口错误结构化 + 语义化命名模型选错工具、瞎猜重试基本消失
第 2 周高频场景聚合接口（order_health_check）单次任务调用数 7 → 2，Token 降 60%
第 3 周大列表接口 cursor 化 + 双视图长任务不再爆上下文
第 4 周写接口幂等键 + 审批点接入低风险写操作开放给 Agent

第 4 步：度量——别凭感觉

任务完成率同一评测集改造前后对比
平均工具调用数聚合是否生效
无效重试率错误结构化是否生效
总 Token 消耗双视图/资源化是否生效
📋
评测纪律评测时记录完整 Harness 配置（模型快照、工具列表、Schema 版本、reasoning 设置），否则指标变化无法归因——到底是接口改好了，还是模型换了？
📌
一句话记住场景①老接口不动，加 Façade；先做错误结构化和语义命名（性价比最高），再聚合、资源化、幂等化；一切用四个指标验收。
场景 ②

API / 工具融入 Skill 与 Agent

👷
打个比方给新员工一台精密机床（工具正确），但不给操作手册（Skill），也不告诉安全规程（Harness）——然后他出了次品，你奇怪"机器明明没问题"。Agent 用不好你的 API，往往缺的不是工具，是怎么用的知识和边界。

2.1 stdin / stdout：人与 AI 的读取差异

接入现有 CLI / 脚本时最容易翻车的地方：同一份输出，人和 AI 的需求几乎相反。

设计点人类偏好AI（Agent）需要
格式对齐表格、颜色高亮、进度条稳定 JSON / 结构化文本，禁止 ANSI 转义码
信息流向全混在终端数据走 stdout，诊断走 stderr，退出码语义化
交互交互式确认 Are you sure? (y/n)默认非交互；确认走显式参数 --yes 或审批层
截断"显示前 20 行..."明确告知总量与游标：total: 1240, cursor: "..."
时间/数字本地化格式（"3 天前"）ISO 8601、Unix 时间戳、无千分位
空结果"No results"结构化空 {"items": [], "total": 0}，并区分"无数据"与"查询失败"

🛠️ 实操做法

  • 自己的 CLI：加 --json 机器视图，保留默认人类视图，Agent 侧只消费 --json；
  • 没有源码的第三方 CLI：包一层 wrapper 把人类输出解析成结构化输出——但优先找官方 API，解析人类输出是下策（格式一变就挂）。

2.2 持久化：接入前必答的四个问题

① 状态存哪？

会话状态（本次任务）→ Run/Task State；长期事实 → Durable Memory（经验证才写入）。别把中间推理当长期记忆。

② handle 谁负责？

Stateful Tool 返回的 handle 要明确 TTL、失效信号（error_type: "handle_expired"）和重建方式。

③ 重试会不会重复？

所有写操作配幂等键；长任务提供 checkpoint，崩溃后从检查点恢复，而不是从头再来。

④ 产物归谁？

Agent 生成的文件/报告登记为 Artifact（ID、版本、所有者），后续任务按 ID 引用，而不是重新生成。

2.3 Skill 化：把"老师傅经验"打包

当一个任务需要多个工具 + 判断规则 + 兜底策略时，就该写成 Skill，而不是指望模型现场发挥：

# 示例：invoice-reconciliation/SKILL.yaml（示意）
trigger:  用户要求对账、核销发票、检查票账一致
boundary: 只读操作；发现差异时生成报告，不自动调账
steps:
  1. 用 query_invoices 拉取周期内发票（summary 视图）
  2. 用 query_payments 拉取回款记录
  3. 程序化 Join 比对 （确定性规则，不进模型上下文）
  4. 差异 < 5 条 → 模型逐条语义判断；≥ 5 条 → 生成差异报告 Artifact
fallback:  handle_expired → 重建后继续；权限不足 → 停止并申请授权
acceptance: 输出差异清单 + 每条差异的证据链（evidence 视图）
⚠️
两个容易漏的点① 渐进加载：先暴露 Skill 名称+描述，命中场景再加载全文（与 Tool Search 同理），别把几十份 SOP 全塞进系统提示。② 写清停止条件——没有明确停止条件的 Skill，是 Agent 无限循环的头号来源。
📌
一句话记住场景②三层包装缺一不可：工具做正确（错误可恢复、双视图）、Skill 教用法（步骤+边界+停止条件）、Harness 管约束（审批、重试上限、状态存储）；CLI 接入记住"人机分流"——--json 给 AI，表格高亮给人。
场景 ③

WebUI 应用 → Agent 对话式应用

🕳️
最大的坑：模拟点击"让 Agent 操作浏览器点按钮"看起来最快，但它脆弱（UI 改版即挂）、慢、无幂等、难审计。只能作为没有 API 时的临时过渡，绝不能作为主路径。正确方向是把 UI 背后的业务能力接口化。

目标架构：同一能力层的两个消费者

🖥️ WebUI（给人用）表单、按钮、可视化——保留
🤖 MCP Tools（给 Agent 用）结构化调用、双视图、幂等
↓ 两个消费者，同一层能力 ↓
业务能力层 → 数据 / 服务UI 背后的业务动作才是资产，页面只是它的一种投影

四步迁移法

① 能力提取页面 → 业务动作 → Tool
→
② Tool Search 组织按用户意图分 namespace
→
③ SOP Skill 化多工具场景写成流程
→
④ 人机分工重新设计各自角色

第 1 步：能力提取（从页面到工具）

把每个核心页面倒推："这个页面到底在做什么业务动作？"以报销系统为例：

WebUI 页面用户实际操作提取为 MCP Tool
报销列表页按状态筛选、看金额汇总query_expenses(status, period) → 双视图输出
报销填写页填表单、传发票、提交submit_expense(items[], attachments[]) → 幂等键 + 审批
制度查询页搜索差旅标准search_policy(keyword) → summary + evidence
✂️
粒度判断一个页面可能拆成多个 Tool（查询和提交必须分开），也可能多个页面聚合成一个 Tool（向导式五步表单 → 一个结构化提交接口）。标准还是那个：步骤间是否需要新的语义判断。

第 2 步：Tool Search 组织

工具超过 15 个后，按用户意图划 namespace，而不是按后端服务：

namespace: expense   — 报销相关（query / submit / cancel），高频
namespace: policy    — 制度查询（只读，直接加载）
namespace: approval  — 审批流（低频 + 高风险，defer_loading）

高频只读工具直接加载；写操作和低频工具 defer_loading，模型需要时才加载完整 Schema——既省 Token，又减少误选。

第 3 步：场景 SOP → Skill 化

📋 样例：差旅报销 SOP

查行程calendar tool
→
匹配制度policy tool
→
生成草稿expense tool
→
用户确认审批点
→
提交幂等键
→
返回 Artifact单号+凭证

触发："帮我报销上周上海出差"。边界：单笔 > 5000 元必须人工审批；缺发票时停止并列出缺失项，而不是编造或跳过。

第 4 步：人机分工重新设计

WebUI 不会消失，它的角色变了：

角色Agent 对话式WebUI
信息收集、草拟、批量处理✅ 主力辅助
高风险确认、审批签字发起请求✅ 审批界面（保留）
复杂数据可视化浏览摘要 + 引用✅ 主力
审计追溯写 Trace✅ 查询入口

分阶段上线：风险控制

阶段 1 · 只读助手查询/汇总/解释，出错成本≈0，快速验证工具设计
阶段 2 · 草稿模式Agent 生成草稿，人确认后提交——跑通审批点
阶段 3 · 低风险直写可逆、有幂等保障的写操作（改备注、加标签）
阶段 4 · 高风险开放付款/删除/外发——强制审批 + 完整审计 Trace

每个阶段用场景①的四个指标（完成率、调用数、无效重试率、Token）验收，达标再进下一阶段。

📌
一句话记住场景③拒绝模拟点击，提取业务能力 MCP 化；工具按意图组织、按需加载；多工具场景写成 Skill；UI 退到"审批 + 可视化 + 审计"；上线走只读 → 草稿 → 低风险写 → 高风险审批四阶段。
✅

学完了吗？六道题自测一下

先自己作答，再点开看答案。

改造传统 API 给 Agent 用时，为什么不能直接改老接口的返回格式？
答：老接口已有真实消费者（前端、脚本、合作方），直接改 = 生产事故。正确做法是新增 Agent-facing Façade 层，与老接口复用同一业务核心——"加一层，不改一层"，像老楼贴外墙加装电梯，不动承重结构。
五个改造动作里，哪个性价比最高、应该最先做？
答：错误结构化。把 500/"error" 换成 {error_type, field, expected, received, retryable}，一天能做，模型立刻从"瞎猜重试"变成"自我恢复"。其次是语义化命名与描述。
接 CLI 工具给 Agent 用，stdout/stderr 应该怎么设计？
答：数据走 stdout（稳定 JSON，加 --json 机器视图），诊断信息走 stderr，退出码语义化；默认非交互（确认走 --yes 参数或审批层）；截断必须带 total 和 cursor；时间用 ISO 8601；空结果返回结构化空并区分"无数据"与"查询失败"。
一个工具接入 Agent 前，持久化方面必须回答哪四个问题？
答：① 状态存哪（会话态 → Task State，长期事实 → 验证后入 Durable Memory）；② handle 谁负责（TTL、失效信号、重建方式）；③ 重试是否安全（写操作幂等键、长任务 checkpoint）；④ 产物归谁（登记为 Artifact，按 ID 引用）。
WebUI 转 Agent 应用，为什么"模拟点击"是错误主路径？
答：四个硬伤：脆弱（UI 改版即挂）、慢（整页渲染与等待）、无幂等（重复点击 = 重复提交）、难审计（动作不可追溯）。正确路径是把 UI 背后的业务能力接口化为 MCP Tools，WebUI 与 Agent 做同一能力层的两个消费者。
分阶段上线的四个阶段是什么？为什么是这个顺序？
答：只读助手 → 草稿模式 → 低风险直写 → 高风险开放。顺序按"出错成本"递增：先用只读场景零风险验证工具设计，再通过草稿模式跑通审批链路，然后放开可逆、有幂等保障的写操作，最后才在强制审批+完整审计下开放付款/删除/外发。

📄 一页纸总结

  1. 共同原则：加一层，不改一层。老消费者与 Agent 各走各的入口，复用同一业务核心。
  2. 共同框架：三层包装——工具做正确 → Skill 教用法 → Harness 管边界。只做第一层是"Agent 用不好"的头号原因。
  3. 场景① 传统 API：盘点分级（读写风险 × 语义密度）→ Agent-Ready 清单 → 五动作（错误结构化 → 双视图 → 聚合 → 幂等 → 资源化）→ 四指标验收。
  4. 场景② 融入 Agent：CLI 人机分流（--json + stdout/stderr 分离 + 非交互默认）；持久化四问；Skill 写清触发、边界、停止条件，渐进加载。
  5. 场景③ WebUI 转型：拒绝模拟点击；能力提取 MCP 化 → 意图导向 Tool Search → 场景 SOP Skill 化 → 人机分工（UI 管审批/可视化/审计）。
  6. 上线节奏：只读 → 草稿 → 低风险写 → 高风险审批，每阶段用完成率/调用数/重试率/Token 验收。
Agent 化改造的本质，不是让 AI 去适应为人设计的系统，而是把系统的业务能力，用 AI 能消费的方式重新暴露一次。
