从 Chat API 到 Agent Runtime：
大模型接口如何解锁模型的隐藏能力

同一个模型，不换权重、不重新训练，只改接口与状态管理方式，基准得分翻了近三倍。这份讲义带你搞懂：接口到底改了什么，为什么会有效，以及你该怎么用。

原文档日期：2026-08-08 ｜ 范围：推理接口 · Tool 接口 · MCP · Skill · A2A · Policy/Memory Plane

13.3% ➜ 38.3%

ARC-AGI-3 公开集上，同一个 GPT-5.6 Sol 的得分变化。没有重新训练，只是换了 Harness（保留推理状态 + 压缩上下文）。同时输出 Token 降到原来的约 1/6。
这就是本讲义要解释的"魔法"——而它其实完全是工程。

开场

先建立一个直觉：模型 ≠ 你观察到的能力

🧑‍🍳
打个比方（全讲义最重要的一个类比） 把大模型想象成一位厨艺精湛的厨师。Chat API 相当于你每道菜都站在厨房门口口头点单：厨师做完一道，你把盘子端走，下次再来时他已经忘了刚才做过什么、尝出什么味道。而 Agent Runtime 相当于给厨师一间自己的厨房：有记事本（推理状态）、有冰箱和储物架（上下文管理）、有顺手的工具架（Tools）、还有食品安全规范（Policy）。
厨师还是同一个厨师，但你吃到的菜完全不是一个水平。

传统 Chat API 暴露的是模型的「说话能力」；下一代 Agent API 进一步暴露的是：

  • 在多轮、多次工具调用之间保持推理连续性；
  • 上下文增长后压缩而不是简单截断历史；
  • 按需发现并调用 Tool；
  • 把可确定的工具循环交给程序执行；
  • 以 Task、Event、Artifact、Checkpoint 表达长程工作；
  • 在授权、审计、租户隔离和持久记忆的约束下完成任务。

所以，你在生产环境里实际看到的能力，是一个多变量函数：

Observed Capability = F( Model, Inference API, Reasoning State, Context Policy, Tools, Harness )

模型权重只是六个变量之一。其余五个全是接口与工程——这就是"不换模型也能变强"的数学表达。

🧭
本讲义的学习路线 我们先看清现状（第 1~3 章：推理接口 → 工具接口 → 协议层），再用 ARC-AGI-3 案例亲眼验证"接口改变能力"（第 4 章），然后收走可以直接抄的实战 Tricks（第 5 章），最后展望未来（第 6 章）。建议按顺序读，每章末尾都有"一句话记住"。
第 1 章

推理接口的四次进化

大模型推理接口沿着一条主线演化：从"一次性问答"走向"持续工作的运行时"。先看全景时间轴，再逐个拆解。

第一代
Chat / Message API messages 进，message 出。简单、兼容好，但推理状态随响应一起被丢弃。
第二代
Responses-like API 把一次运行拆成可组合的 Item，状态可以跨回合保留与回放。
第三条轴
Realtime API 优化持续连接、低延迟与打断——改变的是"交互节奏"，不是推理强度。
第四条轴
Async / Background 优化长耗时执行、断线恢复——改变的是"任务能活多久"。
接口形态典型代表核心对象状态管理适合场景
Chat/Message APIOpenAI Chat Completions、Anthropic Messages、Gemini generateContentMessage / Content通常由客户端重传消息历史单轮问答、普通多轮聊天、分类、抽取、改写
Responses-like APIOpenAI Responses APIMessage、Reasoning、Tool Call、Tool Output、Compaction 等 Itemprevious_response_id、Conversation 或完整 Item 回放多步推理、复杂 Tool Use、长程 Agent
Realtime APIWebSocket / WebRTC 实时接口连续音频、文本、事件和工具调用连接级实时状态语音助手、实时客服、低延迟交互
Async/Background APIBackground、Batch、异步任务接口Job / Task / Event服务端任务状态深度研究、批处理、长耗时任务

1.1 Chat API：一位"健忘但健谈"的助手

Chat API 的基本抽象一句话就能说完：

messages[]客户端组装全部历史
→
model推理（状态用完即弃）
→
assistant message只返回可见文本

它简单、兼容性好，适合一次请求就能完成的任务。问题不在于"无状态"本身，而在于 Message 这个对象装不下太多东西：推理状态、工具执行阶段、压缩检查点、长任务生命周期，都表达不了。

⚠️
什么时候这个差异会咬人？ 普通问答差别不大。但如果任务需要连续几十次「观察—行动」循环（比如 Agent 写代码、打游戏、做研究），接口保不保留推理与工具状态，可能直接决定任务能不能完成。第 4 章的案例会让你看到这个差距有多大。

1.2 Responses-like API：把一次运行拆成"积木"

核心变化：不再只吐一段文本，而是把一次模型运行拆成可组合的 Item：

💬 消息用户 / 助手
+
🧠 reasoning私有、不可见
+
🔧 tool call / output工具调用与结果
+
📦 compaction压缩检查点
+
🖼️ 多模态文件 / 图像

抽象也因此从"消息进、消息出"变成了：

input items + previous state + tools + context policy
→ response items + new state

OpenAI 官方文档明确建议：推理模型在多轮、Tool Calling 场景中优先使用 Responses API，并允许通过 reasoning.context 控制是否使用早期回合的推理状态。Reasoning models ↗

1.3 Realtime 与异步接口：解决另外两个维度

⚡ Realtime：节奏维度

  • 持续连接、低延迟、可打断
  • 语音助手、实时客服
  • 改变"交互体验"，不改变单次推理强度

⏳ Async / Background：寿命维度

  • 长耗时执行、断线恢复、轮询或通知
  • 深度研究、批处理
  • 改变"Agent 能否持续工作，用户能否观察、取消、恢复"
📌
一句话记住第 1 章Chat API 是"健忘的话痨"，Responses API 是"有记事本的工作者"；Realtime 管节奏，Async 管寿命。选型先问：我的任务需要跨回合的推理连续性吗？
第 2 章

Tool 接口的五级台阶

Tool 接口也在升级：从"模型每次点一次名"的单次 Function Calling，进化成一个多层工具运行时。五种形态像五级台阶，越往上，模型上下文里需要搬运的东西越少：

LEVEL 1
Function Calling模型生成符合 Schema 的工具名与参数
LEVEL 2
Hosted Tool平台托管执行：搜索、代码解释器、Computer Use
LEVEL 3
Tool Search按需检索并加载工具定义
LEVEL 4
Programmatic Calling模型写程序，组合多个工具
LEVEL 5
Stateful Tool返回 handle，跨调用操作同一对象
Tool 形态优点主要限制
Function Calling通用、容易接入现有 API每次调用通常需要模型与应用往返
Hosted Tool平台负责执行与回传平台绑定较强，权限与数据边界需单独评估
Tool Search减少上下文污染与工具选择干扰需要良好的 namespace 和工具描述
Programmatic Tool Calling可并行、循环、过滤、聚合；中间结果不进模型上下文不适合每步都需要新语义判断或审批的任务
Stateful Tool避免模型搬运大量原始数据handle 生命周期、权限和失效恢复必须明确

2.1 Function Calling：Schema 是模型理解工具的"说明书"

Function Calling 的价值是分工：模型负责理解意图和填参数，传统程序负责执行。但 Tool Schema 不只是技术参数定义，它也在教模型怎么理解这个工具：

  • 名称能否区分相近工具？必填字段是否明确？
  • 枚举与格式约束是否足够？
  • 是否说明前置条件、副作用和失败方式？
  • 错误能否指导模型改参数后重试？

❌ 不友好的工具

400 Bad Request

模型只知道"失败了"，不知道怎么修，只能瞎猜重试。

✅ Agent-friendly 的工具

{
  "error_type": "invalid_argument",
  "field": "start_date",
  "expected": "YYYY-MM-DD and not earlier than today",
  "received": "2026/08/08",
  "retryable": true
}

2.2 Tool Search：别把整本工具手册拍在模型脸上

📚
打个比方考试时可以带一本 500 页的工具手册进考场——但每次答题前都把手册全翻一遍，既慢又容易看串行。聪明的做法是先看目录（namespace 的名称和一句话描述），确定章节再翻正文。Tool Search 干的就是这件事。

当工具数量增多时，把全部 JSON Schema 塞进每次请求会消耗 Token，还增加模型选错工具的概率。OpenAI Tool Search 已支持对 Function、Namespace 和 MCP Server 延迟加载：模型开始只看到高层名称与描述，需要时再加载具体定义。Tool search ↗

🧰 实用原则（可以直接抄）

  • 按用户意图划分 namespace，而不是按后端微服务划分；
  • namespace 描述要短而有区分度；
  • 低频、Schema 大的工具用 defer_loading；
  • 单个 namespace 尽量保持在约 10 个以内；
  • 高频、关键工具直接加载，省掉一次搜索步骤。

2.3 Programmatic Tool Calling：把"体力活"移出模型大脑

模型编写受控 JavaScript，在运行时内完成并行调用、循环、条件、过滤、Join、去重和聚合，只把缩减后的结果交回模型。Programmatic Tool Calling ↗ 那什么时候交给程序、什么时候留给模型？用这个判断图：

下一步只依赖结构化字段和确定性规则吗？
是 → 程序化 交给程序做 批量查询多个对象；排序、过滤、去重、聚合；根据结构化返回值生成下次调用参数；有明确次数上限的重试。
否 → 回模型 留给模型逐步判断 搜索结果会改变研究方向；每个结果都要语义判断；涉及写入、付款、删除、对外发送；需要保留原始引用；执行前必须用户审批。
📌
一句话记住第 2 章工具的演进方向是"让模型少搬砖、多动脑"：Schema 教会模型用工具，Tool Search 按需给手册，程序化调用外包体力活，Stateful Tool 用 handle 代替搬运原始数据。
第 3 章

协议全家桶：MCP、Skill、A2A 各管一段

这几个名词经常被笼统叫作"Agent 接口"，但它们解决的问题完全不同。先看一张分层地图，建立全局观：

🧠 Responses-like Runtime单个模型的认知运行时
面向单个模型 / Agent Runtime 的推理与工具循环：状态连续性、Compaction、模型内 Tool Loop。
📦 Skill可装载的软件包
按需加载的操作知识：告诉模型在当前环境里"怎么做一类事"——步骤、判断原则、脚本、模板、失败处理。
🔌 MCP设备驱动与 I/O 总线
Agent 与 Tool/Data 之间的能力总线：能力发现、参数调用、资源引用、结果传输。
🤝 A2A分布式任务协作协议
Agent 与 Agent 之间的任务协议：委托、Task 生命周期、流式进度、Artifact 交付。
🛡️ Policy / Memory Plane治理与持久化层（横向贯穿）
为以上所有层提供身份、授权、审批、审计、租户隔离和持久记忆。

3.1 MCP：Agent 世界的"USB 总线"

🔌
打个比方MCP 就像电脑主板上的总线 + 设备驱动：文件、数据库、搜索、企业服务都是"外设"，MCP 让不同 Agent Runtime 用相对一致的方式即插即用。它管"怎么连、怎么传数据"，不管整个任务怎么规划。

MCP 的核心对象是 Tools、Resources 和 Prompts。当前已支持输入/输出 Schema、结构化结果、可供模型自我修正的 Tool Execution Error，以及通过显式 handle 维护跨调用状态。

🔐
一个容易忽视的安全细节MCP 本身没有统一的协议级状态会话——handle 在协议层只是普通字符串。因此服务端必须在每次调用时重新验证调用者权限，不能因为"上次验证过"就放行。MCP Tools specification ↗

3.2 Skill：把"老师傅的经验"打包给模型

Skill 不是远程调用协议，更接近可装载的软件包。它描述模型在当前环境中应如何使用已有资源完成一类任务，通常包含：

触发条件什么时候用我
→
操作步骤判断原则 + Tool 组合
→
资源包文档 / 脚本 / 模板
→
验收与兜底验证方式、失败处理、停止条件

Skill 的主要价值不是新增一个能力端点，而是把个人、团队或垂直场景的操作经验变成模型可按需消费的流程。理想的加载方式和 Tool Search 一样：先暴露名称与描述，命中场景后再读完整说明。

3.3 A2A：Agent 之间的"外包合同"

A2A 的核心对象不是 Tool Call，而是 Agent Card、Message、Task、Task State 和 Artifact：

  • 远程 Agent 可以返回即时 Message，也可以创建一个可查询、可流式订阅、可取消、可恢复的 Task；
  • 任务成果通过 Artifact 表达；
  • Streaming 区分状态事件与 Artifact 更新，适合分钟、小时级的异步任务。A2A specification ↗ Streaming & Async ↗
📋
打个比方MCP 是"叫外卖"——点一道菜（一次工具调用），送达就结束。A2A 是"找装修公司"——签一个任务合同，对方有自主性，工期可能很长，你要能查进度、中途改需求、验收交付物（Artifact）。

3.4 Policy / Memory Plane：看不见但缺了会出事的一层

它不是单一协议，却是企业 Agent 不可缺少的一层：身份与租户、授权、高风险操作审批、调用日志与审计、Artifact 所有权、数据分类与跨境策略、持久记忆的写入审核。

特别地，四种状态必须分开放，不能一股脑存成"记忆"：

状态类型主要用途是否应直接长期保存
Reasoning State当前模型推理连续性通常不应直接作为长期记忆
Run / Task State当前目标、进度、阻塞与恢复点保存到任务结束或审计期
Artifact State文件、代码、报告、数据及版本按业务生命周期保存
Durable Memory经确认的偏好、事实和环境经验经过筛选、验证后才保存

3.5 为什么 MCP 和 A2A 不会合并成一个"万能协议"

因为它们面向的抽象根本不同：

  • MCP → 相对原子的能力与数据访问；
  • A2A → 有自主性的远程执行者和长生命周期任务；
  • Skill → 可加载的操作知识与场景适配；
  • Responses-like API → 单个模型的推理与工具循环；
  • Policy/Memory Plane → 跨所有层的治理与持续状态。

一个 Agent 可以同时通过 MCP 调数据库、通过 A2A 委托另一个 Agent；被委托的 Agent 内部还可以加载 Skill、继续调自己的 MCP Tools。统一底层传输格式，消除不了这些语义差异——是否具备自主任务生命周期，就是 Tool 与 Agent 的分界线。

📌
一句话记住第 3 章Runtime 管思考，Skill 管经验，MCP 管外设，A2A 管外包，Policy/Memory 管规矩。它们是协同的五层，不是互相替代的竞争者。
第 4 章

案例深扒：ARC-AGI-3 分数如何翻三倍

理论讲完了，现在看真刀真枪的实验。这是全讲义最有说服力的一章——它证明了前面所有概念不是纸上谈兵。

4.1 这是一个什么测试？

ARC-AGI-3 是一系列规则未知的二维交互游戏。模型不会预先拿到规则说明书，必须像人类玩家一样边玩边摸索：

👀 观察画面当前状态
→
💡 形成假设规则猜想
→
🎮 选择动作验证猜想
🖼️ 新画面动作结果
→
🔧 修正假设更新认知
↺ 循环几十甚至上百步——早期发现的规则，后期还要持续用

注意它的本质：这是长程闭环任务，不是一问一答。所以它对"状态连续性"极其敏感——恰好打在了老接口的软肋上。

4.2 原始 Harness 的两个致命伤

🩹 致命伤 ①：每步之后丢弃私有推理

模型能看到过去的动作记录，却无法继续使用产生这些动作时的内部推理状态。刚发现的游戏机制、待验证的假设，下一步要重新推导。

  • 每步花大量 Token 重新解释游戏
  • 已验证的规律不能稳定复用
  • 策略在相邻动作间不连贯
  • 探索难以累计成长期知识

🩹 致命伤 ②：滚动截断早期历史

上下文超阈值后直接删除最早的动作和观察。模型不仅失去过去的推理，还逐渐失去"过去发生过什么"。

  • 不只是减少信息量
  • 更会破坏因果链：后期决策依赖的早期规则发现，已经从上下文里消失了
🧩
打个比方想象你在玩一个密室逃脱：每解开一个机关，管理员就让你忘掉刚才的推理过程（致命伤①）；房间快记满时，就把你最早的笔记撕掉（致命伤②）。你的智商没变，但你永远走不出这个密室。

4.3 新 Harness 只做对了两件事

🔧 调整 ①：Retained Reasoning

通过 Responses API 的 previous_response_id 和 persisted reasoning，让模型在后续动作中继续使用兼容的 reasoning items。保留的不是公开的 Chain-of-Thought，而是不透明的内部推理状态。GPT-5.6 提供三档：

  • all_turns：用更早回合的推理状态
  • current_turn：只用当前回合（避免旧推理干扰新任务）
  • auto：模型默认，GPT-5.6 相当于 all_turns

🗜️ 调整 ②：Compaction

上下文到阈值后，不再删除最早记录，而是生成一个不透明的 compaction item，用更少 Token 承载后续仍需要的状态与推理。Compaction ↗

  • 更像"有损但面向继续执行的工作状态检查点"
  • 不是普通对话摘要
  • 不能替代可审计的原始 Trace 或业务数据库

同时输出 Token 降到原来的约 1/6。更少"从头思考"，反而策略更连贯——收益来自减少重复推理和状态丢失，而不是思考次数越多越好。

🧪
科学解读：别过度外推接口没有凭空创造三倍通用智能——是原接口严重限制了模型展开已有能力。单轮生成、分类、简单问答不会获得同等收益；收益最明显的是目标持续稳定、反馈连续、需要跨多次 Tool Call 累计发现的任务。

4.5 可以直接参考的 Responses 配置

用于"目标稳定、长程、多轮"任务的简化示例（compact_threshold 是示意值，应根据模型上下文、平均 Tool 输出和预留输出空间通过评测确定）：

from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="gpt-5.6",
    input="分析这个项目，定位故障并给出经过验证的修复。",
    reasoning={
        "effort": "medium",
        "context": "all_turns",   # 保留跨回合推理状态
    },
    context_management=[
        {"type": "compaction", "compact_threshold": 200_000}
    ],
)

# 后续只提交新增输入，并引用上一轮 Response：
response = client.responses.create(
    model="gpt-5.6",
    previous_response_id=response.id,   # ← 状态接力的关键
    input="继续执行，并检查刚才的修改是否通过测试。",
    reasoning={"effort": "medium", "context": "all_turns"},
    context_management=[
        {"type": "compaction", "compact_threshold": 200_000}
    ],
)
🚫
无状态模式的坑如果用 store=False 或无状态模式，就不能只保留可见文本——要把上一轮返回的完整 response.output（含 reasoning、tool、program、compaction items）按原顺序加入下一轮 input，否则状态接力就断了。
📌
一句话记住第 4 章ARC-AGI-3 证明：评测的对象不是"模型"，而是"模型 + API + Harness"。丢推理状态 = 反复从头思考；硬截断 = 破坏因果链；保留推理 + 压缩 = 三倍分数 + 六分之一 Token。
第 5 章

八个可以直接抄的实战 Tricks

把前面的原理浓缩成八条操作清单。每条都可以独立使用，不用全部上。

Trick 1先判断任务是否需要推理连续性

任务类型建议设置
分类、抽取、短改写Chat 或 Responses；none/low；无需 retained reasoning
多轮 Tool Use、Agent CodingResponses；medium/high；目标稳定用 all_turns
独立复核、反方验证新 Session 或 current_turn，避免路径依赖
超长研究 / 数据处理Responses + Compaction + 外部 Task State
高风险写操作直接 Tool Call + 显式审批，别藏进自动循环

Retained reasoning 不是常开最好。目标变了、假设被推翻了、要独立验证时，切到 current_turn、开新分支或新会话。

Trick 2用 Compaction 替代硬截断，但保留外部权威状态

  • 在接近上下文极限之前触发 compaction；
  • 用 previous_response_id 时别再手工裁剪历史；
  • 无状态回放时保留最近 compaction item 及其后完整 Item；
  • 目标、验收条件、关键事实、Artifact ID、未完成事项存外部 Task State；
  • 别把 compaction item 当可读、可审计、可复用的持久记忆。

Trick 3推理强度按阶段设，别全程拉满

  • 路由、抽取、格式转换 → none/low
  • 普通 Tool Use、编码执行 → low/medium
  • 复杂诊断、规划、研究 → medium/high
  • xhigh/max/pro → 只在评测证明显著收益时用

更高 effort 不保证更高完成率，可能增加延迟、让模型在错误方向上探索更久。比较配置时同时看：完成率、总 Token、重复工具调用、延迟、证据覆盖率。

Trick 4别把全部工具定义预先塞入上下文

  • 高频基础工具直接加载；
  • 大型工具集合用 namespace 分组；
  • 低频工具走 Tool Search + defer_loading；
  • 名称和描述要强调工具之间的区别；
  • 记录"模型看见了哪些工具"，否则实验无法复现。

Trick 5区分直接调用与程序化调用

判断标准一句话：下一步是否只依赖结构化字段和确定性规则？是 → 程序化（并行、过滤、聚合）；否 → 回模型做语义判断。

写入、删除、付款、发布、对外发送——默认走直接调用，并保留审批点。

Trick 6Tool 输出提供"双视图"

summary:    供模型快速判断的精简结论
structured: 供程序消费、经 output schema 校验
resources:  原始文件、游标或对象 handle
evidence:   来源、版本、时间与校验信息
control:
  status: completed
  retryable: false

Markdown 适合阅读，结构化数据适合组合，handle 适合存大对象，evidence 适合验证——别把一切都转成 Markdown，也别把原始数据全塞给模型。

Trick 7错误信息要支持模型自我恢复

把错误分成五类，分别处理：

  • 参数可修复 → 告诉模型怎么改；
  • 临时错误 → 有限重试；
  • 权限不足 → 请求用户或系统授权；
  • 状态失效 → 重建 handle；
  • 永久失败 → 停止并说明原因。

错误结果应显式包含 retryable、错误字段、期望格式、建议动作。重试必须有上限，并用 idempotency key 避免重复副作用。

Trick 8评测记录 Harness，不只记模型名

至少记录：模型快照、接口类型、reasoning mode/effort/context、store 与回放方式、compaction 阈值与策略、Tool 列表与 Schema 版本、direct/programmatic 调用方式、retry/stop/approval 规则、Sandbox 与依赖版本。

否则所谓的"模型能力变化"，可能只是接口和执行环境变了。

第 6 章

未来：接口会长成什么样

6.1 从 generate() 到 run()：生成接口 → 任务运行时

过去：生成接口

generate(messages) → text

输入消息，输出文本。仅此而已。

未来：任务运行时

run(
  task, state_refs,
  available_capabilities,
  policy, budget,
  output_contract
)
→ events + artifacts
  + evidence + checkpoint

接口的核心对象将从 Message 扩展为一整个"任务词汇表"：

对象含义
Task要完成的目标与生命周期
Item / Event一次运行中的消息、推理、工具和状态事件
Artifact真正交付给用户或下游系统的结果
Checkpoint任务恢复点
Capability可发现、可授权的工具或 Agent
Policy谁可以在什么条件下执行什么动作
Memory哪些经验证的信息可以跨任务复用

6.2 五层接口将长期并存（各自行进化）

层核心职责演进方向
Responses-like Model API推理、状态连续性、Compaction、模型内 Tool Loop更细粒度状态控制、自动上下文管理、任务级预算与恢复
MCPAgent 与 Tool/Data 的能力总线动态发现、结构化结果、异步 Task、权限与企业治理扩展
Skill按需加载的环境操作知识标准 Manifest、依赖与权限声明、测试、版本与兼容性
A2AAgent 间任务委托、状态与 ArtifactAgent 发现、异步任务、流式进度、跨组织授权
Policy/Memory Plane授权、审计、租户、持久记忆与数据治理细粒度委托、Memory 写入门槛、数据谱系、跨 Agent 审计

6.3 另外三个值得记住的趋势

🔀 上层更语义化，下层更类型化

未来接口不会全面变成自然语言 API，而是两阶段：① Agent 用自然语言表达目标、约束和成功标准；② Runtime 把意图编译成可检查的类型化计划，校验权限、成本、副作用后再执行。"Agent-friendly"不等于弱化 Schema——Schema 还会表达前置条件、副作用与风险等级、幂等性与补偿操作、授权范围、成本延迟、结果证据。

🗂️ 上下文会变成"被调度的工作集"

即使上下文窗口继续扩大，模型也不该当搬运工。未来更像一个 Context OS：原始数据留在外部系统；Agent 用 handle / URI / cursor / Artifact ID 引用；按阶段以 summary / slice / query / raw 视图读取；Tool Schema 和 Skill 按需加载；Compaction 只维护当前任务的工作集；Durable Memory 只存验证过的信息。

🧱 协议边界不会消失

MCP（I/O 总线）、A2A（分布式协作）、Skill（软件包）、Responses-like API（认知运行时）、Policy/Memory（治理层）会共享身份、Schema、Artifact 和事件格式，也会相互引用——但是否具备自主任务生命周期这条 Tool 与 Agent 的分界线不会消失。

Chat API 暴露模型的"说话能力"；下一代 Agent API 暴露的是模型在一个受控世界中持续工作、恢复状态、调用能力并交付可验证结果的能力。

学完了吗？六道题自测一下

先自己作答，再点开看答案。能答对 5 题以上，说明你已经掌握了这份材料的主干。

为什么 ARC-AGI-3 上同一个模型换 Harness 后得分能从 13.3% 涨到 38.3%？
答：不是模型变强了，而是原 Harness 丢掉了两个关键状态：① 每步后丢弃私有推理，模型被迫反复从头推导；② 滚动截断早期历史，破坏了"早期规则发现 → 后期决策"的因果链。新 Harness 用 Retained Reasoning 保留推理状态、用 Compaction 替代硬截断，让模型已有能力得以展开，还顺带把输出 Token 降到约 1/6。
Chat API 的问题仅仅是"无状态"吗？
答：不是。真正的问题是 Message 这个抽象装不下关键对象：推理状态、工具执行阶段、压缩检查点和长任务生命周期都无法表达。对单轮问答无所谓，但对几十次观察—行动循环的 Agent 任务可能直接影响完成率。
MCP 和 A2A 既然都是"Agent 接口"，为什么不会合并？
答：它们面向的抽象不同：MCP 面向相对原子的能力与数据访问（像设备驱动 / I/O 总线），A2A 面向有自主性的远程执行者和长生命周期任务（像分布式协作协议）。"是否具备自主任务生命周期"是 Tool 与 Agent 的分界线，统一传输格式消除不了语义差异。
一个工具返回 "400 Bad Request"，对 Agent 来说问题在哪？
答：模型不知道错在哪、能不能重试、该怎么修，只能瞎猜。Agent-friendly 的错误应包含 error_type、出错字段、期望格式、实际收到值、是否 retryable 和建议动作，让模型能自我恢复。
什么时候应该把 retained reasoning 关掉（用 current_turn 或新会话）？
答：三种情况：① 用户目标改变了；② 早期假设已被推翻，旧推理会误导；③ 需要真正独立的验证（如反方复核）——继承原执行者的推理会产生路径依赖，让"复核"形同虚设。
Compaction item 可以当作长期记忆或审计日志来用吗？
答：不行。Compaction 是"有损、不透明、面向继续执行的工作状态检查点"，不是可读可审计的记录。目标、验收条件、关键事实应保存在外部 Task State；审计要靠原始 Trace 和业务数据库；跨任务复用要靠经过筛选验证的 Durable Memory。

📄 一页纸总结

  1. 能力公式：观察到的能力 = F(模型, 推理API, 推理状态, 上下文策略, 工具, Harness)。模型只是六分之一。
  2. 推理接口：Chat API 健忘；Responses-like API 以 Item 为单位保留状态；Realtime 管节奏；Async 管任务寿命。
  3. 工具接口：五级台阶——Function Calling → Hosted → Tool Search → 程序化调用 → Stateful（handle）。方向是让模型少搬砖。
  4. 协议层：Runtime 管思考、Skill 管经验、MCP 管外设、A2A 管外包、Policy/Memory 管规矩。五层并存，不会合并。
  5. ARC-AGI-3 铁证：保留推理 + 压缩替代截断，同模型得分 13.3% → 38.3%，Token 降至 1/6。评测对象是"模型 + API + Harness"。
  6. 实战：按需开推理连续性；Compaction 前先备好外部 Task State；推理强度按阶段调；工具按需加载；危险操作走审批；错误信息要可恢复；评测记录全量 Harness 配置。
  7. 未来：generate() → run()；上下文变成被调度的工作集（Context OS）；上层语义化、下层类型化。
