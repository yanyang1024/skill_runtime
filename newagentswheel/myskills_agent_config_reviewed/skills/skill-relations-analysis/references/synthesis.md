# 主 agent 模式：协调与综合

你负责把 N 个单 skill 画像汇总成关系图谱、共性/差异、抽象模式与依赖网络。综合是主 agent 独有职责，不下放给 worker。

## 阶段一：准备与派单

1. **确认输入**：skill 集合根目录与输出根目录（未指定按 SKILL.md 的唯一运行目录约定并说明）。核对根目录可读、与使用者描述大致相符；明显不符（数量、结构）先澄清。
2. **枚举 skill**：默认每个含 `SKILL.md` 的直接子目录为一个 skill，兼容根目录直接放定义文件或其他等价布局——在 plan.yaml 中说明实际采用的枚举规则。来源可为单个或多个根目录；多个来源时 skill_id 加来源前缀消歧。得到任务清单：task_id ↔ skill_id ↔ skill_path。
3. **写 plan.yaml**：来源根目录、枚举规则、计划清单、输出结构。这一步同时创建输出目录。
4. **选择执行主体**：小集合、简短材料可由当前主体按 worker-mode.md 分别画像；材料量、隔离或并发收益明确且 Task 已允许时，向 skill-profiler 派自包含任务包。无 Task 能力按顺序处理；用户硬性要求独立上下文而不具备时报告该要求阻塞。并行输出独立，实际并发受运行时容量限制。
5. **复用已有画像**：先核对材料版本、目标维度及读取覆盖；只对变更或缺失部分补提取。plan.yaml 记录 execution=inline/delegated/reused 与原因，不把复用记为新执行。

## 阶段二：覆盖校验

逐份核对回传：task_id/skill_id 匹配、状态语义成立、`profile_path` 存在可读（以回传实际路径为准）。计划内每个 skill 归入：完成（PASS）、失败（FAIL）、阻塞（BLOCKED）、未回传（超时/无有效回传）。错配、重复、缺项先核实，不进入综合。缺失输入可补充时发起针对性任务；仍缺则记为分析缺口。

## 阶段三：综合（读取全部可用画像）

按顺序执行，每步都保留证据引用。画像数量多时先读取头部与依赖字段建立索引，再按下列步骤分批细读，控制上下文占用。

1. **数据角色归一化（屏蔽数据差异）**：把各 skill 的具体数源映射到数量受控的数据角色（初始角色参考：原始输入 / 参考基准 / 上游产物 / 配置参数 / 知识语料 / 运行产物；可按证据增删，建议总量 ≤ 8），产出映射表（数据角色 ↔ 具体数源 ↔ 所属 skill）。后续比较在角色层进行，具体差异保留在映射表中备查。
2. **关系边抽取**：依据画像与 relationship_signals 建边，每条边给 confidence（explicit / inferred / ambiguous）与依据——
   - `consumes_output`：from 为消费者 A，to 为生产者 B；转换执行图时反向为 B→A；
   - `scenario_prerequisite`：from 为依赖方 A，to 为前置方 B；执行次序 B→A；
   - `shares_source`：共用同一具体数源（名称不同但指向同一来源时先归并，证据不足标 inferred）；
   - `soft_link`：互补、推荐搭配等弱关系。
   ambiguous 边进入待确认清单，不与确证边混列。数源侧同步建 `source_skill`（读取/生成/引用）与 `source_source`（同源 / 派生 / 配合使用 / 其他）关系。
3. **共性簇**：按数据角色、处理模式、分析方法、场景族聚类，每簇 ≥2 个 skill。防伪共性：措辞相似不算共性，必须在抽象层有实质重叠（同角色输入 + 同类处理/分析方法）。簇内记录共享不变量与各 skill 的具体变体。
4. **差异分析**：每个 skill 的独有场景、独有数据角色、独有方法；以及"同一抽象模式的不同实现"对照。
5. **抽象模式提取**：把跨 skill 重复出现的处理/分析逻辑写成模式——名称、抽象描述、输入角色、逻辑骨架、触发条件、各 skill 实现与偏差点。这是本次分析最重要的可复用产出。
6. **场景依赖链**：按 orchestration.md 区分方法依赖与产物依赖，展开具体阶段并检查环；未验证接口不直接排成可执行 DAG。逐段标注明文依据、推断及缺口。
7. **缺口汇总**：阻塞/失败 skill、材料缺口、ambiguous 边、无法判定项。

## 阶段四：产出与自检

按 output-format.md 写 `analysis.yaml` 与 `report.md`，然后过自检清单：

- 每个计划内 skill 都有状态交代，覆盖数字与 plan.yaml 对得上；
- 每条边、每个簇、每个模式都能引用到画像证据；无画像支撑的内容不进产物；
- 抽象层描述被 concrete 支撑，未夸大；inferred / ambiguous 已标注；
- 阻塞与缺口如实呈现，不用"未提及"冒充"不存在"；
- 读回产物，核对 YAML 结构、Mermaid 语法与引用可回溯；产物只写输出根目录。

最后向使用者汇报：分析范围、覆盖情况、产物路径、关键发现摘要、缺口与未验证项。


## 可选后续阶段

需要场景组合时按 orchestration.md 与 skill-semantics.md 生成生态计划。要求生成 Agent 时按 design-handoff.md 交出设计输入；由当前 Agent 根据请求与权限选择 agents-creator。本方法到此完成，不规定其他主体必须自动调用创建器。

## 增量与资产整理

来源或目标变化时先按 incremental.md 确定有效材料与潜在影响；大集合先构建短能力索引再细读候选。需要合并/拆分时按 consolidation.md 形成建议，不直接修改被分析材料。相似簇不等于可合并集合，独有约束必须保留。
