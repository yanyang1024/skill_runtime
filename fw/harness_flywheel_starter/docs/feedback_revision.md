# 从实测反馈收敛信号层：会话证据、部门切片、可验证改动

这次最值得保留的是三件事：**以会话为主数据源；对文件先区分存储身份；把部门差异用于发现适配需求。** 我对上一版的修正是：不再把拿不到的完整文件版本、run/branch/issue ID 当成产生诊断候选的前提。强证据不足时仍可排查，但输出名字和用途必须随证据一起降级。

这份说明依据你上传的七份反馈 Markdown，未访问原始 JSON、公司 adapter、文件系统或内网。数字均为报告转述，不是本次复算。代码是已有参考包的增量，可挑选函数合并到你自己的实现。

配套代码在 `harness_flywheel_starter.zip`。解压后从 `README.md` 开始；最短演示为 `python3 demo_session_first.py demo_v11`，会生成虚构会话、候选信号、任务分布和部门比较报告。两个主要新增入口是 `session_first.py` 与 `compare_departments.py`，均只用 Python 标准库。

## 1. 先修正会改变行动的几个判断

| 反馈中的判断 | 更贴近现有证据的解释 | 对方案的影响 |
|---|---|---|
| I/O hash 交集为 0，字节哈希方法被证伪 | 写入参数与包装/截断后的读取输出不是同一种指纹；源文件集合也可能少有交集 | 不用 I/O hash 冒充 file_bytes；保留路径候选补召回 |
| 相同绝对路径就是同一资产 | 还必须同租户、同实际存储命名空间/挂载实例；同路径容器可能互不共享 | 路径角色可用规则猜；是否共享要依赖实际部署约定 |
| 私有 workspace 的 110 个候选 identical=0，证明都无关 | 只说明当前指纹未建立内容一致证据 | 不确认复用，也不声称已经证明全部无关 |
| 去空白+casefold 能确认语义近等 | 缩进、标识符大小写、字符串和单位可能有语义 | 仅可做文本候选，不能提升为金标准；本版不计算这个指标 |
| edit/bash 占 41.5%，都能作为漏掉的实际文件操作补入 | edit 有明确目标与修改参数；bash 语法只提示可能的副作用 | 先补 edit；bash 先放复盘队列，不做完整 shell 解析器 |
| Skill 加载后无 invoke，92% 是沉默供给 | 很多 Skill 通过加载指令即参与任务，本来没有独立 invoke | 按事件语义统计接触；需要真实可见清单才能做供给分析 |
| event_id 绑定了 97 次 Skill 失败 | 绑定证明那一次 Skill 加载/调用报错，不证明后续工作流根因 | 加载错误、下游错误共现、验收失败分列 |
| 两部门指标相近，已排除人的使用影响 | 还没控制任务、工具、模型、阶段、时期及用户构成；相近也可能来自抵消 | 先看共同切片；结论保持观察性 |
| 调用“自愈”约 30%，所以 70% 需人工介入 | 其余可能是窗口不完整、任务终止、转到子会话、错误非必需等 | 输出后续成功/未见成功/观察不足；人工介入另找证据 |
| 33% 重读说明迭代，超过 40% 表示复杂度增加 | 重读可来自修改后检查、截断、重复注入、正常检索 | 先固定分母和版本/范围口径；不设没有基线的 40% 警戒线 |
| reasoning parts 可算 reasoning token 占比 | 片段数、字符数、计费 token 是不同单位 | 有实际 usage 字段再算 token，且确认是否已含在 output 中 |
| assertion_failed=0 说明测试没有失败 | 全部断言元数据缺失时是没有观测到测试结论 | 同时展示 assertions_observed；0/0 显示 N/A |

另有一个应先厘清的范围问题：报告同时出现“8 用户/1653 会话”“36 部门切片”和“两部门所有用户”，三部门会话数又恰好合计 1653。可能来自不同导出范围或组织层级，但目前无法判断。给每次报告写一行 **dataset_id、时间窗、取样用户、组织层级、统计单位**，不要把这些数字直接拼成同一总体。141 个观测能力与 130 个被审计能力，也分别列分母。

“纯会话来源”说明采集成本低、可追溯，不能自动说明推论可靠。磁盘快照有时间局限；LLM 判断有语义误差，两者都应按信号需要选择，而不是按来源预先排可信等级。

## 2. 两类信号不变，多补两个轻字段

继续用 **确定性观测** 和 **规则/Agent 推理** 两类。每条只要能说明：

```text
发生了什么 / evidence_refs / 推断了什么 / 缺少什么 / 下一步怎样验证
```

再分开写 `observation_scope`（在哪些样本里出现）与 `change_owner_candidate`（谁可能修得动）。**部门特定不等于部门负责；跨部门共有也不等于模型导致。** “会话—系统—模型”适合作为诊断路径，不宜一开始就把观测塞进根因层。

| 层次 | 现在可做 | 暂不直接断言 |
|---|---|---|
| 会话观测 | error 状态、读写/edit 参数、Skill 加载、Agent 分派、时间与实际 usage | 业务完成、用户水平、工具缺陷 |
| Harness 候选 | 反复同参报错、可能重复注入、Skill 选用不合适、记忆冲突线索 | 某项配置一定造成失败 |
| 模型候选 | 同一冻结任务与环境下，更换模型后的质量/资源差异 | 跨部门报错相近所以模型能力不够 |

岗位/部门只用于场景定位和切片。若关心用户是否需要帮助，标注“本任务必要信息是否提供、术语是否清楚、是否知道下一步”，并保留 unknown；不要据对话风格推断人员能力或绩效。

## 3. 优先提取的信号与用途

| 信号 | 可确定的观测 / 推理边界 | 分母或排查单位 | 优先验证的改动 |
|---|---|---|---|
| 工具 error | 记录状态可确定；错误文本分型是规则推理 | error / (success+error)，取消/未知另列 | 错误结构、参数提示、针对特定错误的恢复规则 |
| 同参反复 error | 同会话同工具、参数完全相同、窗口内再错可确定；“无进展”待判断 | 每个初始错误的窗口；不能把重叠信号相加 | 澄清参数约束、阻止已知无效重复尝试 |
| 后续成功线索 | 同工具后来 success；无 issue 时不能确认同问题恢复 | 初始错误及观察完整性，另列窗口长度 | 找前后真正改变的条件，再写小规则 |
| read/write/edit | 工具报告发生的操作；不是磁盘最终状态快照 | 成功/报错分开，按操作计数 | 先补 edit 的路径、片段与证据 ID |
| 会话内路径重读 | 同会话相同路径锚点反复读取；不保证同版本/同范围 | 重复读次数 / 可识别路径的成功 read 次数 | 先检查是否读同版本、同 offset/limit，再考虑缓存 |
| 跨会话共享路径 | 已知共享存储下，先修改后另会话读取 | 唯一逻辑路径×消费会话；另列原始事件数 | 选少数知识文件验证“被用到且有帮助” |
| Skill/Agent 接触 | skill 加载、task 分派及调用状态；不是效果 | 使用会话数、已知用户数，按能力和部门切片 | 检查匹配任务、返回契约、下游验收 |
| question | 调用发生是观测；必要性与类型需读上下文 | 有 question 的会话 / 已覆盖会话 | 区分必要业务决策和可提前采集的信息 |
| 跨会话重复任务 | 同用户、实体/任务锚点、邻近时间只是候选 | 候选任务家族，不按相似标题计失败数 | 从真实摩擦点抽出回归题 |
| 任务图谱/路由 | 标签来源与预测分数可记录；场景分类可能错 | 一会话一主任务+可选次任务，unknown 保留 | 找边界任务，试同模型下路由提示补充 |

会话内重读要选定一种定义，别把“产后第一次读”“对同一文件第二次读”“相同字节重复读”混在一个复用率里。例如路径重读可按每会话 `成功 read 数 - 唯一路径锚点数` 作为分子；改动后再次读也在其中，所以它不是缓存节省量。脚本输出读事件供你接已有计算，不重算报告中的 33%。

任务级成功优先使用明确验收。感谢结尾、文件生成可以保留为**独立采样标志**，不要相加成完成分数。抽查时也取未触发标志的随机样本，避免只看“看起来好/坏”的对话。

## 4. 文件信号：补召回，但不混淆身份和内容

保留四个不同概念：

1. `resource_key`：租户 + 真实存储命名空间 + 规范路径，标识逻辑资源。
2. `content_version`：某次实际内容的不可变版本，当前未知就 unknown。
3. `payload_hash + hash_origin`：工具输入、工具输出或 edit 片段的取证指纹，不冒充完整文件字节。
4. `source_artifact_id/source_version`：若平台确有上传来源链，才使用；不能从同名反造 lineage。

本版 `session_first.py` 输出 read/write/edit 事件；edit 保留 old/new 片段联合指纹。工具报告 completed 仅是操作报告，具体工具是否“成功但没改动”还依赖其契约。bash 的 `>`、tee/cp/mv 文本只生成复盘候选；引号内文本和未执行的条件分支都可能命中。

跨会话路径关联放在单独的 `shared_path_candidates.jsonl`，只纳入明确 `storage_scope=shared_persistent` 且有可信来源的 `storage_namespace`。最近已观测修改者也不一定是真实生产者；未记录的写入、并发、符号链接、路径重新挂载均可能影响关系。脚本保留同一时刻多修改者的歧义，不给内容一致和业务采用标签。

示意：把已有部署约定接进 adapter，而非每次扫描文件系统：

```python
# 仅当你确知同租户这些会话挂载的是同一个实际卷时配置。
if actual_mount_id and path_is_on_that_mount(file_path):
    event.update(storage_scope="shared_persistent",
                 storage_namespace=actual_mount_id, storage_source="manifest")
# 只知道路径长得像 skills/：只加 role_hint，storage_scope 仍 unknown。
```

如果以后补完整内容指纹，请附实际采集时刻与完整性范围；今天从磁盘读到的内容不能回填成上个月的字节版本。文件改名、复制和上传可能跨路径，所以路径一致也不是一切复用的必要条件。

知识/记忆文件值得优先复盘，但 `context.json` 或 `memory/candidates/` 只提示可能角色。至少再确认“写了什么条件化经验、后来是否读到、是否应用、是否通过验收”。写入/读取次数用于追踪传播，不能替代记忆有效性。

## 5. 部门比较：三个观察状态，单独决定改进归属

建议把“部门特定/部门无关”改成：

| 观察状态 | 合适的报告说法 | 下一步 |
|---|---|---|
| 部分部门切片集中 | 在当前相近任务/工具条件下，这些部门切片出现更多该现象 | 核对开发试错、任务输入、工具版本与少数用户集中度 |
| 共同切片中均出现/描述上相近 | 在本次可比范围，多部门观察到相似现象 | 作为平台改进候选；再抽真实案例确认原因是否相同 |
| 覆盖不足或混杂未解 | 暂不足以判断差异来自哪里 | 缩小结论范围，补几条标注；不硬分两类 |

先按 **时期 × 任务类型 × 模型 × 工具** 分层；若已有可靠阶段、来源或工具版本，则纳入。阶段未知的历史数据仍可看，只能称“未控制开发/生产差异的观察比较”。部门名称不自动变成 development，也不自动代表特定经验水平。

`compare_departments.py` 做三件事：

1. 先报各部门原始分子/分母、会话数、已知用户数。
2. 只在双方都有足够调用、且所选字段已知的共同切片内计算。默认每侧每格 20 次是演示门槛，不是统计充分性保证。
3. 给双方使用相同权重：`w_s = (n_A,s + n_B,s) / 所有共同切片的两侧总调用数`，`调整率_d = Σ w_s × 切片率_d,s`。同时报共同调用覆盖，不把范围外记录填成 0。

这借用直接标准化的同权重思想，是观察性工程分析，不是随机控制实验。原理可参考 [CDC 的直接标准化说明](https://www.cdc.gov/nchs/hus/sources-definitions/age-adjustment.htm)；这里只借方法，不类推其业务结论。

虚构 demo：甲的困难任务更多，原始 error 率 18.2%；乙为 3.8%。两部门困难任务都为 20%，常规任务都为 2%；换成同一任务构成后均为 11%。由此只能说**这个例子里的原始差异由构成解释**，不能把真实数据中的相近率直接解释为部门无关。

脚本还看逐格差异，避免正负差异在总率中抵消。`--gap 0.03` 只是挑选人工复盘的示例阈值；不表示已证明等效。没有共同切片就 N/A。共同范围很窄、用户很少、任务标签来自未校准路由时，应在结论中明确限制。

后续若做区间估计，重采样单位优先考虑用户或任务家族，不能把同一用户的上千次调用当独立证据。[NIST 的 Wilson 区间说明](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)针对比例不确定性；一个区间不能修复错误的恢复标签、遗漏字段或混杂。本版暂不加推断统计，先让分母和可比范围可检查。

跨月比较请固定切片定义与权重版本；每次重算的新权重会改变目标总体。两两比较的权重也不能直接用于给多个部门排序。

## 6. 最小接线与输出口径

已有 `opencode_adapter_v3.py` 等公司代码没有上传，本版不声称已修改它们。你只需把完成态 tool parts 映射到以下结构；原有 case wrapper 也支持：

```json
{
  "tenant_id": "YOUR_TENANT", "session_id": "s1", "user_id": "u1", "dept": "IAD-D",
  "task_type": "lookup", "task_label_source": "human_v1",
  "coverage": {"tool_events_complete": false},
  "tool_events": [{
    "event_id": "original-tool-part-id", "ts": "2026-09-01T10:00:00+08:00",
    "name": "edit", "status": "completed", "model": "实际产生该调用的模型",
    "args": {"filePath": "/shared/skills/example/SKILL.md", "oldString": "旧片段", "newString": "新片段"}
  }]
}
```

`args` 应为 JSON 对象；`ts/started_ts` 用带时区 ISO 时间，毫秒时间戳先在 adapter 转换。`name` 用本平台工具名，若别名不同改那几处映射即可。代码使用最终调用快照：重复开始/结束事件先合并，父/子会话的重复投影只保留原始归属。不要拿导出行号伪造稳定调用 ID。

可选项只有实际拿到时才填：`user_turn_id/run_id/branch_id`、阶段来源、工具来源/版本、存储身份、断言元数据。多个模型混用时不要把会话主模型填给所有调用；无法绑定就 unknown。只有明确 `model_scope=single_model` 才允许回退到会话模型。

新入口按导出范围分析，`period` 按事件 UTC 月份分桶。需要月度报表时先在现有导出器固定窗口；若要找旧资产来源，可携带更早事件，但须在你自己的报表侧分清来源历史与当期分母。

`recorded_tool_error` 包含已观测的所有 error，已确认测试负例的计数另列；不是“生产错误率”。旧入口仍保留 `unexpected_errors` 字段以兼容，现增加解释与 `assertions_observed`。测试元数据全空时不能从这个字段名推断错误一定非预期。

时间窗默认 300 秒，只是便于复盘的起点。脚本同工具匹配，并在真实 turn/branch 已知时阻止跨越；已知调用时间重叠则不连接。缺链接时标记缺口。未见 success 且没有完整窗口，只输出 `window_incomplete_or_unknown`。窗口内多个初始错误可能共享同一次成功，不能把这些记录直接当独立“自愈事件”。

Skill/Agent 联系表保留原事件 ID。失败只归给加载或分派调用，不顺着“同会话出现过某 Skill”归因下游所有错误。旧供给入口新增两项要求：真实 `publication_source`，以及 `usage_event_semantics=invoke_required`；否则不产出“无 invoke”供给候选。观测清单仍可按 `first_seen_at/last_seen_at` 维护，不能把 first_seen 冒充 published_at。

`task_map.jsonl` 按会话计数，包括无工具会话；同一用户可能出现在多个格子，格子用户数不能相加成部门人数。多任务会话先选一个主任务，保留混合/未知标志即可，不急着做复杂任务切分或图数据库。把 capability_contacts 按 session_id 接上，可看“部门×任务×已接触能力”的稀疏表；接触多不表示贡献大。

## 7. 先走通一次信号到真实评测的循环

优先选一个有明确验收的问题：例如同参日期格式反复出错、某工具缺少必要参数、重复追问已经给出的条件。当前最值得做的次序是：

1. **补 edit、保留哈希来源、纠正 Skill 加载口径。** 可立即增加诊断覆盖；先不扩展复杂 shell 分析。
2. **各取少量共同/差异切片的真实对话，复核 question 和错误前后变化。** 另取普通随机样本作对照，不只挑极端案例。
3. **从这些案例中整理 3–5 道可复跑的真实题，做一个 Prompt/Skill 改动。** 三五道只是走通流程，不能支持全平台泛化收益。

`bench_card.example.json` 是待人工确认的题卡：保留原始来源、输入截止点、必要附件/工具快照、任务家族、验收条件。缺目标、输入或可核对答案就保持 draft；不要让 Judge 根据末尾感谢生成 pass。

真实会话中的后续修正、成功答案只能放到验收资料，不能提前放进初始题面。多次尝试同一任务应放同一 source_group，不能分散到调 Prompt 和未见考试中。相同实体可能是批次变体，任务家族仍需人工核对。

| 小实验 | 固定什么 | 主要验收 | 辅助成本信号 |
|---|---|---|---|
| 路由后补充任务提示 | 同模型、原始用户约束、工具与输入 | 正确性不下降、没有篡改意图、必要澄清保留 | 总 token、耗时、重复追问 |
| 给特定工具补错误恢复规则 | 原始失败、原成功与新来源三组题 | 真正解决该错误；没有误重试或改变业务参数 | 所有尝试消耗、重复失败数 |
| 文件摘要/范围缓存 | 同文件版本/访问条件、允许回源 | 跨段细节、更新后内容与引用仍正确 | 实际减少的输入 token/读取字节 |

不要同时改模型、路由、Skill 和缓存再宣称单点收益。已有 tfidf+logreg 的结果可作为当前路由基线；在独立人工标签和同任务切分上再验证。模型分数 0.42 不自动表示 42% 的正确概率。

“高 I/O”“长上下文调用占比高”可以指导选长输入题，但不能直接证明反复重读、模型过度推理或有缓存收益。失败尝试消耗可以记录为失败相关消耗，不直接改名浪费；并非全部可避免，也不能把输入 token 当真实货币成本。

先继续使用已有运行器与 `compare_change.py`。历史日志没 loaded_harness 就保持观察性；下一次小实验可手工记录实际运行副本、模型部署和工具配置，用现有启动流程加载该副本。若仍无法确认实际生效，记录限制，不虚构版本哈希。无需先改造全平台版本服务。

评测集维护两个视角：按真实任务分布抽的代表集；按失败/边界问题选的挑战与回归集。分别汇报，不能把困难题集通过率当生产成功率。再分别列真实回放、由真实案例重建、纯合成题比例；20/20 合成只能说明那批合成题的结果。

每轮新增候选，人工核实后进入下一版题集；保留固定回归集，未见题按任务家族隔离。反复用来调提示的题已变成已见题，不再算新能力证明。训练样本也不要吸收评测保留家族；先验证标签和任务收益，再考虑小模型/后训练。

## 8. 记忆和向上汇报都保留“证据到效果”的距离

仍沿用一张 change record：`source_refs、适用条件、修改前后版本、验收结果、是否启用、supersedes、复查触发条件`。新的经验先是候选；与旧经验冲突时比较适用条件和来源，不能默认最新写入优先。退役经验退出默认注入，证据历史保留。

向上汇报可以写：

> 在明确的采样范围内，我们观察到若干共性摩擦点，并完成了对应案例复核。某项改动在固定题集上的改善、退步及资源变化分别为……。业务采用与实际节省还需用户确认，当前不外推全平台收益。

对业务用户，询问“结果后来是否用上、还需要改哪里、哪一步最费劲”，比请用户认可一个平台价值分数更有用。**平台建设价值用可验证的改进说话；业务价值通过采用和验收建立桥梁。**

本轮实现到观测、候选、描述性比较和题卡模板，没有调用 LLM。Judge 继续复用已有人工参考与校准流程；新增 question/记忆应用等标签时，各自抽样校准，并保留 unknown 和分歧，不复用一个整体准确率替所有维度背书。
