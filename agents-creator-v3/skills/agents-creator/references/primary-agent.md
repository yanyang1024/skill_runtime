# Primary 写作模板

创建或调整 primary 时读取。配置规则见 [frontmatter.md](frontmatter.md)；这里仅给出正文骨架。实际文件必须补上按目标职责配置的 YAML frontmatter。

## 单 primary：默认形态

```markdown
你是<领域>助手，负责<稳定职责和最终交付>。

## 设计意图
<说明为什么此处一个主体足够，以及真正需要调整为多主体的条件；无需复制通用方法论。>

## 能力导航
- <任务触发条件>：加载 `<实际 skill 名称>`，按其中的流程执行。
- <其他任务条件>：<另一个 skill 或简短稳定行为>。
- 无匹配能力或路由依据不足时，说明缺口；仅在缺口影响结果时向用户澄清。

## 交付责任
汇总所需结果，依据所用 skill 的验收要求完成检查，并向用户说明产物、证据和未解决项。验证失败不声明完成。

## 工作边界
<授权资源范围、职责边界和必要的停止条件>。
```

按实际需求删减。单 skill 助手无需能力表；只需要一句明确的加载指令。没有 skill 依赖时可内联简短稳定行为，不生成空壳 skill。

不要写脚本路径、参数表、完整业务 SOP 或 skill 内部检查项。保留“为什么这样分工”“何时调用”和“对交付负什么责任”。设计原则要简短且贴合当前 agent，不把所有行业的拆分标准抄进每份正文。

## 协作 primary：确有必要时使用

先读 [multi-agent.md](multi-agent.md)。在单 primary 骨架上补充：

- **设计意图**：为什么需要这些边界，哪些工作可以直接完成，何种独立验收不能跳过。
- **派单条件**：哪些任务交给哪个真实 subagent，哪些简单任务可以直接处理。
- **协作次序**：依赖顺序、必要的独立验收，以及不能被普通成功结果覆盖的阻塞。
- **任务输入**：下发目标、输入、允许范围、验收条件和输出位置；具体字段遵循双方共享契约。
- **结果处理**：按共享契约的 PASS / FAIL / BLOCKED 处理，不只看一句“完成”。

详细领域契约如已有独立 reference，应写明实际位置和“派单前读取”，不要在双方复制整份 schema。没有共享资源的小型系统，可在双方保留短小一致的公共字段。

主 agent 可以执行轻量任务。需要隔离的大段解析、中间推理和独立验收才交给子会话；不把“primary 绝不亲自干活”作为通用规则。
