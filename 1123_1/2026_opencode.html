智能体知识分层与治理综合分析：从公开前沿到 OpenCode 企业落地

融合公开前沿调研（Anthropic、Manus、Google OKF v0.2、腾讯 WeKnora v0.9.0、A-RAG、MemGov）与项目级工程指南（v2.1），围绕“模型能力学习、当前上下文供给、可执行机制保障”重构知识放置、检索组合与业务闭环。

3 类作用方式
参数化能力 · 当前上下文 · 可执行机制
替代“大一统七层知识架构”

核心判断：不存在已经收敛的“Agent 知识七层行业标准”，真正的架构主线是“权威来源与受控策展 → 多种可追溯视图 → 有预算的访问接口 → 当前步骤证据工作集 → 结果验证 → 分类型写回”。知识分层首先服务于放置决策：同一个业务规则可以同时拥有权威正文、Skill 导航、确定性校验工具和训练样例，但必须明确谁拥有真值、谁负责执行，绝不能把知识库检索结果直接当作业务执行依据。

破除“七层幻觉”：从多维坐标与三种作用方式重新定义分层

将“行为契约、事实、记忆、派生视图”硬压成单一层级，会制造“业务知识是否等于长期记忆”“Skill 是否等于知识库”等伪冲突。结合近期记忆综述（arXiv:2512.13564 与 AACL 2026）与工程实践，更稳健的做法是将信息载体、认知功能、变化规律与治理角色拆开交叉标注，并按“参数、上下文、可执行机制”三种作用方式决定放置位置。

正反实证对齐：Skills、AGENTS.md 与“反共识”洞察的真实边界

行业中既有 Manus 的 100:1 文件卸载与 Logit Masking 保 KV-Cache（Manus Blog），也有 Claude Code 放弃本地向量库改用 grep/glob/LSP 的实战转向；但对 Skills 与常驻上下文，2026 年的实证研究同时给出了显著增益与明确回退两面证据，必须剥离实验条件审慎解读。

实证来源与时间 观察到的原始结果 工程启示与严格边界（不能外推什么）
Vercel Next.js 评测
(2026-01-27)		 基线 53%；默认 Skill 53%（56% 用例未被调用）；明确触发提示后 79%；8KB 压缩 AGENTS.md 索引 100% 发现与触发是第一瓶颈：若最小导航前提被藏在待发现资源里，模型可能永远不加载。但不能据此推出 AGENTS.md 普遍优于 Skill。
SkillsBench v4
(2026-06-14)		 87 个任务、8 个领域、18 种模型与 harness 配置下，人工策展 Skills 平均成功率从 33.9% → 50.5%（+16.6 个百分点） 高质量、任务对齐的方法包价值显著：证明策展 Skill 有效，但不证明自动生成的任意 Skill 都有益。
ETH Evaluating AGENTS.md
(2026)		 仓库上下文文件未提升任务成功率，反而增加 >20% 推理成本（多余约束诱导无效探索与测试） 常驻冗余即成本税：不要把教学型全面流程或非必要规范塞进常驻提示；指令应明确区分“必需 / 条件 / 可选”。
Microsoft 回退归因研究
(2026-08)		 分析 307 个 Skill 导致的归因回退案例（125 个功能回退 + 182 个效率回退），过度验证与重型流程是主因 知识也会施加错误流程负担：307 是回退样本数而非总体失败率，但它警示高复杂度 Skill 必须做配对消融对比。

方案地图再校准：RAG、Grep、Worktree、WeKnora、OKF 与 MemGov 的真实定位

将技术方案放入正确层次后，很多选型争议会自然消失。例如 git worktree 只是同仓库多工作树管理（Git Docs），并不提供 OS 安全隔离；OKF v0.2 提供了带 verified 与 Attested Computation 的概念契约，但格式可读不等于事实自动正确。

检索形态与“查询形状”契约

  • 接口按形状拆分：将需求明确拆为点查（get）、枚举（list）、检索（search）与统计（aggregate），防止模型把 top-k 误当全量覆盖。
  • 结构保真优先于统一转 Markdown：借鉴 DoclingDocument，保留原件与表格/页面定位，防止 OCR 丢失负号、单位与合并表头。
  • 召回后治理（Post-Retrieval Governance）：借鉴 MemGov (AACL 2026)，Rerank 解决相关性，而规则校验解决“是否有资格共存”（如禁止已撤回版本、不同产品 ID 混用）。

双时态、权限与受控写回

  • 业务有效 vs 系统知道：试点阶段记录 source_version 与 as_of，回溯审计场景再引入 valid_from 与 ingested_at（参考 Graphiti）。
  • 权限前置过滤：tenant_id/user_id 必须由服务端认证上下文绑定，不可由模型自由填入；多源摘要不得越权继承宽权限源。
  • 分类型写回策略：日志、检查点与显式偏好可按作用域自动保存；新案例与 SOP 必须先入 candidates/ 候选区，经验证与 diff 审查后才可发布。

OpenCode＋自部署模型业务落地：SOP、案例、参数与规则的治理闭环

针对“业务 SOP + 历史案例 + 产品实时参数 + 跨产品复杂规则”的典型企业场景，最危险的反模式是把四类内容全量灌入 WeKnora 后让通用 Agent 自由检索并直接执行。正确做法是按数据本质拆解权威源，并以三阶段路线渐进演进。

—— 14.9 理想证据诊断实验原则

下一步收敛动作：从“建大库”转向“理想证据诊断与预算对齐评测”

1. 建立数据源地图

用最小注册表（source_id、authority、data_class、preferred_route、allow_vector_copy）明确哪类数据走点查、哪类走精确 grep、哪类进混合检索，禁止所有文件无差别入向量库。

2. 统一最小证据契约

所有查询工具统一返回 entity_id、source_version、as_of、locator 与由服务端生成的 complete_for_request，并在 runs/<task-id>/attempts/ 按次追加留痕。

3. 预算对齐的分桶回放

建立覆盖点查、表面相似负例、陈旧版本、无答案与高风险拦截的 12 类分桶评测集，固定 backbone 与检索预算，分别报告“成功加载后效果”与“含触发失败的端到端效果”。
