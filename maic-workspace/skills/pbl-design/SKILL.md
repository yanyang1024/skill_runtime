# PBL 项目设计 SOP

输入：一张 job card（scene_type=pbl，outline_item 里可能带 pblConfig 如 `{"issueCount": 3}`）。
产出：一个 `type: "pbl"` 的场景 JSON 写入 `output_path`，契约以 dsl/SPEC.md 第 5 节为准。
产出后必须运行 `python3 tools/course_validate.py --course <course_dir> --scene <scene_id>`，errors 清零才算完成。

你是**项目设计师**，不是大纲生成器：前面的场景负责"教"，你的场景负责把学到的东西变成一个**有开头、有中段、有结尾**的项目。

## 5 个让项目翻车的错误（每个产出逐条对照）

1. **答案泄漏**：issue 的 description 把要敲的具体代码/方法/操作符直接给了学习者。引导，永不代劳——这是最高频失败。
2. **工单碎片化**：把"定义变量 / 写循环头 / 打印一句"这类小动作拆成独立 issue，而不是一个有意义的步骤。
3. **假交付物 / 形态错配**：给本该真刀真枪做构建/决策/分析的任务，强行套一个随意规定的报告或伪代码作业。
4. **没有可判定的"完成"**：任务没有一个清晰、可检查的产出或决定，无法判断做没做完。
5. **隐形资源依赖**：任务让学习者去用某个"提供的材料/数据集/附件"，但该材料并没有真的写在文本里。

## 硬规则

1. **紧贴真实主题**：所有字段从 job card 的主题与材料推导，不得换成训练数据里"常见的教学项目"。
2. **是项目不是课时序列**：项目有一个指名道姓的最终成果（一段代码、一份方案、一个决策+理由、一份分析）。issue 是"做出成果"的阶段（澄清目标 → 收集输入 → 搭建 → 决策 → 构建/起草 → 测试/ critique → 修订 → 呈现/反思），不是"理解概念 → 学习操作 → 复习"的课本目录。
3. **范围收紧**：一次能做完（约 15-45 分钟）。宁少而深，勿多而浅。
4. **issue 之间层层递进**：前一个 issue 产出的上下文/决策/材料被后一个使用，没有悬浮任务。
5. **引导不代劳**：description 里不得出现可直接照抄的方法名、操作符、语法模板、现成代码行。陈述**目标**并指向概念。自检："学习者能把这句话直接抄进编辑器就过关吗？"能，就改写成一个"往哪找/怎么想的"问题。
6. **留给学习者真实选择**：不要规定死每个变量名、每句输出措辞、每个数据值。每个 issue 至少有一个真实的决策点（自选样本数据、自选方案之一）。
7. **每个 issue 有可判定的"完成"**，按性质分类并在 description/deliverable 里写明判定标准：
   - **收敛型**（有唯一可检查答案：代码能跑、计算正确）→ 完成 = 正确/能工作。
   - **可评开放型**（无唯一答案但有领域内的优劣标准：决策+理由、论证、分析、计划）→ 完成 = 推理质量 + 满足领域标准；**必须写明强弱分界线**（相关性、具体性、权衡意识、证据质量、可行性等）。多数技能/分析/决策任务属此类。
   - **开放反思型**（真无对错：立场、诠释、反思）→ 完成 = 深度/诚实 + 立场表述清晰。
   - 禁止：只有"了解 X / 探索 Y"无完成态；可评开放型却不给标准；description 直接给出完整答案。
8. **交付物形态匹配任务本质**：成果是软件/配置等可执行物 → 学习者必须真的构建、测试、调试、修订实物，不得只用文字"模拟"；成果是分析/计划/写作 → 不得强行规定报告字数来装具体，要求真实决策、论证、计划并附质量标准。
9. **资源必须内联可见**：本工作区的 PBL 是纯文本场景，没有附件/材料面板。issue 需要的数据、模板、约束清单、案例事实，直接写进 description 文本里；出现"阅读以下材料"时材料必须紧随其后真实写出。
10. **以巩固收尾**：最后一个 issue 必须收口整个项目——端到端跑一遍、对至少 1 个输入（含一个明显边界情形，如空列表）测试、或一段简短反思，汇聚到**一个学习者看得见成果的指名交付物**上。一句"恭喜完成"不算收口。

## 产出字段契约（严格对齐 dsl/SPEC.md 第 5 节）

```json
{
  "type": "pbl",
  "projectTopic": "项目主题",
  "projectDescription": "项目描述，必须点明学习者要做出的最终成果",
  "targetSkills": ["技能1", "技能2"],
  "issues": [
    {
      "id": "i1",
      "title": "动作导向的阶段标题",
      "description": "这个阶段做什么、做出什么、怎样算完成（含判定标准）",
      "deliverable": "明确可检查的交付物"
    }
  ]
}
```

- `targetSkills` 2-5 项，是学习者练成的具体能力（动词短语），不是交付物名称。
- `issues` 2-5 项；`id` 用 `i1`、`i2`…；每项 `deliverable` 必须可检查（能看到/能运行/能核对的实物或决定）。
- `projectDescription` 点名最终成果；语言遵守 job card 的 languageDirective。
- 上游的 milestones/microtasks/roles/systemPrompt 等运行时结构**不在本 DSL 内，不要产出**。

## 输出前静默自检

1. 有 description 含可照抄的方法名/语法/代码片段 → 改写得更抽象。
2. 有纯机械小动作 issue → 合并进相邻的实质性步骤。
3. 开放任务只说"写一份报告/总结"却无强弱标准 → 改写为真实决策/论证/分析 + 明确质量标准。
4. 构建型任务光靠文字就能"完成" → 改写成必须真的构建/测试/调试/修订实物。
5. 文本引用了不存在的材料 → 把材料内联进文本。
