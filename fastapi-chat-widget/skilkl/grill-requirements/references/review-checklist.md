# 需求 Review 检查清单

阶段三逐项评审。每项给出结论：✅ 通过 / ⚠️ 风险（附缓解建议）/ ❌ 缺口（附回到阶段二的追问）。

## 完整性
- [ ] 所有已识别角色在主流程与异常流程中都有定义好的行为？
- [ ] 三分类清单中的"我的假设"已全部转化为用户确认的决策？
- [ ] 每条需求都能追溯到至少一个业务目标？
- [ ] 验收标准覆盖全部用户故事？

## 一致性
- [ ] 术语全程统一（与术语表一致，无同义词混用）？
- [ ] 各条需求之间无相互矛盾（权限、状态流转、数据口径）？
- [ ] 与已有 ADR / 架构决策 / 旧需求文档不冲突？

## 可行性
- [ ] 依赖的内部模块与外部服务确认存在且可用？
- [ ] 技术约束（栈、性能、数据量）内可达成？
- [ ] 时间与资源约束下有明确的砍范围顺序？

## 可测试性
- [ ] 每条需求都有客观可判定的验收条件（无"好用""尽量快"类措辞）？
- [ ] 非功能指标全部量化（毫秒、QPS、百分比、分钟）？

## 边界与异常
- [ ] 每条主流程都有对应的异常路径定义？
- [ ] 幂等、并发、超时、降级的行为已明确？
- [ ] 数据迁移与回滚方案存在？

## 非目标
- [ ] 非目标清单存在且每条经用户确认？
- [ ] 已识别"可能误以为包含"的人群并明确告知？

## 风险登记
- [ ] 每条 ⚠️ 都有 owner 与缓解/接受结论？
- [ ] 最高风险的三个假设已标注验证方式？

## Review 报告格式

```
## 需求 Review 报告 — <需求名称> — <日期>

### 结论：<通过 / 有条件通过（仅⚠️）/ 不通过（含❌）>

### 共识复述
<决策、取舍、非目标的完整复述>

### 检查结果
| 维度 | 结论 | 说明 |
| --- | --- | --- |
| 完整性 | ✅/⚠️/❌ | ... |
...

### 待办（❌ 项 → 回到阶段二）
1. <缺口 + 建议追问的问题>
```
