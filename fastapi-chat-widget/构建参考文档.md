# FastAPI 悬浮对话窗 · 构建参考文档

> 版本：v1.0（2026-10-20）
> 适用场景：在**已有 FastAPI Web 应用**上，以**一行 script** 嵌入一个对话悬浮窗；悬浮窗只承载两个能力面——**Skill 调用** 与 **文件输入输出槽位**；支持**页面刷新后会话继承**与**历史会话管理**。
> 本文档是可施工的设计参考：包含架构、数据模型、API/SSE 契约、前端结构、安全清单与分阶段验收标准。代码片段为骨架示意，按工程实际调整。

## 1. 需求与约束

| 项 | 结论 |
| --- | --- |
| 宿主应用 | 已有 FastAPI 应用，**不改其业务路由与页面**，仅在 base 模板加一行 script |
| 嵌入形态 | 右下角悬浮气泡 → 点击展开对话面板（路线 1） |
| 能力范围 | 对话 + Skill 调用 + 文件上传/产物下载，**不做通用 Agent 平台** |
| 会话管理 | 刷新后继承当前会话；可查看/切换/新建/删除历史会话 |
| 技术栈 | 后端 FastAPI（异步 SSE）；前端自包含 JS 包 + Shadow DOM |
| 身份 | 复用宿主应用的登录态（session cookie / Authorization 头），对话服务不另建账号体系 |

设计原则（继承自 web-agent-rebuild / web-native-bulilder 两个 Skill 包的方法论）：

- **最小纵向切片**：先打通"一条真实消息 → 一个真实 Skill → 可核对结果"，再扩展。
- **服务端是权限与状态的源头**：conversation 归属、文件归属、run 代次全部由服务端绑定，前端持有的只是 ID。
- **模型输出不可信**：不渲染模型给的 HTML/JS；文件路径、用户身份不接受模型输入。

## 2. 总体架构

```
┌─ 宿主 FastAPI 应用（业务代码零改动）────────────────────────┐
│  base.html 中新增一行：                                       │
│  <script src="/chat-static/chat-widget.js" defer             │
│          data-api-base="/chat-api"></script>                 │
│                                                              │
│  ┌─ 悬浮窗 Widget（Shadow DOM 隔离，自包含）──────────────┐  │
│  │ 气泡按钮 → 对话面板                                     │  │
│  │  · 消息流（Markdown 增量渲染）                          │  │
│  │  · 输入区 + 📎 文件槽位（待发送文件卡）                  │  │
│  │  · 会话栏（当前会话标题 / 历史会话抽屉 / 新建会话）      │  │
│  │  · 产物槽位（可下载文件卡）                              │  │
│  └──────────────────────────┬────────────────────────────┘  │
└─────────────────────────────┼────────────────────────────────┘
                              │ 同源请求（cookie 自动携带）
┌─ 对话子应用（挂载进宿主 FastAPI：app.mount / include_router）▼─┐
│  REST：                                                       │
│   GET  /chat-api/conversations            历史会话列表        │
│   POST /chat-api/conversations            新建会话            │
│   GET  /chat-api/conversations/{id}       会话详情+消息回放    │
│   PATCH/DELETE /chat-api/conversations/{id} 重命名/删除       │
│   POST /chat-api/conversations/{id}/messages  发消息（SSE 流） │
│   POST /chat-api/conversations/{id}/files     上传文件        │
│   GET  /chat-api/files/{file_id}/download     下载产物        │
│   GET  /chat-api/skills                       能力目录        │
│  ┌─ 会话协调层 ─────────────────────────────────────────┐    │
│  │ 会话历史持久化 / run_id 代次 / 取消标记 / 工具调用循环 │    │
│  └──────┬──────────────────────────────┬───────────────┘    │
│    Skill 适配层（能力契约+白名单调用）  文件服务（会话工作目录）│
│  存储：SQLite（会话/消息/文件元数据）+ 磁盘 workdir/         │
└──────────────────────────────────────────────────────────────┘
```

**部署形态**：对话子应用与宿主同进程（推荐，`include_router` + 挂静态目录），因此：
- 天然同源，无 CORS，宿主 session cookie 直接可用；
- 宿主鉴权依赖（`Depends(get_current_user)`）直接复用；
- 若宿主是多 worker 部署（多 uvicorn worker），注意内存态（run 句柄、取消标记）不能跨 worker 共享——见 §5.5。

## 3. 嵌入方式：一行 script

### 3.1 宿主侧改动（唯一一处）

在宿主 base 模板 `</body>` 前：

```html
<script src="/chat-static/chat-widget.js" defer
        data-api-base="/chat-api"
        data-title="智能助手"
        data-accent="#1C64F2"></script>
```

- `data-api-base`：对话 API 前缀，widget 内所有请求以此拼接；
- `data-title` / `data-accent`：面板标题与主题色（气泡按钮、发送按钮）；
- 宿主任何页面继承该模板即自动获得悬浮窗。

### 3.2 Widget 构建

- 构建工具：Vite **lib 模式**，产物单文件 `chat-widget.js`（IIFE 格式，无外部依赖请求）；
- 技术选型：**Vanilla TS 或 Preact**（~4KB）。**不要用宿主同款全局框架 + 全局 CSS**——宿主栈虽然已知是 FastAPI（模板渲染 HTML），但页面 CSS 不可控，Shadow DOM 是硬性要求；
- 样式全部内联进 Shadow Root（`adoptedStyleSheets` 或构建时注入 `<style>`），宿主样式进不来、widget 样式漏不出去；
- 入口伪码：

```ts
// src/index.ts（构建为 chat-widget.js）
import { createWidget } from './widget';

const cfg = document.currentScript!.dataset; // apiBase, title, accent
const host = document.createElement('div');
host.id = 'chat-widget-host';
document.body.appendChild(host);
const shadow = host.attachShadow({ mode: 'open' });
createWidget(shadow, {
  apiBase: cfg.apiBase ?? '/chat-api',
  title: cfg.title ?? '智能助手',
  accent: cfg.accent ?? '#1C64F2',
});
```

### 3.3 布局规则

- 桌面：气泡 `position: fixed; right: 20px; bottom: 20px; z-index: 2147483000`（接近上限，避免被宿主弹层盖住）；展开面板 400×600（可通过 data 属性覆盖）；
- 窄屏（<640px）：面板全屏覆盖；
- Shadow host 本身 `all: initial`，不参与宿主布局流。

### 4.2 关键交互规则

| 交互 | 规则 | 出处 |
| --- | --- | --- |
| 中文输入 | Enter 提交前判断 `e.isComposing \|\| e.keyCode === 229`，拼音选词 Enter 不误发 | 渲染方案第 5 课 |
| 滚动 | 跟随最新输出；用户上翻即暂停跟随，显示"回到最新"按钮；不因每个 token 强拉到底 | composable-agent-ui §3 |
| 流式取消 | 发送新消息或点"停止"→ `AbortController.abort()`；旧流迟到数据按 run 代次丢弃 | streaming-and-events |
| 消息渲染 | Markdown 增量渲染（markdown-it 或 Streamdown）；**永远不渲染模型输出的原始 HTML** | 渲染方案第 5 课 |
| 错误态 | 网络失败/超时/interrupted 都显示真实状态，保留输入内容，提供"重试" | 两个 Skill 包通用要求 |
| 暗色模式 | Shadow 内用 `prefers-color-scheme` 媒体查询，代码块双主题 | 渲染方案第 5 课 |

### 4.3 流式接收

原生 `EventSource` 不支持 POST，用 `fetch + ReadableStream` 手动解析 SSE：

```ts
async function streamChat(apiBase: string, convId: string, body: object,
                          onEvent: (evt: string, data: any) => void,
                          signal: AbortSignal) {
  const res = await fetch(`${apiBase}/conversations/${convId}/messages`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    credentials: 'same-origin',          // 携带宿主 session cookie
    body: JSON.stringify(body),
    signal,
  });
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`);
  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });   // 增量 UTF-8 解码
    const frames = buffer.split('\n\n');
    buffer = frames.pop()!;                              // 残帧留到下一轮
    for (const frame of frames) {
      const evt = frame.match(/^event: (.+)$/m)?.[1] ?? 'message';
      const data = frame.split('\n')
        .filter(l => l.startsWith('data:'))
        .map(l => l.slice(5).trimStart()).join('\n');    // 多行 data 拼接
      onEvent(evt, JSON.parse(data));
    }
  }
  // EOF 但未收到 done → 视为 interrupted，不算成功
}
```

## 5. 会话管理（重点）

这是本方案最需要想清楚的章节。核心答案：**会话状态全部在服务端，前端只持有"当前会话 ID"；刷新 = 用 ID 从服务端回放。**

### 5.1 概念模型

```
User（宿主登录用户，服务端绑定，前端不可指定）
 └─ Conversation（会话）      id, title, created_at, updated_at, status
     ├─ Message（消息）        id, role, content_md, status, run_id, created_at
     ├─ Run（一次执行）        id, conversation_id, status, cancelled, created_at
     └─ File（文件槽位）       id, direction(in/out), name, path, status
```

- **Conversation 是持久实体**：存在服务端 SQLite，按 user_id 隔离；
- **Run 是执行实体**：每次发送消息产生一个 run，承载取消标记与代次；刷新后 run 不可恢复为"继续流式"，只能呈现已落库的部分（见 5.4）；
- **Message 是展示实体**：用户消息发送即落库；助手消息**流式过程中按节流落库**（见 5.4），因此刷新能恢复大部分内容。

### 5.2 刷新继承策略

```
打开页面
  │
  ├─ localStorage 有 activeConversationId？
  │    ├─ 有 → GET /conversations/{id}
  │    │        ├─ 200 → 回放消息列表，进入该会话
  │    │        └─ 404/403 → 清除本地 ID，走"无"分支
  │    └─ 无 → 不自动建会话！显示空态欢迎页，
  │            用户发出第一条消息时才 POST /conversations
  │
  └─ 切换/新建会话 → 更新 localStorage.activeConversationId
```

要点：
- **不预建空会话**：避免用户每次刷新都产生一条空历史。第一条消息发送时，前端先 `POST /conversations` 拿 id，再发消息（或由一个复合端点 `POST /conversations` 直接携带首条消息，服务端建会话+启动 run 一步到位，推荐后者，少一次往返）；
- **会话不存在时降级**：localStorage 里的 ID 可能因删除会话、换账号、清库而失效，必须走 404 分支而不是白屏；
- **多标签页**：两个标签页各自持有 activeConversationId，互不干扰；如需同步可监听 `storage` 事件，非必需，v1 不做。

### 5.3 历史会话管理

| 功能 | 端点 | 说明 |
| --- | --- | --- |
| 列表 | `GET /conversations?cursor=&limit=20` | 按 updated_at 倒序，游标分页；每条返回 id/title/updated_at/最后一条消息摘要 |
| 新建 | `POST /conversations`（可携首条消息） | 返回 conversation_id，前端写入 localStorage |
| 切换 | `GET /conversations/{id}` | 拉取全量消息回放（消息量大时加分页，v1 单会话消息量小可全量） |
| 重命名 | `PATCH /conversations/{id}` | 双击标题或抽屉内菜单触发 |
| 删除 | `DELETE /conversations/{id}` | 级联删消息/文件/工作目录；若删的是当前会话，清 localStorage 回到空态 |
| 自动标题 | 服务端行为 | 首轮消息完成后，用模型生成 10 字内标题异步回填（`event: conversation_title` 推送） |

所有端点服务端校验 `conversation.user_id == current_user.id`，**越权访问返回 404 而非 403**（不暴露存在性）。

### 5.4 流式中断与刷新恢复

刷新发生在流式中途是常态，必须定义清楚：

**服务端落库策略**：助手消息在流式期间**每收到 ~200ms 或 ~500 字符就 UPDATE 一次 content_md**（而非只在结束时写），run 结束（done/failed/cancelled/断连）时写终态。

**消息状态机**：

```
streaming → done            正常完成
streaming → interrupted     连接断开/页面关闭（finally 中检测客户端断连后标记）
streaming → failed          模型/工具报错
streaming → cancelled       用户主动停止（若服务端支持取消端点）
```

**刷新后的呈现规则**：
- `done` 消息正常展示；
- `interrupted` 消息展示已落库的部分内容，尾部追加灰色提示"输出中断"，附"继续"按钮（重新发一条"继续"消息，而不是尝试恢复旧流——SSE 流不可恢复，恢复的是**上下文**）；
- 不把 EOF 当作成功——只有收到 `event: done` 的消息才算完成。

### 5.5 多 worker 部署注意

- run 的取消标记、SSE 流句柄是**进程内存态**：宿主若以 `--workers 4` 运行，"发消息"和"停止"两个请求可能落在不同 worker。v1 方案：**单 worker 运行对话子应用**，或取消功能先不做（前端 abort 只断本地流，服务端靠客户端断连检测在 finally 中终止模型调用）；
- 会话/消息/文件元数据在 SQLite，天然跨进程共享，无此问题；
- 未来扩展（多副本）：把 run 状态挪到 Redis，SSE 改 Pub/Sub——本文档不要求 v1 实现。

## 6. 后端 API 契约

统一前缀 `/chat-api`；统一鉴权 `Depends(get_current_user)`（复用宿主依赖）；错误格式 `{"error": {"code": "...", "message": "...", "retryable": bool}}`。

### 6.1 会话

**`POST /conversations`** — 新建会话（可携首条消息，一步到位）

```jsonc
// 请求
{ "message": "帮我检查这份数据", "file_ids": ["f_01..."], "skill_hint": "data-check" }
// 响应 200（无 message 时）
{ "id": "c_01J8Z...", "title": "新会话", "created_at": "..." }
// 携 message 时：直接返回 SSE 流（同 6.2），会话 id 通过首个事件下发：
// event: conversation_meta
// data: {"conversation_id": "c_01J8Z...", "title": "新会话"}
```

**`GET /conversations?cursor=&limit=20`**

```jsonc
{ "items": [
    { "id": "c_01...", "title": "检查销售数据", "updated_at": "...",
      "last_message_preview": "发现 3 个缺失值…" }
  ],
  "next_cursor": "eyJ..." }
```

**`GET /conversations/{id}`**

```jsonc
{ "id": "c_01...", "title": "检查销售数据",
  "messages": [
    { "id": "m_01", "role": "user", "content_md": "帮我检查这份数据",
      "attachments": [{"file_id": "f_01", "name": "a.csv"}], "created_at": "..." },
    { "id": "m_02", "role": "assistant", "content_md": "发现 **3** 个缺失值…",
      "status": "done", "artifacts": [{"file_id": "f_02", "name": "report.xlsx"}],
      "created_at": "..." }
  ] }
```

**`PATCH /conversations/{id}`** — `{ "title": "新标题" }`
**`DELETE /conversations/{id}`** — 204；级联清理（见 §8、§10）。

### 6.2 发消息（SSE 流）

**`POST /conversations/{id}/messages`** → `text/event-stream`

```jsonc
// 请求体
{ "content": "缺失值怎么处理比较好？", "file_ids": [], "client_msg_id": "uuid-..." }
```

- `client_msg_id`：前端生成的幂等键，服务端去重——**防止重试/双击产生两条用户消息**；
- 响应头：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`（防 Nginx 缓冲导致流"一次性全到"）；
- 事件序列见 §7。

### 6.3 文件

**`POST /conversations/{id}/files`** — multipart 上传（输入槽位）

```
限制：单文件 ≤ 20MB（可配）；类型白名单 [csv, xlsx, pdf, docx, txt, md, png, jpg]
响应：{ "file_id": "f_01...", "name": "a.csv", "size": 15234 }
```

**`GET /files/{file_id}/download`** — 下载（输入文件回取 + 产物下载共用）
校验 file 所属 conversation 的 user_id；`Content-Disposition: attachment; filename*=UTF-8''...`

### 6.4 能力目录

**`GET /skills`** → 前端用于展示"这个助手能做什么"（空态引导/斜杠提示）

```jsonc
{ "skills": [
    { "id": "data-check", "name": "数据检查",
      "description": "检查 CSV/Excel 的列名、缺失值与基本统计",
      "accepts_files": ["csv", "xlsx"] }
  ] }
```

## 7. SSE 事件协议

应用级事件（自定义，非任何供应商标准），每条消息发送的事件流：

```
event: run_meta
data: {"run_id": "r_01...", "message_id": "m_02", "client_msg_id": "uuid-..."}

event: delta
data: {"text": "我先调用**数据检查**工具…"}        ← 可多条，追加到 message_id

event: tool_status
data: {"tool": "data-check", "status": "running", "summary": "正在检查 a.csv"}

event: tool_status
data: {"tool": "data-check", "status": "succeeded", "summary": "3 个缺失值，2 列类型异常"}

event: file_ready
data: {"file_id": "f_02", "name": "report.xlsx", "size": 40211}   ← 产物槽位

event: delta
data: {"text": "检查完成。发现 **3** 个缺失值…"}

event: done
data: {"message_id": "m_02", "usage": {...}}       ← 唯一成功标志
```

异常路径：

```
event: error
data: {"code": "llm_timeout", "message": "模型响应超时", "retryable": true}
（error 是终态，前端标记该消息 failed，保留重试按钮）
```

协议纪律（来自 streaming-and-events.md 的硬约束）：

1. **只有 `done` 算成功**；连接中途 EOF → 前端把该消息标 `interrupted`；
2. 不用 `data: {}` 之类负载形状判断结束，用 event 名；
3. `json.dumps(..., ensure_ascii=False)`，中文不转义；
4. 工具参数片段**先累积、Schema+权限校验通过后才执行**；工具状态/产物走独立事件，不从 Markdown 里正则反推；
5. 前端发新请求前 abort 旧 reader，并在每个回调检查 run 代次——旧流迟到数据不得写入新消息。

## 8. 数据模型（SQLite）

SQLite + WAL 模式对单团队工具足够；ORM 用 SQLModel 或 SQLAlchemy 均可。

```sql
CREATE TABLE conversations (
  id          TEXT PRIMARY KEY,           -- c_ + ulid
  user_id     TEXT NOT NULL,              -- 宿主用户 id，服务端绑定
  title       TEXT NOT NULL DEFAULT '新会话',
  status      TEXT NOT NULL DEFAULT 'active',   -- active | deleted
  created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_conv_user_updated ON conversations(user_id, status, updated_at DESC);

CREATE TABLE messages (
  id             TEXT PRIMARY KEY,        -- m_ + ulid
  conversation_id TEXT NOT NULL REFERENCES conversations(id),
  run_id         TEXT,                    -- 助手消息关联的 run
  role           TEXT NOT NULL,           -- user | assistant
  content_md     TEXT NOT NULL DEFAULT '',
  status         TEXT NOT NULL DEFAULT 'done',  -- streaming|done|interrupted|failed|cancelled
  client_msg_id  TEXT,                    -- 用户消息幂等键
  attachments    TEXT,                    -- JSON: [{file_id,name}]
  artifacts      TEXT,                    -- JSON: [{file_id,name}]
  created_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_msg_conv ON messages(conversation_id, created_at);
CREATE UNIQUE INDEX idx_msg_idem ON messages(conversation_id, client_msg_id)
  WHERE client_msg_id IS NOT NULL;

CREATE TABLE runs (
  id              TEXT PRIMARY KEY,       -- r_ + ulid
  conversation_id TEXT NOT NULL REFERENCES conversations(id),
  status          TEXT NOT NULL DEFAULT 'running',  -- running|done|failed|cancelled|interrupted
  error_code      TEXT,
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  finished_at     TIMESTAMP
);

CREATE TABLE files (
  id              TEXT PRIMARY KEY,       -- f_ + ulid
  conversation_id TEXT NOT NULL REFERENCES conversations(id),
  user_id         TEXT NOT NULL,          -- 冗余，下载鉴权快查
  direction       TEXT NOT NULL,          -- in(用户上传) | out(产物)
  name            TEXT NOT NULL,
  mime            TEXT,
  size            INTEGER,
  disk_path       TEXT NOT NULL,          -- workdir/{conv_id}/{file_id}/{name}
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

删除会话时：软删 `status='deleted'`（列表过滤），异步硬清磁盘目录；或 v1 直接硬删 + `shutil.rmtree(workdir/{conv_id})`。

## 9. Skill 集成：能力契约

### 9.1 从 SKILL.md 到能力契约

SKILL.md 是**待分析材料**，不是可执行指令。每个 Skill 落成一条契约（存服务端 `skills/*.contract.json`）：

```json
{
  "capability_id": "data-check",
  "purpose": "检查当前会话中用户上传的数据集（列名、缺失值、基本统计）",
  "source": {"kind": "python_script", "entrypoint": "skills/data-check/scripts/check.py"},
  "input_schema": {
    "type": "object",
    "properties": {
      "file_id": {"type": "string", "description": "本会话中已上传的数据文件 id"}
    },
    "required": ["file_id"],
    "additionalProperties": false
  },
  "server_bindings": ["authenticated_user", "conversation_workdir", "file_path_resolved_from_id"],
  "output": {"summary": "string", "findings": "array", "artifact_refs": "array"},
  "error_codes": ["invalid_input", "file_not_found", "tool_timeout", "tool_failed"],
  "side_effect": "local_reversible",
  "timeout_seconds": 60,
  "invocation": "fixed_argv_without_shell",
  "validation_status": "adapted"
}
```

### 9.2 工具调用循环（服务端，伪码）

```python
async def run_agent_loop(conv_id, user, run_id, user_text, file_ids):
    history = load_messages(conv_id)                 # 服务端权威历史
    tools = [to_openai_tool(c) for c in load_contracts()]   # 能力目录 → function 定义
    budget = 8                                        # 工具轮次预算
    for _ in range(budget):
        check_cancelled(run_id)
        resp = await llm.chat(history, tools=tools, stream=False)  # 决策轮
        if resp.tool_calls:
            for call in resp.tool_calls:
                contract = get_contract(call.name)     # 未知工具 → 服务端拒绝
                args = validate(call.arguments, contract.input_schema)  # 服务端重校验
                args = inject_server_bindings(args, user, conv_id)      # 路径/身份服务端注入
                emit("tool_status", {"tool": call.name, "status": "running"})
                try:
                    result = await run_in_executor(invoke, contract, args)  # 白名单 argv，超时控制
                    register_artifacts(result, conv_id)  # 产物落 files 表 → emit file_ready
                    emit("tool_status", {"tool": call.name, "status": "succeeded",
                                         "summary": result.summary})
                except ToolError as e:
                    emit("tool_status", {"tool": call.name, "status": "failed"})
                    result = {"error": e.code, "message": e.safe_message}
                history.append(tool_output(call.id, result))
            continue
        # 无工具调用 → 最终回答：流式转发模型 delta
        async for chunk in llm.stream_text(history):
            emit_delta(chunk.text); throttled_persist(message_id, chunk.text)
        emit_done(); return
    emit_error("budget_exceeded")
```

红线：
- `file_id → 磁盘路径` 的解析在服务端做，**模型永远拿不到也不允许给文件系统路径**；
- 脚本调用 `subprocess` 用**固定 argv 数组、无 shell**，参数白名单，cwd 绑定会话工作目录，超时强杀；
- 写操作类 Skill（`side_effect: external_write`）v1 不接；只接 `read_only` / `local_reversible`；
- 会话上下文按需加载：系统提示里放能力目录摘要，不灌入全部 SKILL.md 原文。

## 10. 文件槽位设计

### 10.1 输入槽位（上传）

- 前端：📎 按钮 → 选择文件 → 立即 `POST /files` 上传 → 在输入区上方生成"文件卡"（名称、大小、✕ 移除）。**先上传后引用**：发送消息时只带 `file_ids`；
- 上传中/失败状态可视化，失败的文件卡带重试；
- 落盘：`workdir/{conversation_id}/{file_id}/{原始文件名}`，原始文件名仅存元数据，**不用用户提供的文件名拼路径**（防路径穿越）。

### 10.2 输出槽位（产物）

- Skill 在工作目录产出的文件，由适配层登记进 `files` 表（`direction='out'`），SSE 推 `file_ready`；
- 前端在对应助手消息下方渲染产物卡：文件名、大小、下载按钮（`GET /files/{id}/download`）；
- 产物与会话同生命周期，删除会话时级联清理。

### 10.3 文件与 Skill 的衔接

模型在 `input_schema` 里只看到 `file_id`（外加工具描述说明"用户上传的文件以 file_id 引用"）；服务端执行前把 `file_id` 解析成绝对路径注入 argv。这条链路保证：模型无法访问会话目录之外的任何文件。

## 11. 安全与工程红线

| 类别 | 红线 |
| --- | --- |
| 身份 | conversation/file 的 user_id 由服务端从登录态绑定；越权访问一律 404 |
| XSS | 模型输出按纯文本 Markdown 渲染，禁用原始 HTML；任何 `dangerouslySetInnerHTML` 类用法需过 DOMPurify |
| 路径 | 不接受客户端/模型提供的文件路径；一律 ID → 服务端反查 |
| 命令执行 | 固定 argv、无 shell、白名单、超时、cwd 绑定工作目录 |
| 密钥 | LLM Key 只在服务端环境变量；不进前端、URL、日志、错误正文 |
| 上传 | 类型白名单 + 大小上限 + 存储配额；不提供任意文件下载端点 |
| 幂等 | 发消息带 `client_msg_id` 去重；不自动重发可能写入的 POST |
| 流式 | abort 旧流、run 代次丢弃迟到数据、EOF≠成功、断连 finally 清理 |
| 真实性 | 模型失败/超时显示真实失败状态，不用演示数据伪装成功；缺配置时明确标注 demo 模式 |

## 12. 实施路线图与验收

| 切片 | 内容 | 验收标准 |
| --- | --- | --- |
| **S1 骨架** | 宿主加 script；widget 气泡/面板/Shadow DOM；后端 `POST /conversations`（携首条消息）返回 **mock SSE 流** | 页面上发一条消息，看到逐字渲染的 mock Markdown（含代码块/表格）；宿主页面样式零影响 |
| **S2 会话持久化** | SQLite 建表；会话列表/切换/新建/重命名/删除；localStorage 继承 | 发几条消息后 **F5 刷新 → 会话原样恢复**；开历史抽屉切换会话；删除当前会话回到空态 |
| **S3 真实模型** | 接入真实 LLM 端点（流式）；IME 守卫；abort；错误态 | 真实回答流式渲染；中途刷新 → 消息显示"输出中断"且已输出部分保留；选词不误发 |
| **S4 Skill 闭环** | 一个真实 Skill（建议拿数据检查脚本做首个）：契约、白名单调用、tool_status 事件 | 上传 csv → 问"检查一下"→ 看到工具状态 → 得到基于脚本真实输出的回答 |

| **收尾** | 窄屏、暗色、性能（长回复只有最后一条消息重渲染）、README 配置说明 | 真机浏览器走一遍主路径 + 一个失败路径 |

依赖建议：`fastapi uvicorn sqlmodel httpx`（后端）；`vite typescript markdown-it`（widget 构建，或换 Preact）。

## 13. 坑位速查表

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 中文变 `\u4f60\u597d` | `json.dumps` 没加 `ensure_ascii=False` | §7.3 |
| 流一次性全到、不逐字 | 反代/gzip 缓冲 | 响应头 `X-Accel-Buffering: no`，确认无压缩中间件拦截 SSE |
| 悬浮窗样式被宿主污染/污染宿主 | 没用 Shadow DOM 或样式外泄 | §3.3，样式全部进 shadow root |
| 拼音选词把消息发出去了 | 缺 IME 守卫 | `isComposing` 判断 |
| 刷新后会话丢了 | ID 只存在内存 | §5.2，localStorage + 服务端回放 |
| 刷新后流式回复消失 | 只在流结束时落库 | §5.4 节流落库 |
| 重试/双击产生两条用户消息 | 无幂等键 | `client_msg_id` 唯一索引 |
| 停上一条再发新的一条，旧内容串进新消息 | 没 abort / 没查 run 代次 | §7.5 |
| 模型"看到"了别的会话的文件 | 接受了模型给的路径 | §10.3，ID 反查 |
| 删除会话后下载链接还能用 | 只删了会话行 | 级联删 files 行 + 磁盘目录 |
| 多 worker 下"停止"不生效 | run 状态在单进程内存 | §5.5 |
