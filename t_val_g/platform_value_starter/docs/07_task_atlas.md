# 任务分布图谱：先知道"平台在被用来做什么"，再谈评测与训练

任务分布图谱是整个价值体系里**最便宜且三栖**的产物：对内回答领导"平台在被用来做什么"，对外是"某行业工程师如何用 AI agent"的实证研究素材，对评测集它提供选题配额。本包用 `scripts/task_atlas.py` 生成，标准库即可运行。

## 1. 它是什么、不是什么

| 是 | 不是 |
|---|---|
| 首条用户消息的意图标签分布 | 整场会话的完整任务画像（会话可能多目标，先不自动拆分） |
| 带可信度分级的候选标签（human > router > keywords > unknown） | 一个拍平的"真实分布" |
| 按部门/月份/交互深度切片的描述统计 | 部门间优劣排名 |
| benchmark 选题配额的输入 | 模型能力的直接度量 |

核心纪律：**unknown 不消失、不外推**。覆盖率低（比如只有关键词标签）时，图谱的汇报口径是"已标注子集里 X 占多少"，而不是"全平台 X 占多少"。覆盖率本身就是图谱要展示的第一张表。

## 2. 标签来源的分级与升级路径

```text
第一期：--keywords 规则兜底      → 全部标 candidate，覆盖可能只有 30-50%
第二期：router 预测 + 置信阈值   → 达阈值进 candidate，低置信仍 unknown
终态：  抽样人工确认             → 进 human 层，逐级替换候选标签
```

- 关键词和路由器的标签都叫**候选**；进入对领导/对外材料时保留"候选"字样；
- 人工确认不需要全量：每期按部门×意图分层抽 20–50 条核对候选标签的**精度**，把精度写进图谱脚注（例："coding 类候选标签抽 30 条核对，精度 87%"）。这比全量标注便宜两个数量级，且让你的分布数字有了误差棒；
- 实测过的坑：稀有类（如 coding 在工艺科）候选标签精度差，小样本下别下结论——图谱用 `--min-n` 把小单元格直接抑制掉，物理上防止过度解读。

## 3. 三个最有信息量的读法

1. **部门 × 意图**：如果 IAD-D 集中在"数据分析+知识查证"、BEOL 集中在"知识查证"，那 skill 建设、bench 分片、路由默认值的优先级全都不一样——一张表直接给出资源分配建议；
2. **意图 × 月份**：某类任务占比持续上升 = 该平台能力在被更多场景接纳（或该类任务反复失败重试——需要配合完成证据区分，占比上升本身不自动是好事）；
3. **意图 × 交互深度**：深迭代占比高的意图族是"困难任务族"候选——但记住深度 ≠ 复杂度，也可能是模型反复没做对。**这个交叉表是用来生成假设的，不是用来下结论的**。

## 4. 图谱如何驱动评测集（与 docs/03 的接口）

图谱输出最后一张表是 **benchmark 选题配额**：representative 子集按观测占比抽样，保证 bench 反映真实使用结构；regression 子集不按比例，从失败案例定向挑选。两条子集永远分开报告。

闭环如下：

```text
会话数据 → 图谱（分布+候选标签）
        → representative 配额 → curated 任务包 → 冻结 bench（docs/03）
        → 高占比且表现差的意图族 → 修复优先级（接 org_skill_map 的失败热点）
        → 修复后回归 → bench 版本演进（anchor 不动，挑战集新增）
```

没有图谱时选题靠记忆和感觉，题集会慢慢漂向"我们以为用户在做什么"；有图谱，选题偏差可以被审查和纠正。

## 5. 对外/对学术界的形态

脱敏聚合后的意图×部门分布表 + 标签分级方法 + 抽样核对精度，就构成一篇"某行业企业级 agent 使用分布"短报告的核心——这类实证分布研究目前公开文献里几乎不存在（对标 Anthropic Economic Index 的形式）。**原始会话、标题、具体部门业务细节不出厂**；可公开的只有聚合比例、方法论和脱敏后的任务分类体系本身。
