# 用户确认、向上汇报与每周迭代

确认不是让用户帮平台完成 KPI，而是核对事实、了解哪里不好用，并让改进回到用户身上。下面是你可以改成平台内轻量卡片或线下访谈的文案；本包不会发送任何消息。

## 1. 给用户的确认卡

> 我们想确认这次协助里哪些部分实际有用，并优先修掉给你增加工作量的地方。系统预填内容可以修改；可以选“尚不清楚”，也可以跳过。
>
> 这次任务：〔从对话整理，用户可修改〕  
> 结果：〔回答片段/文件/版本的链接〕
>
> 1. 结果目前怎样？可直接用 / 部分能用 / 不能用 / 还没检查。  
> 2. 是否已用到工作里？已使用 / 暂未使用 / 尚不清楚。用了的话，在哪一步？〔可选短句〕  
> 3. 最希望我们改善什么？〔可选短句〕
>
> 如方便估计：同样质量的任务，不用平台你大概要投入多少人工时间？用了平台后，连检查、修改和返工总共投入多少？可填范围或“不知道”。如果原本不会做这项任务，也请直接说明。

技术可用性和业务采用不强行同步。例如“不用，但输出可用”是一条合理记录。不要只提供“节省了多久”的正向问题；“没帮上忙”“增加返工”也应该顺畅填写。

采用情况确认与“允许该内容用于训练/公开案例”分开处理。训练导出的 `allowed_uses` 是明确的内部用途记录，不由一个点赞或感谢词自动推定。

建议同一用户每周至多邀请确认一次（试点默认，可调整）；用户未响应就保留未知。先给出结果链接和一句预填用途，省去让人重读整场对话的负担。

## 2. 案例卡最小字段

| 字段 | 由谁提供 | 用途 |
|---|---|---|
| tenant/session/revision/evidence_ref | 平台自动 | 回到原始证据；会话更新后重新确认 |
| 任务与工作步骤 | 平台预填，用户修改 | 连接交互和业务，不推断项目/收益 |
| outcome 与 adoption | 用户/验收人分别确认 | 可用性、采用情况分开 |
| work_item_id | 明确任务归并，用户/技术核对 | 同一事项跨会话去重 |
| failure_reason | 技术复核 | 模型、工具、数据、权限、需求变更、unknown |
| 人工时间范围与依据 | 用户估计或配对观测 | 仅对完整区间计算，不当现金收益 |
| 下一步动作与验证题 | 平台负责人 | 让反馈转成可回归的改进 |

员工身份/职级不进入价值模型。不做“最浪费用户”榜单。用户维度主要用于帮助其复用成果、定位重复失败和改进接入体验；管理层默认看部门/场景聚合及获准展示的案例。

## 3. 采样：汇报样本与排障样本分开

每周先试 10–20 条即可：一半从新会话随机挑选（包括无产物问答、未知结果），另一半从工具错误、重复重试、用户主动反馈中定向挑选。给每条记录 `sample_reason`；别把只看 Top 产出的确认比例当成全平台成功率。

抽 5–10 条适合调解析器或词表，不足以估计很精确的全平台完成率。未来需要总体估计时，按事先定义的场景/部门/时间分层抽样，记录抽样权重和不响应；统计口径应与“定向复核已知问题”分开。

用户明确纠正也要区分：模型答错、原输入缺条件、业务需求改变、材料更新、风格偏好。不能把“再加一列”都归成模型失败。

## 4. 一个能接受细问的汇报模板

以下是模板，方括号待真实数据填写，不是本次分析结论。

> 在〔时间窗〕，平台发生了〔实测请求/新建会话/主动活跃人数〕，成本台账为〔金额与成本口径〕。输入 usage 覆盖〔n/N〕，组织映射覆盖〔n/N〕；未知与跨期未分摊部分为〔说明〕。这些先说明资源使用与覆盖。
>
> 本期复核〔N〕条，已知结果〔K〕条，其中〔U〕条可用；另有〔X〕条结果未知。在采用情况已知的〔A〕条里，〔B〕条已用于工作，按业务事项去重为〔W〕项。此比例仅限复核子集，不代表全平台完成率。
>
> 具体案例：〔任务〕→〔产物/回答证据〕→〔用户确认用在什么步骤〕。〔有完整基线的事项数〕项提供了人工投入范围，报告该子集的净时间变化，不将其直接外推成公司总节省。
>
> 我们发现〔一个高频可复现问题〕，修改了〔skill/API/工具〕。在〔固定题与版本〕上，原方案通过〔a/n〕，修复后通过〔b/n〕；代价变化为〔token/延迟〕。这证明该项平台建设的具体改进。
>
> 下一阶段优先投入〔一个明确动作〕，用〔固定任务与用户采用确认〕判断是否继续。尚无法证明的部分为〔项目收益/现金节省/良率影响等〕，补证据需要〔明确数据与负责人〕。

展示 3 张具体案例卡（成功、部分成功、失败后修复各一张）往往比价值象限更容易接受细问。案例的作用是解释机制，不代替总体统计；不要用几张最佳案例证明全平台质量。

半导体语境里的可信叙事可以是“实验条件比对材料被工程师采用”“日志解析脚本通过现有输入验证并被使用”“某知识检索的证据定位更完整”。“提升良率、缩短产品周期、替代专家”等更强结论需要额外业务结果和对照设计。

## 5. 每周闭环只留五个动作

| 时点 | 动作 | 产物 | 负责人 |
|---|---|---|---|
| 日常/周初 | 导出变化、幂等导入、保留迟到记录 | 当前案例快照、缺字段报告 | 你维护的批处理 |
| 每周一次 | 小批次用户确认与技术归因 | 使用卡、失败原因 | 用户可选反馈，技术复核 |
| 每周一次 | 修复一个高频且可验证的问题 | 小 diff/skill 版本、一个 regression task | 平台开发 |
| 修复或新模型时 | 固定题同条件对比 | 通过/退步、错误、资源报告 | 现有验收流程 |
| 每月一次 | 整理批准任务，冻结新候选版本 | anchor + 新挑战集，少量训练候选 | 你与领域验收人 |

`run_weekly.sh` 只是批处理参考，不是已为你配置的定时任务。完成真实适配后在公司调度环境调用即可；报告以新目录写出，数据库保留稳定状态。它不自动改人工标签、发布模型或训练。

停止条件也简单：如果错误主要来自 API/资料缺失，就优先改环境；如果 CPU 分类已够用，就不升 LoRA；如果用户反馈负担大，就缩小采样和预填更好的证据；如果 benchmark 无法冻结必要输入，就先不把它计入可比评测。每次只留下一个待验证假设。
