# 拿之前的建议做了数据处理和实践后的实战反馈：从「假设数据」到「全量真实数据」的执行对照

> 说明：之前的（`platform_value_plan.md` / `original_scripts_review.md` / `platform_value_starter/`）未接触真实数据、只按静态 zip 样例假设能力。本文基于**真实平台数据的完整执行**（1200+ 会话、 多部门、多名用户、2500+ 用户全量可拉探针），逐条对照之前的建议分析，分四类反馈：符合且易实现 / 不太符合但可间接实现 / 完全不符 / 之前建议中没想到的价值机会点。末尾附对之前的给的这些脚本和文档的具体修改建议。

## 0. 实际做了什么（30 秒概览）

- **数据接入（C）**：实测平台会话 API 支持按 user 全量拉取——2999/2999 用户 100% 可拉、全程 7.6s、0 个 404、898 人（29.9%）探测日有活跃、健康 workspaces=3420。
- **组织映射（A）**：`lookup_emp` 把 1226 会话归到 3 个科：智能分析与决策D科（IAD-D，1059 会话/4.5% 失败/2600 产出）、后段蚀刻五科（132/3.8%/489）、后段蚀刻四科（35/4.1%/137）；技能×科归因出强规律。
- **评测/训练基建（E + bench/router）**：扩展 `build_datasets.py` 支持 org_section 切分（防同科泄漏）；冻结 bench_v2=51 题（31 真实跨科路由 + 10 合成 query_extract + 10 合成 recipe_diff）；CPU 意图分类 router 真实训练（dev macro-F1 0.570 vs 多数类 0.137，holdout 0.434 vs 0.163）。
- **红线全程遵守**：不做自动 DPO/SFT、sft_*=0、合成不进 router、unknown 单列、缺失不计平局、标签显式 `AUTO:*` 待人工复核。

## ③ 完全不符的地方（前提失效 / 判断相反）

1. **「假设只有静态 zip 导出、没有原始数据、不能确认数字」——前提彻底失效**。
   实测平台会话 API 支持**按用户全量拉取全部历史**（`/api/sessions?user=&date=&mode=active`，200/404 判别），2999 用户 100% 可拉、0 个 404。之前的建议假设中的「只能拿小样例 zip」假设与真实能力差了一个数量级——这不是"间接实现"能补的，是**机会上限被低估**。

2. **「跨部门价值排名暂缓」——判断相反**。我们做的 org_skill_map（组织×可靠性×技能归因）是最便宜却信号最强的一步：
   - IAD-D 高频用高失败技能：etch-data 43.3%、etch-doe 75%、etch-literature 75.8%（几乎全在 IAD-D）；
   - BEOL 两科用低失败技能：apple-to-apple 1.5%、beol-etch-domain-mapper 0%、g2-dyh-hx2-data-nav 0%。
   一次静态分析就给出「高频问题修复清单」的明确落点，远超建议暂缓的范围。

3. **六维中「组织」只是切片注释**。实战中组织身份是**信息量第一的切片**（技能归因、失败率、token 占比全按科分化明显），不是第六个维度。

4. **每周 30-60 分钟人工运营节奏不现实**。无持续人工资源，只能一次性+自动化替代；之前建议和假设中的"每周复核"应降级为"抽样+自动化+待复核标记"。

5. **asset_reuse 的 basename 同名担忧前提不成立**。担忧建立在"有可挖的复用证据"上；真实数据里**跨会话读取事件根本不存在**，该维度是空白而非"可修"。

## ④ 建议和假设中没想到、但实际有价值可重点做的机会点（跨用户/跨组织/多会话核心）

1. **组织×技能×可靠性的三角归因（最高 ROI）**：IAD-D 1059 会话集中在高失败技能（xxx1 skill 75.8% / xxx2 skill 75% / xxx3 skill  43.3%）→ 直接产出**按科的高频问题修复清单 + 回归题**，比"抽最贵 5 条"更系统、可交给对应科。

2. **跨组织技能供给/需求错位检测**：g2-dyh-hx2-data-nav 使用率 0% 却是 BEOL 领域技能 → 要么没被宣传、要么匹配错。量化"哪些技能没被用起来"是平台运营的新抓手，之前的假设和建议中只谈"使用覆盖"没谈"供给侧"。

3. **组织级默认路由**：各科任务/语言模式稳定（IAD-D 写报告/查数据、BEOL 查 CH 刻蚀）→ 可做 **per-org 的 router 先验/默认值**。我们在做跨科泛化 router（IAD-D 训→BEOL 验），反向即为"给每科配默认路由"。

4. **组织切分 = 防泄漏的评测设计（之前的建议未涉及）**："IAD-D 训 → BEOL5 dev → BEOL4 holdout" 跨科泛化比随机 split 更接近真实上线。建议和假设里对这个字段 `split_registry` 只按 source_group 切，**没防同科泄漏**；我们加了 `org:` 键与 manifest org_level，这是评测设计层面的新增价值。

5. **组织级 token/成本归因**：tokens_in IAD-D 982M / BEOL5 186M / BEOL4 53M → 成本账可**按科切片**，直接回答领导"钱用在哪/哪个科最烧"，建议和假设里成本账没给组织抓手。

6. **按组织分片的 bench**：单一通用 20-30 题不如 **BEOL bench / IAD-D bench** 分片可信——业务方的准绳是"我的科能不能用"，而非全公司均值。

7. **全平台首次全量分析**：既然 2999 用户全量可拉，第一次做"全平台跨用户分析"（谁在用/哪个 skill 没用起来/token 分布/失败模式）是从"个别演示"到"全量证据"的跃迁——你之前的假设受限于 zip 样例看不到这一步。

8. **多会话聚合成组织知识库候选**：1226 会话×3 科，每科有稳定的技能/问题模式，可提炼成**组织级 RAG/bench 素材**（不只是单案例）。
