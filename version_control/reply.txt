**建议把它做成一个“资产历史＋会话版本关联＋owner 维护”的工作台。** 你现有的个人/公共资源导出接口，已经足以启动快照、版本对比和历史恢复；再补少量运行时记录，就能接上之前的评测飞轮。

详细方案已整理为文档：[](sandbox:/workspace/scratch/ba3c80b651dc/deliverables/skill_agent_asset_platform_proposal.md)。

**最需要调整的一点：定时快照可以保存历史，但不能单独证明会话使用了哪个版本。**

例如，10:00 抓到 A，10:05 用户临时改成 B 并运行会话，10:10 又恢复成 A，两次快照都会漏掉 B。因此，建议区分：

| 概念   | 回答的问题              |
| ---- | ------------------ |
| 采集记录 | 什么时候、从哪个范围拉取，是否完整？ |
| 内容版本 | 实际保存了哪些文件和内容？      |
| 会话关联 | 哪次运行实际加载了哪个版本？     |

定时拉取继续做，同时逐步在 **primary 切换、subagent 启动、Skill 加载**时记录实际解析的来源和内容版本。历史数据只能按时间推定的，就标为“近似”，仍然可以用于探索性复盘。

**搭建方式可以很轻：一个管理应用、现有数据库、受控文件存储和后台同步任务。**

数据库保存资产身份、owner、版本索引、会话关联和变更记录；文件存储保存不可变内容。如果已有成熟内网 Git，可以用它承担目录历史和 diff。Git 的内容寻址存储适合保存和取回不同版本，但应用仍需另外管理权限、会话关联和评测结果。([Git Objects][1])

这里有几个设计细节值得第一版就做好：

* **资产身份包含命名空间。** 公共 `review` 与员工 A 的 `review` 是不同资产；同名覆盖关系以运行器实际解析为准。
* **Skill 保存整个运行所需目录。** 包括脚本、references、assets；Agent 保存 frontmatter 和正文，并记录依赖。
* **内容没变就复用版本。** 每次同步仍留下采集记录，避免“同步次数＝版本数量”。
* **不要直接用 ZIP 字节判断内容变化。** 打包时间等也可能改变 ZIP；应根据内部文件内容和稳定清单判断。
* **同步失败不等于删除。** 超时、分页不完整或无权限，都不能触发归档。

**至少需要具备这些功能，可以分两批完成。**

| 功能       | 最小实现                                          |
| -------- | --------------------------------------------- |
| 资产目录     | 个人/公共、owner、Skill/Agent、primary/subagent、当前状态 |
| 快照同步     | 定时＋手动；成功、失败、部分成功、最后成功时间                       |
| 历史与 diff | 文件增删改、正文差异、Agent 配置字段差异                       |
| 独立恢复     | 将指定历史版本恢复到实验工作目录                              |
| 会话版本关联   | 已确认、按时间推定、未知；保留证据来源                           |
| 候选维护     | owner 编辑或上传候选，附修改原因、来源会话和 diff                |
| 更新与回滚    | 防并发覆盖、记录发布、核对实际生效；回滚也留新记录                     |
| 归档与依赖    | 查看调用方、替代能力、归档原因和恢复入口                          |

前五项先解决历史和 baseline，后三项完成维护闭环。

**自动更新接口最重要的能力，是防止覆盖，以及确认生效。**

一次更新建议携带：

```text
目标资产
候选版本
基于哪个旧版本修改
变更原因／相关问题
本次提交标识
```

服务器发现当前内容已经不是那个旧版本时，返回冲突，让 owner 或自动化流程重新比较。HTTP 接口可以采用 ETag／`If-Match`，其用途就是避免并发更新造成覆盖。([rfc-editor.org][2])

Skill 目录宜先完整暂存，再受保护地切换，避免读到半套新文件。发布之后还要区分：

* 文件已经更新。
* 平台已发现或重新加载。
* 后续会话已确认使用新版本。

这三个状态分开，才能避免“上传成功，但评测仍跑着旧版本”。

**对于 baseline，资源版本只是其中一部分。**

还应保存原始任务输入、输入截止点、相关附件、模型与参数、必要工具和环境信息。动态 API、数据库和检索结果没有固定时，要显示差异或缺口。原会话最终产物与原始输入分开，防止复现时提前给出答案。

恢复优先进入独立工作区；新旧版本各使用同一份初始材料。准确恢复资源，也不代表模型会逐字重复原输出，应通过任务验收判断是否可比。

**Dashboard 建议围绕四个页面设计。**

| 页面    | 主要展示                          | 支持的决策           |
| ----- | ----------------------------- | --------------- |
| 总览    | 资产范围、同步覆盖、失败/超期、版本关联覆盖、待维护事项  | 当前历史是否可信，哪里缺数据？ |
| 资产详情  | owner、依赖、版本时间线、diff、相关会话、评测结果 | 这个能力哪里需要修改？     |
| 会话复现  | 原始输入、资源版本、确认程度、环境缺口、新旧结果      | 这次对照是否可比？       |
| 维护工作台 | 修改/新建/归档候选、原因、评测、发布与生效状态      | 哪些事情值得处理，进展到哪里？ |

总览优先展示**覆盖与缺口**，不要只展示资产数、版本数和调用量。资产详情中的“最近没使用”也需要附采集窗口；低频可能来自季度任务、发现困难或数据不完整。

对于你的飞轮，这个应用主要承担**版本、证据和工作区管理**。原有的信号分析、诊断、creator、评测 Skill 通过接口读取固定版本、生成候选、回写评测结果即可。

建议第一轮选少量个人资产和公共资产，跑通一个完整案例：**从会话问题找到当时版本，生成小改动，在两份独立工作区比较，再由 owner 发布并确认生效。** 跑通后扩大同步范围，比先收齐所有资源更能验证这个应用是否真正支持迭代。
