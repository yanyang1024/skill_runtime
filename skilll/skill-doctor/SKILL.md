# Skill Doctor

给 Skill 看病：先做确定性体检，再按症状开方，最小修改，最后复验。

## 工作原则

1. **先体检后诊断。** 先跑 `scripts/check_skill.py` 拿客观报告，再结合用户描述的症状定位病因。不跳过体检直接改。
2. **用户症状优先于检查清单。** 报告里的 warning 不必全修——只修与症状相关的，以及所有 error 级（违反规范）项。
3. **最小修改。** 一次只解决用户反馈的问题；不顺势重构，不改写风格。每处改动都能说清"改了什么、对应哪个症状"。

## 流程

### 第 1 步：体检

```bash
python3 scripts/check_skill.py <skill目录>
```

输入是 `.skill` 包时先解压再检查。报告分三级：**error**（违反规范，必须修）、**warning**（质量问题，结合症状修）、**info**（提示）。

### 第 2 步：按症状定位病因

| 症状（用户反馈） | 大概率病因 | 处方 |
|---|---|---|
| 该触发时不触发 | description 太抽象、缺用户原话级关键词；"何时用"写在了正文里 | 重写 description：功能 + 触发场景 + 关键词，语气可略强势 |
| 不该触发时乱触发 | description 过宽，或与同库其他 skill 的 description 重叠 | 加边界限定词，写明"不用于 X 场景"；收窄关键词 |
| 输出格式/质量不稳定 | 需要确定性的任务只用了高自由度文字；缺模板和正反例 | 给输出模板或正反例；脆弱操作下沉为 `scripts/` 脚本 |
| 太啰嗦、挤占上下文 | 正文超 500 行；细节与核心流程混杂；同一信息多处重复 | 细节拆 `references/` 并在正文写明何时读；去重；逐段过"值回 token 吗" |
| 引用的文件没被读到 | SKILL.md 没写明何时读；references 多层嵌套 | 正文加明确的"当 X 时读 Y"指引；嵌套拍平到一层 |
| 脚本一跑就报错 | 脚本从未实测；环境依赖未声明 | 实际运行并修复；依赖写进正文或 `compatibility` 字段 |
| 改了但没效果 | 改错了层：触发问题改了正文，或表现问题改了 description | 重新分层：触发类只动 frontmatter，表现类才动正文/资源 |

### 第 3 步：修复

- **触发问题**：只动 frontmatter 的 description，保持 ≤1024 字符、无尖括号。
- **结构问题**：移动文件后同步更新所有引用路径（一律正斜杠）。
- **资源问题**：删除无用文件；`references/` 内容在正文必须有入口指引。
- 修完重跑 `check_skill.py`，确认 error 清零、症状相关 warning 消除。

### 第 4 步：复验与交付

- 向用户说明：改了哪几处、各对应哪个症状、预期效果。
- 用 2~3 条正反例口头验证触发逻辑：正例应命中 description 关键词，反例不应命中。
- 用户要求分发时，重新打成 `.skill` 包（zip 格式改后缀即可）。

## 安全红线（顺手排雷，不替代专业扫描）

`check_skill.py` 内置少量危险模式检查（管道执行远程脚本、硬编码密钥、`shell=True` 等）。它只是快速排雷：**查无问题不代表安全**。若 skill 来自不可信第三方且要进生产环境，明确告知用户应使用专业安全扫描器并辅以人工审查。
