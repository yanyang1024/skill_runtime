# Skill Builder

从素材到可复用 Skill 的最小流程。核心立场：**做减法**——只沉淀真正会重复使用的模式，只打包真正可复用的资源。

## 三条核心判断（动手前先过一遍）

1. **该不该做成 Skill？** 一次性任务、答案靠模型通用能力就够的任务——不做。Skill 存在的唯一理由：下次遇到同类任务时，省掉重新摸索的成本。
2. **description 是路由代码。** 它是触发机制的唯一依据（正文在触发后才加载）。必须同时写清"做什么"和"什么时候用"，包含用户可能说的原话关键词，语气可以略微强势（模型天然倾向于漏触发）。不要把"何时使用"写进正文。
3. **默认 agent 已经很聪明。** 只写它原本没有的信息：流程、约定、领域知识、可复用脚本。每一段都要通过拷问："这段话值回它的 token 成本吗？"

## 工作流程

### 第 1 步：消化素材，提炼可复用模式

按素材类型处理：

- **会话记录 / 工作日志**：通读全文，找出其中完整的"问题 → 解决"回路。关键一问：这次会话里哪些摸索（试错、查资料、反复改写）是下次可以直接跳过的？那些"可以被跳过的部分"就是 Skill 的内容。会话中的一次性细节（具体文件名、临时数据、当时的心情）不要带进去。
- **场景描述**：场景通常不完整，访谈补全三类信息（一次问完，不要挤牙膏）：① 用户会怎么开口说这件事（触发原话）；② 成功的输出长什么样（格式、质量标准）；③ 边界情况和不希望发生的事。
- **参考文件 / 文档**：把文档切成"每次都需要的核心流程"与"偶尔查阅的细节"——前者进正文，后者进 `references/`。

本步产出：一两句话的**用途声明**，加上 **3 条正向触发例 + 1~2 条反向例**（不该触发的情况）。写不出来就回到素材继续提炼——这说明模式还不够清晰，动手写也是返工。

### 第 2 步：规划内容，决定自由度

- **正文指令**：多条路径都合理、判断依赖上下文 → 用高自由度文字指导。
- **脚本 `scripts/`**：同一串代码会被反复重写，或操作脆弱需要确定性 → 固化成低自由度脚本。**脚本必须实际运行测试过才允许放入。**
- **参考 `references/`**：细节文档（schema、API、模板说明）按需加载；正文里必须写明"什么时候读它"。
- **资源 `assets/`**：最终输出要用的模板、样板文件。
- 三者都不需要的 Skill 完全合法——很多好 Skill 只有一个 SKILL.md。

### 第 3 步：创建骨架

```
skill-name/
├── SKILL.md          # 必需
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：按需加载的文档
└── assets/           # 可选：输出用资源
```

规范速查（违反了运行时直接不触发或报错）：

- `name`：kebab-case（小写字母/数字/连字符），≤64 字符，**必须等于目录名**。
- frontmatter 只放 `name`、`description`（极少数情况加 `license`/`metadata`/`compatibility`），禁止自创字段。
- `description`：≤1024 字符，不含尖括号 `<>`。

### 第 4 步：写 SKILL.md

- 一律用祈使句（"做 X"，不是"你应该做 X"）。
- 正文 <500 行；逼近上限时把细节拆进 `references/`，并在正文给出明确的"当 X 时读 Y"指引。
- 同一信息只在一处出现：正文或 references，不重复。
- 引用本地文件一律用正斜杠相对路径，且只从 SKILL.md 直接链接（references 不要再套 references）。
- 不创建 README、CHANGELOG、安装指南等多余文件——Skill 里只放 agent 干活需要的东西。

### 第 5 步：验证并打包

1. 用 `scripts/validate_skill.py` 做确定性校验（零依赖、秒级）：`python3 scripts/validate_skill.py <skill目录>`
2. 过一遍下方自查清单。
3. 校验全过后用 `scripts/package_skill.py` 打包交付：`python3 scripts/package_skill.py <skill目录> [输出目录]`

## 交付前自查清单

- [ ] description 同时包含"做什么"和"何时用"，且有用户原话级关键词？
- [ ] 拿第 1 步的反向例自问：这个 description 会误触发吗？
- [ ] 正文每一段都是 agent 原本不知道的信息？
- [ ] 每个脚本都真的跑过、输出符合预期？
- [ ] `references/` 里每个文件都在正文有"何时读"的指引？
- [ ] 没有任何一次性细节（临时文件名、某次对话的具体数据）残留？

## 常见反模式

- 把 Skill 写成科普教程（"什么是 X"）而不是操作指南（"怎么做 X"）。
- description 只有功能罗列，没有触发场景。
- 把素材原样塞进 references 美其名曰"完整"——上下文窗口是公共资源。
- 为不存在的问题设计配置项、分支逻辑和"未来扩展性"。
