下面是一版适合在内部会议中汇报和引导讨论的演讲稿，整体语气偏分析和开放讨论，不急于得出单一结论。

各位同事，今天我想和大家讨论一个比较开放的问题：大模型和应用结合之后，应用形态到底在发生什么变化，以及这些变化背后的核心推动力是什么。

我们现在大致可以看到这样一条演化路径：

从最早的 Chatbot，到 Chatbot 加知识库 RAG，再到 Tool Use、Dify 这类 Workflow、Skill，以及最近越来越多的 Workspace Agent，或者所谓的 AI Coworker，例如 OpenCode、Claude Code 这一类产品。

表面上看，这似乎是一条不断叠加功能的路线：先让模型能回答问题，再让模型能查知识、调工具、执行流程，最后让模型进入一个工作空间，直接处理文件、运行程序、修改项目。

但我觉得，如果只把它理解成“聊天机器人不断加功能”，可能会低估这次变化。

更深层的变化是：我们正在逐渐把原本依赖人类临时提供的知识、工具、流程、经验和工作状态，外置到一个模型可以理解和操作的系统环境里。

最早的 Chatbot，主要解决的是表达和推理问题。用户提一个问题，模型返回一段回答。它的交付物本质上还是文本。

加入 RAG 之后，解决的是模型不知道私有知识、垂直知识和最新知识的问题。模型不再只依赖参数，而是可以读取外部资料，再基于资料回答。

再往后加入 Tool Use，模型开始不仅能“知道”，还可以“做”。比如查数据库、调用接口、执行代码、发送请求。

Workflow 又进一步解决了稳定性问题。因为企业并不只需要模型灵活，还需要流程可控、步骤可复现、结果可追踪。所以像 Dify 这样的 Workflow，本质上是在模型的灵活性外面，重新加上一层确定性的业务骨架。

Skill 则又向前走了一步。Tool 更多表达的是“模型可以做什么”，例如搜索、计算、调用接口；Workflow 表达的是“固定按照什么顺序做”；而 Skill 更像是“面对某一类任务，应该怎样做”。

一个 Skill 里不仅可以包含工具，还可以包含使用条件、处理步骤、参考资料、脚本、输出规范和异常处理方式。

所以可以简单理解为：

Tool 是动作。

Workflow 是动作的固定排列。

Skill 是可复用的做事方法。

Workspace 则是这些方法真正运行、产生中间状态和留下成果的环境。

到了 OpenCode、Claude Code 或 Coworker 这类产品，模型获得的已经不仅是知识和工具，而是一个持续存在的工作空间。

它可以读取文件、修改文件、运行脚本、查看执行结果、根据失败继续调整，也可以在多轮任务中保留工作状态。

这个时候，应用交付的核心就不再是一段回答，而可能是一份报告、一张表格、一段可运行的代码、一个修改后的项目，或者一个已经实际执行完成的业务结果。

所以我认为，这条演化路线背后的第一个核心推动力，是从“回答问题”转向“完成任务”。

用户真正想要的通常不是多聊几轮，而是把事情做完。

甚至可能出现一个比较反直觉的趋势：AI 应用越强，用户实际需要输入的对话轮数反而越少。

第二个推动力，是模型能力提升之后，系统瓶颈逐渐从模型本身转移到了模型之外。

早期大家更关注 Prompt 怎么写、模型要不要微调、上下文长度够不够。

但当模型逐渐具备多步推理、工具调用和代码执行能力以后，很多失败并不是因为模型不会推理，而是因为它找不到正确的文件、环境缺少依赖、工具定义不清楚、权限配置不合理、上下文被污染，或者任务做完后没有办法验证结果。

因此，未来应用之间的差距可能越来越不只是模型差距，而是工作环境差距。

也就是：谁能给模型提供更好的 Workspace、更清晰的工具、更合理的权限、更稳定的执行环境，以及更明确的验证方式。

第三个推动力，是企业需要同时获得灵活性和确定性。

模型擅长处理模糊需求、不确定任务和开放问题，但企业系统往往要求流程稳定、权限明确、结果可审计。

这也是为什么 Workflow 不会因为 Agent 出现就消失。

比较可能的方向不是 Agent 替代 Workflow，而是 Workflow 作为确定性骨架，Agent 处理其中难以提前编码的部分。

比如财务审批、数据同步、固定报表，这些任务通常更适合 Workflow。

而调研未知问题、排查程序故障、根据不同文件生成报告，这类任务更适合 Agent。

未来很多系统可能会变成一种混合结构：确定的部分写成流程，不确定的部分交给模型动态决策。

第四个推动力，是人和 AI 的控制关系发生了变化。

传统软件中，人类控制每一个操作步骤：点击按钮、填写参数、查看结果。

Workflow 中，开发者提前控制步骤。

而在 Coworker 或 Workspace Agent 中，人类可能越来越多地只负责定义目标、边界和验收标准。

例如告诉模型要完成什么、哪些目录可以访问、哪些动作不能做、最终结果如何判断。

模型负责执行，人类则负责观察、纠偏、暂停和接管。

这里有一点需要特别强调：更少的确认，并不等于更少的人类控制。

一个成熟的 Agent 系统，可能不是每一步都让用户点击确认，而是提供更强的可观察性、更方便的中断机制、更明确的权限边界和更可靠的回滚能力。

第五个推动力，是应用开始从静态软件向可持续演化的软件转变。

传统应用的能力主要来自开发者发布的新版本。

但 Skill 和 Workspace Agent 的能力，还可能来自真实使用过程中积累的用户反馈、成功和失败轨迹、新增文档、新脚本以及项目规则。

这意味着系统有机会把每次使用中的经验沉淀下来，让下一次使用更好。

不过这里也不能太乐观。

能记录经验，不等于能安全地自动成长。

如果系统把每次会话中的临时要求、错误判断甚至恶意输入都自动写入长期 Skill，能力反而可能逐渐劣化。

所以未来重要的可能不是简单的“自动学习”，而是一套受控的演化机制：

先从运行日志中提取候选经验，再进行验证，由人类确认或者经过质量门，最后版本化发布，并且支持回滚。

接下来我想讨论几个在这轮变化中，已经被部分推翻或者需要重新理解的观点。

第一个观点是，RAG 会成为长期的核心壁垒。

我认为这个观点已经被部分削弱。

RAG 仍然很重要，但“接一个向量数据库”越来越像基础能力，而不是核心壁垒。

真正有价值的部分，可能是知识来源是否可信、权限是否准确、知识是否及时更新、什么时候应该检索、检索结果如何验证，以及检索到的信息怎样参与后续行动。

换句话说，RAG 没有消失，但它正在从应用的主角，变成 Agent 的一个知识感知组件。

第二个观点是，Prompt Engineering 是 AI 应用最核心的资产。

Prompt 当然仍然重要，但单独的 Prompt 已经很难构成完整的系统能力。

现在越来越重要的是 Workspace、Tool Contract、Skill、权限、测试、可观测性和状态恢复。

一个非常好的 Prompt，放在混乱的工作环境里，可能不如一个普通 Prompt 配合清晰、稳定、可验证的执行环境。

第三个观点是，上下文窗口越长，就越不需要 RAG、Skill 和记忆系统。

这个观点也基本被推翻了。

上下文长度解决的是“能不能装进去”，但没有解决“应该装什么”“哪些内容可信”“哪些内容已经过期”“哪些经验应该长期保存”。

能看到更多信息，并不代表模型能更好地组织信息。

第四个观点是，Agent 越自主，产品就越先进。

这个观点也需要重新考虑。

无限自主可能带来成本失控、错误扩散、权限风险和任务漂移。

成熟的 Agent 可能不是无条件地做更多事情，而是更懂得限制自己：不访问无关目录，不调用不必要的工具，不在没有验证时直接发布结果，也不把所有经验都自动写入长期记忆。

第五个观点是，Multi-Agent 就是模拟一个数字化组织。

我觉得这也是一个容易被过度包装的概念。

很多多 Agent 系统会设置经理、研究员、审核员等角色，但它真正的技术价值，可能更多来自上下文隔离、权限隔离、并行探索和独立验证，而不一定来自模拟一个组织结构。

所以一个非共识的判断是：Multi-Agent 首先是一种上下文和执行隔离机制，其次才是组织模拟机制。

复杂的数字组织，不一定比一个主 Agent、少量子任务和一组确定性工具更有效。

再来看未来的发展，我觉得有几个可能方向。

第一个方向，是应用变成“薄界面加 Agent Runtime”。

未来很多应用的前端可能只保留三类功能：输入意图、展示状态和成果、进行确认和纠错。

真正复杂的执行被放到后台的 Agent Runtime 中，由 Workspace、Skill、Tool、Sandbox、Memory、Evaluator 和权限策略共同完成。

第二个方向，是 Workspace 可能成为新的中间件。

过去中间件连接系统和系统。

未来 Workspace 可能连接人的目标、模型、文件、数据库、SaaS、工具、历史任务和验证器。

模型可以更换，但一个已经组织好的 Workspace，里面包含组织规则、项目结构、工具、权限和历史成果，它的迁移成本可能会非常高。

第三个方向，是 Chat 变成控制面，Artifact 变成事实面。

今天很多 AI 产品仍然以聊天记录为核心，但聊天记录并不是一个很好的正式状态载体。

对话里有很多试探、错误、重复和临时信息。

未来可能需要明确区分：

Chat 用于协商、澄清和解释。

Artifact 是正式成果。

Trace 记录模型实际做了什么。

Workspace State 表示项目当前真实状态。

Skill 和 Memory 则保存经过验证、可以复用的经验。

也就是说，对话不能继续承担数据库和项目状态的全部职责。

第四个方向，是 Skill 有机会成为可执行的组织知识。

过去组织知识存在于文档、SOP、培训材料、脚本和老员工经验中。

Skill 可以把这些内容组合成一套模型能够实际执行的方法。

它不只是告诉模型“什么是正确的”，还告诉模型“应该怎样做、调用什么、输出什么、如何检查”。

第五个方向，是 Agent 会反过来改变传统软件的设计。

过去软件主要为人类设计，所以重点是菜单、按钮、页面和表单。

未来软件可能还要同时为 Agent 设计，需要提供更稳定的 API、更明确的语义、更严格的权限、更好的撤销机制，以及可以被机器理解的错误信息。

因此未来并不一定是没有 UI，而是同时存在 Human UI 和 Agent Interface。

Human UI 让人类观察、比较和纠错。

Agent Interface 让模型发现能力、读取状态和安全执行。

最后，我想提出几个可能值得继续讨论的非共识观点。

第一，未来真正重要的壁垒可能不是模型，也不是单纯的数据，而是高质量的任务环境。

也就是模型能看到什么、能操作什么、怎样知道自己做对了、失败后如何恢复，以及经验如何安全沉淀。

第二，最好的 Agent 产品，表面上可能反而显得没有那么自主。

它不会为了展示智能而规划很多步骤，而是稳定、克制、可验证地完成任务。

第三，Coworker 可能是一个方便传播但容易误导的比喻。

当前 Agent 更像一个可监督的智能执行系统，而不是真正承担责任、理解组织后果的同事。

第四，未来重要的个人能力可能不是写 Prompt，而是布置一个可执行的任务环境。

包括说明为什么做、成功标准是什么、有哪些输入、可以使用哪些工具、哪些事情不能做、怎样验收，以及出现问题后如何反馈。

第五，Agent 不一定会减少软件数量，反而可能制造更多软件。

因为生成临时脚本、小工具、看板和自动化流程的成本会越来越低。

减少的可能不是软件本身，而是人类需要亲自学习和操作每个软件的必要性。

综合来看，我目前比较倾向于这样理解这条趋势：

它不是简单地从 Chatbot 进化到 Coworker，也不是所有应用最终都会变成一个万能聊天框。

更可能的变化是，软件正在从“由人操作的功能集合”，逐渐变成一种混合工作系统。

人在其中负责提出目标、提供背景、定义边界和验收结果。

模型负责理解任务、组织执行和处理不确定性。

Workflow、权限、数据库和测试系统负责提供确定性约束。

最终通过文件、代码、报告和业务状态这些真实产物，判断任务是否完成。

所以接下来我们可以重点讨论几个问题：

第一，我们当前做的应用，核心交付单位还是回答，还是已经开始变成工作成果？

第二，我们的系统瓶颈，到底还在模型能力，还是已经转移到文件、工具、权限、环境和验证机制？

第三，哪些流程应该继续保持确定性，哪些部分适合交给 Agent？

第四，我们希望 Skill 只是静态能力包，还是未来可以基于真实使用持续迭代？

第五，在我们的场景里，Chat、Workflow、Skill 和 Workspace 分别应该承担什么角色？

这些问题可能没有统一答案，但我觉得，它们会比单纯讨论应该选择哪个模型、哪个框架，更接近下一阶段应用设计的核心。
