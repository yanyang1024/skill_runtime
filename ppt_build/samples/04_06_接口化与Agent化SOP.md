# 能力接口化与 Agent 化 SOP

> 对应痛点 04「频繁变更」与 06「运维不足」。
> 一句话：**成熟代码接口化，接口 Agent 化**——代码提供稳定底层能力，Agent 提供应对频繁变更的对话入口。

---

## 1. 三层架构

```
业务用户
   │  自然语言对话（应对频繁变更的需求）
   ▼
Agent 层      ← 对话入口：参数收集、意图识别、结果解释、转人工
   │  调用标准化接口
   ▼
接口层        ← RESTful API：参数校验、权限控制、限流、日志
   │  调用
   ▼
能力层        ← 成熟稳定的算法代码：模型推理、取数、规则引擎
```

## 2. 代码 → 接口 改造清单

| 检查项 | 标准 |
|---|---|
| 入参规范化 | 所有可变项（阈值、名单、时间窗）都做成参数，禁止硬编码 |
| 幂等与重试 | 同一请求重复调用结果一致 |
| 权限与审计 | 按业务域鉴权，调用留痕 |
| 文档 | OpenAPI 描述 + 3 个调用示例 |
| 灰度 | 新接口先内部灰度 1 周再开放 |

## 3. 接口 → Agent 接入清单

| 步骤 | 说明 |
|---|---|
| 注册工具 | 把接口描述（名称/参数/返回）注册为 Agent tool |
| 对话模板 | 为高频需求配置参数收集话术（如"要查哪个时间窗？"） |
| 结果解释 | Agent 把接口返回翻译为业务语言，附口径引用 |
| 兜底策略 | 参数缺失追问；超出接口能力则生成人工工单 |

## 4. 典型场景示例

- 业务方："把高风险工单阈值从 0.8 调到 0.85 看看效果" → Agent 调用规则引擎沙箱接口，返回对比报告，**无需改代码、无需排期**。
- 业务方自助："按我上传的名单跑一遍模型打分" → Agent 接收文件 → 调用批量推理接口 → 返回下载链接。

## 5. 运维约定（对应 06）

1. WebUI 之外，所有高频运维操作（重跑、查数、调参）都要有 Agent 对话入口。
2. 新需求开发完成后，先回答"能否接口化"，再回答"要不要进 Agent"。
3. 接口调用量、Agent 解决率、人工工单量纳入月度运维报告。
