# 从“接需求写应用”到“封装能力，让用户自助组合”

> 核心观点：过去我交付的是一个页面和一套代码；现在我更希望交付一套被封装、被说明、可验证、可对话调用的业务能力。Web UI 是稳定入口，对话式 Agent 是灵活入口，Skill 和 Workspace 让这些能力可以被持续理解、使用和维护。

## 第一部分：改写和充实后的分享内容

### 1. 我遇到的问题：传统交付往往是“一次性工程”

传统开发通常是这样：

1. 开发者接到需求。
2. 找数据库、接口、文档和工具。
3. 写代码，做页面，跑通测试。
4. 交给用户验收。
5. 过一段时间，用户提出新需求或系统出现问题，开发者再重新理解当初的代码和背景。

表面上看，我们交付了一个可用的应用；但真正容易丢失的是：

- 当时为什么这样设计；
- 底层用了哪些数据和工具；
- 每个模块的能力边界是什么；
- 哪些业务规则是确定的，哪些是当时的临时判断；
- 系统应该怎样测试和验收。

所以，后续二开困难不只是因为“忘了代码”，而是因为需求、能力、规则和验收方式都没有成为可持续复用的工程资产。

| 维度 | 传统应用交付 | 能力化、Agent 化交付 |
| --- | --- | --- |
| 主要交付物 | 页面和代码 | 能力内核、使用入口、说明与验证 |
| 用户能做什么 | 使用预设功能 | 使用预设功能，也能组合已有能力 |
| 需求变化 | 重新找开发者改页面、改流程 | 先通过对话组合；高频组合再固化 |
| 问题定位 | 从整个应用重新排查 | 按能力模块、调用记录和验证结果定位 |
| 知识留存 | 依赖开发者记忆 | 留在 Skill、Workspace、测试和运行记录中 |

### 2. 我的构想：一套能力内核，两个使用入口

我希望把开发者的工作，从“只完成这一次需求”，调整为“先为这类需求准备一套可复用的能力”。

~~~mermaid
flowchart TD
    S["数据、业务系统与原始资料"] --> C["统一能力内核：API、脚本、规则、知识"]
    C --> W["Web UI：高频、固定、结构化任务"]
    C --> A["对话入口：探索、组合与二次开发"]
    K["Skill / Workspace：说明、路由、验证与记录"] --> A
~~~

这套模式可以概括成：

- **一个能力内核**：Web UI 和 Agent 调用同一套 API、脚本和业务规则，不维护两套业务逻辑。
- **两个使用入口**：
  - Web UI 适合高频、稳定、字段明确、风险较高的任务；
  - 对话式 Agent 适合低频变化、探索分析、跨能力组合和临时二开。
- **一套持续工作环境**：Skill 告诉 Agent 怎样工作，Workspace 保存本次项目的输入、输出、运行记录和阶段状态。

这里的“双入口”并不意味着每个功能都要重复做两遍。关键是先有统一能力内核，再按任务特点选择是否提供表单、对话，或者同时提供两者。

### 3. 开发流程怎样变化

新的开发流程可以保持很简单：

1. **先确认任务和验收标准**  
   用户究竟要完成什么，结果怎样才算正确。

2. **盘点可用资源**  
   找到相关数据库、现有 API、脚本、业务文档和知识来源。

3. **封装少量稳定能力**  
   不直接把数据库账号、内部表结构和复杂调用过程暴露给用户或 Agent，而是封装为有明确输入、输出和权限边界的能力。

4. **把确定性和变化性分开**  
   - 不太会变化、必须稳定执行的部分写成代码、API 或脚本；
   - 需要理解用户意图、选择能力、组合步骤、解释结果的部分交给 Agent。

5. **让两个入口复用同一能力**  
   Web UI 和对话式应用都调用同一个能力层，避免结果不一致。

6. **交付 Skill 和可验证的 Workspace**  
   除了应用，还交付能力说明、调用示例、业务规则、测试方式和运行记录。

7. **从真实使用中继续固化**  
   用户通过对话形成的高频、稳定组合，可以再由开发者沉淀为新的固定功能、脚本或表单。

这形成了一个很朴素的循环：

> 开发者封装能力 → 用户自助组合 → 发现高频模式 → 开发者再次固化。

### 4. “Agent 化”不等于“把每个模块都做成 Agent”

这是这套模式里最需要澄清的一点。

Agent 化的目标不是制造很多有角色名称的 Agent，也不是把每个函数包装成一个独立智能体。真正有价值的是让一个能力变得：

- Agent 能发现它；
- Agent 能理解它适合做什么；
- Agent 能正确传入参数；
- 出错后 Agent 能看懂原因并纠正；
- 执行结果能够被验证；
- 重要操作能够确认、审计和追溯。

因此，更准确的说法是：

> 不是把所有东西都变成 Agent，而是把底层能力变成 Agent 可消费的对象，再由 Agent 负责理解、选择和组合。

### 5. 这套模式带来的价值

#### 价值一：增强开发者对 AI 辅助编程的掌控

AI 辅助编程的风险，不只是开发者没有读懂每一行代码，而是开发者不知道系统由哪些能力组成，也不知道怎样判断每个能力是否正确。

模块化以后，掌控不等于必须手写或逐行理解所有代码，而是至少能够回答：

- 系统分成哪些模块；
- 每个模块解决什么问题；
- 输入、输出和副作用是什么；
- 通过什么测试确认它可用；
- 出错时应该定位到哪里。

这让验收从“这个大应用看起来能跑”，变成“这些能力分别经过了验证，并且组合后满足需求”。

#### 价值二：二开和运维更容易

当系统出现问题时，可以按模块、调用参数、返回错误和运行记录排查；当用户提出新需求时，也可以先判断是复用、组合还是新增能力，而不是从整个应用重新开始。

#### 价值三：业务用户可以在受控边界内自助

业务用户通常最了解字段的真实含义、业务场景和结果是否有用。开发者则更了解数据库、接口、权限和开发环境。

这套模式让双方各自负责更擅长的部分：

- 开发者负责“后厨”：数据访问、能力封装、安全、稳定性和验证；
- 业务用户负责“搭配”：描述实际问题、选择分析方向、判断结果是否满足需要；
- Agent 负责“翻译和组合”：把业务语言映射成能力调用，并把执行结果解释给用户。

所谓“自助餐”，不是让用户直接进入数据库或随意修改生产代码，而是在开发者准备好的安全能力范围内自由组合。

#### 价值四：减少系统对个人记忆的依赖

Skill、Workspace、能力目录、测试和运行记录共同保存了“系统怎样工作”。即使几个月后再回来，开发者也可以先看能力地图和执行证据，而不是依赖自己回忆当时写过什么。

### 6. 一个需要保留的边界

这套模式并不适合所有项目。

它更适合：

- 同一类需求会反复出现，但具体组合经常变化；
- 底层数据和工具能够被安全封装；
- 结果可以检查、比较或验收；
- 业务用户愿意参与探索和反馈。

如果任务是一次性的、流程完全固定、风险很高，或者结果必须百分之百确定，那么传统表单、固定工作流和确定性代码往往仍然是更好的主入口。Agent 可以辅助开发和解释，但不必强行进入生产执行链路。

## 第二部分：Skill、Agent 与 Workspace 的简单设计

### 1. 三者各自负责什么

| 对象 | 简单定义 | 不应该承担的事情 |
| --- | --- | --- |
| Agent | 根据当前任务理解、选择、调用和组合能力 | 不重复实现已有的确定性业务逻辑 |
| Skill | 一份可按需加载的“能力使用说明书与操作流程” | 不把所有文档、代码和知识全部塞进主提示词 |
| Workspace | 当前项目或任务的工作台，保存输入、输出、阶段状态和执行记录 | 不代替可复用的 Skill 和正式数据源 |

一句话区分：

> Agent 负责做决定，Skill 负责教会它怎么做，Workspace 负责让它记得做到哪里、产生了什么。

### 2. 底层能力应该怎样封装

| 对象 | 推荐形式 | 最低要求 |
| --- | --- | --- |
| 共享业务能力 | API 或 Tool；有多种 Agent 客户端时再考虑 MCP 适配 | 名称清楚；输入输出结构化；权限明确；错误可理解 |
| 本地确定性操作 | 非交互式脚本 | 支持帮助信息；参数明确；退出码可靠；输出尽量结构化 |
| 业务规则 | 简洁 Markdown；确需机器校验时再使用 YAML/JSON | 说明适用范围、例外和来源 |
| 数据字典与领域知识 | 小而稳定的内容放在 references；大或常变化的内容通过检索/API 获取 | 标注来源、更新时间和负责人 |
| 示例与模板 | examples 或 assets | 至少包含一个正常案例和一个常见失败案例 |
| 验证逻辑 | 单元测试、校验脚本或明确检查清单 | Agent 执行后能够得到“通过/不通过”和原因 |

几个简单原则：

1. **API 不直接暴露数据库秘密**：凭据留在服务端，Agent 只看到被授权的业务能力。
2. **脚本不要依赖交互式问答**：参数从命令行或结构化输入传入，方便 Agent 稳定调用。
3. **返回值既要给机器，也要给人**：保留结构化数据，同时提供简短摘要和下一步建议。
4. **错误要能帮助纠正**：不要只返回“失败”，要说明哪个参数、哪条规则或哪个权限出了问题。
5. **写操作增加保护**：优先提供 dry-run；展示影响范围；必要时再让用户确认。
6. **大结果不要全部塞回上下文**：保存为文件或资源，返回摘要、位置和关键指标。

### 3. 能力封装到什么粒度

合适的能力通常不是最底层的数据库函数，也不是已经锁死全部业务流程的完整应用，而是一个“稳定的业务原语”。

可以用四个问题判断粒度：

1. 能否用一句业务语言说明它做什么？
2. 是否有清楚的输入、输出和副作用？
3. 是否可以单独测试？
4. 用户能否在不知道内部数据库和代码细节的情况下，将它与其他能力组合？

四个问题大体都能回答“是”，粒度通常就比较合适。

例如，与其直接开放“执行任意 SQL”，不如提供：

- 查询指定范围的数据；
- 对一组参数执行规则校验；
- 比较两个版本的差异；
- 生成标准格式的分析报告。

### 4. 推荐的最小 Skill 目录

不必一开始设计很多目录。一个简单版本就够了：

~~~text
business-self-service/
├── SKILL.md
├── scripts/
│   ├── query_data.py
│   └── validate_result.py
├── references/
│   ├── capabilities.md
│   ├── data-dictionary.md
│   ├── business-rules.md
│   └── examples.md
└── assets/
    └── report-template.md
~~~

其中：

- `SKILL.md`：只写什么时候使用、基本流程、资源路由、边界和验收方式；
- `scripts/`：放稳定、可重复、可独立验证的执行逻辑或 API 适配器；
- `references/`：放能力目录、数据字典、业务规则和示例，按需读取；
- `assets/`：放需要原样复用的模板或静态资源。

如果已有“知识目录”的概念，可以保留；但为了简单，也可以先统一放进 `references/`。只有当知识规模和更新方式明显不同，再拆分 `knowledge/`、检索库或远程知识接口。

Skill 里也不必复制完整 API 服务端代码。它更应该装配：

- 能力入口；
- 调用方法；
- 必要的适配脚本；
- 业务知识和规则；
- 验证方法；
- 权限与安全边界。

### 5. 一个可直接改写的 SKILL.md 骨架

~~~markdown
---
name: business-self-service
description: 当用户需要查询业务数据、校验参数、组合已有能力或生成标准报告时使用。
---

# 目标

在不暴露数据库凭据和内部实现的前提下，使用已有能力完成业务任务。

# 工作流程

1. 确认用户目标、范围和成功标准。
2. 阅读 references/capabilities.md，选择最少的必要能力。
3. 只询问缺失的必填参数。
4. 读取任务所需的数据字典或业务规则，不预先加载全部资料。
5. 调用 scripts/ 中的脚本或已配置 API。
6. 对写操作先 dry-run，展示影响并按规则确认。
7. 运行验证，失败时根据错误修正；不要绕过校验。
8. 返回结果摘要、产物位置、关键假设和执行记录。

# 资源路由

- 选择能力：references/capabilities.md
- 理解字段：references/data-dictionary.md
- 判断业务约束：references/business-rules.md
- 查看输入输出示例：references/examples.md
- 查询数据：scripts/query_data.py --help
- 验证结果：scripts/validate_result.py --help

# 边界

- 不直接访问未授权数据库或表。
- 不把密钥写入输出、日志或生成代码。
- 不猜测关键业务参数；缺失时向用户确认。
- 不因校验失败而生成占位结果或伪造成功。

# 完成标准

- 结果满足用户确认的范围和格式；
- 验证通过；
- 关键数据来源和假设可追溯；
- 写操作的影响已获得必要确认。
~~~

这个骨架的重点不是提示词写得很长，而是让 Agent 知道：

- 何时使用；
- 先做什么、后做什么；
- 需要时去哪里取信息；
- 哪些事情不能做；
- 怎样判断任务已经完成。

### 6. Workspace 只保存“这次工作”的状态

可以从最小结构开始：

~~~text
workspace/
├── context.md
├── input/
├── output/
└── runs/
~~~

- `context.md`：当前项目目标、已确认约束、未决问题；
- `input/`：本次任务输入；
- `output/`：交付物；
- `runs/`：每次执行的参数、结果、错误和验证记录。

Skill 是可复用的方法，Workspace 是一次具体工作的状态。把两者分开，Skill 才不会被单个用户的临时信息污染，Workspace 也不会变成无人理解的临时目录。

### 7. 最小可行落地方式

不要先做一个庞大的 Agent 平台。可以选一个“经常有小改动”的现有应用做试点：

1. 从现有代码中找出 3—5 个可独立测试的业务能力。
2. 为每个能力补齐名称、输入、输出、错误和一个示例。
3. 让原 Web UI 与对话入口复用同一能力层。
4. 写一个最小 Skill，告诉 Agent 怎样选择、调用和验证这些能力。
5. 邀请少量业务用户尝试组合，记录他们反复提出的需求和失败点。
6. 只把高频、稳定、确实有价值的组合固化成新能力。

先证明“用户能否在受控范围内完成一次真实自助”，再决定要不要扩展目录、协议、角色或自动化机制。

## 第三部分：开放讨论问题，以及我可以准备的回答

### 问题一：开发者应该把能力封装到多底层？

**我的回答：**封装到“稳定业务原语”即可。不能粗到只能完成一个固定页面，也不要细到要求用户理解数据库表和技术实现。判断标准是：能说明、能测试、能复用、能组合。

### 问题二：API、脚本和 MCP 应该怎样选？

**我的回答：**

- 多用户、远程访问、需要集中鉴权和审计：优先 API；
- 本地转换、校验、批处理：优先脚本；
- 多种 Agent 客户端都需要统一发现和调用能力：再增加 MCP 适配。

MCP 是能力标准化暴露方式，不必成为第一天的前置条件。已有 API 和脚本能解决问题时，先把输入、输出、错误和权限做好。

### 问题三：知识文件应该复制进 Skill 吗？

**我的回答：**只放小、稳定、使用频繁的核心知识。大文档或经常变化的数据，应通过检索、知识库接口或业务 API 按需获取。每份本地知识至少标注来源和更新时间，避免副本逐渐变成错误的“第二真相”。

### 问题四：为什么既要 Web UI，又要对话入口？

**我的回答：**它们解决不同问题。表单把稳定流程做得快、清楚、可控；对话让用户表达模糊需求、组合能力和探索临时方案。两者最重要的前提，是共用同一个能力内核，而不是复制两套业务实现。

### 问题五：业务用户自助生成的东西，谁负责质量？

**我的回答：**探索阶段可以由用户和 Agent 快速试验，但进入共享、重复或生产使用前，应有“毕业机制”：补齐测试、权限、说明和负责人，再固化为正式能力。自助不等于没有治理。

### 问题六：怎样避免 Agent 乱调用、乱改数据？

**我的回答：**先用四个简单措施：

1. 只暴露白名单能力；
2. 权限在 API 或工具层执行，不只写在提示词里；
3. 写操作提供 dry-run、影响预览和确认；
4. 保存调用参数、结果与验证记录。

这些措施比堆叠复杂的多 Agent 角色更直接。

### 问题七：这会不会让开发者前期工作更多？

**我的回答：**会有一些额外封装成本，所以不应对所有一次性需求都使用。它适合需求会反复变化、能力会被多次复用的场景。目标不是让第一次交付最省事，而是降低第二次、第三次变化的边际成本。

### 问题八：对话产生的“二开”怎样反哺正式系统？

**我的回答：**把用户对话中的重复组合当作候选需求，而不是自动变成生产代码。经过使用频率、业务价值和验证成本判断后，再由开发者把值得保留的组合升级为脚本、API 或 Web UI 功能。

---

## 第四部分：建议的 8 页分享结构

1. **标题页**：从交付应用到交付可组合能力。
2. **传统模式的痛点**：代码交付了，但需求背景、能力边界和验收方式没有留下。
3. **一句话方案**：一套能力内核，两个入口，一套持续工作环境。
4. **开发流程变化**：盘点资源、封装能力、分离确定性与变化性、共同复用。
5. **三方分工**：开发者负责后厨，业务用户负责搭配，Agent 负责翻译和组合。
6. **Skill / Agent / Workspace**：分别负责教会、执行和记住。
7. **最小目录与落地方式**：3—5 个能力开始，不先做大平台。
8. **开放讨论**：粒度、API/脚本/MCP、知识更新、安全边界和“毕业机制”。

## 第五部分：分享演讲稿

大家好，今天我想分享的，不是某个 Coding Agent 工具怎么安装，也不是怎样写出一条更厉害的提示词。我更想分享的是，我在实际使用 AI 辅助编程之后，对开发和交付模式的一点重新理解。

我想讨论的问题是：有了 Coding Agent 以后，我们是不是仍然只是用更快的方式，继续交付一个页面和一套代码？还是可以进一步改变开发者和业务用户之间的协作方式？

我先从自己比较熟悉的传统开发模式说起。

过去接到一个需求，我会先理解用户想要什么，然后去找数据库、接口、文档和工具，接着写代码、做页面、测试，最后交给用户验收。这个过程本身没有问题，而且大多数项目现在仍然应该这样做。

但它有一个很现实的问题：这经常是一次性工程。

项目交付以后，过几个月用户再提出一个新需求，或者系统出了一个问题，我可能已经不记得当时为什么这样设计，也不记得代码里哪些部分是稳定业务规则，哪些部分只是为了赶这次需求做的临时处理。用户看到的通常只有一个页面，也不知道页面后面到底有哪些能力可以复用。

所以我后来发现，我们丢失的不只是代码细节。更容易丢失的是：为什么这样做、底层用了什么、能力边界在哪里、怎样判断结果正确。

AI 辅助编程在某些时候还会放大这个问题。代码生成得更快了，但如果代码仍然是一整块，开发者可能更难建立对系统的整体掌控。

这里我对“掌控”有一个比较务实的理解。掌控并不一定意味着，我必须逐行手写、逐行记住所有代码。至少我应该知道：系统分成哪些模块，每个模块解决什么问题，输入输出是什么，怎样测试，出了问题应该去哪里找。

因此，我现在更倾向先把系统拆成少量可独立说明、独立测试和重复使用的能力。不是为了追求架构漂亮，也不是把系统拆成几十个微服务，而是为了把一个大黑盒，变成几个可以验收的小盒子。

在这个基础上，我构想了一种新的交付模式。我把它概括为一句话：一套能力内核，两个使用入口。

所谓一套能力内核，就是开发者先把数据库、内部系统、脚本和业务规则，封装成少量稳定能力。比如查询某一范围的数据、校验一组参数、比较两个版本、生成一种标准报告。

这些能力要有清楚的输入、输出、错误和权限边界。用户和 Agent 不需要知道数据库密码，也不需要理解内部表结构。

所谓两个入口，一个是传统 Web UI，一个是对话式 Agent。

Web UI 仍然非常重要。对于高频、固定、字段清楚、风险较高的任务，表单通常更快、更稳定，也更容易控制。对话入口则适合需求表达还不完整、需要探索、需要组合多种能力，或者用户想临时做一次二次开发的场景。

重点不是做两套系统，而是两个入口共用同一个能力内核。否则 Web 页面得到一个结果，对话 Agent 得到另一个结果，维护成本只会更高。

在这套模式里，我认为确定性交给代码，变化性交给 Agent。

不太会变化、必须准确重复执行的逻辑，应该写进 API、脚本和测试。需要理解用户想法、选择工具、组合步骤和解释结果的部分，再交给 Agent。

所以，Agent 化并不是把每个模块都做成一个 Agent，也不是为每个功能虚构一个岗位和角色。真正需要做的，是让底层能力变成 Agent 能发现、能理解、能调用、出错后能纠正、执行后能验证的对象。Agent 负责选择和组合，确定性逻辑仍然由代码执行。

这也带来一种新的开发者和业务用户分工。

开发者更熟悉数据库、接口、权限、安全和开发环境；业务用户更熟悉数据在真实业务里的含义，也最能判断结果有没有用。

我会用“自助餐”来比喻这种协作。开发者负责后厨：准备食材、定义可以提供的菜、保证安全和质量。业务用户负责搭配：根据自己的实际问题选择和组合。Agent 像中间的翻译和服务员，把业务语言转换成能力调用，再把技术结果解释给用户。

但自助餐不意味着用户可以直接进入后厨。用户自助的前提，是在开发者准备好的能力和权限范围内组合，而不是直接执行任意 SQL、拿到数据库密码，或者让 Agent 随意修改生产数据。

接下来，我想用 Skill 和 Workspace 来承载这套模式。

我对三者的区分非常简单：Agent 负责做决定，Skill 负责教会它怎样做，Workspace 负责让它记得做到哪里、产生了什么。

Skill 不应该是一份巨大百科全书，也不应该把所有文档一次性塞给模型。它更像一份能力使用说明书和路由表。主文件只需要说明：什么时候使用、基本流程是什么、需要什么资料时去读哪个文件、哪些操作有风险、怎样验证已经完成。

确定性的执行逻辑放在 scripts 目录；能力说明、数据字典和业务规则放在 references；需要原样复用的模板放在 assets。Agent 根据任务按需读取，而不是每次把所有内容都放进上下文。

Workspace 保存的是这一次具体工作的状态，例如当前目标、用户已确认的条件、输入文件、输出结果和每次执行记录。这样几个月后再回来，我们看到的不是一个陌生代码库和一段找不到的聊天记录，而是任务背景、能力地图和验证证据。

至于 API、脚本和 MCP 怎么选，我认为也不必一开始复杂化。

多用户、远程访问、需要集中鉴权和审计时，优先 API。本地转换、校验和批处理，脚本通常已经够用。等到多种 Agent 客户端都要统一发现和调用这些能力时，再考虑加 MCP 适配。协议应该解决真实的互操作问题，而不是成为项目启动的仪式。

同样，知识也不要全部复制进 Skill。小而稳定的核心知识可以作为参考文件；大文档或者经常变化的信息，应该通过检索或业务接口按需读取。否则复制出来的知识很快会过期，反而形成一个错误的第二真相。

如果要开始实践，我建议不要先建设一个大而全的平台。可以选一个经常有小改动的现有应用，找出三到五个可独立测试的能力，为它们补上输入、输出、错误和示例。然后让原来的 Web UI 和一个对话入口同时调用这套能力，再写一个最小 Skill，告诉 Agent 怎样选择、调用和验证。

接着让少量真实用户试用。我们只观察几个问题：用户能不能理解这些能力，能不能在受控范围内完成一次真实组合，最常失败在哪里，又有哪些组合反复出现。

反复出现、价值明确、已经验证过的组合，再由开发者固化成正式脚本、API 或 Web UI 功能。这样，对话不是替代正式开发，而是变成发现需求和孵化功能的前置空间。

最后，我想用三句话总结今天的分享。

第一，一套能力内核，两个使用入口。表单负责稳定，对话负责灵活，但两者不要分裂成两套业务逻辑。

第二，确定性交给代码，变化性交给 Agent。不要为了 Agent 化而把所有东西都变成 Agent。

第三，Skill 负责教会，Workspace 负责记住。让项目的背景、能力、边界和验证方式成为资产，而不是只存在于某位开发者的记忆里。

我认为，Coding Agent 真正有意思的地方，可能不只是让开发者写代码更快，而是让开发者能够把自己熟悉的技术资源，封装成业务用户可以安全理解和组合的能力。开发者不再包办所有最后一公里，业务用户也不再只能等待排期。双方在一套受控能力之上，各自负责自己更擅长的事情。

这就是我目前对 Coding Agent 应用模式的理解。它还不是一个成熟答案，但我觉得可以从一个很小的试点开始验证。接下来也希望和大家一起讨论：能力应该封装到什么粒度，怎样管理知识更新，哪些任务适合对话入口，以及怎样让用户探索出来的组合平稳地进入正式系统。

谢谢大家。

## 参考的当前实践

这份设计刻意保持简单，但与当前较成熟的 Agent 工程实践基本一致：

- [Agent Skills Specification](https://agentskills.io/specification)：Skill 以 `SKILL.md` 为入口，并可按需装配 `scripts/`、`references/` 和 `assets/`；强调渐进加载，而不是一次注入全部内容。
- [Using scripts in skills](https://agentskills.io/skill-creation/using-scripts)：建议脚本避免交互式输入，提供帮助信息、清晰错误和结构化输出。
- [MCP Tools Specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)：强调工具输入输出 Schema、超时和调用审计，为“Agent 可消费的能力”提供了协议层参考。
- [GitHub Copilot repository instructions](https://docs.github.com/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)：强调在项目说明中写清如何理解、构建、测试和验证代码变更。
