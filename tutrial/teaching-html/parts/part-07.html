第七部分

多 Skill、MCP、A2A 与 Multi-Agent

先分清六种组合机制，再谈编排。不要因为"多 Agent"听起来更先进，就把一个函数拆成三个角色互相聊天。

7.1 六种组合机制对比

机制解决的问题控制流是否新上下文典型产物
Tool / API执行一个可定义的能力Agent 调用函数否结构化结果
Skill告诉 Agent 一类任务怎样做模型按说明执行默认否方法、流程和 Artifact
Workflow固定或半固定步骤编排开发者定义图通常否节点结果、最终输出
MCP标准化 Agent 与 Tool/Data/Prompt/UI 的连接Client–Server 协议不等于新 Agent 上下文Tool result、Resource 等
Subagent把子任务放入独立 Agent 会话Primary 委派是子任务结论与 Artifact
A2A跨进程或组织委托有状态 Agent 任务Agent Client–Agent Server是，且远端拥有生命周期Task、Status、Message、Artifact

MCP 用于以标准方式发现和调用 Server 暴露的能力，不是天然的多 Agent 编排器；A2A 围绕 Agent Card、Task、状态更新、消息和 Artifact 描述远程 Agent 协作。

🧭 实用选型顺序（六问）
  1. 能否写成确定性函数？能 → 优先 Tool / API；
  2. 缺的是"如何正确完成"的场景知识？→ Skill；
  3. 步骤稳定、需要清楚审计？→ Workflow；
  4. 需要跨客户端标准接入外部能力或数据？→ MCP；
  5. 需要上下文隔离、独立探索或独立验证？→ Subagent；
  6. 远端是拥有自身状态、能力发现和长任务生命周期的 Agent？→ A2A。

7.2 OpenCode 中的 Primary 与 Subagent

Primary 承担主对话；Subagent 可由 Primary 调用，也可由用户点名。推荐职责：

角色应负责不应负责
Primary理解用户目标、拆分任务、管理状态、处理确认、最终验收和交付把所有原始上下文无差别复制给每个 Subagent
Explore Subagent在只读条件下查找代码、资料和候选方案直接修改主工作区
Builder Subagent实现边界清楚的独立子任务替 Primary 改变需求或接受风险
Reviewer Subagent在独立上下文中检查 Diff、证据和规则继承实现者的自我辩护并默认通过
✅ 使用 Subagent 的充分理由只有三类
  • 需要隔离大量上下文，避免污染主会话；
  • 子任务彼此独立，确实可以并行；
  • 需要不同信息条件下的独立验证。

角色扮演本身不是充分理由。

7.3 多 Skill 融合策略

组合模式适用场景做法主要风险
单 Skill一个 Skill 已完整覆盖任务只激活命中最高者覆盖不足
主 + 辅助 Skill一个负责主流程，另一个提供局部能力主 Skill 持有任务所有权，辅助只返回局部结果指令优先级冲突
顺序管道A 的 Artifact 是 B 的输入显式定义 A → Artifact → B错误传导
分阶段切换用户请求包含多个不同目标完成并验收 A 后再激活 B会话过长
Subagent 隔离Skill 很大、相互冲突或需独立验证每个子任务独立上下文，只回传摘要与 Artifact协调成本

组合时的最小协议（七字段）

字段含义
intent解决哪类用户目标
inputs需要哪些已确认输入
outputs返回什么 Artifact 或结构化结果
side_effects是否写文件、发消息、写数据库
stop_conditions何时完成或阻塞
conflicts与哪些 Skill 不应同时激活
owner谁对最终验收负责
 
skills:
  - name: data-analysis
    intent: analyze_experiment_data
    provides: [analysis_report, cleaned_dataset]
    consumes: [dataset, metric_definition]
    side_effects: [write_workspace_files]
    conflicts_with: [quick-unverified-summary]
    composition: primary

  - name: report-publisher
    intent: publish_approved_report
    provides: [published_report_url]
    consumes: [approved_report]
    side_effects: [external_write]
    composition: terminal

这些字段可维护在团队自己的 skill-registry.yaml 中。它们不是 Agent Skills 标准字段，不要假装成跨平台通用协议。

防止语义递归和循环

Skill A 要求调用 Skill B
→ Skill B 判断任务仍属于 A
→ 再次加载 Skill A
→ 上下文膨胀、重复工具调用或 doom loop
  1. Harness 记录本 Session 已激活的 Skill，重复加载时去重；
  2. 维护 activation_chain 和最大深度；
  3. 依赖由 Router/Primary 解析，不让 Skill 通过自然语言无限递归调用；
  4. 组合前检查 conflicts_with；
  5. 同一 Tool 输入重复多次时触发 loop guard；
  6. 每个 Skill 返回明确终止状态：completed / blocked / handoff_required。

多 Skill 测试矩阵（十项）

  • A 单独运行 / B 单独运行；
  • A → B 与 B → A；
  • A 与 B 同时满足但只能选一个；
  • 显式点名 A、语义上更像 B；
  • A 完成后不应再次触发；
  • 无关 Skill C 不应被加载；
  • 权限拒绝 B 后，A 能否安全停止；
  • 上下文压缩后，已加载 Skill 的关键规则是否仍有效。
