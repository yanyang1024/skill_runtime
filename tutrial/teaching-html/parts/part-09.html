第九部分

一版可落地的参考架构

第一版不要一开始就在建设复杂 Multi-Agent 网络。先把单 Agent 的闭环做扎实，再按需扩展。

9.1 推荐的整体结构

Chat + Files + Cards + Artifacts（UI）
↓
Agent Runtime / Session Manager
← AGENTS + Skill Catalog + Memory
↓
Tools / Workflow / MCP / Subagents
↓
Business APIs / Data / Workspace
↓
Task State / Trace / Artifact Store

Permission / Sandbox / Identity / Audit 作为控制面，贯穿 Runtime 与能力层（虚线控制关系）。

9.2 最小可用组件（九件）

组件职责
Agent Runtime模型调用、Tool Loop、取消、超时和停止
Session Manager用户、项目、会话和 Task 的映射
Context LoaderAGENTS.md、Skill 目录和按需资源
Tool Gateway统一 Schema、身份、错误、幂等、限流和审计
Workspace文件上传、执行、Artifact 与隔离
Policy Layerpermission、沙箱、网络和凭据
Observability事件、Trace、Tool Call、成本和失败原因
Eval Harness触发测试、任务测试、安全测试和回归测试
Hybrid UI对话、参数卡、任务状态与 Artifact 预览

9.3 "先简单做"的优先级

① 一个 Primary Agent
↓
② 3–8 个窄而稳定的 Tools
↓
③ 一份简洁 AGENTS.md
↓
④ 1–3 个高价值 Skills
↓
⑤ Session + Workspace + Artifact
↓
⑥ permission + 系统隔离
↓
⑦ 任务级验收与 Trace
↓
⑧ 确认存在上下文隔离或独立验证需求后，再加 Subagent
↓
⑨ 确认存在跨系统 Agent 委托后，再考虑 A2A
💡 要点

⑧ 和 ⑨ 是"确认有真实需求后再加"，不是默认起点。复杂度应该由需求拉动，而不是由技术新鲜感推动。
