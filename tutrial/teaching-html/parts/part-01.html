第一部分

应用形态为什么从 Chatbot 走向 Agent

一个只会"接收文本、返回文本"的大模型，再聪明也像缸中之脑。本讲回答：从 Chatbot 到 Agent 的演进，到底补齐了什么。

1.1 开场：模型为什么像"缸中之脑"

🧠 讲师讲解

只接收文本再返回文本的大模型，即使很聪明，也存在六个"做不到"：

  • 不知道企业当前真实数据是什么；
  • 不能直接读取项目文件、数据库和业务系统；
  • 不能可靠地持续完成一个长任务；
  • 做完动作后，不一定能看到真实反馈；
  • 不知道哪些动作被允许、哪些不可逆；
  • 可能给出看起来合理、实际没有执行过的答案。
🔑 核心框架：演进在补齐五类条件
条件含义
Grounding让模型看到真实知识和真实环境
Action让模型能调用工具、API、文件系统和程序
State让任务、会话、文件和中间结果能够延续
Feedback让模型看到动作的真实结果，并据此调整
Governance用权限、沙箱、审计和验收限制其行动范围

从 Chatbot 到 Agent 不是产品名词升级，而是模型与数字世界之间的接口逐渐完整。

阶段主要控制者执行单元补齐的能力优势典型局限代表工具
Chatbot用户与应用一轮消息自然语言理解与生成上手快、交互自然只能"说"，事实和行动能力弱各类聊天应用
RAG + Chat检索程序文档片段与回答外部 / 私有 / 时效知识降低知识缺口，便于更新检索错误会传导；通常不执行真实任务LangChain、FastGPT
Workflow + Chat开发者预定义图节点、条件、变量确定性编排、系统集成可视化、稳定、易审计长尾需求需要不断加分支Dify、Coze（扣子）
Agent + Workspace模型在 Harness 边界内决策Task、Tool Call、Artifact动态规划、工具选择、反馈循环、状态延续能处理开放任务和异常概率性、成本、延迟、安全与验证更复杂OpenCode、Pi、OpenClaw

① Chatbot：暴露模型的"说话能力"

中心是 message → model → message。适合解释、翻译、改写、头脑风暴等低风险、结果由人直接判断的任务；不适合必须读实时业务状态、需要执行/验证/回滚的长任务、高风险且必须留证据链的操作。

② RAG + Chat：给模型接入"可查阅的资料室"

RAG 在推理时检索相关内容作为上下文，解决的是"模型不知道或记不准"，而不是天然解决"模型会不会做"。典型链路：

用户问题 → 查询改写 → 召回 → 重排/过滤 → 上下文拼装 → 模型回答 → 引用来源
RAG 的生产重点（不在"有没有向量库"）
  • 查询是否被正确理解；
  • 数据是否有来源、版本、权限和有效期；
  • 召回结果是否覆盖真正需要的证据；
  • 模型能否区分"资料中没有"与"自己不知道"；
  • 回答能否追溯到原始材料。

③ Workflow + Chat：把工作过程变成可执行图

把模型、知识库、代码、HTTP 请求、判断条件变成节点，由开发者提前决定大部分控制流。适合路径稳定、输入输出明确的业务（审批、批处理、内容流水线）。代价：长尾问题越多，分支越复杂，业务变化后需持续改图。

④ Agent：把"下一步做什么"的部分决定权交给模型

📌 教学定义

Agent 是一个在受控环境中，根据当前目标、状态和观察结果，循环选择下一步行动，直到完成、阻塞或被停止的运行系统。Agent ≠ 完全自治。

OpenCode 提供会话、文件与命令工具、规则、Skills、Primary/Subagent、权限以及 Server/SDK；Pi 强调可扩展的终端 Coding Harness；OpenClaw 更接近持续运行的个人助手 Gateway。共同点不是"有聊天框"，而是给模型一个可持续观察和行动的环境。

1.3 重要修正：演进不是"确定性越来越少"

问题类型更适合的承担者
理解模糊意图、处理例外、选择策略模型 / Agent
计算、格式转换、查询、写入Tool / API / Script
稳定且高频的固定路径Workflow
企业共识与项目约定AGENTS.md / Rules
场景化操作方法Skill
不可突破的限制Permission / Sandbox / Policy
成功与否的判断测试、断言、业务验收、人类评审
💡 一句话总结

把不确定性留给模型，把确定性沉淀到环境；把灵活性放在决策层，把安全和正确性放在模型无法绕过的边界上。
