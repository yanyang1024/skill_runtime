# 先做组织能力诊断，再证明一项可重复的改进

v2.1 的近期补充：先用 [任务分布与评测选题指南](07_task_atlas_and_bench.md)，把已有会话按组织 × 主任务整理，再选少量覆盖/失败案例做题。不新增价值总分或训练工程。

你的数据能力已经足够开始全平台只读分析。新的优先级应围绕可做的动作：已有导出、组织映射、请求记录、skill/agent、文件产物、可调整的提示与模型。无需先建设复杂价值评分，也无需把持续人工运营或工具修复权限当作依赖。

实证逐项判断见 [06_empirical_update.md](06_empirical_update.md)。本文件是实施与向上汇报口径；报告数字仍以公司内原始记录核验为准。

## 1. 最小优先级

| 顺序 | 优先做 | 最小产物 | 到这里就够了 |
|---|---|---|---|
| P0 | 保留现成用户级导出，补范围/分页/详情审计与请求去重 | 覆盖审计、rejected、usage 明细 | 能解释一个用户与一个时间窗的数差；不重写已工作的拉取器 |
| P0 | 组织 × tool/skill/agent × 使用阶段 | 原始错误、预期负例、剩余错误、错误类型、样本数 | 找出一个值得复现的问题，明确谁/什么依赖能改变它 |
| P0 | 能力扩散与产物再次上传/使用 | 提供部门→使用部门；有来源/有歧义的文件关联 | 核对少量已知产物的关联是否合理；未观测不报“没有复用” |
| P1 | 同一模型的 A/B/C/D 提示对照 | 成对通过/退步、token、耗时、提示应用覆盖 | 能判断通用提示/类别提示是否有增量；没增量就不推广 |
| P1 | 真实诊断题 + 程序真值能力题，分片冻结 | 组织/任务/真实合成/参考标签来源分别出分 | 新模型能用同题比较；不追求全企业一次覆盖 |
| P2 | 一个高频窄任务的小模型训练 | 独立真实保留集上的增量 | 规则和提示不足、标签可靠、执行收益大于维护投入时再开 |

这是推进顺序，不是工期承诺。暂缓：全量对话 SFT、自动 DPO、部门价值总分、复杂仪表盘、大规模半导体推理数据合成。H20 等训练资源不决定上述 P0/P1 能否启动。

## 2. 组织是入口，证据维度仍分列

推荐报告首页按组织展示；下钻到能力与工具。不要把部门当作用户任务的硬性先验：同部门有人开发工具、有人试用、有人正常查资料，任务也可能跨部门共通。

| 维度 | 现在能用的证据 | 必须区分 |
|---|---|---|
| 资源投入 | 去重请求的输入/输出 token、模型、事件期组织 | token 与钱；输入含缓存的语义；父子会话投影 |
| 使用覆盖 | 同窗口主动用户消息、skill/agent 实际调用 | 注册/可访问/活跃/回访；加载/调用/采用 |
| 使用摩擦 | 分阶段、来源、版本的工具事件和恢复记录 | 测试负例/缺陷/权限/业务无数据/取消/未知 |
| 能力与产物积累 | 可调用能力目录、跨部门调用、文件再次上传/读取 | 功能存在/被发现/被调用/结果被用 |
| 可验证改进 | 同任务同环境下的提示/模型对照 | 诊断弱标签一致性/程序验收/业务采用 |
| 业务采用 | 用户确认、已有明确业务回执或可核对工作事项 | 技术正确/用户接受/业务影响；没有回执保持未知 |

不会生成六维总分。每个指标保留时间窗、scope、分子、分母、字段覆盖与来源版本。组织图谱只是读取已有身份/目录的连接，不需要先做知识图谱工程。

## 3. 修正“算得出但名称过强”的指标

| 原称谓 | 现在怎么报 |
|---|---|
| 中止且无文件 = 浪费 | 中止/无文件候选；问答、探索和止损可能有效 |
| token / 文件数 = 单位交付成本 | 资源/写文件活动量；同类已验收任务完整尝试成本另算 |
| 感谢词 + 无工具错 = 完成率 | 用户语言候选；结果已知子集的可用情况另列 |
| 单轮有文件 = 首次命中 | 单轮产物会话数；首次交付接受需要配对验收 |
| 多轮、token 高 = 复杂 | 交互深度与投入；复杂度未独立标注就未知 |
| 累计次数分层 = 留存 | 累计使用强度；真留存需要首次/后续主动事件和完整观察窗口 |
| session 开始到结束 = 人工耗时 | 会话跨度；机器执行、等待、人工检查分别采集 |
| basename/同哈希 = 已证实资产复用 | 同名不用；同字节候选与明确来源关联分开 |
| 低工具失败率 = 高部门价值 | 同条件的可靠性描述；不能推出项目贡献或员工效率 |
| 自动标签评测准确率 = 用户任务真实准确率 | 对该参考标签的一致性；独立金标准另列 |

## 4. 成本“花得值”怎样讲得具体

向上回答三件事：投入对应了什么使用与能力；有什么可被复查的改进；下一笔投入准备解决哪个明确问题。

**成本账**：固定容量成本、变动现金支出、运维投入按一致期间记录。采购额与折旧不在一个口径中重复相加。自建推理条件下，输入 token 是工作负载，部门 token 占比是资源归属；没有 GPU 时间、缓存与模型运行成本时，不直接叫部门账单占比。

**证据账**：覆盖的实际用户/部门、能力从提供部门扩散到哪里、已观察到的产物重新使用路径、固定任务改进、业务采用的已知子集。没有确认时可以完整报告前四项，但不能把“已观测使用”升级为全平台工时收益。

837M 与 750M 的差约 11.6%（以 750M 为分母），差异存在不等于原因已被证实。先对齐：输入/总 token、窗口/时区、模型范围、父子请求去重、重复导出、迟到日志、缓存计数及缺失字段。`usage_ledger.jsonl` 提供窗口内计入明细；CSV 若只有汇总，最多先定位范围差，不能逐请求证明归因。

22.5× 也先写清分母。网关真实计费/执行的重复上下文是实际开销，不应作为“重复数据”从成本中删除；同一请求在两个 session 导出里出现才应去重。

## 5. 从交互到业务，只补一条轻量连接

用 `work_item_id` 关联同一事项的多个 session，附一个可查看产物/回答与可修改用途。业务锚点优先采用用户选择或已有项目/工单回执；组织与文件扩展名只产生用途候选。

确认问法：“这份比较表是否用在了实验准备？哪些部分可用，哪些还需要改？”可以选择未检查、暂未使用、没有帮助，未反馈维持 unknown。没有持续反馈渠道时，先做自动链路，有机会才补关键案例；不向用户强要一张肯定平台价值的证明。

若以后有人工基线，净时间变化用区间：

```text
[无 AI 人工投入下限 - 有 AI 人工投入上限,
 无 AI 人工投入上限 - 有 AI 人工投入下限]
```

包含检查、改写、返工，保留负值。用户估计和配对观测分别汇总，不变成现金收益；本来不会做的新任务先记能力增量。确认覆盖不足时，不用全平台成本除以少数确认采用事项称单位成功成本。

## 6. 一个近期汇报框架

1. 资源与覆盖：窗口、数据完整度、部门请求/token、调用能力。
2. 能力供给与实际使用：哪些能力跨部门被调用，哪些可见却尚未观察到调用。
3. 体验问题：开发/验收/生产/未知分别看，给出调用分母与可复现证据。
4. 已验证改进：同模型提示试验的通过/退步及资源，或已获权限的其它改动。
5. 已知业务用途与未知部分：有则引用，没有则说明采用未证实；下一步只验证一个假设。

这能把汇报从 token 消耗记录推进到“实际供给、使用证据、问题与增量”，同时避免承诺数据尚不能支持的良率、现金节省或人员绩效结论。
