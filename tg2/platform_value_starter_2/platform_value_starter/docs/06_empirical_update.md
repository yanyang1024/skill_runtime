### 对你实证的四个保留意见

1. “开发部门天然高失败”是合理解释假设，不是豁免规则。部门、工具来源与使用阶段分开；没有可靠阶段标签时保留 unknown。
2. “TF-IDF > keywords > majority”可以作为本次实验观察。但 AUTO 标签若来自关键词规则，应检查基线是否就是制标签那套规则、类别和弃权口径是否一致，否则成绩首先衡量弱标签一致性。
3. 没有跨会话 read 不意味着无法开始复用分析；优先已有上传记录和能力事件。不过上传、加载、调用、读取、技术验收、业务采用是不同证据，不能合成一个未经验证的“价值分”。
4. 全部用户查询 HTTP 200 不能推出历史详情齐全；token 两表差额也不能只凭差额断定为窗口/去重所致。沿用现有取数，先核对查询范围和少量 request_id 即可，不再新建采集系统。

### 刻意不扩大实现的地方

- 任务图谱是组织 × 主任务 × 能力事件的表和共现边，不是知识图谱系统，也没有自动拆复杂会话。
- 提示“改写”先实现为**保留原输入 + 可撤销短任务提示**。不做另一次大模型自由重写；模型大小不变。规则、标签、提示模板需按公司 taxonomy 对齐。
- 当前 `bench.py` 主要考固定 JSON 输出，没有沙箱代码测试器、开放回答通用打分器或完整 Agent 工具回放。日志脚本测试可先用你们已有测试框架；不可把文档中的候选题型都说成已经支持。
- 单次模型调用计时含提示策略处理，不能冒充用户整个任务周转时间。固定顺序批跑也会受到网关负载影响；若速度差异决定采用，再用新目录换时段复跑或适配交错顺序。
- 不自动把 good/bad case 变成 SFT/DPO；失败轨迹先做问题复现或负例测试，通过可验证修正后再谈训练。

## 2. 工具失败：先把分母和发生阶段讲清楚

你提出的开发部门差异非常关键，但也不能反向把开发部门的失败全部豁免。开发测试里可能有正常负例，也可能有真实缺陷；自定义工具发布以后同样承担生产质量责任。

最小二维标签为：

- `tool_origin`：native / custom / unknown。优先来自工具注册表；原生 `bash` 的底层目标另记 `underlying_target=xxx.py`。
- `usage_phase`：development / acceptance / production / unknown。优先来自测试运行标签、发布注册表或显式清单；不从部门名称、工具自定义与否或失败多少猜测。

已有日志不能恢复阶段时，历史记录保留 unknown。从今后的测试入口写一条标记，比训练一个“测试意图识别模型”更简单。阶段也可先在少量运行 manifest 上明确，无需给每条会话增加人工标注。

**至少并列两个指标：**

```text
原始工具错误比例 = error / (success + error)

已验证预期错误 = error 且测试定义明确预期出错，且测试断言通过
剩余错误比例 = (error - 已验证预期错误) / (success + error - 已验证预期错误)
```

取消和状态未知单列，不塞进成功分母。第二个比例只表示“排除了有证据的预期负例”，仍不自动等于缺陷率。断言失败另记，即使工具状态是 success，也可能是应报错却没报错。没有断言的 “expected_error=true” 不足以剔除错误。

首先核对你报告中 **IAD-D 总失败 4.5% 与部分 skill 75% 左右** 的分母是否一致：前者可能是工具调用率，后者可能是“加载过该 skill 的会话中至少出现一次错误”。一次错误若被归给该会话所有 skill，会进一步放大归因。新版只有工具事件携带直接 capability 绑定时才归给对应 skill/agent；“一起出现”留作关联线索。

排查顺序建议：同阶段/同版本内先看剩余错误次数、影响会话/用户范围，再看比例与样本量；20 次调用只是演示的小样本标记，不能作为自动质量门槛。发现 75% 时显示 `3/4` 或 `750/1000` 的差别，比增加复杂评分更有意义。

## 3. 复用的两条线：能力扩散与产物再次进入

| 信号 | 可以报告 | 尚不能报告 |
|---|---|---|
| 文本提到某 skill/agent | 能力提及候选 | 已调用 |
| 成功加载 SKILL.md / 配置 | 能力材料被加载 | 该能力已完成任务 |
| runtime 明确调用 skill/agent | 使用人数、调用会话、提供部门 → 使用部门 | 输出正确、投入业务 |
| 工具事件绑定 skill/agent | 该能力路径中的工具错误/资源线索 | 能力是错误根因 |
| 产物在别的会话重新上传，明确来源 ID/版本 | 产物再次进入工作流程，来源可追踪 | 已阅读/业务采用 |
| 同租户、较早产物与后来上传文件字节哈希相同 | 同内容再出现候选 | 一定来自该生产会话或该部门 |
| 来源关联明确且后续成功 read | 观察到跨会话文件使用 | 节省工时/提高良率 |
| 技术验收通过 / 业务采用回执 | 对应验收或用途事实 | 未覆盖任务的总体成功/收益 |

产物关联按 `tenant + artifact_id + version` 优先；文件搬运后新 ID 可用 `source_artifact_id/source_version`。只有本地文件时，显式清单逐个计算 SHA-256。时间顺序、跨会话、同租户必须同时满足；字节哈希不同不能排除修改后复用，字节相同也可能只是公共模板。多生产来源保留歧义，不能“最近写过的人获全部功劳”。

能力目录只要补：类型、ID、版本、提供部门、发布时间、可见部门。优先查看跨部门实际调用次数和重复使用用户数；目前脚本给出每部门观察到的用户数/调用会话，重复回访可由带时间戳的事件再聚合。若需要可复用的 skill/agent 类别，把注册表中已有 category 当维度；暂不训练额外分类器。

“可见但未观测到调用”是供给候选，还需检查采集覆盖、上线时长、入口可发现性、已有替代办法、真实需求、用户资格。没有可靠可见范围不生成这类候选。你报告里 `g2-dyh-hx2-data-nav` 同时出现在“失败率 0%”与“使用率 0%”的描述中，需要先核对是否混淆了两个零。

## 4. 路由先改任务提示，不必先换模型大小

你的思路可以收敛成一个小试验：**分类结果选择一段短任务提示，和原始用户输入一起交给同一个模型。** 不让另一个大模型自由改写所有原文，也不要求暴露或拟造模型内部推理。

先试四种策略：

| 策略 | 实际改变 | 回答哪个问题 |
|---|---|---|
| A：原提示 | 无 | 当前基线 |
| B：通用短提示 | 所有题追加同一段目标/格式提醒 | 仅仅加一点指导是否够用 |
| C：关键词类别提示 | 唯一命中类别才加短提示，歧义透传 | 简单分类是否有增量 |
| D：TF-IDF 类别提示 | 分数过开发集阈值才加提示，其他透传 | 训练路由是否比 B/C 更值得维护 |

当前包实现 A/B/C/D，保留原始 message 列表内容，追加的提示明确要求保持数字、单位、权限边界、任务范围和原输出格式。自动分类仍可能诱发执行偏差；保留原文只是可审查性措施，不是效果保证。模板需和你们真实 taxonomy 对齐。多轮分类在本版透传，待明确需要时再做只包含已知条件的上下文路由。

查询改写研究给出了“通过下游任务衡量输入变换”的方法启发，但论文里的 Rewrite–Retrieve–Read 涉及检索与问答，**不能据此认定通用 Agent 加提示会提速**。这里提出的是待测假设。[Ma 等，EMNLP 2023](https://aclanthology.org/2023.emnlp-main.322/)

选择提示策略要看：同题通过/退步、关键字段错误、含路由与失败重试的总 token、端到端耗时、实际加提示覆盖率。提示也会增加输入开销。D 若没有超过 B/C，就保留更简单的策略；不要因为分类 F1 更高自动推广。没有流量随机化时，固定题离线对照只证明题集上的结果，线上收益仍需小范围复查。

**不要把 intent_routing 题作为这个试验的下游指标。** 把预测类别加到提示再让模型输出类别，容易直接泄露被考答案。新版会拒绝这种组合。改用完整输入的字段抽取、recipe 差异、日志解析、固定数据计算；测试实际完成质量。

## 5. 你的路由成绩应怎样汇报

你报告里至少有两组实验，不能混为一个模型的改进曲线：

| 实验 | 你方报告值 | 当前能支持的表述 |
|---|---|---|
| 1013 条实验 | macro-F1 0.67 vs majority 0.09；阈值 0.5 覆盖 23%，选中正确 95.7% | 在该数据与标签口径上存在可学习结构；需记录分集、规则/标签版本和选中数 |
| IAD-D train → BEOL5 dev → BEOL4 holdout | dev 0.570 vs 0.137；holdout 0.434 vs 0.163 | 存在跨组织转移差异；若标签是 AUTO，则是对弱参考标签的一致性 |
| 同一跨组织实验的阈值 0.42 | holdout 覆盖 74.2%，选中正确 73.9% | 若阈值在 dev 决定，可作为一次保留集观察；若看 holdout 后选，则该集已参与调参 |
| coding 类 | holdout 仅 3 条，F1=0 | 暂不支持稳定路由；不能靠多数类成功掩盖稀有关键任务 |

如果生成真值的关键词规则，和比较的 keyword baseline 完全相同，在相同覆盖样本上通常应高度一致。出现 TF-IDF > keywords 时，先核对是否用了另一版本规则、不同标签合并、first-match 与弃权策略、不同样本，或真值含其它来源。这个核对很便宜，往往比调参更先决。

弱标签可以用于初步训练与探索。程序验证的结构化 golden 也能用于能力评测。两者都不是用户采用的替身。Snorkel 的官方示例同样把程序弱标签和手工标注的保留集区分开。[Snorkel 官方教程](https://snorkelproject.org/use-cases/01-spam-tutorial/)

## 6. 组织隔离、时间隔离分别回答问题

- 新部门接入：保留 IAD-D → BEOL 的组织迁移试验，`--org-field org_section` / `--org-holdout`。
- 已有部门的后续使用：同来源组不跨集，再按时间建立未来窗口；不要求同一科所有任务永远在一个集合。
- 同 recipe/lot/run/复制材料的变体：只换科标签无法防泄漏，仍需要来源族与父子关系。

scikit-learn 的分组与时间验证文档支持按数据依赖和部署目标选拆分方法；“更严格”不等于“更贴近所有上线情况”。[官方交叉验证文档](https://scikit-learn.org/stable/modules/cross_validation.html)

注册表会继续禁止历史 holdout 或其已登记衍生来源进入训练。变更评测目的时建立有说明的新实验，但不能删除隔离记录来释放旧测试题。

## 7. 没有长期人工运营，也能形成闭环

自动导出/审计 → 当前证据快照 → 组织能力诊断与失败候选 → 自包含评测题 → 改提示/换模型的小对照 → 保存版本与退步题。人工确认是可选证据支路；它不阻塞这条自动链路。

只在关键歧义处用一次短核对：例如“75% 中是否多数是预期测试”“这份对比表是否进入实验准备”。若仍拿不到确认，业务采用保持 unknown，汇报平台实际供给、可验证技术结果和改进实验。这里可说清楚花费对应了什么能力、哪些人实际调用、哪里有已测增量；尚不能说总体节省多少工时。

你暂无工具修改权限，清单可以作为内部讨论材料，但本包不自动发给部门。若错误来自权限/接口不可用，换提示也可能无效；标记依赖问题即可，不制造“模型优化能解决一切”的闭环。

## 8. 下一步只做这一轮

1. 用现成导出跑组织诊断，先检查一个高失败 skill 与一个低失败 skill 的分母、绑定和阶段。阶段全 unknown 也可以出表，先暴露缺口。
2. 找 5–10 个已知产物，检查它们是否能通过上传元数据/本地文件哈希接起来；同时导出已有 skill/agent 注册目录。不为了补复用率重做文件系统。
3. 从现有题库挑 10–20 个真正下游、可程序判定且来源独立的任务跑 A/B/C/D。保留 AUTO 路由成绩为诊断参考，SFT 继续为 0。

工作量取决于导出字段，以上是推进顺序而非工期承诺。完成这三步，下一次要回答的是“哪些证据已能稳定重复、哪种简单改动真的有效”，再决定是否增加模型规模或训练项目。
