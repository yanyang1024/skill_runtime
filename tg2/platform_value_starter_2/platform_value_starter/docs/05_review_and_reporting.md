# 没有持续人工运营，也能更新证据与改进

默认执行自动链路：导出审计 → 幂等入库 → 组织能力诊断 → 问题/使用候选 → 版本化评测 → 提示/模型对照。用户确认是可选证据支路，不阻塞批任务，也不由关键词替代。

## 1. 自动分析和业务确认各自记录

| 数据 | 默认用途 |
|---|---|
| 请求、工具事件、能力目录/调用、上传/读取 | 观测计数与来源；缺失不补零 |
| AUTO 关键词/模型标签 | 排障与任务分类候选；不计人工作用/采用分子 |
| 程序验收目标 | 狭窄任务技术正确性；真实/合成分列 |
| 用户明确确认或已有业务回执 | 用途、采用事实；必要时按 work_item 去重 |

本版 value_loop 的业务确认通道仍只计算 human 记录，程序真值属于题集通道。若你们以后接上可靠业务回执，应扩展专门来源字段和校验逻辑，不要把它伪装成 `AUTO:heuristic` 或手工确认。

0/1055 人工确认覆盖意味着“采用情况尚未得到确认”，并不意味着平台无价值，也不意味着统计可直接代替确认。没有反馈资源，就报告已观察使用、能力扩散、可复现问题和技术改进。

## 2. 只在少量高影响歧义上核对

优先核对两类：会显著改变动作的解释（高失败其实是不是测试）；要写入具体业务案例的采用事实（产物用在了哪个步骤）。不要求每周 10–20 条，不要求用户持续填卡。初次 5–10 条只适合发现解析/标签错误，不能拿它估精确全平台成功率。

必要时给一张短卡，允许修改、跳过与负面反馈：

> 这次任务：〔可修改摘要〕  
> 结果：〔文件/回答及版本链接〕  
> 目前是：可用 / 部分可用 / 不能用 / 还没检查？  
> 有没有用到工作里：已使用 / 尚未使用 / 不清楚？如已用，在哪一步？  
> 希望我们先改善什么？〔可选〕

只有用户愿意估计时再问人工投入，包含检查、修改和返工，可填范围或未知。不预设节省为正；本来不会做的任务记新增能力。业务认可不等于训练用途许可，`allowed_uses` 不从点赞/感谢词推定。

技术失败也允许多个解释：模型答错、资料缺失、权限/API 不可用、测试负例、需求改变、未知。没有工具修改权限时，保留复现材料即可；不假装已经完成修复，也不自动给别人发通知。

## 3. good/bad case 的最小资产化

一个当前案例保留 case_id、source_revision、组织、原始证据定位、自动候选、可选人工确认。不要整场对话标 good 就训练全部 assistant 回复。

- 可复现失败：形成输入条件、相关工具/skill 版本、错误类型、预期结果待确认的回归候选。
- 有程序验收的窄任务：提取自包含任务与验证目标，按来源组进候选题集。
- 明确业务采用：增加 work_item_id、用途、结果链接；多个会话同事项不重复记收益。
- 仅有“谢谢”或长期无回复：结果 unknown，可以继续用于活动与路由探索。

自动候选可以按组织/能力聚合帮助排查；定向失败样本的比例不能当线上完成率。固定 anchor 与新挑战集分别版本化；已有 holdout 用于调参后不再称未见测试。

## 4. 更适合当前现实的向上汇报模板

下面都是待填字段，非本次实测结论。

> 在〔窗口〕，我们完成了〔输入名单/分页/详情/usage〕范围内的只读分析。主动使用人数〔n〕、观测请求〔r〕，成本台账〔金额/口径〕。部门 token 表示工作负载，尚缺〔资源字段〕时不直接当作费用分摊。
>
> 〔提供部门〕的〔skill/agent〕被〔使用部门/人数〕实际调用；〔产物〕出现了〔明确来源的再次上传/读取〕。这些证明能力与材料进入了后续使用路径，业务采用〔已确认事项/仍未知〕分别列出。
>
> 诊断显示〔能力/工具/版本〕在〔生产/开发/验收/未知〕阶段有〔error/known_calls〕。其中〔n〕次是已验证测试负例；剩余问题主要为〔已知错误类型〕，未知为〔n〕。这用于决定排查顺序，不评价部门贡献。
>
> 在〔冻结下游题及版本〕上，同一模型的〔提示策略〕相对原流程新增通过〔a〕、退步〔b〕，资源变化〔token/耗时/覆盖〕；真实与合成子集分别为〔数据〕。如没有实际模型调用，明确写“仅流程验证”。
>
> 下一步只投入〔一个可执行动作〕，用〔固定验收与来源〕决定继续还是停止。尚不能证明的业务收益包括〔工时/项目周期/良率〕，不填推导出来的精确数字。

若有采用实例，用一张任务→产物→用途卡解释机制；没有则用一项严格对照的技术改进支持建设价值。不要用精选成功案例、token 增长、低失败部门排名代替全平台价值结论。

## 5. 最小更新节奏

| 触发 | 动作 | 保留产物 |
|---|---|---|
| 有新导出 | 审计、幂等入库、迟到事件回拉 | 原始快照、rejected、当前案例 |
| 定期批处理 | 更新组织能力/资产关联与覆盖 | 新目录报告，保留 unknown |
| 有重要候选 | 必要时一次核对或补程序验收 | 来源、标签版本、可复现条件 |
| 改提示/引入模型 | 相同冻结题同条件比较 | 全部试次、缺失、退步题、资源 |
| 有足够独立新题 | 冻结新挑战/未来 holdout | 同一个 split_registry、来源谱系 |

