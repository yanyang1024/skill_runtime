# 组织归因的公平性，与复用证据的分级

对应脚本：`org_skill_map.py`（部门×技能×工具可靠性）、`reuse_signals.py`（产物与技能复用）。这两份分析都是**只读的**——随时可对全量数据跑，不改任何状态。它们服务的具体问题：「哪个科的哪个工具该修」「哪些技能没被用起来」「产出的资产有没有被别人真正用」。

## 1. 为什么工具失败率必须先谈公平，再谈排名

实证观察：工具开发部门（如 IT/平台科）会对自己搭建的自定义工具反复测试试错，打磨到不怎么失败才开放给其他部门。这意味着：

- 同一工具的失败事件混着两种性质完全不同的会话：**开发测试**（失败是工作内容）和**生产使用**（失败是用户受损）;
- 直接按部门排失败率，惩罚的恰是为全公司造工具的人——排名一旦发出，合作意愿受损，数据质量随之下降。

因此 `org_skill_map.py` 把四条护栏写死在代码里，而不是写在建议里：

| 护栏 | 实现 |
|---|---|
| 开发测试与生产使用分列 | 会话级 `purpose` 字段（tool_dev / tool_use / unknown）;tool_dev 永不进生产失败率和修复候选清单 |
| 工具来源拆分 | 事件级 `origin`(builtin / custom / unknown);unknown 不归因到任何一侧 |
| 小样本不排名 | `--min-calls`（默认 20）以下只列出、标「样本不足」 |
| 不输出跨部门总榜 | 只有各部门内部表 + 排除测试会话后的修复候选清单 |

`purpose` 和 `origin` 需要在导出侧填充：origin 通常能从工具注册表直接 join;purpose 的可靠来源是"会话发生在该工具的测试 workspace/项目"，**不要用关键词猜**——猜错的代价是把真实用户失败洗成"开发测试"。

### 读数口径

- 「IAD-D 的 etch-data 失败率 43.3%」的正确读法：这是**修复优先级信号**，不是技能质量 verdict；先确认 origin、purpose、绝对调用量；
- 「BEOL 的 apple-to-apple 失败率 1.5%」也不自动等于优秀——可能是该科任务本来就简单。**跨部门比较的是问题落点，不是部门优劣**。

## 2. 技能供给侧：平台运营的新抓手

会话数据里天然不出现"没人用的技能"，所以零使用检测需要一份**技能登记表**(`--skill-registry` JSON:技能 → 目标部门/负责部门）。登记表本身值得维护——它就是平台的"供给侧资产台账"。

错位只有两种成因，排查动作完全不同：**没被宣传**（运营问题：培训、文档、默认可见性）或**匹配错**（产品问题：技能假设的业务场景在该科不存在）。报告只给候选清单，成因必须人工确认，脚本不做猜测。

## 3. 复用证据的阶梯

`reuse_signals.py` 把"产物被复用"分成强度不同的证据级，**逐级分开报，永不加总**:

```text
跨用户 upload  ── 最强：别人把你的产物主动带进新任务
跨用户 read    ── 强：产物被其他会话读取
同用户复用     ── 粘性证据，不算平台资产扩散
同名文件       ── 不是证据（basename 相同太常见）
```

身份对齐只认「同租户 + artifact_id + version」（或内容哈希）。没有稳定身份时宁可报"无法观测"，不要回到 basename 匹配——旧包 0.18% 的"复用率"就是这么来的。

**skill/agent 本身也是可复用资产**，而且天然有稳定身份（技能名）:skill_reuse 表给出每个技能覆盖的部门数、用户数、会话数。它回答的是供给侧问题——"我们建的资产有多少被实际采用"，建议与文件产物复用并列进汇报。

### 汇报时的安全句式

- ✅「本期观测到 N 条跨用户产物复用（其中 M 条为上传），涉及 K 个部门的产物」;
- ✅「技能 S 已被 X 个部门的 Y 名用户使用」;
- ❌「平台复用率 12%」——分母（可被复用的产物全集）不可观测，这个数字必然造假；
- ❌「产物存活率」——没有持续观测手段时，没有记录 ≠ 已死亡。

## 4. 与月度节奏的关系

三份只读分析（task_atlas / org_skill_map / reuse_signals）可以每次导入后直接重跑，成本是秒级。建议固定输出到 `analysis/YYYY-MM/` 版本化目录，不覆盖历史——三个月后"修复候选清单的变化"本身就是平台改进的证据。
