# 从会话信号改进 Skill 与 Agent 文档：修改、创建与归档

基于 agents-creator v3、实际会话样例和处理反馈 · 2026-09-20

## 1. 这次固定优化对象，再倒推需要的信号

本文的 Agent 是 `.opencode/agents/` 下的 primary / subagent Markdown 定义，包括 frontmatter 与正文。`AGENTS.md` 是环境中的另一种上下文来源，不混入这类 Agent 的使用统计。

优化对象固定为 Skill 与 Agent 文档后，评测的问题应是：

> 这些文档是否让合适的任务找到合适的方法和执行者，减少反复补充指导，保留必要约束，并交付可信结果？

工具与脚本轨迹提供证据。它们可以帮助发现文档中的错误路径、缺少的前置条件或不合适的恢复指导；若根因是实现缺陷，则记录依赖问题，避免把文档越补越长。

新版 agents-creator v3 已给出可用的修改边界：

| 文档对象 | 应主要负责 | 优化时优先观察 |
|---|---|---|
| Skill 的 description / 名称 | 适用场景、发现与选择 | 明明适用却没找到、被错误场景加载、同类能力难以区分 |
| Skill 的正文与 references | 场景内的方法、条件分支、输入输出、检查与恢复 | 用户反复补步骤、约束遗漏、必要澄清缺失、方法重复发明 |
| primary Agent 文档 | 职责、能力导航、分工选择、交付责任 | 误选 Skill / worker、漏传条件、重复派单、漏汇总、错误宣布完成 |
| subagent 文档 | 子任务职责、上下文边界、回传责任 | 输入不足仍猜测、跨任务串用信息、回执不可消费、超范围行动 |

命令或参数细节集中在 Skill / references；Agent 不重复维护完整 SOP。只有名称、适用范围、对外契约或必需权限变化时，才检查调用方文档是否需要同步。

## 2. 先修正四个会影响生命周期决策的口径

### 2.1 Skill 的 load 与 Agent 的 invoke 不是同一套漏斗

旧反馈中的“load > 0、invoke = 0，所以 Skill 沉默供给”不能成立。Skill 通常通过加载影响当前主体的后续行为，不一定有一个独立的 invoke 事件。

分别记录：Skill 加载请求、加载结果、可观察的后续相关行为、任务产物证据。后两项可能缺失，也可能无法唯一归因；不能把不存在的 invoke 字段当成未使用，更不能据此归档。

### 2.2 Agent 不只是 task 调用中的 subagent_type

`task.input.subagent_type` 可以说明请求派给谁；它不能覆盖 primary 的运行，也不能证明最后实际解析、加载的是哪一份定义。

f64e 的 Assistant 标题先出现 `Course-Director`，后出现 `Build`。这说明一个 session 可能有角色切换；整条 session 不宜只归到一个 Agent。标题可作为当前已有的角色线索，实际名称映射和文档版本仍以平台记录为准。

因此修正旧反馈“Agent 没有磁盘定义可核对”的前提：你的 primary / subagent 确实有文档。当前目录有它，只说明当前存在；不能据此证明历史时刻加载了它。

### 2.3 加载错误与方法失败分开

同事件 ID 绑定可以可靠定位“这次 Skill 加载报错”，但不能把它直接命名为“Skill 方法失败”。名称、路径、权限、加载服务异常，需要与执行后未满足业务要求分开。

同样，task completed 是派发返回状态；worker 完成复核不等于被复核数据正常。v3 的 lot-master / lot-worker 样例已经特别区分这两层。

### 2.4 当前存在、当时可见、当时加载、结果有效分别记录

不要继续让一个 `verified` 字段承担全部含义。可以用几项事实代替：当前是否有文件、当时是否可发现、加载返回什么、版本是否绑定、结果检查到什么。

同名跨用户 Skill 需要命名空间；首次观测时间不等于发布时间；观察到哪些部门用过，不等于哪些部门有权使用。

## 3. 最值得采集的六组信号

以下重点是能够改变文档决策的信号。规则先做定位和计数，语义判断只处理抽样与候选；所有“适用、重复、遗漏、改善”标签保留证据和未知项。

### A. 适用任务有没有找到能力

**采集：** 用户目标与输入类型、已有能力目录、当时可见性、选择的 primary / subagent、Skill 加载、用户显式点名或改选、选后退出或切换。

**语义复核：** 这是该能力适用的任务吗？输入与依赖满足吗？是否允许多个合理选择？

**可以推动：** 修改 description、触发边界、Agent 能力导航、同类能力的区别；当能力已存在时，优先修发现与选择问题。

**评测：** 使用适用任务和相近但不适用的任务，看能否选择合适能力并完成任务。不要只提高加载率。需要取到“没有加载目标 Skill”的相关会话，否则看不到漏选。

### B. 用户是否反复补充相同的方法或约束

**采集：** 用户纠正、补充步骤、指定格式、重复给同一规则、要求重新读取某份材料，以及这些操作前后的产物证据。

**语义复核：** 是最初要求被漏掉，还是用户新增需求？是当前项目的特殊规则，还是可复用方法？前一轮是否有足够输入？

**可以推动：** 给 Skill 补前置条件、检查项、条件分支或示例；给 primary 补任务包约定；将特定项目数值留在输入规则中。

**评测：** 对冻结需求检查必要条件是否满足，以及用户还需补充多少有效指导。不能把用户消息少直接当作改善，必要澄清仍应发生。

这里适合重点看你已发现的 question 工具：区分补缺失信息、请求业务决策、重复询问已知信息。前两者经常是正确行为，第三类才是精简文档或修复状态衔接的候选。

### C. 必要步骤是否正确执行，而不仅是出现过

**采集：** 文档规定的关键步骤、可定位的调用与产物、校验对象和结果、同目标重试、阻塞后的处理方式。

**语义复核：** 步骤在当前场景是否必要？有没有合理等价路径？是文档不清、未被遵循，还是底层能力做不到？

**可以推动：** Skill 写清检查对象、执行时机、成功证据、何时停止；删除过时命令；把复杂条件放入按需参考。

**评测：** 已知正常例与缺陷例能否分别正确通过和被识别。缺步骤轨迹记 unknown，不因日志里没看到就直接判没做。

### D. Agent 是否正确选择、交接和收尾

**采集：** primary 角色区间、task 请求、子会话 ID、输入引用、必要条件、输出契约、回执、下游接受或拒绝、最终未完成项。

**语义复核：** 输入是否自包含？角色边界是否有意义？是否把子任务 PASS 当成总体 PASS？是否把生成者自评交给独立验证者？

**可以推动：** primary 的路由和交付责任；subagent 的输入不足处理与回传规则；共享契约的集中维护。

**评测：** 对缺输入、分支失败、部分完成和正常完成的任务，检查状态与交付是否准确。独立上下文是否存在是运行事实；独立验收是否有效，还要看能否识别错误产物。

### E. 文档是否造成重复工作或相互冲突

**采集：** 同一会话反复加载、不同文档对同一事项的不同要求、用户重复确认、没有新证据的重复派发、读取量及相关步骤成本。

**语义复核：** 重读是否因上下文压缩或内容更新而必要？要求是否真的矛盾？不同角色是否在重复维护同一份方法？

**可以推动：** Agent 保留导航，SOP 集中到 Skill；重复分支合并，按需读取；两个 creator 之间保留目标和已完成进度。

**评测：** 小改动后在同类任务上减少重复工作，同时保留质量与检查覆盖。文档短、token 少只能作为辅助收益，不能牺牲目标完成。

### F. 哪些需求持续存在，哪些能力已被替代

**采集：** 任务家族、独立需求次数、用户覆盖、业务周期、成功方法重复出现、产物后续使用、可见能力、入站依赖和替代能力。

**语义复核：** 重复的是稳定方法，还是只是同一主题？低使用是低需求、难发现、依赖坏了，还是业务季节性？替代品是否覆盖少见但重要的任务？

**可以推动：** 新建、合并、减少默认展示、归档与恢复。

**评测：** 创建看新增覆盖或减少的重复指导；归档看依赖迁移和少见任务是否仍可完成。单纯“最近没调用”不够。

## 4. 三类操作各自需要什么证据

### 4.1 修改：把观测问题对应到文档中的具体责任

| 现象 | 优先修改位置 | 需要排除的解释 |
|---|---|---|
| 相关任务经常没选已有 Skill | Skill description / Agent 导航 | 能力当时不可见、用户明确选择了其他方法 |
| 选对 Skill 后重复遗漏同一必要条件 | Skill 流程、示例或分支 | 原输入缺失、工具没有返回数据、用户后来改了需求 |
| 两个 Skill 在同类任务上难以区分 | 触发描述、导航或方法合并 | 实际适用条件不同，不能只按标题相似判断 |
| worker 常缺主会话里的关键信息 | primary 的任务包约定，必要时共享 Skill 契约 | 文件接口或权限问题导致信息不可达 |
| worker 已明确 BLOCKED，primary 仍宣称全部完成 | primary 的状态与交付责任 | 回执解析失败或证据缺失，不能先判模型不听话 |
| subagent 无规则时猜测、越过职责 | subagent 的边界及缺口回传 | 运行时实际权限和文档声明不一致 |
| Agent 与 Skill 复制命令，修改后不一致 | 详细方法归入 Skill，Agent 保留引用 | 公开接口变化确实要求双方同步 |

把修改提案写成一句可验证的假设：

> 在已提供规则的复核任务中，Skill 没有明确“先提取例外条件”，导致例外被漏掉；补这一条及一个反例，检查漏判是否减少，正常规则是否仍正确执行。

这比“优化提示词，提升准确率”更容易验证。文档已经明确且样例充分时，继续堆规则未必有用；可以保留模型或工具问题候选，不强行生成文档 patch。

### 4.2 创建：高频任务先寻找可复用方法，再判断是否需要新主体

你已有的 TF-IDF + Logistic Regression 可以继续用于已知任务分类；低置信度任务及同类输出中的重复流程作为新需求候选。它的分类结果只负责找样本，不直接决定新建对象。

整理候选时看“目标 + 输入 + 产出 + 方法”，不要只看关键词。相同标题的一串失败重试不能当作多份独立需求；一个用户也可能有真实高价值的重复需求，不强制要求跨部门才成立。

| 条件 | 优先动作 |
|---|---|
| 已有能力能做，只是不容易找到 | 改 description / 导航或说明入口 |
| 现有 Skill 缺一个相近分支 | 补分支或参考文件 |
| 多次任务重复一套稳定方法，已有主体可执行 | 创建 Skill，或先把很短的规则内联 |
| 需要稳定的独立用户入口、职责和交付边界 | 考虑 primary；同时检查能否扩展现有 primary |
| 需要独立上下文、独立验收、不同能力/权限或有实际并行收益 | 考虑 subagent 与调用方约定 |
| 缺数据、API 或模型能力 | 明确依赖需求，文档不能把不可用能力写成可用 |

v3 的 lot-master / lot-worker 给出了合适例子：二十个 lot 可以复用一种 worker 定义，产生二十个运行实例，不需要创建二十份 Agent 文档。部门不同、任务量多或步骤长，都不能单独证明需要新增角色。

自动生成时向 creator 提供“能力缺口简报”，不要直接扔几百条会话让它自行总结：

```yaml
proposal: create_skill  # 或 revise_skill / revise_agent / create_agent / archive_candidate
task_family: 待确认的任务家族
goal_and_scope: 稳定目标、输入、产出、适用与不适用条件
sources: [诊断样例的事件或文件引用]
known_good_and_bad: 已复核的正例、反例和证据
existing_options: 已核对的同类能力及仍存在的缺口
dependencies: 实际可用工具、数据、权限和未知项
intended_users: 相关使用场景；不含无关身份信息
acceptance: 此次新增能力要满足的可检查要求
target_scope: 候选文件的目标目录与允许修改范围
```

只给 creator 诊断材料。用于独立比较和最终验证的题目、答案与判分说明由评测侧保留。

### 4.3 归档：先区分“不需要、找不到、坏了、被替代”

| 信号组合 | 更合理的动作 |
|---|---|
| 很少使用，但相关任务很多且能力没被发现 | 修入口和触发描述 |
| 最近没有相关任务，能力用于季度或少见流程 | 保留，降低日常推荐频率 |
| 名称或依赖失效，仍有用户与 Agent 引用 | 修复或迁移调用方 |
| 两项能力高度重复，替代品已通过代表任务 | 合并并迁移依赖，旧版本进入归档候选 |
| 需求已确认退出，无活跃依赖且维护成本持续存在 | 归档候选 |
| 小对照显示缩减/替代文档不损失必要能力，并减少误选 | 考虑移出默认发现或合并 |

归档窗口依据业务周期，避免写死“30 天无调用就归档”。检查入站引用和近期运行引用，二者都不完整时标出未知。subagent 可以很少被直接选中，却仍是 primary 的关键依赖。

归档不是删除：保留版本、原因、替代路径与恢复入口。先迁移引用或停止默认推荐，再检查旧任务是否仍有可行路径；不能以“删掉文件后调用报错”作为它有价值的反证，也不能在新旧定义同时可见时声称已完成替代实验。

## 5. 最小采集：复用现有会话解析，只补决策所需关联

建议先输出两种记录，不增加复杂平台架构。

### 记录一：能力接触与运行事实

| 信息 | 当前可用方式 | 需要时再补 |
|---|---|---|
| session、消息/事件、时间、用户命名空间 | 现有解析器 | 主子会话关联 |
| primary 角色及切换区间 | 导出元数据或 Assistant 标题线索 | 运行器实际解析的 Agent ID / 来源文件 |
| subagent 请求与返回 | task 的 subagent_type、任务包、回执 | 实际加载身份及子轨迹 |
| Skill 请求、加载状态和返回内容 | skill 工具事件 | 加载内容指纹或实际资源版本 |
| 模型、工具、文件与检查结果 | 现有会话事件 | 缺失的产物、校验对象与覆盖信息 |
| 当前文档和依赖 | 指定目录或只读目录接口 | 运行时文档快照绑定 |

资源标识至少考虑租户/拥有者、kind、实际名称与来源，避免同名混合。Agent 正文、frontmatter 和 Skill 引用资源可能分别变化；做对照时冻结相关资源，不能仅用同名文件证明新版本生效。未知版本可以继续用于发现问题，限制其用于效果归因。

### 记录二：文档改进候选

从前一层筛出的片段生成：

```json
{
  "target": {"kind": "skill", "name": "待核对", "namespace": "待核对"},
  "operation_candidate": "revise",
  "task_family": "复核后的任务类型",
  "signal": "在输入齐全时反复遗漏同一必要条件",
  "evidence_refs": ["session/message/artifact 引用"],
  "alternative_explanations": ["输入截断", "工具未返回有效数据"],
  "suggested_document_area": "前置条件或检查步骤",
  "evaluation_target": "必要条件覆盖，同时保留正常例正确性",
  "status": "needs_review"
}
```

字段用于解释提案，不要求对每个会话都填完。优先保留少量有证据的候选，避免把所有统计变化变成待修改任务。缺证据时可以建议补采、保留原状或关闭候选。

特别注意采集范围：只查询某个 Skill 的使用会话，适合分析已加载后的问题；要找新需求、漏选和归档依据，还需一份不按该 Skill 过滤的代表样本。保留查询命中、下载、解析成功的数量与窗口，避免把默认 limit 截断当成全量使用情况。

## 6. 用旧样例与 v3 样例检验这些信号

| 材料 | 可以提取的信号 | 文档优化假设 | 怎么检验 |
|---|---|---|---|
| f64e：builder / verifier 依赖场景清单校验 | 调用约定、清单状态、回执中的单文件校验自述 | Skill 明确构建中与汇总后的校验范围，Agent 验收要求目标证据 | 空清单、不存在目标、合法/非法文件；工具实现缺陷单独记录 |
| f64e：大纲、job、回执与场景 | 交接字段、描述差异、状态传播 | 必要要求在交接时保留，回执由实际消费者正确处理 | 冻结输入及允许改写范围，检查必要约束与失败处理 |
| f650：doc-reshaper | 加载、参考读取、产物附录、用户需求 | 按条件组织保真检查，而不只要求附录存在 | 原文与改写关键条件对照，并检查可读性；现有轨迹不证明增量效果 |
| v3：同一助手加载两个 creator | 切换顺序、重复询问、进度是否重置、实际 diff | 联合创建后续接装配，不重复开始；方法内改动不波及 Agent | 用联合创建与仅改 Skill 两种任务，检查产物和无关改动 |
| v3：doc-router / parse-verifier | 任务包、独立会话、checked_ids、缺失证据 | 验证者只根据可达原始证据判断，主 Agent 处理未覆盖项 | 输入错误结论、缺图像能力、部分证据；验证 FAIL / BLOCKED 与汇总 |
| v3：lot-master / lot-worker | 每个 lot 的输入、状态、汇总覆盖 | 同一 worker 定义复用，避免串用规则与遗漏批次 | 两个规则不同的 lot，加一个输入缺失 lot |

前三行是已有运行材料可支持的诊断方向；后三行来自 v3 定义和教学样例，是待执行的行为题，不能标为已经发生的缺陷或已经通过。

## 7. 评估“文档改了更好”，需要区分发现与执行

一类评测从原始用户请求开始，检查是否找到正确 Agent / Skill。这适合 description、导航、合并和归档调整。

另一类评测固定合适的能力与输入，检查方法是否改善。这适合修改 Skill 步骤、subagent 回传或 primary 的状态处理。

强制加载 Skill 能测试方法，却测不到发现问题；只看是否选中，又测不到方法质量。改动影响两者时各留少量题，不要求完整大型 benchmark。

| 操作 | 对照方式 | 主要验收 |
|---|---|---|
| 修改 Skill 方法 | 同任务、同模型、旧/新文档 | 必要要求、错误恢复和产物质量；成本作辅助 |
| 修改 primary / subagent | 同任务、同可用工具与输入、旧/新角色定义 | 路由、交接、状态、最终结果 |
| 新建 Skill | 现有可工作的处理方式 vs 使用候选方法 | 增加的覆盖、减少的重复指导或资源消耗 |
| 新建 Agent | 现有主体/拓扑 vs 候选主体/拓扑 | 隔离、职责或并行的实际收益，以及协调代价 |
| 合并/归档 | 现有入口 vs 依赖已迁移的替代入口 | 相关任务仍能找到可用能力；少见重要任务不丢失 |

对照基线要可工作，不能故意保留断开的 Skill 引用制造“无 Skill 组失败”。两组都成功时，仍可比较人工修订、稳定性、时延与成本；没有差异证据时记录尚未证明增益。

结构化规则检查可以处理名称、引用、格式和确定的约束；Judge 处理语义要求与开放式偏好，并要求证据；少量人工复核重点看误放行、误拒绝和适用性判断。状态保留 pass / fail / unknown / not_applicable；低证据覆盖率不能包装成高成功率。

诊断中常见的正例可作为 creator 的说明素材；用于选择和最终验证的任务按来源/任务家族隔离。反复改 prompt 使用过的题不能再宣称独立验证。一次随机生成的差异不当作稳定提升，有争议时再重复相关题，不进行无目的全量重跑。

## 8. 把它接进现有五个评测 Skill 与两个 creator

| 现有能力 | 在本方案中的职责 |
|---|---|
| 合并后的 session-usage-analysis / session-observe 能力 | 收集事实、任务分布、能力接触与代表/定向样本；生成三类操作候选 |
| harness-diagnose | 检查候选是否真与文档有关，定位条款、替代原因与可验证改动 |
| eval-curate | 把已复核问题变成任务题，固定输入、要求与独立验证材料 |
| skill-creator / agents-creator | 根据缺口简报修改或生成候选文件，提供实际 diff、依赖和未验证项 |
| harness-compare | 验证旧/新或现有/候选方案，说明收益与退化 |
| experience-screen | 保存有范围的经验、保留/归档理由与反例，不把一次通过升级成通用规则 |

v3 的 `agents-create-assistant` 可以在同一主体内按需加载两个 creator；它当前 `task: deny`，不能把这个设计建议误解为让创建器去执行全部业务子任务。生成候选与独立评测可以由现有评测入口衔接，发布沿用平台已有版本和权限流程。

自动化优先承担：聚合、选样、生成候选、准备 diff 与评测题。涉及业务规则泛化、归档依赖和效果争议时，集中复核关键判断；不需要让人逐条审核全部原始事件。

## 9. 当前建议先做的小闭环

1. 修正 load/invoke、primary 覆盖、角色切换和加载错误分类，避免错误候选进入后续流程。
2. 在已有代表样本之外，挑选“用户反复补方法”“交接丢条件”“相关任务没选已有能力”三类片段，各复核少量。
3. 先交付一个 Skill 的小修改和一个 Agent 的小修改：分别验证方法与交接，不同时改很多配置。
4. 高频任务只形成一份新能力候选简报，先核对能否复用；归档先形成候选清单并核对业务周期、依赖和替代。
5. 每次记录改了哪个文档、针对什么问题、在哪些任务有效、哪些尚未验证。用这些记录累计“维护过的能力带来什么改善”，再用于平台价值汇报。

部门/职位在这里用于了解实际任务、选样和联系维护方，不用于评判个人能力。区分能力维护部门与使用部门；部门差异不能自动解释为文档质量差异，开发试错也不能自动豁免所有失败。
