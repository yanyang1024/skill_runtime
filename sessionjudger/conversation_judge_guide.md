# 从会话精读到可信裁判：先看懂，再自动化

针对你的半导体企业 Agent 平台，建议先完成三个产出：**一份有证据定位的会话标签表、一份少量人工参考、一份裁判分歧报告。** 不先追求总质量分，也不把“搭好裁判”直接当成“已经证明平台业务价值”。

本包是上一版价值分析与任务图谱的独立增补。没有读取真实内网会话、运行真实模型或验证你给出的比例；所有示例均为虚构。脚本是适配起点，优先复用你现有的导出和验收工具。

## 1. 精读的目标是可检验的发现，不是读满几百条

300–500 条是合理的累计观察规模，不是必须完成后才能行动的门槛。先读 20–30 条，试出一张好用的标注卡，再扩到 100，最后积累 300–500 条。记录每条阅读耗时；假设平均 8 分钟，400 条已需约 53 小时，尚不含附件核对和分歧处理。“一周”宜指管线原型与一轮小规模校准，不保证单人一周精读完全部样本。

你举的“70% 不是模型不行，而是首轮缺背景”应当作为**待验证假设**。看到背景不足与失败同时出现，仍不能排除模型没有主动澄清、skill 没补业务上下文、工具无权限、导出没带附件等解释。

更可信的汇报句式是：

> 在窗口 W 随机抽取 N 条会话，完成审阅 R 条，其中 F 条有足够证据判定目标未满足；F 条中有 X 条观察到必要输入缺失。它们常出现 A/B 特征。当前是关联发现；下一步用补充上下文或主动澄清的对照实验验证是否可改善。

分母不能悄悄把 unknown、未读完和缺附件的会话删掉。若 F 只含 unmet，就不要临时又加入 partial。失败优先补样用于找问题，另表统计，不混入随机样本比例。

## 2. 两类指标可行，但要分清“断言本身从哪里来”

| 类别 | 具体例子 | 能直接支持什么 | 不应跨越的解释 |
|---|---|---|---|
| 确定性观测 | 工具返回 error、文件成功上传、skill load、用户说“这个字段还不对” | 日志中的事件或原话存在 | error 不一定是任务失败；用户原话不自动等于领域事实 |
| 确定性验收 | 已有测试定义及断言结果；固定输入下的字段/数值/差异集合比较 | 在该验收范围内通过/失败 | 工具退出码 0 不等于内容正确；局部测试通过不等于整个业务目标达成 |
| Agent/LLM 判断 | 主任务、是否满足用户目标、必要条件是否缺失、主要卡点 | 有证据支撑的标签和解释 | 不掌握的材料、规则、真实采用不能凭推理补成事实 |
| AI 提议的新检查 | “检查 recipe 差异是否漏掉单位变化” | 一项值得实现的验收候选 | AI 临时生成的期望值不是独立真值 |

因此两条路线是：**已有规则直接算；需要解释的先判断；新提出的规则经确认和固定后，才转为可重复断言。** 不是把所有难算的指标都交给 Agent 自由打分。

你的工具开发部门尤其适用：原始 error 数保留，只有测试定义明确预期出错且断言通过才作为通过的负例；assertion_failed 即使 status=success 也要记录。部门、native/custom、development/acceptance/production 是不同字段，缺失为 unknown。

## 3. AI 先标四个维度，人工核对证据

| 字段 | 标签 | 人工最值得核对的地方 |
|---|---|---|
| `task_type` | knowledge / data_analysis / coding / parameter_compare / document / capability_build / mixed / unknown | 用户真正想做什么；不是加载哪个 skill 就是什么任务 |
| `context_sufficiency` | sufficient / missing_necessary / unknown | 缺的是不是完成当时目标所必需的条件；平台初始上下文是否已包含 |
| `observed_outcome` | met / partial / unmet / unknown | 满足哪个明确目标；依据是成果、适用测试，还是仅有用户确认 |
| `blocking_point` | missing_input / ambiguous_goal / tool_access / tool_execution / output_mismatch / no_observed_block / unknown | 是当前卡点还是已恢复的历史错误；是观察还是根因猜测 |

每维统一保留 `label + evidence_ids + reason`，另有一句 `next_check`。暂不加 1–10 的“综合好坏分”、复杂度等级、节省工时推断。

“用户水平如何”改成**本次输入与协作行为**的观察笔记：是否提供可复现输入、是否说明验收标准、是否指出具体错误、是否根据反馈补充条件。这些能指导产品改进，却不能可靠地给员工贴“初级/高级”标签。术语多、轮次多、token 多、工具试错多都不是个人能力证据。本版把这类笔记放在人工备注，不计算用户画像分。

`initial_context` 是首次响应前可用的请求、附件、系统/skill 规则等快照；它不只是首句文本。无法恢复时，背景充分性为 unknown。脚本不会拿最后一轮新增要求倒推最初用户没说清楚。

参考输入增量：

```json
{"initial_context":{"complete":true,"user_request":"比较附件中两版参数差异，保留单位","attachments":[{"id":"input-a","content":"已冻结的必要内容"}],"available_resources":["当时可用的单位换算规则"]}}
```

只有实际覆盖了该任务必要输入时才标 complete=true；路径或文件名不等于裁判已读到内容。真实附件内容可由既有解析器提取并冻结，脚本不自动打开任意路径。

## 4. 抽样：一条随机主线，一条问题补样支线

最简单的主线：选定固定窗口和可审阅租户 → 每会话一份当前快照 → 随机抽 400 条 → 保留来源、缺失和未完成审阅记录。它描述“会话分布”，不是“用户分布”；高频用户自然占更多会话。如要研究用户差异，应另按用户抽样，不能偷换结论。

`sample_review.py` 默认将已抽中的会话按同源家族分到以下用途，同源不跨集；目标数量因家族大小可有偏差，实际数量见 manifest：

| 用途 | 默认目标 | 怎么读 |
|---|---:|---|
| pilot | 30 | 精读、修 taxonomy/rubric，可以看 AI 建议；不再拿来做最终考试 |
| calibration | 40 | 人工参考 + 裁判提示迭代；尽量独立读，辅助核验须注明 assisted |
| audit | 60 | 先独立人工标，再对冻结裁判做一次核验；避免提前查看 AI 结论 |
| reading | 剩余约 270 | 累积发现，可用 AI 辅助；不自动成为新的金标准 |

40+60 是首批约 100 条人工参考的示例分配，不是统计保证。样本不足时不复制凑数；脚本展示实际数量。标签极少的类别、复杂任务和小部门可能不足以评价，应另补覆盖题，并和代表性随机样本区分。

与上一版兼容：cases.jsonl 可直接进入；同源家族从 session.source_group 读取。若你的家族信息在另一个表，先按 case_id 合并。缺家族信息时只隔离 session，不能声称已排除相同 recipe/lot/模板衍生题。这里的分集只约束裁判开发，不覆盖上一版 train/dev/holdout 注册表。

## 5. 人工参考如何形成

1. 先读证据，独立给标签与证据位置。只检查 AI 标签的对错容易受锚定影响，不能完全替代独立标注。
2. pilot 中看到真实歧义再改 rubric，尽量一次稳定四个维度。保留明确正例、反例和 unknown 例子。
3. 从约 100 条参考中拿 20–30 条让另一位合适的同事独立标；不先展示第一位或 AI 的答案。先看人和人分歧，再要求机器与人一致。
4. 共同核对分歧；缺附件、缺领域规则就保留 unknown。需要半导体业务判断的题交给懂该任务的人核对，不能由 AI 工程师单独宣布工艺真值。
5. 保留原始两份标注和最终审定记录。只有核对后的行才标 verified；assisted 和 independent 分开。

没有第二位同事时，先称“单人审阅参考集”，照样能做诊断，但不宣称已验证人工标注可靠性。自动写 reviewer_id 或 verified 只是文件声明，脚本无法证明真的有人认真读过。

## 6. 裁判先用一次 LLM 调用；确实缺证据再升级 Agent

| 方式 | 何时够用 | 最小做法 |
|---|---|---|
| 规则/程序 | 目标能精确比对 | 直接运行已有解析器和测试，结果连同适用范围进入证据 |
| LLM-as-Judge | 材料已经齐全，需要语义判断 | 独立上下文，固定 rubric，一次结构化标签输出 |
| Agent-as-Judge | 必须读产物、定位证据、调用已有验证器 | 独立上下文，只访问该题允许的冻结材料；固定预算；拿不到就 unknown |

不是 Agent 数量越多越可信。生成任务的 Agent 和裁判隔离；裁判不能边改产物边验收、自己改标准直到通过。当前脚本只实现 LLM 请求适配，不执行 Agent 工具。

可供你接已有平台的 Agent 伪代码：

```python
def judge_with_evidence(packet, rubric, allowed_tools):
    # 接口伪代码，不是本包已实现的工具运行器。
    evidence = packet.frozen_evidence
    for _ in range(2):  # 预算示例，不是普遍最优值
        need = propose_missing_evidence(evidence, rubric)
        if not need:
            break
        # 工具必须已注册；只读指定产物或运行隔离的已批准 validator。
        result = allowed_tools.read_or_validate(need, snapshot=packet.snapshot)
        evidence = append_trace(evidence, result)
    return label_with_citations(evidence, rubric, allow_unknown=True)
```

LLM/Agent 建议“补一个单位检查”可进入规则候选池；人工确认输入、规则和参考值，验证器版本固定后，才进入下一版评测。运行中临时生成的检查仅作补充线索，不混成和旧版本可比的正式得分。

## 7. κ 是校准工具，不是单一达标按钮

Cohen's κ 衡量两位标注者的分类一致性，并校正按边际类别分布得到的偶然一致：`κ=(观测一致率−偶然一致率)/(1−偶然一致率)`。本包四维是名义类别，逐维算未加权 κ，不先把多个维度平均成总分。[官方定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.cohen_kappa_score.html)

每轮并列看：

- 有效人机对数 / 合格人工参考数；超时、坏 JSON、缺失和过期记录单列。
- 各维 κ、原始一致率、混淆矩阵、每类 support/precision/recall。
- unknown 的数量；同时报含 unknown 的指标及双方非 unknown 子集指标和该子集规模。
- 人工 unmet/partial 被判 met 的比例，及人工 unknown 被判 met 的数量。
- 部门切片及具体分歧；小样本不作质量排名。

两边全填同一个类别可能有很高一致率，但 κ 不可定义；程序返回 N/A，不伪造为 1。unknown-unknown 的一致也不等于裁判有能力完成判断。相关会话、同用户重复出现和稀有类别会限制结论，400 条总量不能替代每类样本覆盖。

不要写“不断调提示直到 κ≥0.8”。应该先在 calibration 上约定用途、可接受误报和需要覆盖的类别；迭代两三轮仍无改善就检查 rubric 或输入。固定提示后只看一次 audit。没有通用 κ 门槛：用于找待复盘线索，和用于自动宣布业务成功，需要的错误容忍度不同。

这版输出报告与分歧队列，不自动发出“达标”判决。你若要加 gate，至少同时约束关键错判、unknown/调用覆盖和必要任务类别的样本量，阈值在 audit 前写清楚。

记录实际模型部署版本；只写一个可能变化的模型别名不够。temperature=0 也不等于永远确定。若裁判不稳定影响决定，可只对一小组固定案例重复运行观察翻转，不必一开始把整批会话跑很多次。

LLM 裁判已有研究指出位置、冗长、自我偏好及推理能力方面的局限；对照人类偏好的一致成绩不能直接迁移为半导体任务正确性保证。[Zheng 等，2023](https://arxiv.org/abs/2306.05685)

## 8. 这批会话如何接上图谱、benchmark 和训练

| 产物 | 下一步 | 不能直接做 |
|---|---|---|
| 人工核对的 task_type | 按 case_id/source_revision 映射到上一版任务图谱标签文件，记录实际标注来源 | 因采用确认是 human，就把未核对的任务类别也标 human |
| 人机分歧 | 形成 review_queue，区分材料不全、规则歧义、人工误读、裁判错误 | 默认人工全对或 AI 全错 |
| met / unmet 会话 | 选题线索：完整输入 + 验收目标 + 适用验证器 + 同源归组 | “会话被判 met”本身不是一道任务 benchmark 的标准答案 |
| 反复出现的输入缺口 | 候选澄清提示/skill 补充规则；固定任务同模型比较 | 把相关性称为用户责任，或声称已经证明节省工时 |
| 可靠的四维标签 | 特定分类小模型训练候选，先同源分集并检查用途 | 把 audit/holdout 及其改写用于训练 |
| AI 修正建议与 bad case | 先验证修正结果，再决定能否用于训练 | 自动构成 DPO 偏好对或 SFT 真值 |

裁判 benchmark 考“判断是否符合人工参考”；任务 benchmark 考“Agent 是否真正完成冻结任务”。同一案例可以提供线索，但目标、输入边界和验收方式不同。不要把这两种成绩混在领导汇报里。

## 9. 一周原型与之后的轻量循环

| 时间 | 只完成这一件事 |
|---|---|
| 第 1 天 | 固定取数窗口、随机样本和证据卡；先看缺附件/空会话情况 |
| 第 2 天 | 精读 20–30 条，收敛四维 rubric；记录真实耗时后调整标注规模 |
| 第 3–4 天 | 完成可承受数量的独立人工参考；安排少量双人复核 |
| 第 5 天 | 在 calibration 上跑裁判，检查两三个主要混淆，不追一个总分 |
| 第 6 天 | 固定规则、提示、模型和输入；如参考尚不足，继续标注而不是硬凑 100 |
| 第 7 天 | 有条件才做 audit；交付分歧表、适用范围与下一步试验 |

以后每期更新候选池，抽少量新会话核对已上线裁判的错误和未知比例；发现新任务或模型/skill 变化，再补题。用过的 audit 若用于调优，就转为已见回归集并补未来独立来源。不要自动重标所有历史会话导致过去的报表悄悄改口径。

向上说明可以围绕这样一条证据链：

> 我们先把日志事实与语义判断分开，精读形成规则和人工参考，再用独立样本核对自动裁判。裁判输出保留证据、未知与分歧；它先帮助发现问题和选评测题。对实际改进，另用固定任务比较完成质量和资源投入，再用业务采用回执补价值证据。

这比单说“用了 Agent-as-Judge”更容易经得起追问。
