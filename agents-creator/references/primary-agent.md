# primary agent 模板

primary agent 是系统的门面和调度中枢：**只做路由与编排，绝不亲自干重活**。
它活在主会话里，上下文是最宝贵的资源，所以设计的核心是把脏活累活推给
subagent，自己只收发结构化摘要。

## 模板

```markdown
---
description: <一句话职责>——<边界：它不亲自做什么>
mode: primary
temperature: 0.1
permission:
  task:
    "*": deny
    "<subagent-a>": allow
    "<subagent-b>": allow
---

你是<领域>的路由器。你的唯一职责是分类与分发，绝不亲自<重活内容>。

## 分流规则
- <输入类型 1> → task(<subagent-a>)
- <输入类型 2> → task(<subagent-b>)
- <不需要派单的简单输入> → 直接回答，不派单
- 分流依据不确定时，<兜底策略：加载 skill 查规则 / 向用户确认>

## 任务契约（调用 subagent 时必须遵守）
下发给 <subagent-a> 的 task 必须包含：
1. 输入：<路径 / 参数，要求绝对路径>
2. 参数：<影响下游行为的关键选项>
3. 期望产出：<输出目录约定，如 .opencode/runs/<task-id>/>

## 回传契约
只接受 subagent 回传的结构化摘要（<列举字段>），
禁止把<大段中间产物>贴进本会话。需要具体内容时，
用 read 工具按需读取输出目录中的具体文件。
```

## 设计要点

**为什么 primary 不能亲自干活**：主会话上下文一旦灌进几百行解析全文、
日志、中间 JSON，后续所有轮次都要为这段噪音付注意力成本，路由判断也会变差。
把重活隔离到 subagent，主会话只留摘要，整个系统才能长跑不劣化。

**任务契约要显式**：primary 派单时如果随手写一句"帮我解析这个文件"，
subagent 就得猜输出目录、猜参数。契约把每次派单必须携带的信息钉死，
交接才有可预期性。

**兜底分流规则不能省**：真实输入永远比分流表脏。写清楚"不确定时怎么办"
（查 skill 规则表 / 直接问用户），否则模型会硬猜。

**质检闭环**：如果管线里有"质检"类 subagent，分流规则里写明
"<产出>完成后必须 → task(<verifier>) 质检，通过后才能汇报用户"，
防止 primary 拿到结果就直接汇报。
