## 1. KV cache 分层卸载机制与互联底座（对应模型问题 1）

### 1.1 KV 冷热划分与分层卸载机制现状

#### 1.1.1 冷热 KV 的划分依据：调用频率、reuse 距离与 attention 重要性

生产系统对键值缓存（KV cache）的冷热判定已收敛到三类信号。第一类是**访问频率与新近性**（系统层、块/对象粒度）：Mooncake 将 CPU 内存中的 KVCache 组织为分页块，支持 LRU、LFU 或基于请求特征的驱逐算法，其 Store 主服务以高水位（默认 0.9）、批量驱逐比例（0.1）与对象租约（TTL）管理生命周期，并支持驱逐对象自动落盘 SSD[^4^][^5^]；NVIDIA Dynamo 的 KV 块管理器（KVBM）采用频率型驱逐——块访问频率初始为 1、命中翻倍、随时间衰减，频率不低于 2 的块才有资格从低层晋升[^9^]；AIBrix 提供 LRU/S3FIFO 可插拔策略[^12^]；SGLang HiCache 在 L1/L2 从 HiRadixTree 叶子节点开始驱逐以保持前缀完整性，L3 暂为对象级 LRU[^8^]。第二类是**reuse 距离与前缀局部性**（请求间共享）：RadixAttention/HiRadixTree 以基数树组织前缀，"热"等价于"近期被多请求共享的前缀"，调度器经缓存感知路由把请求派发到已持有该前缀 KV 的节点，Mooncake Conductor 并按 KVCache 分布主动复制、迁移热点块[^4^][^6^]。第三类是 **attention 重要性**（模型层、token 粒度）：H2O 按累计注意力保留 heavy-hitter token、SnapKV 以观察窗投票、PyramidKV 按层分配金字塔式预算[^13^][^14^]——但该族属于不可逆驱逐（信息永久丢失），与"卸载到慢层、需要时取回"的可逆分层是正交机制，对需要全史随机访问的多轮/长文档任务存在质量风险[^15^]。

冷热的时间尺度证据表明，"冷 KV"本质是容量与时间问题而非价值问题：约 2 TB DRAM 仅能保留约 5 分钟的 KV cache，而 100 TB 级 NVMe 可保留 1 小时以上[^16^]；Third Bridge 专家测算 100B 参数模型、千万级日活全量保留 KV 需约 250 PB SSD/天（专家访谈口径，置信度中低），迫使生产系统每 0.5–1 小时激进删除缓存[^22^]。阿里云生产 trace（USENIX ATC'25）进一步给出复用分布：to-C 聊天负载 80% 的复用间隔小于 10 分钟、to-B API 小于 10 秒，KV 块 P99 寿命仅 97 秒，10% 的块贡献 77% 的复用[^206^]；编码 agent 轨迹平均 157 轮、平均上下文 32.7K token、每轮仅追加 429 token，KV 命中率达 98.7%[^208^]。两组数据共同界定了"冷"的边界：秒级以内为热前缀，秒到十分钟为温历史，小时级为冷历史。

#### 1.1.2 分层卸载四大机制：placement、eviction、prefetch、逐层流水

分层卸载的工程实现可拆解为四个机制件。**放置（placement）** 解决"放哪层"：vLLM 按 GPU→CPU→KVConnector 顺序查找块，CPU 侧块池 LRU 驱逐、主机与设备间传输走独立 CUDA 流异步执行[^7^]；Dynamo KVBM 明确 G1（GPU 高带宽内存 HBM）→G2（DRAM）→G3（本地 SSD）→G4（网络存储）四层，支持 GPU→CPU、GPU→CPU→Disk 与实验性 GPU→Disk 三种配置[^9^][^10^]；FlexKV 以 DRAM/本地 SSD/云存储三级实现"逻辑 LRU"（空间不足时只改索引、不搬数据）[^26^]；更早的 FlexGen 将放置形式化为线性规划搜索，面向吞吐优先的离线场景[^17^]。**驱逐（eviction）** 的趋势是从纯 LRU 走向频率衰减、租约与预测式（贝叶斯复用概率、S3FIFO），并把前缀结构信息传递给 L3 做前缀感知驱逐[^8^][^27^]。**预取（prefetch）** 利用排队间隙把后续请求的 KV 从慢层提到快层：LMCache 从远程盘预取到本地内存/GPU[^3^]；HiCache 提供 best_effort、wait_complete、timeout 三种预取停止策略，以专用线程加远程直接内存访问（Remote Direct Memory Access, RDMA）并行多节点读，预取完成时间的不确定性被列为核心工程难点[^8^]；Mooncake 多轮对话基准中"预填充"配置取得全场最优首 token 时延（Time To First Token, TTFT）[^25^]。**逐层流水（layer-wise pipeline）** 以三条 CUDA 流（compute/load/store）在第 N 层计算时异步加载第 N+1 层 KV，GPU 侧只需单层 KV 大小的缓冲，理想时 TTFT 约等于 prefill 计算时间加最后一层传输时间[^3^][^28^][^29^][^30^]。但需注意该机制对 SSD 层适得其反（见 1.2.3 节）[^16^]。

#### 1.1.3 产品化现状：Mooncake/LMCache/vLLM KVConnector/SGLang HiCache/Dynamo KVBM+NIXL/AIBrix

分层卸载在 2024–2026 年完成产品化，且抽象层与介质解耦。Mooncake（月之暗面 Kimi 生产系统，FAST'25 最佳论文）以 GPUDirect RDMA 的 Transfer Engine 聚合集群 CPU/DRAM/SSD/NIC 资源构建解耦式 KVCache 池，真实 trace 下有效请求容量提升 59%–498%，生产 A800/H800 集群分别多承载 115%/107% 请求，数千节点日处理超 1000 亿 token[^1^][^2^]。vLLM 的 KVConnector 是事实标准接口：LMCache、NixlConnector、MooncakeConnector、AIBrix Offloading Connector 等均挂接其上，调度器侧暴露 `get_num_new_matched_tokens`，执行侧暴露 `start_load_kv/wait_load_kv/start_store_kv` 与逐层钩子[^3^][^7^]。SGLang HiCache 组织 GPU L1/主机 L2/分布式存储 L3，`--hicache-storage-backend` 运行时可插拔 mooncake、3FS、NIXL、AIBrix、file 后端，page_first_direct 布局使一页 KV 连续、可零拷贝整存整取[^8^]。NVIDIA Dynamo KVBM 构建于 NIXL（NVIDIA Inference Xfer Library，2025 年 GTC 开源）之上：NIXL 统一抽象 GPU 显存/DRAM/存储的描述符注册与单边 RDMA 传输，后端覆盖 UCX（InfiniBand/RoCE/TCP）、GPUDirect Storage（GDS）、NVMe over Fabrics（NVMe-oF）与 S3 对象存储[^9^][^20^][^119^]。字节跳动 AIBrix 以 L1 DRAM 加 L2 RDMA 远程缓存（InfiniStore）实现论文口径吞吐 +50%、时延 −70%[^12^]。国内另有华为 UCM 加 OceanDisk 的"以存强算"路径：DPU 硬化 KV 语义，xPU—DPU—SSD 三跳直通旁路 CPU/DRAM，单框 160 GB/s、1600 万 IOPS，KV Connector 对接 vLLM/SGLang/Mooncake（厂商口径 TTFT 再降 80%）[^147^]。对本章主旨的含义：放置、驱逐、预取、逐层流水均已产品化，且各接口为层无关设计——新介质（含高带宽闪存 HBF）可作为新层插入，无需重写调度逻辑[^3^][^8^][^9^]。

|---|---|---|---|---|---|
| GPU HBM | 80–192 GB/卡（B300 288 GB） | 3.3–8 TB/s | 约 ns–1 µs | 约 $100/GB | [^18^][^19^] |

该阶梯跨越约六个数量级，存在两处断档。其一在 DRAM 与 NVMe 之间：带宽差约 20–40 倍、时延差约三个数量级，KV 保留时间窗从约 5 分钟跳到 1 小时以上——HBF 的目标区间（单堆 512 GB、读 1.6 TB/s）恰好插入该断档，但其 µs 级读时延与 4 KB 最小读粒度决定它只能承接"可预知地址的大块流式读"，而非细粒度随机读[^16^][^220^]。其二在传输侧：KV 每 token 体积约 250 KB（Qwen3-32B，bf16；LMCache 默认 256-token chunk 约 62.5 MiB）[^31^]，而小消息严重吃不满链路——64 KB 传输仅达 4 GB/s、1 MB 约 30 GB/s、16 MB 才到 49 GB/s[^3^]，这决定了任何慢层（含 HBF）的有效带宽取决于对象聚合粒度，而非介质标称值。

#### 1.2.2 代表系统实测：命中率 80–98% 负载下 TTFT 降 56–84%、吞吐最高 15×

高前缀复用负载是分层卸载收益的放大器。编码 agent 多轮会话（Claude Code/SWE-bench trace）自第二轮起前缀命中率稳定超过 95%、均值约 98%[^33^]；DualPath 实测编码 agent 轨迹命中率 98.7%[^208^]。在此区间，各系统实测收益为：SGLang HiCache 官方复测吞吐最高 6 倍、TTFT 最高降 80%，蚂蚁集团在线通用问答（DeepSeek-R1-671B、预填充/解码分离即 PD 分离）缓存命中时 TTFT 平均降 84%，Novita AI（Qwen3-Coder-480B 加 3FS 后端）命中率 40%→80%、TTFT 降 56%、吞吐翻倍[^8^]；LMCache 加 vLLM 跨负载吞吐最高 15 倍、TTFT 缩小 1.9–8.1 倍[^3^]；Dynamo KVBM 仅 CPU 卸载即在 Qwen3-8B/H100、20K 输入长度下取得 TTFT 改善 2.2–12 倍（随 QPS 变化）[^11^]；Tutti 的 SSD 后端在严格服务水平目标（SLO）下 TTFT 降 78.3%、可承载请求率 2 倍、服务成本降 27%，性能逼近 DRAM 后端[^16^]。命中率向时延的传导链亦有定量锚点：Marconi 的 FLOP 感知准入与驱逐使 token 命中率最高提升 34.4 倍、TTFT 降 71.1%[^210^]；ATC'25 的负载感知策略命中率提高 8.1–23.9 个百分点，对应排队后 TTFT 降 28.3–41.9%[^206^]；阿里 RTP-LLM 生产部署 TTFT P95 降 35–37%、prefill 机器减少 75%[^215^]。第三层对象存储同样有效：NetApp 报告加 S3 层后聚合处理速度最高 +173%、单请求 TTFT 最高降 99%（厂商自建基准口径）[^21^]。但需注意命中时间（hit time）与命中率同样决定收益：10–50 Gbps 链路下 KV 通信已占作业完成时间的 16–60%[^217^]。

#### 1.2.3 SSD 层争议：CPU-centric I/O 致 70–80% GPU stall 与"读不如重算"拐点

SSD 层是否应入列是当前最大争议（交叉验证冲突区 C2），反方核心证据来自 Tutti 的系统实测：Llama3-8B、64K 序列、75% 命中下，从 SSD 恢复 KV 导致的 GPU 气泡超过总推理时延的 70%，逐层流水反而把气泡推高至约 80%；即便启用 GDS 仍高于 70%——GDS 去掉了 CPU 数据拷贝，但每次 I/O 仍需 CPU 发起，控制路径依旧以 CPU 为中心（CPU-centric）[^16^]。根因不是 SSD 原始带宽而是布局碎片化：128K token 的 KV（Qwen3-32B、64 层、块长 64）对应约 25.6 万个散落的 80 KB 对象，LMCache 按 256-token chunk 聚合后仍需逾千次多为随机的访问[^201^][^202^]。更严峻的是"读不如重算"拐点会移动：随 vLLM 从 v0.12 升级到 v0.17（计算侧变快），SSD 恢复从勉强划算变为不再划算[^16^]。独立量化给出拐点位置：7B/13B/30B 模型约需 24/21/37 GB/s 存储带宽方能使取回与重算等速[^204^]；链路级 80 Gbps 时 I/O 恢复快于重算、10 Gbps 时慢于重算[^205^]。正方证据同样成立：Tutti 自身改用 GPU 中心化对象存储加 GPU 侧 io_uring 后，SSD 后端达到近 DRAM 性能[^16^]；NetApp 报告 S3 层"几乎无场景变差"[^21^]。本章判定：分歧本质不在介质而在 I/O 路径（CPU 中心化 vs GPU 中心化）、对象粒度与负载命中率；条件性结论为——命中率不低于 95% 的 agentic 负载下层间带宽是主瓶颈、介质带宽收益被放大[^33^]，而低命中负载叠加算力更快的新引擎时，慢层取回可能不如重算。ThunderAgent 亦指出高频 agentic 工作流中频繁换入换出的开销常抵消多层缓存收益[^32^]。

#### 1.3.2 KV 搬运事实标准 GPUDirect RDMA；国内多轨格局：灵衢 UB、UALink、ETH-X、OISA 与 RoCEv2 兜底

2024–2026 年生产部署的实际形态为"跨节点 GPUDirect RDMA、节点内 NVLink/PCIe P2P、下沉存储 NVMe-oF/GDS"。Mooncake 生产机型每 A800 GPU 配 100/200 Gbps NIC、每 H800 配 200/400 Gbps NIC，经 RoCEv2 承载 KV 块迁移[^111^][^112^]；NVIDIA Dynamo 以 NIXL（UCX 加 GDS 后端）做单边 RDMA 写，抽象覆盖 NVLink/InfiniBand/Spectrum-X/RoCE[^116^]；llm-d 的 P2P 同样以 RDMA 与同机 NVLink/NCCL 为主[^119^]。需强调软件栈默认值对实际 KV 传输性能的影响远大于链路理论带宽：vLLM 社区实测同机 NixlConnector 未走 NVLink 时吞吐仅约 1.8 GB/s[^152^]。

国内 Scale-up 互联呈"三轨并行、尚未收敛"格局。**专用总线轨**：华为灵衢 UB（UnifiedBus）是唯一规模商用的 NVLink 级私有总线——CloudMatrix 384 以 UB 平面全对等互联 384 颗昇腾 910C 与 192 颗鲲鹏（每 NPU 350–392 GB/s 单向，论文口径与 SemiAnalysis 拆解口径并存），官方明确其 RDMA 平面（每 NPU 400 Gbps RoCE）的首要用途即"预填充与解码 NPU 之间活动 KV 缓存的高速传输"，UB 平面则承载跨 CPU/NPU 内存的池化 KV 与权重点对点访问[^126^][^127^]；2025 年 9 月华为开放灵衢 2.0 规范（基础协议 600 余页、累计下载 2.4 万份），Atlas 950 SuperPoD 目标单卡 2 TB/s、8192 卡全互联、2026Q4 上市（厂商口径）[^128^][^132^][^133^]。**以太优化轨**：腾讯与信通院牵头 ETH-X（ODCC 已发布 1.0 规范，PAXI 传输层支持 256 卡全互联，2025 年 4 月原型机点亮，牵头方实测跨卡访存时延较 RoCEv2 降 12.7 倍）[^139^]；字节跳动 EthLink 的已验证技术点被博通 SUE（Scale-Up Ethernet）吸收标准化（目标单跳 RTT <2 µs、单域 1024 XPU）[^140^]；中兴 OLink 宣称 800 GB/s（厂商自述、口径未经第三方验证）[^141^]。**开放架构轨**：中国移动 OISA（全向智感互联）2.0 目标 1024 卡、TB/s 级带宽、数百纳秒时延，配套 GSE（全调度以太网）已在哈尔滨万卡集群商用[^142^][^143^]；阿里则站队国际 UALink 联盟（董事会级），自研 ALS/ALink 超节点与 HPN（每 GPU 专属 400 Gbps RDMA）[^135^][^136^]（二手资料中"阿里 MNNVL"系术语混淆，本节已按 ALS/ALink＋HPN 纠正；互联带宽的 Gb/GB 口径混淆一并见 8.2 节冲突区 C5）。工信部牵头 CLink 试图制定全国统一标准[^141^]。

本章判定：2026 年内国内不存在唯一"国家队"标准，跨厂商 KV 池化短期仍需落在 RoCEv2 这一最大公约数上；DeepSeek 的硬件论文亦同时点名 UEC、UALink 与灵衢 UB 为值得关注方向，模型厂商在倒逼"总线"与"网络"融合[^148^]。对存储介质的含义：HBF 类新产品若绑定单一私有总线将丧失跨厂商 KV 池化市场，支持 RoCEv2 加 PCIe/CXL 双接口是风险最低的切入点；CXL 3.x/4.0 用于 GPU 直连 KV 池化是 2027 年后的期权项，当前国内外 CXL 落地均为 CPU 侧内存扩展[^123^][^146^]。

### 1.4 专家验证：冷热 KV 卸载至 HBF 的判定标准

#### 1.4.1 五条判定标准：带宽拐点、prefetch 可掩盖条件、块粒度、reuse 可预测性、写耐久预算

综合三个维度的实测证据，本章将"冷热 KV 能否卸载至 HBF"形式化为五条可操作判定式。

**标准一：读-算带宽拐点。** 卸载读回划算的充要条件为 $T_{fetch}=KV_{bytes}/BW_{eff}+t_{fixed}<T_{recompute}(ctx)$。单机侧拐点约 24–37 GB/s（7B/13B/30B 模型）[^204^]，网络侧 80 Gbps 以上取回快于重算、10 Gbps 以下慢于重算[^205^]；且拐点随推理引擎计算提速持续右移[^16^]。HBF 读带宽目标值 1.6 TB/s 较 NVMe SSD（约 14 GB/s）高约两个数量级，越过拐点的余量充足——这也是评估 HBF 的第一指标应从"命中率"转为"有效延迟预算与聚合带宽利用率"的原因[^219^][^224^]。

**标准二：prefetch 可掩盖条件。** 逐层/逐块预取能完全掩盖加载时延的条件为

$$T_{load} \cdot L_{hist} \le T_{pref} \cdot L_{new} + \frac{S_{buf}}{BW_{eff}}$$

其中历史长度 $L_{hist}$ 与追加长度 $L_{new}$ 之比决定掩盖窗口：agent 短追加场景（98% 以上命中率、每轮仅约 429 个新 token）掩盖窗口最小，必须依赖调度器前瞻信息提前预取[^203^][^208^]；不足部分可用 HBM 读缓冲补齐，$S_{buf}=B\cdot(T_{load}\cdot L_{hist}-T_{pref}\cdot L_{new})$[^203^]。

**标准三：块粒度匹配。** NAND 页（4–16 KB）与 HBF 最小读粒度（4 KB）要求 KV 聚合到 256-token 级 chunk（约 62.5 MiB）或对象级批量 I/O；碎片化分页布局（25.6 万个 80 KB 对象）是 GPU 气泡的主因，粒度聚合与前缀共享细粒度之间存在取舍[^201^][^202^][^31^]。

**标准四：reuse 可预测性。** 生产 trace 显示复用强偏斜（10% 的块贡献 77% 复用）且可建模：按请求类别拟合复用概率可使命中率提高 8.1–23.9 个百分点[^206^]；FLOP 感知准入、多步预测与贝叶斯先验分别报告 34.4 倍 token 命中率、1.85 倍加速与 70–84% 命中率[^210^][^211^][^213^]；复用不可预测的负载则退化为 LRU 并接受较低命中。

**标准五：写耐久预算。** 判定式为 $\Sigma(\text{每日 KV 写入量}) \times 365 \times \text{年限} \le \text{容量} \times P/E \times \text{WAF 折减}$。KV 写一次读多次（实测读:写约 186:1）使历史 KV 具备可行性[^218^]；FlashAccel 的完整核算显示，agent 负载下每 HBF-GPU 写入 988 MB/s、5 年共约 14.9 万 TB，在 1152 GB 容量、100 万 P/E（以数据保持期从 3 年降至 3 天换取 10 倍耐久）下供给 112.5 万 TBW、余量 7.6 倍，但若按常规 10 万 P/E 则供给不足——结论对 P/E 假设一阶敏感，而 HBF 耐久公开口径本身在 $10^3$–$10^5$ 之间不一[^221^][^223^]。

#### 1.4.2 验证结论：读多写少的历史/共享 KV 适配 HBF；活跃逐 token KV 禁入

表 1-3 KV 类别、访问模式与卸载 HBF 判定

| KV 类别 | 复用间隔 | 访问模式 | 适配介质 | 卸载 HBF 判定 |
|---|---|---|---|---|
| ① 活跃 decode KV（逐 token 追加） | 每步 | 细粒度随机读+持续写 | HBM/DRAM | **禁入**：写耐久与时延均不满足[^219^][^220^] |
| ② 热前缀/系统提示（秒级复用） | <10 s（to-B 80%） | 高频整块读 | HBM→DRAM | 不必入：2 倍 HBM 容量即可逼近理想命中[^206^] |
| ③ 温历史会话 KV（多轮/agent） | 10 s–10 min | 大块顺序读、可预取 | DRAM 为主，SSD/HBF 经预取兜底 | **有条件适配**[^206^][^208^] |
| ④ 冷历史 KV（小时级） | 数小时 | 整块批量读、可提前预取 | NVMe SSD/HBF/对象存储 | **适配**[^204^][^226^] |
| ⑤ 共享预计算只读 KV | 写一次读 N 次 | 流式大块只读 | HBF | **最佳适配场景**[^220^][^222^] |

**专家判定：调研问题 1 的原假设"冷热 KV 可卸载至 HBF"——部分成立，且边界清晰。** 成立侧：③④⑤类读多写少的历史/共享 KV 与 HBF 的设计点（读优化、单堆 512 GB、读 1.6 TB/s 目标值、8–16 倍 HBM 容量）高度吻合；SK hynix H³ 方案已按此二分——共享预计算只读 KV 放 HBF、生成的活跃 KV 留 HBM，模拟显示百万 token 上下文吞吐 1.25 倍、千万 token 达 6.14 倍、能效 2.69 倍（二手报道口径）[^222^]；Ma 与 Patterson（IEEE Computer 2026）明确"HBF 必须承载不频繁更新的数据，如推理权重与缓变上下文"[^220^]；机制侧分层、驱逐、预取、逐层流水均已产品化且接口层无关，NVIDIA 亦在推进 BlueField-4 DPU 上的闪存后端 KV 层（ICMS，Inference Context Memory Storage，硬件辅助驱逐与预取）[^227^]。不成立侧：①类活跃 decode KV 每 token 产生新写，"NAND 耐久无法承接"（行业分析口径一致），且其细粒度随机读与 HBF 的 4 KB 最小读粒度、µs 级时延失配[^219^][^220^]。三项前提构成判定边界：I/O 路径 GPU 中心化（绕开 CPU 控制路径，呼应 1.2.3 节）、对象粗粒度化（不低于 256-token 聚合）、写耐久预算按 P/E 假设显式核算。不确定性声明：全部 HBF 性能数字在 2026 下半年出样、2027 年设备落地前均为厂商目标值，无第三方实测[^23^][^223^]；上述判定应在样品可用后以真实负载回放复核。
