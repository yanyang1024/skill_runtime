# 候选发现与最小充分组合

仅当需要跨 Skill 选择时读取。任务是选择可用方法，不是为名称相似的材料自动连线。

## 从目标发现能力

1. 提取目标、交付物、对象、约束、已给输入与禁止项。先列所需能力，不先按 Skill 名拆任务。
2. 明文指定与排除项先固定；候选来自授权集合。动态选择可以为空：通用能力已足够则直接完成；确有工具/知识缺口则报告缺口。
3. 小集合先看 name/description 与短画像；集合扩大时按能力族、输入对象、输出角色建立索引，再细读候选。允许同一 Skill 属于多个能力族，目录树只是检索视图，不是执行依赖。
4. 对候选核对前置条件、真实工具权限、输入可得性、触发反例和已知限制。相似度只负责召回，不能替代可行性判断。
5. 选择覆盖目标所需的最小充分集合，再检查必要依赖与替代方案。发现缺口后可扩展召回，受本次范围和预算约束；不硬编码所有任务只能选 top-3。

索引最小字段：skill_id、runtime_name、source、version/fingerprint、capabilities、use_when、avoid_when、inputs、outputs、required_resources、profile_ref。短索引来自证据，不能用它替代涉及冲突与接口的正文复核。

## 重叠和同名

- **同名多来源**：保留来源限定 ID 供分析；实际 runtime_name 冲突必须核实发现结果。未确认加载哪份前不生成看似可区分的调用名。必要时提出重命名草稿，但不擅自覆盖安装目录。
- **同能力不同前提**：依据数据规模、输入格式、工具和领域选择；不因文本相似而合并。
- **互补视角**：明确各自贡献及最终如何汇总，保留必要信息。
- **新旧版本**：默认采用目标环境已确认版本；新版本形成候选，对照后再替换，不能“最新即兼容”。

选择记录包含 selected、rejected（原因）、unresolved、capability_gaps 和 stop_reason。用户固定集合中不合适的对象仍逐项列出，不静默删除。

## 将选择与编排分开检查、联合修正

检索得到集合不意味着计划成立。发现依赖、冲突或成本超限后可以回到选择阶段替换候选，但记录变更原因并遵循重规划预算。每个增加的 Skill 都要回答“补了哪个目标或必需前提”；每个步骤都要有完成/停止依据。

速度、质量、成本是约束或偏好，不能简单分别等同于并行、更多 Skill、较少 Skill。并行可能增加协调成本；更多阶段可能降低质量。优先满足硬约束，再说明具体取舍，无测量时不报定量收益。
