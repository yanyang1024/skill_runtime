# 多 Skill 输入：决策与提问

在接收含糊的多 Skill 请求、发现材料缺口、接收 worker 问题或中途变更时读取。primary 负责面向用户的澄清；subagent 只回传调用方。Skill 本身不拥有提问身份，是否可 question 取决于当前 Agent 的实际配置。

## 先确定当前交付

| 请求 | 默认动作 | 停止点 |
| --- | --- | --- |
| “看看这些 Skill / 能怎么组合” | 读取入口和必要材料，给能力总览与有依据的组合候选 | 说明适用前提；不必先问行业、数据、模型、预算等整套问题 |
| “为这个目标选择/编排” | 围绕目标选择最小充分集合，检查关键依赖与冲突 | 场景路线与缺口 |
| “整合这些 Skill，做一个 Agent” | 默认保持 Skill 独立，生成统一导航的 Agent 草稿 | 用户指定目标；未指定时可先做能力入口草稿，标明适用边界 |
| “合并这些 Skill 文件/目录” | 做内容和资源合并设计，再按授权进入 skill-creator | 修改后的草稿或指定源文件，以及兼容性说明 |
| “只讲方案/审查，不改文件” | 在回复中给结论与建议 | 不生成配置文件，不修改源资产 |
| “生成配置草稿/Agent 文档” | 属于文件生成请求，可写默认草稿输出根 | 不把“草稿”理解为不能落盘 |
| “全部分析” | 冻结可读的输入集合并逐项覆盖 | 全量材料分析，不代表执行全部业务 Skill |
| “直接用它们跑业务/发布” | 检查当前入口的执行能力与授权 | 本包是分析/创建入口，不执行业务；提供已完成设计和具体执行交接，不假报执行 |

用户给出的明确要求优先于默认。若“合并/全部做”在上下文中存在会改变资产修改或外部动作的两种实质解释，先完成共同的只读分析，再由 primary 问一个范围问题。

## 把缺口分成四类

| 类别 | 处理 | 举例 |
| --- | --- | --- |
| 可从材料确定 | 读取、核对并继续；不问用户替代读文件 | Skill 的真实名称、脚本参数、已给输出格式、原 Agent 模型 |
| 可采用低影响默认 | 告知默认，直接继续 | 单 primary、同主体方法续接、唯一草稿目录、内部 task_id、只做自检 |
| 只影响后续运行 | 写成运行时必需输入/条件依赖，继续当前设计 | 设计分析 Agent 时未给 CSV、业务阈值、发布空间、API 凭据 |
| 当前交付必须由用户决定 | 由 primary 提问，只暂停受影响分支 | 无依据的业务口径冲突、无法确定要修改哪份同名资产、不能同时满足的输出要求 |

“确定”表示有材料或用户说明支持；“默认”是可回改的设计选择；“未知”是证据缺口。默认不能伪装为业务事实。没有运行证据时，加载、权限、并发和业务效果仍是未验证。

## primary 的问题处理顺序

1. 先查当前对话、已授权材料和可读产物。相同问题已有答案就引用；不得要求用户再次填写。
2. 判断是否影响本次交付。设计需要定义“运行时问阈值”，不等于现在必须得到阈值。静态画像可以完成，业务输入未知另列 gaps。
3. 可默认、可参数化或可推迟的事项记入假设/运行输入，并继续。对当前正确性、来源选择或修改范围有实质影响且无可靠依据的问题才询问。
4. 合并多个 worker 的相同问题，通常一次只问当前阶段最关键的 1–3 项。不要把内部字段、技术选型细节和完整缺口列表直接转给用户填写。
5. 问清“差异是什么、影响哪一步、可选项与建议”。只在有可信默认时推荐；业务事实无依据时不能替用户猜。已有授权足够时不再以提问形式重复索取确认。
6. 等待回答期间完成可独立完成的工作；回答后只补受影响画像/边/步骤，不重启全套分析。

入口允许与用户交互、只是环境没有专用 question 工具时，primary 可用普通回复提出同样的问题；明确禁止用户交互的角色不得以普通回复绕过限制。无人值守场景将必要问题交给调用方或形成 pending_questions；保留可完成结果，不当作用户同意默认。是否可继续由问题影响决定，不以工具存在与否决定结论。

## subagent 的回传

subagent 不 question 用户、不转派问询，也不替用户决定关键业务事实。使用 contract.md 的 missing_inputs 与可选 clarification_requests 回传。能按本次目标形成有效画像时 PASS + gaps；无法读取核心材料或无法形成任务产物时 BLOCKED。缺业务执行数据通常不阻塞静态画像。

缺少 task_id、输出路径等委托字段先回传调用方；调用方自己补齐即可，不转问用户。外部引用超出范围时记录依赖线索，不能扩大读取授权。

primary 判断 worker 的问题是补委托、读材料、记录未知，还是询问用户。worker 提出问题不等于用户必须回答。

## 最小决策记录

小任务在回复或交接段落记录即可：已确认事实、采用的默认、运行时待提供、当前阻塞问题、受影响步骤与继续范围。只有长任务/恢复需要才将这些写入已有 plan 或 design-brief，不强制多建协议文件。

同一问题无新证据或用户回复时不重复提问/派单。用户改目标只使依赖该决定的步骤失效；保留仍有效的分析与产物。

## 输入尚不可读

输入为压缩包时先检查环境是否已提供解压后的路径或可读附件内容；有现成授权解包工具才使用。当前只有文件读取工具且无法读取压缩内容时，由 primary 精确说明需要“可读的解压目录/材料”，不把它描述成业务信息不足，也不自行放开 bash。部分材料可读时先分析可读集合并标出覆盖缺口；完整性要求确实受阻时才暂停相关结论。
