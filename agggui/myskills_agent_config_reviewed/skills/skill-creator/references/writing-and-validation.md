# 编写与验证

## 发现与接口

- 目录名与 frontmatter `name` 一致；名称使用小写字母、数字和单连字符，长度 1–64。
- `description` 写清实际能力、触发情形和必要边界，避免塞入完整流程；上游要求长度 1–1024 字符。
- 输入、输出、必要工具与失败行为放正文。加载 skill 不会让原本不可用的工具出现，不会扩大 agent 权限。
- 修改时区分内部实现与公开接口：换脚本或细化步骤通常不动调用方；改名、扩大输入要求、改变输出字段或新增权限时检查调用方。
- 使用上游支持的 frontmatter 字段；不要添加自定义 `dependencies` 字段并声称运行时自动解析它。依赖发现和加载条件用正文表达。

## 内容放置

| 内容 | 位置 |
| --- | --- |
| 所有调用都需遵循的核心流程 | SKILL.md |
| 某种输入／模式专用规则 | references，并在入口标注读取条件 |
| 完整输入输出示例 | examples，区分合成示例与真实数据 |
| 可重复执行的确定性操作 | scripts，交代参数、依赖和失败返回 |
| 直接用于产物的骨架 | assets，交付前替换占位内容 |

规则尽量只维护一份。保留调用前必需的导航，不把所有文件都设置为“首先全部读取”。相对资源路径以 skill 根目录解析；输入输出路径以明确的项目或任务目录解析，不依赖当前 shell 恰好在哪。

## 检查与证据

1. 文件存在、非空，frontmatter 可被 YAML 解析；名称、目录和触发描述一致。
2. 所引用的本地文件可解析，所需 tool／skill 在目标环境确实可用或已明确为条件依赖；无占位脚本与虚构 API。
3. 示例与正文一致；正常输入、缺必要输入和验证失败三种情况能给出诚实结果。
4. 新增脚本实际运行一个有代表性的正常输入和一个相关失败输入；不能只检查退出码，需核对产物内容。
5. 修改时比较 diff，检查下游公开契约，不覆盖无关配置。

如果没有 YAML 解析器，记录未执行解析检查，不以手工阅读冒充解析通过。没有目标 OpenCode 或实际工具时只报告已完成的静态检查。需要独立上下文的验收应交给用户已授权的验证流程，不擅自扩大当前创建助手的 task 权限。

参考：[OpenCode Skills](https://opencode.ai/docs/skills/)。上游约定核对日期：2026-09-20；内部 fork 以本地验证为准。

## 面向组合的 Skill 设计

写清触发及不适用场景、当前阶段需要的上下文、完成条件、工具依赖与副作用。方法或知识 Skill 的输入可以是目标与约束，输出可以是判断和指导，不为迎合管道设计强行落文件。

引用其他 Skill 时明确是方法依赖、可选建议还是材料引用，并说明加载条件；由当前 Agent 决定是否采用。避免对整个会话规定不相关的强制输出格式；将阶段规则限于对应阶段。不要声称“切换 Skill 会清空上下文”或“加载后自动获得工具”。

创建器回交只给方法产物与契约，不自动调用另一个创建器；调用方保留任务状态并续接。

## 方法中的提问与时机

Skill 只描述何种缺口需要澄清，不假定执行主体都能 question。primary 可直接询问；subagent 回传缺口给调用方。未来业务运行的输入要求写在方法内；“这次只创建配置”的交付限制留在创建说明，不固化进业务 Skill。
