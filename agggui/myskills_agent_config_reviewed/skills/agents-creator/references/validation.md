# 交付检查

生成交付前或完整审查时读取。检查应覆盖实际产物，不仅判断命令退出码。

## 静态检查

- 文件已写入授权目标目录，存在、非空，YAML frontmatter 可解析且正文不为空。
- description、mode 与实际职责一致；单 primary 不强制派单契约。
- 新建字段与权限配置有目标环境依据；既有未知字段先核实，不擅自删除。
- 引用的 skill 真实存在，目录名、name、调用名和白名单一致。
- 引用路径可解析；模板占位内容已替换，包外背景实例未成为运行依赖。
- Agent 保留与职责相关的设计意图和选择原则，未复制已有 skill 的完整 SOP、命令参数或详细检查项。
- 需要配套 skill 时，名称、目录、导航、实际发现结果与权限一致；两个 creator 有明确交接，不相互自动触发。
- 可选外部 skill 与必需依赖分开，skill 加载不被误当成工具授权或 subagent 派单。
- 若参考完整样例，复制该例的完整依赖到目标项目；源 agent、skill 与契约只维护一份，不在说明文档内再保留代码副本。
- 示例独立复制后，所有运行引用都指向本项目；不依赖两个 creator 或原分发包的 examples 目录。
- 禁止派单者显式配置 task deny；审查者的实际工具能力与只读边界一致。
- 协作时上下游状态、字段和语义一致，缺输入可以返回 BLOCKED。
- 修改现有文件时检查 diff，保留与任务无关的配置和定制内容。

## 运行时验证（环境可用时）

使用目标安装提供的发现或加载方式确认 agent 与 skill 可见，核对权限生效和引用可读。不要发明 CLI 子命令。仅当已授权且环境允许时执行最小任务；不因验证而执行业务副作用。

环境不可用时报告“静态检查通过，目标运行时加载/权限尚未验证”。YAML 解析成功不等于 OpenCode 加载成功。

## 结构调整后的代表场景

按改动相关性选择，不要求每次全部执行：

1. 新建单 primary：只读配置和 primary 模板，不加载多智能体参考，不产生无用派单章节。
2. 修改已有 agent：保留用户模型与无关配置，只改授权部分。
3. 设计执行与独立验收：输入自包含、验收者不修复、状态一致、失败能处理。
4. Skill 不可用或必要输入缺失：报告阻塞，不伪造能力与完成结果。
5. Skill 内部更换脚本或检查项：agent 无需同步；公开契约变化时能定位调用方。
6. 同时缺 agent 和方法：同一创建助手进入 skill-creator，完成后继续装配，不重复问已知信息、不循环调用。
7. 仅讨论／只审查不改文件：回复建议；明确要求生成配置草稿时可以落盘，不能误停在方案。
8. 示例中的模型或工具不可用：报告该分支 BLOCKED，不能用猜测内容替代真实执行。

这些是行为验收目标；只有静态阅读时不要声称已经通过实际运行评测。

## 从未来使用者视角复查

- 所有生成 primary 默认 question: allow；subagent 默认 question: deny，角色与模板一致。
- 输入齐备的未来业务请求能进入工作流程；没有把本次创建限制（“不分析数据”）复制为业务 Agent 永久禁令。
- 缺实际数据时仍可完成配置草稿；需要固化的业务规则冲突则由 primary 提问，不静默猜测。
- 对同名材料，分析可以保留多个来源；只有选择加载/修改对象无法确定时才阻塞相关动作。
- worker 的 missing_inputs 不直接全量转问用户；内部字段由 primary 补齐，多个相同业务问题合并一次问。
- 小比较不被强制转换成九节报告和多份 YAML；用户要结构化交付时才按正式契约输出。
