# 多智能体边界与通信

仅在设计或修改协作关系时读取。单 primary 任务无需加载。

## 拆分依据

先判断是否存在真实收益：上下文隔离、独立验收、可并行子任务、模型或权限差异。用户要求多智能体代表已授权设计，仍需选择最少且有用的分工；不等于每个设想角色都有必要。

每个子任务应有明确目标、自包含输入、可检查产出和失败处理方式。若做不到，先澄清边界，不机械创建更多 agent。协调成本取决于实际通信关系；树形或星形系统并不是所有节点两两通信。

能力不足也可以通过工具或模型调用补充，不必自动拆 agent。大量中间产物可先资源化，仅在隔离收益明确时增加子会话。

## 最小任务包

调用方给出：任务目标、输入或可访问引用、影响结果的参数、授权资源和可写范围、预期产物及验收条件。需要落盘时指定输出目录；并行写入使用互不冲突的目录。

不得假设 subagent 自动拥有主会话全部信息。独立验收只提供任务要求、待验产物或 diff、证据及规则，避免生成者的自评结论污染判断。

## 统一状态语义

| 状态 | 含义 | 调用方处理 |
| --- | --- | --- |
| PASS | 已完成本次委托，适用检查通过 | 核对证据，再进入后续环节或交付 |
| FAIL | 已执行，但产物不满足要求或检查失败 | 根据具体问题决定修复；无新证据不重复派同一任务 |
| BLOCKED | 缺输入、能力、权限或环境，无法完成有效执行 | 补充必要条件，或明确向用户报告阻塞 |

PASS 仅表示本次委托完成，不代表整个系统已通过最终验收。超时或无有效回传由调用方记录为未完成并说明原因，不伪造子任务结论。需要重试时由场景定义预算与停止条件；无法继续则保留已完成结果并报告未完成项。

回传包含状态、摘要、产物引用、证据、问题和缺失输入。业务统计字段按需追加。多处使用的大型 schema 放在目标项目可共同访问的一份契约中，双方在调用或回传前读取；创建器自身 references 不应成为生成 agent 的隐式运行依赖。

独立验收者只检查，不修复待验产物；修复交还执行者，完成后再验。上下文隔离与权限隔离分别配置，不能仅靠“质检员”角色名保证。

## Skill 与主体不是一一对应

Skill 提供方法；Task 启动子 Agent。同一主体连续使用多个 Skill 不产生独立会话；串行阶段通常无需拆主体。并行需要真实工具/任务并发能力，独立会话仍可能共享工作区和外部系统。

不要断言所有 OpenCode/fork 都自动继承或完全不继承主上下文；任务包自包含，隔离保证用目标运行时验证。Task 白名单限制委托目标，不能替代子 Agent 自己的工具权限；hidden 只是界面可见性，不是访问控制。

## 问题汇聚与续接

默认 primary 可 question，subagent 不可。worker 返回缺口及影响范围；上游先核对任务包与材料，再将确需用户决定的重复问题合并。缺 task_id/输出路径等内部编排信息由上游修复；未来执行所需数据不应阻塞当前画像或配置设计。

用户回答后更新共享已确认事实，只对受影响子任务补输入或重新派单，保留未受影响结果。无回复/新证据不反复派同一任务；独立分支可继续，最终交代未解决项。不能借用别的 primary 或额外子 Agent 绕过 question: deny。
