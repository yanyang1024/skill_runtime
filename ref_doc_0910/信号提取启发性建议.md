# Agent 自进化飞轮 · 信号（评测）阶段：启发性建设建议

> 基于《一篇讲透 Agent 自进化飞轮怎么搭：评测→记忆→落地→控制》（腾讯技术工程，2026-08）第一章，
> 结合 Anthropic 递归自改进报告 / Outcomes / Dreaming 机制、EvoAgentX 开源框架（TextGrad / AFlow / MIPRO）、
> 以及 LLM-as-Judge 偏差缓解文献（MT-Bench / G-Eval / Prometheus 谱系）综合整理。

***

## 0. 先校准认知：信号不是分数，是飞轮的燃料

PDF 中最重要、也最容易被跳过的一个认知转变：

**传统评测只承担"质量门控"一个职责；自进化场景下，评测必须同时承担三重职责：**

| 职责   | 回答的问题          | 信号流向              |
| ---- | -------------- | ----------------- |
| 方向指引 | 哪里有问题？下一步往哪改？  | → 落地环节（生成修复方案）    |
| 质量门控 | 改了之后是更好还是更差？   | → 版本合入 / 回滚决策     |
| 经验筛选 | 这次执行的经验值不值得沉淀？ | → 记忆系统（写入正例 / 反例） |

由此推出本文第一性原理：**评测的可信度 > 系统的复杂度。**

传统评测打错分，代价是"上线了一个不够好的版本"；自进化评测打错分，代价是
**"Agent 学到了错误经验并持续污染后续所有任务"**。信号一旦失真，飞轮的自动化程度越高，
犯错的速度就越快——错误的正反馈比没有反馈更可怕。

> 启发 ①：在搭任何自动化之前，先回答一个问题——"如果我的评测信号有 15% 的系统性错误，
> 我的系统会往哪个方向偏？" 如果回答不了，先别自动化。

## 1. 信号源矩阵：信号从哪里来（六个层级）

PDF 提出了"分层组合、把成本花在刀刃上"的原则。结合 Anthropic 的实践，可以扩展为一个六层信号源矩阵：

### L0 · 真实业务指标（最高优先级，PDF 5.3 节）

用真实 CTR、拒审率、工单修复成功率、用户留存做反馈信号。
**这是飞轮最自然的燃料——真实指标天然不存在评测集漂移问题（业务在变，指标跟着变）。**
已成功跑通闭环的案例（工单修复率 30%→90%、内容推荐 CTR 驱动）共享这个特征。

> 启发 ②：盘点你的业务里有没有"天然的对错信号"。有，就用它做主轴，人工构造的评测集只做补充。

### L1 · 规则 / 自动化校验（零成本、零偏差，PDF 1.3 节）

代码能跑、测试通过、SQL 结果匹配、格式合规、延迟达标。
这是评测体系的**基石**，也是大多数团队最没有充分利用的层级——很多本可以用规则校验的维度
（格式、字段完整性），却在用 LLM Judge 评，纯粹浪费还引入噪声。

> 启发 ③：审计你现有的评测维度，凡是可以写成确定性断言的，全部从 LLM Judge 中剥离。
> 每剥离一个维度，信号可信度就提升一分、成本就下降一分。

### L2 · LLM-as-Judge + 对照实验（需要治理的中间层）

适用于开放式任务和语义理解维度。这是**风险最高、最需要工程化治理**的信号源（详见第 3 节偏差治理）。

### L3 · 过程 / 轨迹信号（PDF 1.2 难题二 + 1.4 节）

Agent 的输出是"推理过程 + 工具调用序列 + 中间结果 + 最终答案"的组合体。只看最终答案会产生三类盲区：

* **虚假通过**：过程中幻觉，碰巧答案对了——下次大概率翻车

* **低效通过**：做对了但消耗 5 倍 Token

* **记忆性通过**：推理链错了但模型"记住"了答案——换个问法就垮

> 启发 ④：引入 trace-level evaluation。Skill 评测的四层验证（对照实验 → 难度校准 → 轨迹追踪 → 路径验证）
> 是 PDF 中最具操作性的方法论之一："结果对了但路径不对，意味着下次会翻车。"

### L4 · 人工抽样 + 元评测集（顶层锚点）

定期随机抽样人工复核，比较人与 Judge 的一致率；维护几十条"绝对正确 / 绝对错误"的极端样本作为元评测集，
定期检查评估器是否还能识别——**连极端 case 都判错的评估器，其所有打分都不可信，系统应告警。**

### L5 · 跨会话慢变量信号（Anthropic Dreaming 机制的启发）

同步评测一次只看一个任务，看不到**跨会话的系统性模式**：30 次会话里 30 次在"时间格式转换"出小问题，
单次看都是偶发个例，合起来是系统性短板。Anthropic 的 Dreaming（2026.5 研究预览）正是这类信号源：
一个专职异步进程在空闲时审阅多达 100 个历史会话，提取反复出现的失败模式、低效模式、知识缺口，
产出修订建议（最终决策仍由人完成）。

> 启发 ⑤：把信号采集分成两个时标——**同步信号**（每次作业批改，抓具体错误）+
> **异步信号**（期中总结，发现慢变量和全局模式）。很多团队只有前者，导致飞轮对系统性短板失明。
> Anthropic 内部数据显示 Dreaming 类机制可使任务完成率显著提升（公开报道提及高达 6 倍量级，
> 具体数值取决于场景，需自行验证）。

### 补充：Anthropic Outcomes 的设计启示（2026.5 公测）

Outcomes 用**独立评分器**按 rubric 评估 Agent 输出，关键设计是评分器拥有自己的上下文窗口，
与被评 Agent 完全隔离——避免了经典自我评价引入的推理偏差（self-enhancement bias）。
内部测试显示任务成功率提升 8-10 个百分点（docx +8.4%、pptx +10.1%）。

> 启发 ⑥："生成模型和评估模型必须分离"不能只停留在实例层面，**要做到上下文层面的隔离**——
> 评估器不应该看到被评 Agent 的推理过程自我辩护，只看产出物本身。

## 2. 信号的七个失效模式（PDF 七大难题速查表）

PDF 把评测难题按"最致命 → 最常见"排序。前四个是**信号质量问题**，后三个是**信号新鲜度和成本问题**：

| # | 失效模式     | 本质                                                              | 关键对策                                 |
| - | -------- | --------------------------------------------------------------- | ------------------------------------ |
| 1 | 弱评估器     | LLM Judge 有系统性偏差（偏好长文本/特定格式/表面正确）——非随机噪声，多轮进化中 Agent 会"学会"骗过评估器 | 见第 3 节偏差治理协议                         |
| 2 | 评什么维度    | 只评结果不评过程，盲区问题永不暴露                                               | trace-level 评测，覆盖结果质量+过程质量+安全质量三维度   |
| 3 | 评什么粒度    | 粗粒度无法归因、细粒度成本爆炸                                                 | 日常粗粒度快速筛选，失败 case 细粒度深度归因            |
| 4 | 开放式任务难量化 | "好的方案"没有确定性标准                                                   | 偏好排序代替绝对打分；AI 初筛 + 人复核争议 10-20%      |
| 5 | 评测集漂移    | 旧集刷高分，线上体验持续下降——**评测全绿时没人怀疑评测本身**                               | 线上失败样本定期回流替换旧样本（val 每 2-4 周换 20-30%） |
| 6 | 预算公平性    | "进化"只是多花了钱（Best-of-N、重试择优）——关掉预算就打回原形                           | **一切评估在 Token 预算对等条件下进行**            |
| 7 | 评测成本     | 每次改动跑全量吃不消，不跑怕回归                                                | 分层评测：轻量回归（核心 case）+ 定期全量             |

> 启发 ⑦：难题六"预算公平性"是最容易被忽视、也最深刻的一条。
> **真正的进化 = 相同预算下做得更好。** 建议在每次评测报告中强制并列两个数字：
> 质量分 + Token 消耗。任何"质量 +10%、成本 ×3"的改进都不是进化，是用钱砸分。

## 3. 弱评估器治理：一份可执行的偏差缓解协议

PDF 指出弱评估器是"最致命的问题"，但给的解法偏原则性。LLM-as-Judge 文献（MT-Bench / G-Eval /
Prometheus 谱系及 2026 年后续工作）提供了一套更具体的、已被生产验证的协议：

### 3.1 四类系统性偏差及机械性缓解

| 偏差           | 表现                                    | 缓解（机械性，优先于"更好的 prompt"）                                                            |
| ------------ | ------------------------------------- | ---------------------------------------------------------------------------------- |
| 位置偏差         | 成对比较时偏好先出现/后出现的答案（GPT-4 约 10% 偏好第一位置） | 每次比较跑两遍（A vs B、B vs A），结论翻转则判平局或送人审；rubric 场景用 balanced permutation（每个分数在每个位置等频出现） |
| 冗长偏差         | 更长的答案得分更高，与实际质量无关                     | rubric 显式惩罚不必要长度；或截断到较短答案长度 +20% 再评；成对报告用 length-controlled win rate               |
| 自我偏好         | 评估器偏好同模型家族的输出                         | Judge 与被评模型必须来自不同家族                                                                |
| 格式 / 表面正确性偏差 | 有编号列表、引用了（编造的）数据就得高分                  | 结构化输出（Pydantic / JSON Schema 约束评分维度）；reference-guided grading（提供参考答案锚定真值而非"听起来合理"） |

### 3.2 PDF 原则与文献协议的对齐

PDF 给出的四条原则（生成/评估模型分离、temperature=0、结构化输出、分维度独立评估）
与文献完全一致，可合并为一份**评估器配置基线**：

```
judge_model      : 与被评系统不同家族的强模型
judge_context    : 独立上下文窗口，不看被评 Agent 的自我辩护（Outcomes 模式）
temperature      : 0（可复现是可信的前提）
output_format    : JSON Schema / Pydantic 强约束，禁止自由发挥
granularity      : 一次调用只评一个维度（正确性 / 完整性 / 格式 / 效率 拆开评）
pairwise         : 双向各跑一次，翻转判平局
reference        : 有金标答案时强制注入作为评分锚点
```

### 3.3 评估器契约（Judge Contract）——2026 年的新实践

把 `(judge_model_id, rubric_version, prompt_template_hash)` 三元组固定为一份契约并版本化：

* **换 Judge = 评测集迁移**，不是配置变更——新旧 Judge 必须在校准集上对比后才能切换

* **每月与人类标注校准一次**，一致率低于阈值即告警

* **元评测集定期巡检**（PDF 1.3 建设要点四）：评估器本身也需要被"评测"

> 启发 ⑧：很多团队的评测失真不是 Judge 一开始就差，而是**悄悄漂移**——换了模型版本、
> 改了 prompt、rubric 微调，没有人发现分数线已经不可比。把评估器当作被监控对象，
> 而不是基础设施的透明一部分。

## 4. 信号如何变成"可行动的梯度"：EvoAgentX 三种用法

PDF 强调"评测的终点不是打分，是诊断归因"。EvoAgentX（arXiv 2507.03616）集成的三个优化器，
恰好展示了**评估信号驱动进化的三种不同范式**，理解它们的差异能帮你选对信号的消费方式：

| 优化器             | 信号形态           | 消费方式                              | 类比      | 适用                        |
| --------------- | -------------- | --------------------------------- | ------- | ------------------------- |
| **TextGrad**    | 自然语言反馈（"文本梯度"） | 把评估器的批评当作梯度，沿计算图"反向传播"到各节点 prompt | 梯度下降    | 失败原因可以用语言描述、可归因到具体节点      |
| **MIPRO**（DSPy） | 标量分数           | 贝叶斯优化搜索指令 + few-shot 示例组合         | 超参搜索    | 指令/示例空间离散、评测可批量跑          |
| **AFlow**       | 标量奖励           | MCTS 在工作流拓扑空间上搜索，分数做奖励            | 蒙特卡洛树搜索 | 工作流结构（节点顺序、依赖、执行策略）本身需要进化 |

实测效果参考：TextGrad 将 HotPotQA F1 从 63.58% 提到 71.02%，AFlow 将 MBPP pass\@1 从 69% 提到 79%，
GAIA 上最高提升 20 个百分点。

> 启发 ⑨：**信号的粒度必须匹配优化器的消费方式。**
>
> * 用 TextGrad 式进化 → 评估器必须输出**可归因的自然语言批评**（"第 3 步的正则漏了 YYYY-MM-DD 格式"），
>   而不是一个干巴巴的分数；
>
> * 用 MIPRO/AFlow 式搜索 → 评估器必须**便宜、稳定、可批量**（temperature=0、可缓存），
>   因为要被调用成百上千次；
>
> * 两者混用时 → 粗粒度分数做搜索奖励，细粒度语言反馈做局部修复，各司其职。

> 启发 ⑩：归因粒度决定修复精度。PDF 的血泪教训值得贴在墙上——
> **"某场景连续 3 轮失败率 80%+ 不下降时，先停下来查工具实现层（API 参数错误、服务端异常），
> 而不是继续在配置层打转。"** 配置层的进化解决不了工具层的 Bug，实践中有过 20+ 轮无效迭代的案例。
> 建议在信号管道里加一条硬规则：失败模式停滞检测 → 自动降级到工具层排查。

## 5. 信号管道工程：评测集治理与成本结构

### 5.1 评测集三分法（PDF 1.3，严格职责分离、互不泄漏）

* **train 集（50-60%）**：只用于诊断——"哪类问题失败率最高、失败模式是什么"。诊断信息可暴露给生成修复方案的 LLM

* **val 集（20-30%）**：只用于筛选候选变体。**绝不暴露给生成侧 LLM**（否则它会"记住"val 答案）

* **test 集（15-20%）**：只用于上线前最终验证，捕捉"val 上过拟合但对新问题无效"

更新节奏：val 每 2-4 周替换 20-30%；test 每 1-2 月更新；train 持续追加线上新失败样本。
划分要按问题类型分层抽样，避免"某类问题只在 train 里出现"。

### 5.2 分层评测成本模型

```
每次改动 ──► 轻量回归（核心 case 子集，分钟级）
每周/每版本 ──► 全量评测（全集，含细粒度归因）
每月 ──► 评估器校准（人类标注对比 + 元评测集巡检）
持续 ──► 线上真实指标监控（L0 信号，永不停）
```

> 启发 ⑪：评测成本直接决定飞轮转速。如果一轮评测贵到一周只能跑一次，飞轮就只能一周转一圈。
> 把"单次轻量回归的成本"当作关键工程指标来优化——它和迭代频率成正比。

## 6. 防跑偏：信号层面的对齐保障（Anthropic RSI 报告的警示）

Anthropic《When AI builds itself》（2026.6）及递归自改进报告的核心警告：
**AI 自主迭代修改自身配置时，行为可能发生隐蔽且累积的偏移——每次单独改动看起来合理，累积起来已偏离初始意图。**

门控检查的是"这次改动有没有引入回归"（局部视角），抓不住"整体方向是否偏了一小步"（全局视角）。
迷雾中走路的类比：每一步都没掉坑里，但一百步之后可能已偏了 90 度。

信号层面的三层防护（PDF 4.5）：

1. **方向性约束指标**：除任务成功率外，监控平均输出长度、工具调用次数、拒答率等的趋势——阈值由人设定，越界告警
2. **评测集显式包含"意图对齐"维度**：把"简洁性""语气合适度"等抽象意图具象化为可评测 case
3. **定期方向性审计**：每月半天人工审查进化轨迹——Skill 库朝什么方向发展？记忆在积累什么类型的经验？输出风格在漂移吗？

> 启发 ⑫：警惕"评测信号无意中奖励了错误的东西"。你希望"准确且简洁"，但如果详细答案更容易
> 包含正确内容而得分更高，多轮进化后 Agent 会越来越啰嗦——每一步评测分都在涨，方向却在偏。
> **定期反问：我的信号正在奖励什么行为？这是我想要的行为吗？**

## 7. 一页纸行动清单

按优先级排序，可直接执行：

* [ ] **信号审计**：列出现有全部评测维度，凡能写成确定性断言的从 LLM Judge 剥离（启发 ③）

* [ ] **寻找天然信号**：盘点业务指标中可直接用作反馈的真实信号（CTR / 修复率 / 拒审率），用它做主轴（启发 ②）

* [ ] **评估器基线**：按 §3.2 配置基线固化 Judge 设置；建立 `(judge_model, rubric_version, prompt_hash)` 契约（启发 ⑧）

* [ ] **偏差检测**：对现有 Judge 跑一次位置交换测试 + 长度相关性测试，量化你的评估器偏差有多大

* [ ] **预算对等**：所有对比评测强制 Token 预算对齐；报告中并列"质量分 + 成本"（启发 ⑦）

* [ ] **评测集三分**：train / val / test 职责分离，val 对生成侧保密；建立线上失败样本回流节奏

* [ ] **轨迹信号**：对 Skill 引入四层验证（对照实验 → 难度校准 → 轨迹追踪 → 路径验证）（启发 ④）

* [ ] **归因粒度**：评估输出从"分数"升级为"分数 + 失败类型分组 + 根因定位"；加失败停滞检测（启发 ⑩）

* [ ] **异步信号**：部署一个定期审阅历史会话轨迹的 Dreaming 式进程，专抓跨会话慢变量（启发 ⑤）

* [ ] **方向性指标**：设定输出长度 / 工具调用次数 / 拒答率的趋势阈值告警（启发 ⑫）

* [ ] **元评测集**：构建几十条"绝对对/绝对错"样本，纳入定期巡检，评估器失灵即告警
