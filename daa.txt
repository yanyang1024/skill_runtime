# 1. 先重新定义你真正要预测的东西

目前隐含模型大概是：

```text
截至 Phase t 的知识
      ↓
预测未来 Phase t+1 ... Phase 7
      ↓
预测 knob sequence
      ↓
预测 metric trajectory
      ↓
拿真实 Phase t+1...7 全轨迹评估
```

这里有一个根本问题。

假设模型在 P2 预测：

```text
P3: 调 A
P4: 调 B
P5: 调 C
```

但真实工程师在 P3 调的是 D。

那么从 P3 开始，真实系统状态已经进入：

```text
S2 --D--> S3'
```

而模型预测的是：

```text
S2 --A--> S3
```

此时再拿真实 P4/P5 去评价模型预测的 B/C 后果，其实已经没有严格意义。

所以我建议把核心任务正式定义为：

```text
State S_t
    ↓
选择 Action A_t
    ↓
预测 Transition ΔY_(t+1)
    ↓
观察真实结果
    ↓
Replan
```

也就是一个非常轻量的 **receding horizon / MPC 式 Agent Loop**。

不需要真的做复杂控制算法，只借它的任务结构。

# 2. 你现在任务里其实混了三个不同问题

目前一个 `semantic_forecast.json` 同时在做：

### A. 决策预测

> 下一步应该调什么？

```text
P(A_t | S_t)
```

### B. 工艺响应预测

> 如果这么调，指标会怎么变化？

```text
P(ΔY | S_t, A_t)
```

### C. 多步策略 rollout

> 后面几步会怎么继续调？

```text
A_t → Y_t+1 → A_t+1 → Y_t+2...
```

这三个难度完全不同。

我建议**核心 benchmark 先只保证 A+B 做好**。

多步 C 留着，但从“硬预测未来 sequence”降级成：

```text
conditional rollout
```

例如：

```text
现在：
ME2B +0.3

预计：
DVC -0.2 ~ -0.4
Gouging +0.1 ~ +0.2

下一步条件：
IF DVC 已进窗口 AND gouging恶化:
    调 HT OE ↓
ELSE IF DVC改善不足:
    ME2B 再 +0.1
ELSE:
    STOP
```

这比：

```text
P3 ME2B+
P4 HT OE-
P5 RR+
P6 ...
```

更符合真实调试过程。

因为未来 action 本来就应该依赖未来 observation。

# 3. 目前输入中，我认为最重要的缺失不是 mechanism，而是 `target gap`

你现在有：


但真正决定“下一步调什么”的核心变量应该显式存在：

```text

+

```

例如不要只告诉模型：



否则 Agent 很容易变成：

> “根据历史趋势猜工程师下一步干什么”

而不是：

> “根据目标状态决定下一步应该干什么”。

这两个任务是不一样的。

# 6. 对 25 knob × 9 metric knowhow，我会重新分三类知识



# 7. 我甚至建议 LLM 不直接“拍脑袋预测数值”

这是很适合你这个任务的一个 Agentic 分工。

现在：

```text
LLM → ΔDVC = -0.37
```

这种数字其实很容易产生虚假的精确感。

可以改成：

### 程序先算 baseline

```text
base_delta =
historical_response_coef × knob_delta
```

例如：

```text
DVC baseline = -0.30
```

### LLM 只判断语义修正

```json
{
  "regime": "near_saturation",
  "magnitude_modifier": 0.6,
  "reason": "...",
  "direction_reversal": false
}
```

然后程序计算：

```text
-0.30 × 0.6 = -0.18
```

甚至 modifier 先离散化：

```text
0
0.5
1.0
1.5
```

这样非常符合：

> **LLM 做语义 / 程序做数值。**

LLM 最擅长的是：

```text
这里是不是到了 saturation？
当前 trade-off 是否变得更重要？
历史数据和机理冲突应该信谁？
```

而不是计算：

```text
0.137 × 0.83 × ...
```

# 13. Predictor Subagent 的 prompt 建议大幅缩短

现在不要让它“理解所有东西然后自由预测未来七步”。

可以改成这种逻辑：

```text
你是工艺 tuning decision forecaster。

目标：
根据当前 state 选择下一次最合理的 tuning action，

推理优先级：

1. 首先判断当前离 target 最大的 gap。
2. 从 candidate actions 中选择一个 primary action。
3. empirical response 用于 magnitude baseline。
4. mechanism prior 用于判断：
   - sign 是否合理
```

## 最终我会把整个任务重新概括成一句话

你现在是：

> **让 LLM 根据截至当前阶段的信息，猜未来整条调试轨迹。**

我更建议变成：

> **让程序把当前工艺状态和可行动作整理成一个可推理的局部世界，让 LLM 判断“现在最值得尝试什么、为什么、可能发生什么”；实验结果回来以后重新规划。**

也就是：

```text
Observe
  ↓
Build state
  ↓
Generate candidates     ← 程序
  ↓
Reason / choose         ← LLM
  ↓
Predict local response  ← 程序 baseline + LLM semantic modifier
  ↓
Execute / GT
  ↓
Evaluate                ← 程序
  ↓
Update evidence
  ↓
Replan
```

这其实比现在“强行让 Agent 一口气预测 Phase 3~7”**更 agentic**，因为 Agent 的优势恰恰不是一次把未来猜完，而是**利用新的 observation 持续修正内部状态和下一步决策**。

如果只让我从你现有系统里选 **3 个最可能马上提高实验质量的改动**，我会选：

1. **删掉/隐藏手写 `output_plan`，换成 deterministic `candidate_actions`，先解决 anchoring 和潜在泄漏。**
2. **加入明确的 `current metric + target gap + knob_delta`，把任务变成完整的 state-action-transition。**
3. **加入 `on_policy_horizon`：动作第一次分叉后不再用未来 GT 评价预测状态轨迹。**

这三项的重要性，我认为目前都高于继续增加统计特征。
