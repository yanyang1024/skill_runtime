# 功能理解与渐进改造

## 收集证据

先读项目的 AGENTS.md/约束与启动说明，检查工作区未提交修改。再识别 `Flask()/Blueprint`、`FastAPI()/APIRouter`、app factory、模板和静态资源。查找 `include_router`、`register_blueprint`、装饰器与前端 fetch/表单提交，确认前缀、方法和实际运行入口。

静态辅助：

```bash
python <skill-dir>/scripts/inspect_web_project.py <project-root> --output <task-output>/web-inventory.json
```

脚本不导入或启动项目，只输出 Python 路由候选和 HTML 表单字段名。它不解析完整依赖注入、动态注册、JS 生成表单、继承模板、挂载前缀、授权或副作用；不能将扫描结果当成完整功能说明。

选一个用户经常使用的页面，沿请求追到服务函数和数据读写。可运行时使用项目自己的测试客户端或本地浏览器重放。不要为了解功能点击真实提交、发送或发布动作；用隔离数据和替身验证这些路径。

## 留下一张可核对的功能表

| 用户任务 | 页面/事件 | 路由与输入 | 服务函数与输出 | 身份/范围/副作用 | 验证证据 | 改造点 |
| --- | --- | --- | --- | --- | --- | --- |
| 按条件查询记录 | 检索表单 | GET/POST 条件 | 查询服务 → 结果集 | 当前部门、只读 | 测试/实测/未知 | 可选字段建议 |

主动检查隐藏语义：时区、默认日期、空值、分页、去重、金额/单位、ID 与显示名称、缓存、文件路径、批量处理、错误码。不要从字段名称推定业务规则。

## 复用接口的优先顺序

1. 可独立调用的既有业务函数：直接复用，统一校验与权限输入。
2. 稳定的内部 API：按既有认证和契约调用，不创建绕过业务规则的数据库直写。
3. 与 view 强耦合的逻辑：抽出最小服务函数，原路由和 Agent 适配层共同调用。
4. 只有浏览器操作可用：明确其脆弱性和失败恢复；有可改源码时优先恢复结构化接口。

不要给浏览器的 Agent API 更宽权限；不要把原来的人工审批变成模型自批准。用户已在任务中授权的可逆改动不额外增加确认步骤。

## 实施顺序

- 选择一条收益明确的主任务，不一次改造全站。
- 冻结旧输入/输出行为与需保留的业务语义，准备少量回归样例。
- 新增适配层与必要字段 Schema，让它们调用已有服务。
- 增加页面入口、建议/结果/任务状态与失败恢复；沿用既有视觉与组件。
- 用现有 feature flag/config 机制提供开关；没有复杂发布要求时，用简单条件入口即可，不另造配置平台。
- 检查旧入口、新入口、失败与并发路径；更新启动配置、行为变化和回退说明。

用户明确要求完整替换原页面时，保留的是功能与数据契约，而不必保留每一个旧控件。用功能对照验证迁移完成，不依赖“页面看起来差不多”。
