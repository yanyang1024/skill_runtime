Multi-Agent Systems · 教学讲稿

多智能体不是把一个模型复制很多份，
而是设计正确的能力与上下文边界

一份从问题出发的多智能体教学稿：先找单 Agent 的真实缺陷，再决定要不要拆、怎么拆。

时长 50 分钟讲授 + 20 分钟演示 对象 已用过单 Agent 工具的工程师 形式 离线单文件 · 可直接投影
00

这节课要回答什么

谈到多智能体，很多人的第一反应是：让多个 Agent 分别扮演产品经理、架构师、开发者和测试人员，再让它们开会协作。

这种做法看起来像一个团队，但它不一定真的提升任务质量。几个 Agent 如果使用相同模型、读取相同上下文、拥有相同工具，只是换了不同角色名称，很可能只是把一次推理拆成了多次相似推理，同时增加成本、延迟和沟通损耗。

因此，这节课不从"应该创建哪些角色"开始，而从三个更基本的问题开始：

  1. 单个 Agent 到底缺少什么？
  2. 哪些信息应该共享，哪些上下文必须隔离？
  3. 子任务之间存在依赖，还是可以真正并行？
MULTI-AGENT NET GAIN 多智能体净收益 = 能力互补 + 上下文隔离收益 + 并行收益 − 协调成本

只有三项收益中的至少一项足够明显、且大于协调成本时，多智能体才值得使用。协调成本不只是多花的 token，还包括任务包构造、输出契约对齐、失败排查和汇总规则设计——它随 Agent 数量超线性增长。

讲师提示

开场先问学员："你们用过'多 Agent 角色扮演'的提示词吗？效果如何？"收集 2~3 个回答后再亮出净收益公式，学员更容易把公式和自己的挫败经验对上号。

学完本课后，你应当能够：

  • 判断一个任务是否真的需要多智能体；
  • 区分 Skill、Agent 和 Multi-Agent 的定位；
  • 理解"Agent 调用 Agent"的最小实现；
  • 使用串行或并行方式组织子 Agent；
  • 为代码生成与独立验收设计上下文隔离；
  • 避免把多智能体做成只有角色名称不同的"角色扮演剧场"。

开场白：我们今天不先讨论应该创建几个 Agent。我们先找单 Agent 的真实缺陷：它是缺少能力，受到已有上下文影响，还是任务确实可以并行？只有找到真实边界，多智能体才会带来净收益。

01

为什么需要多智能体

1.1原因一：单个 Agent 存在能力边界

一个 Agent 能做什么，不只取决于它的提示词，还取决于四类资源：模型（文本、视觉、推理深度）、工具（搜索、OCR、执行命令）、上下文（对话历史、文件）、权限（编辑、执行、访问外网）。提示词只能在这四类资源划定的空间里做调度，无法凭空创造能力。

例如，一个使用纯文本模型的 Agent 无法直接理解图片。我们可以为它接入一个多模态模型，让它成为专门的视觉处理模块：

在这里，拆分不是为了模仿人类组织，而是因为两个执行单元拥有不同能力：

执行单元主要能力输入输出
文本 Primary理解任务、规划、汇总和表达用户问题、视觉分析结果最终回答或后续动作
视觉 Subagent图像理解、OCR、物体与布局识别图片、观察指令结构化视觉事实与不确定性

视觉 Subagent 最好不要只返回一段自由文本，而应返回稳定的结构：

JSON · 视觉观察报告
{
  "observations": ["界面右上角存在红色告警图标"],
  "visible_text": ["Connection failed"],
  "uncertainties": ["无法确认告警由网络还是权限问题引起"],
  "limitations": ["图片未包含浏览器地址栏"]
}

四个字段的分工是：observations 是直接看到的，visible_text 是 OCR 原文，uncertainties 是图像无法裁决的，limitations 是输入缺失导致的盲区。这样，Primary 消费的是一份带有来源边界的"观察报告"，而不是把视觉模型的一切判断都当成事实。

这里究竟是"模型调用"还是"Agent 调用"？

如果只是把图片发给另一个模型并取回一句描述，它更像一次模型调用。判断是不是真正的 Agent 调用，看三个问题：

  1. 它有没有自己的任务边界（稳定的职责说明，而非临时拼接的提示词）？
  2. 它有没有自己的执行空间（独立上下文、可用工具、完成判断）？
  3. 它的输出是不是一份可被稳定消费的契约（结构、状态、证据）？

三个都满足，才是一次真正的 Agent 调用。多智能体的关键不在名字，而在是否形成了真实的执行边界。

1.2原因二：同一个 Agent 完成所有环节会产生缺陷

有些任务并不缺能力，但需要隔离上下文。让同一个 Agent 写完代码后再判断"自己写得对不对"，容易出现：

  • 锚定效应：生成阶段形成的假设继续影响验收阶段；
  • 自我辩护倾向：更容易解释自己的方案，而不是主动寻找反例；
  • 盲区延续：生成时忽略的边界条件，验收时也可能继续忽略；
  • 标准稀释：长上下文混杂设计讨论与失败尝试，验收标准反而不突出；
  • 表面通过：真实路径可能仍是 fallback、mock、placeholder 或 hard-code。
课堂提问

让学员回忆一次"AI 自称测试通过、实际跑不通"的经历。追问：它验收时看到了哪些上下文？如果只给它 diff + 验收标准，结论会不会不同？

这些问题的共同根源是：生成和判断共享了同一份上下文，也共享了这份上下文里的所有偏见。

不要让同一个上下文既负责写代码，又负责证明代码正确。

生成 Agent 担任 Primary；验证 Agent 运行在独立上下文中，只读取完成验收所必需的材料：原始任务与验收标准、最终 diff、测试证据、项目规则与必要的代码文件。它不需要读取生成 Agent 的完整思考过程，也不应先看到自我辩护。它应该被允许直接返回 FAIL 或 BLOCKED。

注意：上下文隔离不等于让 Reviewer 什么都不知道。Reviewer 可以不知道 Builder 的思维过程，但必须知道任务目标、约束和验收标准，否则它不是独立验收，而是盲审。隔离的是叙事和推理过程，共享的是事实与标准。

1.3原因三：真正独立的子任务可以并行

当多个子任务之间没有前后依赖时，可以让多个 Agent 同时工作：分别检索互不依赖的资料源；分别分析大代码库的不同模块；同时执行功能、性能和安全检查；对同一候选方案做相互独立的反例搜索。

并行的收益有两个：一是缩短墙上时钟时间（总耗时从求和变为近似取最大值）；二是在上下文隔离的前提下获得多个真正独立的证据源。但"可以拆成多个描述"不等于"可以并行"——判断标准只有一个：每个子任务在启动时是否已经拥有完整输入。B 依赖 A 的结果时强行并行，只会产生猜测、返工和冲突。

1.4哪些场景不需要多智能体

  • 任务简单、步骤短、结果容易验证；
  • 所有步骤依赖同一份连续上下文；
  • 子任务之间强依赖，无法独立推进；
  • 换一个 Skill 或增加一个工具就能补足能力；
  • 多个 Agent 只是使用相同模型复述相同问题；
  • 问题本身没有边界和验收标准，却希望"多人讨论"自动得到正确答案。

尤其警惕最后一种：单 Agent 解决不了的无边界问题，拆给多个 Agent 后并不会自然变得可验证，反而可能得到多份各自自洽但互相冲突的答案。多智能体放大的是结构设计的能力，而不是问题定义的能力。问题定义不清时，先修问题，不是先加 Agent。

本节小结：多智能体只有三个正当理由——补能力、做隔离、真并行。其余动机（显得更专业、更像团队）都不是工程理由。

02

Skill、Agent 与 Multi-Agent 分别解决什么问题

三者不是互相替代的产品形态，而是三个不同层级的设计对象：

层级核心问题主要内容典型变化
Skill在某个场景里应该怎样工作？方法、流程、知识、脚本、模板、验收清单同一 Agent 按场景加载不同工作方法
Agent谁在什么边界内执行？模型、系统提示、工具、权限、上下文、停止条件为一类任务建立稳定执行单元
Multi-Agent多个执行单元如何协作？委托、隔离、串并行、结果汇总、冲突处理对任务进行能力路由和上下文编排

2.1Skill：给运行中的 Agent 动态加载做事方法

同一个编码 Agent 可以按任务动态加载 API 改造、数据分析、安全检查、文档编写等 Skill。多个 Skill 可组合，但它们共享该 Agent 的当前上下文、模型和权限——Skill 改变"做事方法"，不改变"执行边界"。

2.2Agent：建立相对稳定的执行边界

当需要改变模型、工具、权限、系统指令或上下文边界时，才有理由创建另一个 Agent：Vision Agent 用多模态模型；Reviewer Agent 禁止修改代码；Database Agent 只调只读接口；Security Agent 在独立上下文中检查敏感问题。每个例子背后都是一次"边界资源"的变化，而不是角色名称的变化。做事方法不同 → 加 Skill；执行边界不同 → 拆 Agent。

2.3Multi-Agent：能力路由与上下文编排

Multi-Agent 关注的是：Primary 何时委托哪个 Subagent（路由）、子 Agent 拿到多少上下文（编排）、串行还是并行（结构）、返回什么格式（契约）、冲突如何处理（汇总）、何时停止或升级（控制）。

Skill 优化一个 Agent 在场景中的做法；Agent 定义一个执行单元；Multi-Agent 设计多个执行单元之间的关系。

讲师提示

类比收尾：Skill 像给同一位员工发不同场景的操作手册，Agent 像设立有编制有权限的岗位，Multi-Agent 像设计部门间的协作流程。手册可随时换，岗位和流程不能乱设。

不要因为场景变多就立即增加 Agent。多个场景能共享同一模型、工具、权限和上下文边界时，优先加 Skill；只有出现真实的能力差异、权限差异、隔离需求或并行价值时，再拆 Agent。

03

多智能体实现的核心：Agent 调用 Agent

最小闭环只有五步：

  1. Primary 判断当前任务需要委托；
  2. Primary 构造一个受控的任务包；
  3. Subagent 在独立上下文中完成任务；
  4. Subagent 返回结构化结果和证据；
  5. Primary 汇总结果，决定继续、重试、停止或升级。

3.1委托的不是一句话，而是一份任务包

YAML · 任务包
task_id: review-017
objective: 验证本次登录超时修复是否满足验收标准
scope:
  include:
    - src/auth/**
    - tests/auth/**
  exclude:
    - UI 样式
inputs:
  task_spec: artifacts/task.md
  diff: artifacts/change.diff
  test_evidence: artifacts/test-results.txt
constraints:
  - 不得修改文件
  - 不接受 mock 代替真实认证路径
output_contract:
  status: PASS | FAIL | BLOCKED
  findings: 按严重级别列出，并附文件位置和证据
  missing_evidence: 缺少什么就明确写出
stop_conditions:
  - 已覆盖全部验收标准
  - 证据不足时返回 BLOCKED，不猜测

任务包的三个作用：控制上下文（子 Agent 看到什么）、限定行为（可以做和不可以做什么）、稳定消费（返回结果可被程序解析）。它是一份"最小充分委托合同"：少到刚好能完成任务，多到足以界定责任。

3.2输出必须携带状态和证据

JSON · Subagent 输出契约
{
  "status": "FAIL",
  "summary": "超时重试会重复提交登录请求",
  "findings": [
    {
      "severity": "high",
      "location": "src/auth/client.py:84",
      "claim": "重试路径缺少幂等保护",
      "evidence": "测试 test_retry_timeout 连续记录了两次提交"
    }
  ],
  "missing_evidence": [],
  "recommended_next_action": "修复后重新运行认证集成测试"
}

三种状态：PASS 已有证据支持所有验收标准；FAIL 存在明确的不满足项；BLOCKED 信息、权限或工具不足，无法可靠判断。BLOCKED 很重要——没有它，模型会在证据不足时被迫猜一个结论，而猜出来的 PASS 是最危险的结果，因为它带着"已验收"的外观进入下游。同时，每条 finding 强制携带 location 和 evidence：没有证据的 finding 不允许存在。

04

实现方式一：直接调用 V1 推理接口

最直接的做法：由 Primary 的运行代码构造提示词和上下文，调用另一个模型的 OpenAI-compatible /v1/chat/completions 接口。不依赖任何 Agent 框架，适合"一次明确的能力转换"。下面以"纯文本 Primary 调用多模态模型分析图片"为例。

4.1视觉 Subagent 的系统约束

TEXT · system prompt
你是视觉观察子 Agent。

任务：只报告图片中可观察到的内容，不替 Primary 推断业务结论。

要求：
1. 区分直接观察、OCR 文本和不确定推断。
2. 看不清时明确说明，不得补全。
3. 输出 JSON，字段为 observations、visible_text、uncertainties、limitations。
4. 不回答图片之外的问题。

4.2Python 示例

PYTHON · call_vision_agent.py
import base64, json, mimetypes, os
from pathlib import Path
import requests

def to_data_url(image_path: str) -> str:
    path = Path(image_path)
    mime = mimetypes.guess_type(path.name)[0] or "image/png"
    encoded = base64.b64encode(path.read_bytes()).decode("utf-8")
    return f"data:{mime};base64,{encoded}"

def call_vision_agent(image_path: str, objective: str) -> dict:
    base_url = os.environ["VISION_BASE_URL"].rstrip("/")
    api_key = os.environ["VISION_API_KEY"]
    model = os.environ["VISION_MODEL"]

    payload = {
        "model": model,
        "temperature": 0,
        "messages": [
            {"role": "system", "content": (
                "You are a visual-observation subagent. Report only visible "
                "evidence. Return JSON with observations, visible_text, "
                "uncertainties, and limitations."
            )},
            {"role": "user", "content": [
                {"type": "text", "text": objective},
                {"type": "image_url",
                 "image_url": {"url": to_data_url(image_path)}},
            ]},
        ],
    }

    resp = requests.post(
        f"{base_url}/v1/chat/completions",
        headers={"Authorization": f"Bearer {api_key}"},
        json=payload, timeout=60,
    )
    resp.raise_for_status()
    content = resp.json()["choices"][0]["message"]["content"]
    return json.loads(content)

visual_report = call_vision_agent(
    "screenshots/error.png",
    "识别界面中的报错文本、告警位置和可见状态；不要推测根因。",
)
print(visual_report)

4.3真正需要设计的部分

接口调用本身很简单，决定效果的是：图片格式与尺寸上限；任务边界是否清楚（只观察、不诊断）；输出是否结构化；是否显式表达不确定性；Primary 是否把"观察"与"根因推断"分开；以及超时、非法 JSON、图片过大时如何返回 BLOCKED。生产使用时还应在 json.loads 外包容错：解析失败按 BLOCKED 处理，而不是让异常裸奔进推理链。

如果视觉任务只是一次固定转换，这种轻量实现已经足够。框架解决的是编排复杂度，不解决契约设计——契约永远要自己设计。

05

实现方式二：OpenCode 的 Primary–Subagent

OpenCode V2 将 Agent 组织为 primary、subagent 和 all 三种模式。项目级 Agent 放在 .opencode/agents/<name>.md；Subagent 在 child session 中用新的上下文运行，Primary 可前台等待或后台启动。字段可能随版本演进，以当前版本文档为准。下面用"代码生成与独立验收"演示最小设计。

5.1Builder：负责实现的 Primary

.opencode/agents/builder.md
---
description: Implements changes and delegates independent acceptance review
mode: primary
permissions:
  - action: subagent
    resource: "*"
    effect: deny
  - action: subagent
    resource: "reviewer"
    effect: allow
---

你是代码实现 Primary。

你的职责：
1. 根据任务和验收标准修改代码。
2. 运行与变更直接相关的测试。
3. 生成交接包：原始目标、验收标准、最终 diff、测试证据、已知限制。
4. 调用 reviewer 做独立验收。
5. reviewer 返回 FAIL 时，根据明确 finding 修复后重新提交验收。

边界：
- 不得把自己的完整推理过程交给 reviewer。
- 不得要求 reviewer 证明当前方案正确。
- 最多进行两轮"修复—复验"；仍未通过则停止并报告。

Builder 可调用的 Subagent 被限定为 reviewer——委托权限本身也要白名单化，否则拓扑会在运行中失控生长。

5.2Reviewer：只验收、不改代码的 Subagent

.opencode/agents/reviewer.md
---
description: Independently reviews the final diff against acceptance criteria
mode: subagent
steps: 8
permissions:
  - action: edit
    resource: "*"
    effect: deny
  - action: shell
    resource: "*"
    effect: deny
  - action: shell
    resource: "git status *"
    effect: allow
  - action: shell
    resource: "git diff *"
    effect: allow
  - action: shell
    resource: "pytest *"
    effect: allow
  - action: shell
    resource: "npm test *"
    effect: allow
---

你是独立代码验收 Agent。你不参与实现，也不得修改文件。

只根据以下内容判断：
- 原始任务与验收标准；
- 最终 diff；
- 可复现的测试或静态检查证据；
- 项目规则。

重点检查：
- 功能是否走真实路径；
- 是否存在 fallback、mock、placeholder 或 hard-code 掩盖失败；
- 边界条件和失败路径是否覆盖；
- 是否引入安全、权限、依赖或兼容性回归；
- 测试是否真正验证需求，而不只是验证实现细节。

必须输出：
1. status: PASS、FAIL 或 BLOCKED；
2. findings: 按严重级别排序，每项附文件位置和证据；
3. missing_evidence: 无法判断时缺少的材料；
4. next_action: 最小必要下一步。

证据不足时返回 BLOCKED，不得猜测。发现关键问题时允许直接 FAIL。

关键约束是"可读取、可验证，但不可悄悄替实现者修改代码"。steps: 8 与权限白名单一样属于硬约束，防止验收 Agent 在证据不足时无限探索，把 BLOCKED 拖成一场漫长的调查。真实项目应按语言、测试命令和版本调整白名单。

5.3Primary 交给 Reviewer 的内容

MARKDOWN · Review Handoff
# Review Handoff

## Objective
修复登录请求在网关超时时重复提交的问题。

## Acceptance criteria
- 超时重试不得产生第二次业务提交。
- 正常登录行为保持不变。
- 集成测试覆盖超时后的重试路径。

## Changed artifacts
- src/auth/client.py
- tests/auth/test_retry.py

## Evidence
- pytest tests/auth/test_retry.py -q: 8 passed
- artifacts/change.diff

## Known limitations
- 尚未执行完整端到端测试。

原则：共享任务事实和验证证据，不共享会诱导 Reviewer 接受实现者结论的叙事。Known limitations 一节最诚实：Builder 主动声明"我没做什么"，等于圈定了验收边界。

两种基本协作模式：串行与并行

6.1串行多智能体

Primary 在某个节点调用一个 Subagent，等待完成，再根据结果继续：

适合：下一步依赖上一步结果；能力转换链（图片观察后再文字推理）；生成—验收—修复闭环；子任务少、协调成本要保持最低。

TEXT · 两个典型串行链
文本 Primary → 视觉 Agent 读取图片 → Primary 结合用户问题生成回答
Builder 实现 → Reviewer 验收 → Builder 修复 → Reviewer 复验

串行模式必须设置最大循环次数：两轮验收仍失败就停止并报告。无限循环在单 Agent 里是"卡住"，在多 Agent 里是两个 Agent 互相礼貌地消耗预算。

6.2并行多智能体

Primary 在同一节点启动多个互不依赖的 Subagent，统一汇总：

PYTHON · 框架无关伪代码
import asyncio

async def run_parallel_reviews(task_package):
    jobs = [
        call_agent("functional-reviewer", task_package),
        call_agent("security-reviewer", task_package),
        call_agent("performance-reviewer", task_package),
    ]
    results = await asyncio.gather(*jobs, return_exceptions=True)
    return aggregate(results)

最难的不是 gather，而是 aggregate。return_exceptions=True 也值得注意：单个 Agent 失败不应拖垮整批，但失败必须显式进入汇总逻辑，而不是被静默丢弃。

6.3并行结果不能只靠多数投票

三个 Agent 中两个返回 PASS，不代表应当通过——安全 Agent 发现的有证据高危漏洞，不应被两票 PASS 覆盖。Agent 结论不满足投票有效的两个前提：独立性（相同模型、相似提示下结论高度相关）和同分布性（功能检查和安全检查判断的根本不是同一件事）。多智能体汇总不是民主投票，而是证据裁决：

  1. 先检查是否有 Agent 执行失败；缺少关键检查时返回 BLOCKED；
  2. 按"验收条目 + 证据位置"合并重复 finding；
  3. 任一有明确证据的关键 finding 都触发 FAIL；
  4. 普通 finding 由 Primary 汇总，不通过多数票消除；
  5. 冲突且无法通过证据解决时，返回 BLOCKED 或升级给用户。

6.4串行与并行的选择表

判断问题是否
B 是否依赖 A 的输出？串行继续判断
多个子任务能否在启动时拿到完整输入？继续判断串行
结果是否有统一的结构和汇总规则？可并行先改善任务契约
并行节省的时间是否大于协调成本？并行单 Agent 或串行
07

如何设计一个好用的多智能体系统

7.1先拆边界，再起角色名

  1. 找出单 Agent 的具体缺陷；
  2. 判断缺陷属于能力、上下文、权限还是耗时问题；
  3. 定义需要隔离的最小任务边界；
  4. 为边界配置模型、工具、权限和输入输出；
  5. 最后再给 Agent 命名。

从"模拟一个软件公司"开始，往往产生大量角色却没有真实边界差异。命名是最便宜也最诱人一步——把它放到最后，是对抗"角色扮演剧场"的制度性手段。

7.2上下文不是越多越好

上下文通常是否传递原因
原始目标与验收标准是子 Agent 判断任务的基础
必要输入文件或 Artifact是提供可验证事实
工具权限与禁止项是明确执行边界
期望输出格式是便于稳定汇总
Primary 的完整思考过程通常否容易造成锚定和污染
与子任务无关的聊天历史否增加噪声与成本
尚未证实的结论谨慎必须标注为假设而非事实

类比医院检验科：医生（Primary）不把全部诊断思路塞给检验科，而是开检验单——查什么、样本是什么、正常范围是什么。检验科只回报结果，不替医生下诊断。最好的交接是"给你完成当前任务所需的最小充分上下文"。

7.3每个 Agent 都需要权限边界

提示词里的"请不要修改文件"是软约束；工具权限里的禁止编辑才是硬边界。软约束和硬边界的区别在失败模式下才显现：模型在上下文变长、任务变难、指令冲突时，最先放弃的就是提示词里的"请"字条款。权限系统不会疲劳。

  • Reviewer：可读代码、可运行白名单测试、禁止编辑；
  • Database Analyst：只读 API，不暴露数据库密码；
  • Research Agent：允许搜索，禁止修改项目文件；
  • Builder：允许编辑，但不能跳过最终验收门。

7.4让 Artifact 承担跨 Agent 交接

优先传递可检查的 Artifact：task.md（任务与验收标准）、change.diff（最终变更）、test-results.txt（测试证据）、visual-report.json（视觉观察）、review.json（验收结论）、run-summary.yaml（运行状态）。对话是易失的、难以 diff 的；Artifact 能保存、复用、重放和审计。当一次委托值得发生时，它的输入输出往往值得落盘。

7.5必须设计停止条件

  • PASS 目标已满足并有证据；
  • FAIL 存在明确问题，且仍在允许的修复轮次内；
  • BLOCKED 缺输入、缺权限、工具失败或结果冲突；
  • BUDGET_EXCEEDED 超过最大轮次、时间或成本；
  • OUT_OF_SCOPE 任务已超出授权范围；
  • 用户中止。

单 Agent 失控的表现是跑偏；多 Agent 失控的表现是结构化的、看起来分工明确的持续跑偏——每个 Agent 都在认真工作，预算稳定燃烧，系统在兜圈子。停止条件就是断路器。

08

常见误区

✕ 01

Agent 越多，能力越强

Agent 数量同时增加调用成本、延迟、失败节点和汇总难度。一个可靠的"双 Agent 闭环"胜过五个互相观望的 Agent。从最小可用结构开始。

✕ 02

不同角色名称等于不同视角

相同上下文、相同模型、相同工具、相同提示结构下的多个 Agent 高度相关，不构成独立判断。想让输出真正多样化，要改变输入分布，而不是改变名片。

✕ 03

把完整 Primary 上下文交给 Reviewer

虽然创建了新 session，却仍继承生成阶段的锚定。Reviewer 应读取事实、规则、diff 和证据，而不是实现者的自我解释。

✕ 04

Reviewer 发现问题后顺手修改

这会重新混合"生成者"和"裁判"的职责。裁判下场踢球的那一刻，比赛就没有裁判了。Reviewer 输出 finding，修改由 Builder 完成后再独立复验。

✕ 05

并行就是同时启动很多 Agent

没有独立输入、统一输出和汇总规则的并行，只是同时制造多份难以合并的文本。

✕ 06

用多数投票替代证据判断

Agent 的结论不是独立同分布的选票。比较证据、覆盖范围和风险级别，而不是数 PASS 数量。

✕ 07

只写提示词，不设置权限

软提示无法替代工具级权限。验收、数据访问和外部操作场景，必须使用真实权限边界。

09

一套简单的多智能体设计决策流程

创建 Subagent 前，再检查五个问题：

  1. 它与 Primary 的能力、权限或上下文边界有什么真实差异？
  2. 它的输入能否被写成最小任务包？
  3. 它的输出能否结构化，并携带证据？
  4. Primary 知道如何处理 PASS、FAIL、BLOCKED 和冲突吗？
  5. 拆分带来的收益是否大于额外成本？

如果回答不清楚，先继续用单 Agent 和 Skill，而不是先扩展拓扑。默认答案是单 Agent——多智能体需要举证，而不是反过来。

两个课堂演示

10.1演示一：让纯文本 Agent 处理截图问题

目标：让文本 Primary 回答"截图里发生了什么，下一步应该检查什么"。

操作步骤：

  1. 先让纯文本 Primary 直接处理图片，观察能力边界；
  2. 接入视觉 Subagent，只要求它报告可观察事实；
  3. 将视觉结果以 JSON 返回 Primary；
  4. 让 Primary 区分"图片事实"和"基于事实提出的排查建议"；
  5. 故意换成模糊截图，观察 uncertainties 和 limitations 是否有效。

讲解重点：这个拆分解决的是异构能力问题。第 5 步是点睛之笔——一张模糊截图立刻检验"看不清时明确说明"是否真的生效；如果视觉 Agent 开始编造细节，正好顺势讲输出契约的价值。

10.2演示二：代码生成与验收隔离

目标：让 Builder 修复一个带边界条件的缺陷，再由 Reviewer 独立验收。

操作步骤：

  1. 给 Builder 任务、代码和验收标准；
  2. Builder 修改代码并运行测试；
  3. 生成 Review Handoff；
  4. 在独立 child session 中调用 Reviewer；
  5. Reviewer 只看任务、diff、证据和规则；
  6. 对比 Reviewer 与 Builder 自评发现的问题；
  7. Reviewer 返回 FAIL 时，只把 finding 交给 Builder 修复；
  8. 达到最大轮次仍不通过则停止。

可预埋的缺陷：

  • 使用 mock 让测试通过，但真实路径未调用；
  • 对一个固定输入 hard-code；
  • 正常路径通过，但异常路径吞掉错误；
  • 增加 fallback，导致系统表面成功、实际结果错误；
  • 测试只断言 HTTP 200，没有断言业务结果。

讲解重点：拆分的价值不在角色名称，而在于：新上下文、无编辑权限、只按标准和证据判断、可以直接 FAIL、修复复验形成受限闭环。演示高潮在第 6 步——把 Builder 自评和 Reviewer findings 并排投出，两者的差异就是"上下文隔离收益"最直观的注脚。

每次委托至少记录：

  - task.md
  - change.diff
output_status: FAIL
duration_ms: 18320
tool_calls: 4
retry_count: 0

第一阶段不必建平台，只需回答五个问题：

  • Subagent 是否发现了 Primary 没发现的问题？（隔离收益）
  • 新上下文是否降低了误判或锚定？（隔离收益）
  • 并行是否真的缩短了总耗时？（并行收益）
  • 额外 token、延迟和失败率是多少？（协调成本）
  • 哪类任务经常 BLOCKED，说明任务包缺少什么？（契约缺陷）

如果一个 Subagent 长期只是重复 Primary 的结论，就应考虑合并它。多智能体系统同样需要绩效考核，依据是结构化运行记录，不是观感。

12

课程总结

多智能体不是"一个模型不够就多复制几个"，也不是把人类公司的岗位名称搬进提示词。它解决三类真实问题：

  1. 能力互补：不同模型或工具负责不同能力；
  2. 上下文与权限隔离：让生成与验收、执行与监督相互独立；
  3. 独立任务并行：并发处理可并行子任务，再按证据汇总。

一个可靠的 Agent 调用必须同时包含：最小充分上下文、明确的输入输出契约、工具和权限边界、可检查的 Artifact 与证据、以及 PASS / FAIL / BLOCKED 与预算停止条件。

好的多智能体设计，不是把任务分给更多角色，
而是把能力、上下文、权限和证据放到正确的边界里。

  • ☐ 跨 Agent 交接通过 Artifact，而不是整段对话；
  • ☐ 有可观测性记录，能回答"这个拆分是否真的有用"；
  • ☐ 能一句话说清这笔拆分净收益为正的理由。

课后练习

  1. 找边界：选一个你正在用单 Agent 完成的任务，写下它的能力、上下文和权限边界。它真的需要拆吗？
  2. 写任务包：为"让另一个 Agent 检查一份周报数据"写一份 YAML 任务包，含输出契约和停止条件。
  3. 设计汇总规则：三个并行 Agent 分别返回 PASS、FAIL（有证据）、BLOCKED，写出你的汇总决策过程和最终状态。

课堂 FAQ

Primary 和 Subagent 一定要用不同的模型吗？

不需要。模型差异只是边界的一种。相同模型 + 不同上下文 + 不同权限同样是有效拆分（如 Builder/Reviewer）。只换模型不换上下文和权限，往往不构成有效拆分。

Reviewer 验收不通过，Builder 修复后，是把所有材料再给 Reviewer 吗？

复验时给：原始任务与标准、新 diff、新证据、以及上一轮 finding 的逐条回应。不要把上一轮 Reviewer 的分析全文回传，避免验收轮次之间相互锚定。

并行 Agent 的结果互相矛盾怎么办？

先比较证据而非结论：哪一方的 finding 有可复现的证据？证据解决不了就返回 BLOCKED 并升级给人。矛盾本身是信息——它说明任务定义或验收标准存在歧义。

多智能体框架（crew / swarm 类）值得用吗？

先用手写任务包 + 接口调用或 OpenCode 原生机制跑通一两个闭环，理解契约、隔离、汇总的真实难点后，再评估框架解决了哪部分、又隐藏了哪部分。不理解底层直接上框架，调试时会发现黑盒比收益多。

Subagent 能不能再派生 Subagent？

工程上可以，但默认禁止。每深一层，上下文控制和失败排查难度都上升一个量级。确有必要时，用权限白名单显式开放，并限制派生深度。
